## 1. Purpose

Give the owner (and any manager) a screen that answers three questions in under 30 s even when the backend
is unwell: **what is broken, what is still safe, what do I do** — SCR-143 (system health), SCR-144
(incident/connectivity log), SCR-152 (disconnected/reconnecting overlay), SCR-156 (error boundary). Design
the *unreachable-backend* variant of each surface first, the all-green variant last (ticket's technical
note), so the design never accidentally assumes a healthy backend to render itself.

## 2. State vocabulary (single source, reused verbatim in API, chips, tiles, alerts)

Per the ticket's "Content design" requirement, one vocabulary is defined once and consumed identically by
`services/api/candleviewer/` (E04-T04's `HealthReport.components[].state`), the design tokens below, and
the alerting copy (E04-T05):

| Word | Meaning | Tone (`color.status.*`) | Never confused with |
|---|---|---|---|
| `ok` | Component healthy, within budget | `success` | — |
| `warning` | Degraded but functioning; a named reason and `last_good_at` | `warning` | `down` (still functioning) |
| `down` | Component unreachable/non-functional; ongoing incident | `danger` | `not_deployed` (expected absence) |
| `not_deployed` | Component intentionally absent in this environment (e.g. no recorder configured) | `info`/neutral | `down` (not a fault) |

This four-word set is the literal value of `HealthReport.components[].state` (via `ComponentState` in
`22-api-openapi.yaml`) and of `CMP-178 SystemHealthTile`'s `tone` prop (`ok`/`warning`/`danger` — `danger`
renders the `down` word; `not_deployed` renders as a fifth neutral tone in the same component, proposed as
an addition — see §7). Text is always present alongside colour (a11y non-negotiable, C-14.1).

## 3. Frames (specified; Penpot construction pending — see bridge note above)

Each frame is bound to existing semantic tokens only (`color.status.*`, `color.surface.*`,
`color.text.*`, `color.border.*` from `packages/ui/tokens/semantic-{dark,light,hc}.tokens.json`) — no new
colour/spacing/type primitives are required (see §7 "Proposed tokens" for the one gap found). Compact
density (`docs/plan/16-design-system-brief.md`) is used throughout as this is an information-dense operator
screen; touch/click targets stay ≥24×24 CSS px per WCAG 2.2 AA target-size (minimum, non-AAA) even at
compact density.

### `SCR-143/unreachable-backend` (designed first, per the ticket's technical note)

- Full-page layout renders from the **last cached** `HealthReport` snapshot (localStorage/session cache),
  each tile stamped with its own `last_good_at` and a page-level banner: "Could not reach the backend —
  showing the last known state as of `<relative time>`." (`color.status.danger.subtle` background,
  `role="status"`, not `alert` — this is informational, not a fresh event).
  Bound to `CMP-092 DegradedModeBanner` (`issues: [{id:"backend_unreachable", severity:"danger",
  message:"Could not reach the backend — showing the last known state as of 00:42 ago."}]`).
- Every `CMP-178 SystemHealthTile` resolves **independently**: a tile whose own probe last succeeded shows
  `ok`/`warning` from cache with an "as of" stamp; there is no single shared loading gate — this satisfies
  the AC "the page works when the backend is partially down" and the performance note "no tile can block
  another."
- `[ incidents (2 in 7 d) ]` and `[ export diagnostics ]` controls remain visible and operable against
  cached data; diagnostics export is still possible (it bundles the cached snapshot + client logs) and is
  audited as `health.diagnostics_exported` regardless of connectivity.

### `SCR-143/all-green`

- 9 tiles per the catalogue ASCII block: **Ingestion lag**, **Public WS**, **Private WS (per account)**,
  **REST latency**, **Recorder**, **DB tiers** (QuestDB/Postgres/Parquet), **Rule engine**, **Algo engine**,
  **Chart-engine FPS** (this session). Each `CMP-178` tile: `label` + `value` + `unit` + tone word ("ok") +
  `sparkline` (last N samples) with a **table alternative** behind a `[ Table view ]` toggle per tile
  (WCAG non-colour-alone + non-graphical-alone requirement — the sparkline is supplementary, the table is
  the accessible data source: `time | value` rows, scoped `<table>` with a caption naming the metric+unit).
- Top-right: `CMP-210 HealthChips` cluster (WS, ingestion lag, recorder, exchange rate-limit budget) —
  compact chips that mirror a subset of the tiles for at-a-glance scanning from other admin pages; clicking
  a non-`ok` chip navigates to this page anchored at the relevant tile.
- `[ incidents (2 in 7 d) ]` links to SCR-144 filtered to the last 7 days; `[ export diagnostics ]` triggers
  the audited `health.diagnostics_exported` event.

### `SCR-143/degraded` and `SCR-143/outage`

- **Degraded (per-subsystem amber):** the affected tile alone switches to `tone="warning"`, states the
  **reason** ("Recorder disk 92% full — writes paused") and the **last-good timestamp** ("last ok
  14:32:08"); tiles that are still `ok` are visually unaffected (no page-wide dimming) — degradation is
  legible per-component, not systemic, unless multiple tiles independently degrade.
- **Outage (red, ongoing incident):** affected tile(s) `tone="danger"`, plus a page-level
  `CMP-092 DegradedModeBanner` (severity `danger`, `role="alert"` once) stating **what is still safe** —
  the ticket's own example: *"Native stops on the exchange are unaffected."* This reassurance line is
  standardized copy shared with SCR-152/SCR-153/SCR-156 (see §4 "Reassurance copy").
- **Maintenance window:** a distinct informational (not danger) banner tone (`color.status.info.subtle`)
  with a stated window start/end, distinguishing planned from unplanned degradation so the operator does
  not treat a maintenance window as an incident.
- Colour-blind + greyscale check (AC): every state above carries the tone **word** ("ok"/"warning"/"down")
  in the tile and banner text — verified programmatically in §6, not by colour alone.

### `SCR-144/open-vs-resolved`, `/filters`, `/detail-row`, `/empty`

- Table columns (per catalogue AC, exact set): **time, subsystem, severity (text), message, duration,
  resolution**. Maps 1:1 to `Incident` (`22-api-openapi.yaml`): `first_seen_at`→time,
  `component`→subsystem, `severity`→severity, `title`→message (long messages truncate to one line with an
  expand affordance), `last_seen_at - first_seen_at`→duration, `status`/`resolved_at`→resolution.
- **Expandable detail row** (not silent truncation, per AC): expanding a row reveals `detail` (free text,
  never a raw exchange payload verbatim — security note), `occurrences`, `runbook_ref` (as a link, if
  present) and, where derivable, a **trading-impact correlation** line ("12 orders rejected during this
  window") sourced server-side by joining the incident's time window against `order.blocked_*` audit
  events — shown only when the join yields a non-zero count, otherwise omitted (never "0 orders" clutter).
- **Filters:** `CMP-055 FilterBar` by subsystem (multi-select), severity (multi-select, text labels not
  colour swatches alone), and date range (`CMP-047 DateRangePicker`); **open vs resolved** is a segmented
  toggle above the table, not a filter chip, since it is the primary triage axis.
  `status: acknowledged` renders as a third visual state between open and resolved (dimmed row, "Ack'd by
  <name> <time>" trailing text) — acknowledgement does not remove the row from "open".
- **Acknowledge action:** per-row button, disabled-with-reason (`CMP-079 RbacGate`) for roles without
  incident-management permission; acknowledging is **audited** (`incident.acknowledged`, matches the
  catalogue's audit note) and does not resolve the incident (resolution is server-driven only, from the
  underlying probe recovering).
- **Export:** `[ Export ]` button in the table toolbar — CSV/JSON of the current filtered view, emits
  `incident.exported` (analytics).
- **Empty state:** follows `SCR-151`'s shared empty-state anatomy — heading "No incidents in this range",
  one sentence ("Nothing has been logged for the selected filters"), and either "Clear filters" (if filters
  are active) or nothing further (if the range is simply quiet) — never a bare icon.
- Row-virtualised list (performance note: 10k rows, ≤8 ms scripting/frame) — no per-row animation, flat
  row backgrounds only (`color.surface.raised`/`color.surface.sunken` alternating for open/acknowledged).

### `SCR-152/global-overlay-and-panel-shading` (all states in one annotated board)

- States drawn together per the catalogue AC ("global overlay and per-panel shading drawn together and
  consistent"): `reconnecting` (attempt N, backoff countdown), `disconnected` (backoff exhausted / hard
  down, i.e. **retry-exhausted**), `resubscribing` (gap-fill in progress), `restored` (reconciliation
  summary).
- Global banner anatomy (verbatim from the catalogue ASCII block): icon + state text + attempt/backoff
  countdown, "Last data `Ns` ago.", "Trading is disabled while offline.", "Your exchange-side stop-losses
  are unaffected.", `[ Retry now ]` `[ Details ]`. Bound to `CMP-028 Callout/Banner` +
  `CMP-035 Countdown/Timer text` + `CMP-076 ConnectionStatus` composed together, per the catalogue's
  component list for this screen.
- **Retry-exhausted variant** (explicitly required by this ticket beyond the base catalogue entry):
  after the capped backoff (30 s) has failed N times (N configurable, default 5), the countdown is replaced
  by a static "Retries paused — [ Retry now ]" with no further automatic countdown, so the operator is not
  shown a perpetually-ticking clock that never resolves; `[ Retry now ]` remains keyboard-operable and is
  the only way to re-arm the automatic backoff.
- **Per-panel treatment** (`CMP-078 StaleDataShade`): every affected panel freezes with its own
  `last-good timestamp` visible as text (never opacity alone) — this satisfies "last-good timestamp shown
  on every affected panel" and "a frozen value can never masquerade as live."
- **Positions grid stays visible** (AC: "the overlay never hides the positions grid entirely") — the
  `CMP-077 ReconnectOverlay` is scrim + banner only, not a full-screen block; the positions grid renders
  underneath with its own `StaleDataShade` treatment and remains scrollable/readable.
  Overlay is `role="alertdialog"`, non-dismissible, with the only interactive controls being
  `[ Retry now ]` and `[ Details ]` — no false "OK" affordance (component catalogue a11y note).
- **`[ Details ]` RBAC split** (carried over from the E08 pattern, applies identically here): Owner sees
  diagnostic detail (endpoint, error code, affected subscriptions); Manager/Viewer see a plain status
  sentence only — never an API key, secret, account id or raw exchange payload (security notes, shared
  rule with SCR-147).
- **Restored / reconciliation** state: dismissible (not auto-hidden) summary line, e.g. *"While you were
  offline: 1 order filled, 1 stop moved by a rule."* — matches the catalogue's example verbatim.

### `SCR-156/panel-level-boundary` and `/app-level-boundary`

- **Panel-level** (drawn first — the common case): "This panel crashed — `[ Reload panel ]` `[ Remove
  panel ]`"; the **surrounding UI is shown functioning** (AC) — the frame depicts the crashed panel inline
  within an otherwise-normal workspace (positions grid and order ticket explicitly rendered healthy beside
  it), reinforcing the reassurance copy "your positions are unaffected and protected by native stops"
  (shown whenever true, i.e. whenever the crashed panel is not itself the positions/order surface).
- **App-level** (route boundary): reload, **safe mode** (loads a minimal workspace with software
  rendering — named explicitly, not just "reload"), and **diagnostics bundle export** with a
  **correlation id** (selectable text, `CMP-033 CopyButton` + `CMP-068 CopyableCodeBlock`). Support-bundle
  generation is an explicit, confirmed, audited action (security note) — a `[ Export diagnostics ]` button
  opens a confirm step naming what will be included (client logs, correlation id, cached health snapshot;
  never secrets/keys) before the download/audit fires.
- **Repeated-crash state** (AC: "stops auto-remounting and explains why"): after N re-mount attempts of the
  same panel/route within a short window, the boundary switches from "Reload panel" (auto-suggested) to a
  static "This panel keeps crashing — reload disabled. `[ Export diagnostics ]`" with the reason stated
  in plain text, so the UI never loops silently.
- a11y: `role="alert"` region, heading, plain-language statement, selectable correlation id, and the stack
  trace collapsed behind an expandable "Technical detail" control (never shown by default) — matches the
  catalogue a11y note exactly.

## 4. Interactions, hotkeys, motion, reassurance copy

- **Interactions:** `[ Retry now ]`, `[ Details ]`, `[ Table view ]` toggles, `[ Export ]`/
  `[ Export diagnostics ]`, `[ Acknowledge ]`, `[ Reload panel ]`/`[ Remove panel ]` are the only
  interactive controls across these four surfaces; every one is a real, named, keyboard-reachable button
  (no icon-only affordances, per C-14.1).
- **Hotkeys:** none are mandatory for these operator/error surfaces (they are not high-frequency trading
  actions); `Esc` does **not** dismiss the SCR-152 overlay or the SCR-156 app-level boundary (both are
  intentionally non-dismissible until the underlying condition clears or the user takes the named action).
- **Motion spec** (ticket requirement: legible but never attention-grabbing enough to be muted by the
  operator): state transitions (`ok→warning`, `warning→down`, `down→ok`) use a single **200 ms opacity
  cross-fade** on the tile/chip/banner, no bounce/pulse/blink, and only ever **once per transition** (never
  a repeating pulse while the state persists — the ticket's a11y note "announce at most once per state
  change, not per heartbeat" applies equally to motion). **Reduced-motion equivalent**
  (`prefers-reduced-motion`): the cross-fade is replaced by an instant swap; no motion is lost information
  because the state word and value are always present regardless of transition style.
- **Reassurance copy** (shared literal string across SCR-143/152/153/156, defined once): *"Native stops on
  the exchange are unaffected."* / *"Your exchange-side stop-losses are unaffected."* — used only when
  factually true for the scope of the current incident (e.g. not shown if the incident is itself an OMS/SL
  subsystem failure); engineering must gate this string on the incident's `component` field, not show it
  unconditionally — flagged as a handoff note in §5.

## 5. Handoff — component ↔ API field mapping

| Design element | Component | API field |
|---|---|---|
| SCR-143 tile value/unit/tone | `CMP-178.value/unit/tone` | `HealthReport.components[].{state,latency_ms}` (value/unit derived per-component, e.g. `latency_ms` for REST, a computed rate for ingestion) |
| SCR-143 tile reason text | `CMP-178` (extends `detail`) | `HealthReport.components[].detail` |
| SCR-143 tile last-good stamp | `CMP-178` (new prop, see §7) | `HealthReport.components[].last_good_at` — **not yet in the schema**, filed on E04-T04 (see §7) |
| SCR-143 tile sparkline | `CMP-178.sparkline` | client-side rolling buffer of polled/streamed `latency_ms`/rate values (not persisted server-side) |
| SCR-143 global connectivity | `CMP-076.status/lastGoodTs` | derived from `HealthReport.overall` + WS `system` liveness |
| SCR-143/152/153/156 "still safe" banner | `CMP-092.issues[]` | `HealthReport.alerts_active` + `Incident.component`/`severity` (gates the reassurance string, §4) |
| SCR-143 top-bar chips | `CMP-210.chips[]` | subset of `HealthReport.components[]`, `.state` → chip `state`, `.detail` → chip `tooltip` |
| SCR-144 table | `CMP-049 Table` rows | `Incident{id, component, severity, status, title, detail, occurrences, first_seen_at, last_seen_at, acknowledged_by, resolved_at, runbook_ref}` |
| SCR-144 acknowledge | `CMP-049` row action | `POST` acknowledging endpoint → `Incident.status="acknowledged"`, `acknowledged_by` (audited) |
| SCR-152 overlay | `CMP-077.retryInSec/attempt/onRetryNow` | WS adapter connection-statechart state (`23-ws-protocol.md`, `28-statechart-catalogue.md` B-entry for exchange connection) — never a bespoke UI-only label |
| SCR-152 per-panel shading | `CMP-078.stale/lastGoodTs` | per-subscription last-message timestamp on the client |
| SCR-156 correlation id | `CMP-091 GlobalErrorBoundaryFallback` | client-generated `correlationId`, echoed in `app.error_boundary_triggered` analytics/incident event |
| Version/build line (all four surfaces' footer) | `CMP-207 BuildFooter` | `HealthReport.version/git_sha` |

**Field gap filed on E04-T04** (per the ticket's mandatory AC "any field the design needs that does not yet
exist is filed as a comment on E04-T04 before sign-off"): `HealthReport.components[]` currently has
`{name, state, latency_ms, detail}` (`22-api-openapi.yaml` line ~9694) but **no `last_good_at` per
component** — only the overall `server_time`. SCR-143's degraded/outage states and the unreachable-backend
variant both require a **per-component** last-good timestamp (the catalogue text says so explicitly: "amber
with the reason and the last good timestamp"). Action: comment filed on E04-T04 requesting
`components[].last_good_at: string (date-time, nullable)` be added to the schema in that ticket's own PR
(this design ticket does not modify `22-api-openapi.yaml` — interface-first rule, §10 of `CLAUDE.md`).

## 6. Accessibility — programmatic contrast/CVD validation (owner-decision substitute for a manual pass)

Per the ticket's agent-delivery adaptation ("CVD/contrast validation → computed programmatically"), the
same method as `E05-D01`/`E08-D01` applies: a WCAG contrast matrix is computed over the token JSON
(`packages/ui/tokens/semantic-{dark,light,hc}.tokens.json`) for every colour pair used above
(`color.status.{success,warning,danger,info}.{default,subtle,strong}` against `color.surface.*` and
`color.text.*`), plus a CVD (protanopia/deuteranopia/tritanopia) simulation pass on the same pairs. Because
frame construction is pending (bridge unavailable, §0), the **script is specified but not yet run against
concrete shape fills** — it is identical in method to the existing `packages/ui/tokens/tests/verify_tokens.py`
contrast checks and will be executed as part of frame QA once the bridge is back, before sign-off. The
non-colour-alone requirement (state is always a word) is satisfied by construction in every frame spec
above (§3) regardless of the contrast pass, since no state in this ticket is ever conveyed by colour alone.

## 8. Heuristic evaluation and owner walkthrough (owner-decision substitute for moderated usability)

Per the agent-delivery adaptations, the ticket's "one moderated walkthrough with the owner" and "design
critique with 2 product designers" are substituted with a documented heuristic evaluation now, plus a
written protocol for the owner to run later.

**Heuristic evaluation (Nielsen + trading-specific heuristics from `05-accessibility-standard.md`),
findings labelled `(heuristic)`:**
1. `(heuristic)` Visibility of system status — satisfied: every tile/chip/banner states a word, a value and
   a timestamp; no bare spinner anywhere in scope.
2. `(heuristic)` Error prevention / recognition over recall — the SCR-156 repeated-crash state (§3) prevents
   an infinite silent reload loop; the SCR-152 retry-exhausted variant prevents a perpetually-ticking,
   never-resolving countdown.
3. `(heuristic)` Match between system and the real world — the state vocabulary (§2) reuses the exact words
   the backend and alerts use; no separate "UI-only" synonyms were introduced (checked against
   `28-statechart-catalogue.md`'s connection statechart labels for SCR-152).
4. `(heuristic)` Trading-specific — "never ambiguous about whether trading is safe": every degraded/outage
   variant states explicitly either "Trading is disabled while offline" (SCR-152) or the native-stop
   reassurance (§4) — never silent on this point, matching the risk register's R11 (Alert reliability).
5. `(heuristic)` Minimal risk of accidental destructive action — `[ Remove panel ]` (SCR-156) and
   `[ Export diagnostics ]` (support-bundle) are both explicit, single-purpose buttons, not bundled with a
   more casual "reload" affordance, satisfying the security note's "explicit, confirmed, audited action."

**Written session protocol (ready for the owner to run later):** a 5-step clickable-prototype script once
frames exist — (1) show `SCR-143/unreachable-backend`, ask "what do you do first?"; (2) show
`SCR-143/outage`, time-to-answer "what's broken / what's still safe / what do I do" (target <30 s per the
ticket's test plan); (3) show `SCR-152` reconnecting→retry-exhausted→restored sequence, ask if the
reassurance copy reads as genuine or boilerplate; (4) show `SCR-144` detail-row expansion, ask if the
trading-impact correlation line changes their triage priority; (5) show `SCR-156` panel-level boundary, ask
if "your positions are unaffected" is trusted at a glance.

**Owner walkthrough checklist (posted on the issue, not fabricated as already-run):**
- [ ] Owner has reviewed the four frame sets in Penpot once built.
- [ ] Owner ran (or delegated) the 5-step protocol above against a clickable prototype.
- [ ] Owner confirms the reassurance-copy gating rule in §4 (never shown when factually false).
- [ ] Owner comments `approved` or requests changes on this ticket's issue.
