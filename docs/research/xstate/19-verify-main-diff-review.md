## F-1 — Sticky `tripped` flag starves later, unrelated user events (High)

**Evidence:** `src/xstate_statemachine/sync_interpreter.py:636-655` and `:672-684`.

Once the self-generated budget overflows, `tripped = True` is set and — per the
comment at `:679-683` — is *deliberately* never cleared for the remainder of the
drain. The chain-reset at `:673-679` is gated on `not tripped`, so `generated`
stays above `limit` forever. Every subsequent self-generated event in that drain
is dropped on arrival at `:636`, **including events generated by unrelated user
events that arrive later in the same batch.**

The comment justifies this as "a machine that keeps regenerating cannot earn a
fresh 1,000." But the flag is not scoped to the offending chain — it is scoped to
the whole drain, and `send_events()` makes a drain arbitrarily long.

**Repro:** `repro/f_tripped_sticky.py` — one `SPIN` event that self-feeds, followed
by five ordinary `WORK` events whose handlers each raise exactly **one** `INNER`
(one deep, no loop whatsoever):

```
i.send_events(["SPIN"] + ["WORK"] * 5)
INNER handled: 0 of 5 (expected 5)
```

All five `WORK` events are accepted and processed; all five `INNER` events they
raise are silently discarded. The async engine on the identical machine
(`repro/f_sticky_async.py`) reports `ASYNC INNER handled: 5 of 5`, because
`interpreter.py:1222-1226` resets `_raise_depth` unconditionally when a macrostep
raised nothing. **This is exactly the engine-parity divergence #77 claims to have
closed**, in the opposite direction from 0.8.0.

The CHANGELOG states the drop "never [loses] events the caller was told were
accepted." That is true of the *inbox*, but the `INNER` events here are the
observable effect of five events the caller **was** told were accepted, and they
are lost with only a `DEBUG`-level log line (`:646` downgrades the log to `DEBUG`
after the first trip, so the repeated loss is invisible at default log levels).

**CV impact:** any CandleViewer path batching heterogeneous events through
`SyncInterpreter.send_events()` where *any one* event can self-feed. Note the
existing test `test_sync_runaway_does_not_discard_external_events`
(`tests/test_core_algorithm.py:286+`) pins only that the *inbox* survives — it does
not exercise a second, independent raise after the trip.

## F-2 — `**kwargs` clocks receive an unexpected `sync=` (High)

**Evidence:** `src/xstate_statemachine/base_interpreter.py:275-291` (`_accepts_kwarg`),
`:3435-3449` (`_set_timeout`).

`_accepts_kwarg` returns `True` when *any* parameter is `VAR_KEYWORD`:

```python
return any(p.kind is inspect.Parameter.VAR_KEYWORD for p in params.values())
```

A clock written against the **0.8.0** protocol — `def set_timeout(self, fn, delay_sec, **kwargs)`,
a completely ordinary shape for a wrapper forwarding to a legacy scheduler — is
therefore judged to "accept" `sync`, and gets a keyword it has never heard of.
`_accepts_kwarg`'s own docstring frames `**kwargs` as consent, but a 0.8.0-era
clock cannot have consented to a keyword that did not exist.

**Repro:** `repro/f_clock_kwargs.py` — a `**kwargs` clock that asserts on unknown
keys (standing in for any wrapper that forwards `**kwargs` to a backend with a
fixed signature):

```
AssertionError: unexpected kwargs: ['owner', 'sync']
  ... base_interpreter.py, in _set_timeout
      fn, delay_sec, owner=owner, sync=self._clock_sync_lane
```

The failure surfaces at the first `after`/delayed-send, i.e. at runtime under load,
not at construction. The CHANGELOG's promise — "third-party clocks written against
the 0.8.0 `Clock` protocol still work" — does not hold for this shape.

The single-call design (replacing 0.8.0's try/except-`TypeError` retry) is
otherwise a genuine improvement; the defect is narrowly the `VAR_KEYWORD` branch.
A safer rule is to require `sync` to appear by name, treating `**kwargs` as
*not* accepting it.

## F-3 — `create_machine()` mutates the caller's `MachineLogic` in place (Medium-High)

**Evidence:** `src/xstate_statemachine/factory.py:212`, `:241-258` (`_alias_logic_names`);
`src/xstate_statemachine/machine_logic.py:158-186` (`resolve_aliases` — `registry[name] = registry[candidates[0]]`).

`resolve_aliases` writes new keys into the **live registry dict** the caller
passed. `MachineLogic.__init__` copies the caller's input mapping, but the
`MachineLogic` *instance* is shared whenever one is reused across machines — a
documented pattern.

**Repro:** `repro/f_shared_logic.py`

```
after m1, keys: ['storeUser', 'store_user']      # 'storeUser' injected by create_machine(m1)
after m2, keys: ['STOREUSER', 'storeUser', 'store_user']
```

Two consequences:

1. **Observable API surface changes underfoot.** Code inspecting
   `logic.actions` (introspection, diagnostics, `len()` in the init log)
   sees keys nobody registered. Each `create_machine()` against a new
   spelling grows the dict permanently.
2. **Action at a distance into a hard error.** Because the injected aliases
   are indistinguishable from real registrations, they count as *candidates*
   in the ambiguity check. `repro/f_pollute.py`:

```
m1 ok, registry now: ['storeUser', 'store_user']
m2 ERR: InvalidConfigError Logic name 'Store_User' is ambiguous:
  ['STOREUSER', 'storeUser', 'store_user'] are all registered and differ only by case...
```

The user registered exactly **two** callables. The error names **three**
candidates, one of which the library injected itself during an earlier,
unrelated `create_machine()`. The remedy the message suggests ("Keep one")
is not actionable — the third key is not in the user's code.

Aliasing into a private, per-machine overlay dict (or a copy of the registry
owned by the `MachineNode`) would give identical hot-path performance without
mutating caller state. Re-running `create_machine` on the same logic is at
least idempotent (`repro/f_repeat.py`).

## F-4 — Two distinct config names silently collapse onto one callable (Medium)

**Evidence:** `machine_logic.py:170-186`. The ambiguity guard checks
`distinct = {id(registry[c]) for c in candidates}` — i.e. it only fires when the
**registry** holds two different callables for one normalised key. It never
checks the converse: two different *required config names* claiming the same
implementation.

**Repro:** `repro/f_stately.py`

```
both bound: {'fetchData': 'a1', 'fetch-data': 'a1', 'fetch.data': 'a1'}
```

A config that declares `fetch-data` and `fetch.data` as two entry actions gets the
same `a1` run twice, with no warning. `repro/f_collide.py` shows the same for
`["storeUser", "store_user"]` in one `entry` list. This is a plausible Stately
export shape — the CHANGELOG explicitly advertises `inline:m.a#entry[0]`-style
non-identifier names as aliasable, and those are *generated*, so the author never
chose them and cannot reason about their normalised collisions.

The `[` `]` `.` `:` `#` separators are stripped, so `inline:m.a#entry[0]` and
`inline:m.a#entry[]0` — or, more realistically, `entry[0]` and `entry[1]` under a
different generator — normalise apart only by digits. This narrowly works, but
the separator set is aggressive enough that collisions on generated names are
a real class, and only the registry side is defended.

Note the alias direction is verified correct on the safe cases: exact keys always
win (`f_collide.py` keeps `store_user` → `store_user`), and the Stately name binds
as documented.

## F-5 — `logic_modules` duplicate resolution is order-dependent, not rejected (Medium)

**Evidence:** `src/xstate_statemachine/logic_loader.py:404-409`:

```python
for key, impl in logic_map.items():
    normalized_map.setdefault(normalize_logic_name(key), impl)
```

`setdefault` means **first wins by module iteration order**. The CHANGELOG's
"Ambiguous logic registrations are rejected … raises `InvalidConfigError` at build
time instead of silently picking one" describes `resolve_aliases` only. The
auto-discovery path — the one most users hit — still silently picks one.

**Repro:** `repro/f_loader_dup.py` — a module defining both `fetch_data` (returns
`"SNAKE"`) and `fetchData` (returns `"CAMEL"`), with the config naming `FETCH_DATA`:

```
bound to: fetch_data
```

No error, no warning. Which one binds depends on definition order in the module.
Both are genuinely different callables — exactly the case `resolve_aliases` was
written to reject. (`_alias_logic_names` runs afterwards in `create_machine`, but
by then the loader has already placed an exact-name entry, so the guard is
bypassed.)

`repro/f_loader_twoname.py` shows the F-4 shape on this path too: one impl
satisfying two distinct config names.

## F-6 — `done.invoke` from a sync service is dropped after a trip (Medium)

**Evidence:** `sync_interpreter.py:594-600` — the comment explicitly classes
"a `done.invoke` from a sync service" as self-generated work counting against the
budget. Combined with F-1's sticky flag, a service completion that arrives after
an unrelated trip is discarded.

**Repro:** `repro/f_sticky_invoke.py` — `SPIN` trips a `maxIterations: 20` budget,
then `GO` enters a state invoking a trivially-returning sync service:

```
state: {'m.work'}   (expected m.done)
```

The machine parks permanently in the invoking state. The service **ran**; its
`onDone` transition never fires. This is a silent hang — precisely the failure
class the dead-loop validator exists to prevent, reintroduced at runtime.

Due `after` timers are *not* affected in the same way (`repro/f_sticky_timer.py`
correctly reaches `m.done`), because `_pump_timers` re-appends on each loop
iteration and the state is reached before the budget check bites. The
inconsistency between the two self-generated sources is itself worth noting: the
budget's classification is coarser than its enforcement.

## F-7 — Rollback checkpoint predicate does not model `always` / `on` action lists (Medium)

**Evidence:** `base_interpreter.py:2272-2282`. The checkpoint is now taken only when

```python
transition.actions or target_state.type == "history"
  or any(s.exit for s in states_to_exit)
  or any(s.subtree_has_actions for s in path_to_enter)
```

`StateNode.subtree_has_actions` (`models.py:893-896`, `:1483-1496`) is computed
from **`entry` / `exit` only**:

```python
flag = bool(node.entry or node.exit)
```

Actions declared on `on` / `always` / `after` transitions of the entered subtree
are not counted. The optimisation's correctness therefore rests on the assumption
that a transient (`always`) transition taken immediately after entry performs its
own checkpoint via its own `_execute_transition` call.

**That assumption holds in the case tested** — `repro/f_rollback_gap.py` builds a
machine whose transition and entered state have no entry/exit actions but whose
target declares `always: {actions: ["mutate", "boom"]}`, and the context is
correctly restored (`context n = 0`). So this is **not a confirmed defect**.

It is flagged because (a) the predicate is subtle, (b) the CHANGELOG presents this
purely as a ~22 % throughput win with no note that the rollback *scope* narrowed,
and (c) `subtree_has_actions`'s name and docstring ("does this node OR any
descendant declare entry/exit actions") do not match how the call site reads it
("can a user action run in this subtree"). A future change that widens what
`_execute_transition` covers, or a nested-parallel entry that folds transient
actions into the same call, would turn this into silent context corruption under
`rollback` — the policy whose entire purpose is to not corrupt context. Worth a
targeted property test before CandleViewer relies on `rollback`.

## F-8 — Static `raise` of a reserved-namespace event escapes `strict` validation (Low)

**Evidence:** `validation.py:243-272` (`_collect_unknown_raises`) calls
`machine.is_known_event(event_type)`, which returns `True` unconditionally for any
type matching `SYSTEM_EVENT_PREFIXES` (`models.py:1552-1557`).

**Repro:** `repro/f_strict_raise.py` — a `strict` machine that handles
`done.review` but raises `done.reveiw` (typo):

```
built OK - typo'd reserved raise NOT caught
```

The new `UserWarning` about reserved-namespace `on` keys *does* fire, so the user
gets a nearby signal, and the CHANGELOG is upfront that reserved-namespace user
events are second-class pending 0.9 provenance tagging. Low severity, but the
gap is exactly the "typo'd internal event never raised to anyone" failure #51
set out to close, surviving in the namespace the same release warns about.

## F-9 — A legitimate 1001-deep chain is cut; engines differ by one (Low)

**Evidence:** `sync_interpreter.py:635` (`generated > limit`) vs
`interpreter.py:1161` (`self._raise_depth > limit`).

**Repro:** `repro/f_chain.py` — 1500 states chained by a one-deep `raise` per
entry (a legitimate long chain, no loop, `maxIterations` default 1000):

```
SYNC landed:  {'m.s1000'}
ASYNC landed: {'m.s1001'}
```

Two observations:

1. **The answer to the brief's question is yes** — a legitimate 1001-chained-raise
   sequence is truncated. This is the documented, intended purpose of
   `maxIterations` and is configurable per machine, so it is working as designed,
   not a defect. It is recorded here because a CandleViewer state chain deeper
   than 1000 would be silently cut at `ERROR` level with the machine left in a
   mid-chain state and `status == "running"`.
2. **The engines are off by one.** The CHANGELOG says "The budget is per *chain*,
   matching the async engine" and "an engine-parity test pins it." The parity is
   one-event-inexact. The *behavioural* parity claim that matters — independent
   one-deep raises are never truncated — does hold: `repro/f_parity.py` confirms
   `INNER handled: 3000 of 3000` on the sync engine, the headline #77 fix, and
   `test_sync_large_batch_is_not_truncated` pins 5000. The off-by-one is cosmetic
   unless a machine is tuned to an exact `maxIterations`.

## F-10 — Unbounded warn-latch set in `resolver.py` (Low)

**Evidence:** `resolver.py:87-89`:

```python
_SIBLING_FALLBACKS_WARNED: Set[Tuple[str, str]] = set()
```

Module-global, never pruned, keyed on `(source.id, target)`. A long-lived process
that builds many machines with generated or per-tenant ids accumulates one tuple
per distinct pair forever. Small, but it is a new unbounded global in a library
that otherwise scopes state to the `MachineNode`.

By contrast `_WARNED_ACTION_ERROR_POLICY_DEFAULT` (`base_interpreter.py:271`) is a
single bool — correct. Note that its move from per-`MachineNode` to per-process is
a genuine fix for the "warn in a warm-up path nobody reads" problem, but it also
means a process running *many different* machines with unset `actionErrorPolicy`
now hears about only the first. The CHANGELOG says "Set `actionErrorPolicy`
explicitly on every machine to silence this" while the warning can only ever name
one machine — the other offenders are undiscoverable from the warning alone.

| `StateNode.subtree_has_actions` | `models.py:893-896` | New public-ish attribute; see **F-7** re: its name vs. use |
| `normalize_logic_name`, `resolve_aliases` | `machine_logic.py:110-186` | Not in `__all__`, but importable and now load-bearing |

**Behaviour changes in the diff that the CHANGELOG does not flag as risks:**

- **New `DeprecationWarning` on every leading-dot sibling target** (`resolver.py:270-276`).
  The CHANGELOG lists it under *Deprecated*, but not that it fires from
  build-time validation as well as runtime resolution. The library's own suite
  emits it (see `tests/tests_cli/test_round_trip.py::test_dot_relative_target_in_source`
  in the run above). Any CandleViewer config using `.sibling` targets will now
  warn, and under `-W error` will **fail**.
- **New `UserWarning` on reserved-namespace `on` keys** (`validation.py:198-229`),
  raised from `validate_machine` with `stacklevel=4`. Same `-W error` exposure.
- **Rollback now withdraws `raise`d events** (`base_interpreter.py:3361-3396`).
  Correct per #27, but it is a semantic change to what a failed transition
  leaves behind; a machine relying on a `raise` surviving a rolled-back
  transition changes behaviour silently.

## Verified-good (no finding)

- **#75 receipt identity** — `repro/f_receipt.py`: two concurrent
  `send(ev, wait=True)` on one `Event` instance both resolve, no hang.
  `Interpreter._detach` (`interpreter.py:695-711`) handles `Event`,
  NamedTuple and generic objects; the caller's object is not mutated.
- **#76 mixed-tree lane selection** — `repro/f_mixed_clock.py`: one shared
  `RealClock` serving a `SyncInterpreter` and an `Interpreter` inside a running
  loop; both reach `m.b`. The owner-driven lane works as designed for clocks
  with a real `sync` parameter.
- **#77 headline case** — `repro/f_parity.py`: 3000 independent one-deep raises
  all delivered on the sync engine.
- **Stately non-identifier name aliasing** — `repro/f_stately.py`:
  `inline:m.a#entry[0]` binds to `inline_m_a_entry_0`.
- **Exact-name precedence** — confirmed in `repro/f_collide.py` and
  `repro/f_pollute.py`: an exact registry key is never overridden by an alias.
- **Symbolic delays are *not* aliased** — `repro/f_delays.py` /
  `f_delays2.py`. `_alias_logic_names` (`factory.py:245-258`) covers
  `actions`/`guards`/`services` only; `MachineLogic(delays={"my_delay": 10})`
  against `after: {"MY_DELAY": ...}` does **not** resolve. This is arguably an
  inconsistency in the "snake_case ↔ camelCase, **everywhere**" promise, but it
  fails **loudly and safely**: two `WARNING`s (`Named delay 'MY_DELAY' is not
  defined`, `Skipping 'after' transition`) and the machine simply does not take
  the transition. Recorded as a documentation gap, not a defect.
- **Test integrity** — no test function removed, no assertion weakened, no
  `skip`/`xfail` added in the diff. The 13 skips are pre-existing.

## Recommended gate actions

1. **Block on F-1 and F-2** if CandleViewer uses `SyncInterpreter.send_events()`
   with heterogeneous batches, or supplies a custom `Clock`.
2. **F-3** is a correctness hazard for any code sharing one `MachineLogic` across
   machines — audit CandleViewer for that pattern before upgrading.
3. Re-run `docs/research/xstate/gate/run_gate.py` against `5327ba6` and diff the
   result against the 0.8.0 baseline in `20-adoption-gate.md`.
4. Add `-W error::DeprecationWarning` to a CandleViewer canary run to surface the
   new `.sibling`-target and reserved-namespace warnings before they land in CI.
