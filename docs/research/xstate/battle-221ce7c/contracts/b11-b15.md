# Contract machines B11–B15 end-to-end on `221ce7c`

**Library:** `xstate-statemachine` @ `221ce7c` (unreleased 0.8.1; `__version__`
still reports 0.8.0 — key on the commit). Merge of #178 on top of #177
(round‑6 fixes #166–#175, #157, #122-as-designed) and #165/#176 (hot path).

**Scope.** The five OMS-shaped contract machines — B11 `RecordingSession`,
B12 `ReplaySession`, B13 `ExchangeConnection`, B14 `IngestionPipeline`,
B15 `PaperMatcher` — driven end to end under the mandatory config
(`actionErrorPolicy: rollback`, `onUnhandled: defer` on the order path /
`error` on the control path, `guardErrorPolicy: raise`, `strictTargets`,
`strict`, bounded inbox with `OverflowPolicy.RAISE`, `SimulatedClock`,
trace plugin standing in for `CvErrorHooks`).

**Corpus.** Corrected catalogue JSON copied verbatim from
`battle-3ed3099/contracts/B1{1..5}.machine.json` (byte-identical to the
`battle-cec108b` copies — verified by `diff`). Scripts in
`battle-221ce7c/contracts/`, raw results in `contracts/results/*.json`.

## 2. Build + policy plumbing (`g3_build.py`)

All five machines construct with stub logic, and every policy key reaches the
machine object:

| Machine | id | `actionErrorPolicy` | `onUnhandled` | `guardErrorPolicy` | `strictTargets` | `strict` |
|---|---|---|---|---|---|---|
| B11 | `recording` | rollback | defer | raise | ✓ | ✓ |
| B12 | `replay` | rollback | defer | raise | ✓ | ✓ |
| B13 | `ws_conn` | rollback | error | raise | ✓ | ✓ |
| B14 | `book` | rollback | error | raise | ✓ | ✓ |
| B15 | `paper_account` | rollback | defer | raise | ✓ | ✓ |

Two plumbing notes (both pre-existing, both benign-but-sharp):

- **`spawnBlockingTimeout` is parsed and dropped.** Every machine declares
  `spawnBlockingTimeout: 5000`; validation accepts it, but there is no
  corresponding attribute on the machine (`ABSENT` in `policy_honoured`).
  A value we believe we set has no effect. **NEEDS-WRAPPER**: assert the
  attribute exists at build time rather than trusting the JSON.
- **Unknown top-level keys are accepted silently** (`P2_typo_keys`): a typo'd
  `onUnhandledd` leaves the default in place with no diagnostic, while a
  *bad value* for a known key is caught cleanly (`InvalidConfigError` for
  `onUnhandled`, `actionErrorPolicy`, `guardErrorPolicy` alike). Config typos
  are a silent downgrade to defaults.

`create_machine` with **no** logic raises `ImplementationMissingError` for all
five (expected — the contracts declare actions/services we supply at runtime);
with an empty `strict=True` `MachineLogic` it builds. No `InvalidConfigError`
anywhere, so **there is no our-contract defect in the JSON itself.**

## 3. 🔴 LIB-R6-01 — **STILL OPEN on `221ce7c`.** Blocker.

**Shape (present in two of our five contract machines):** a state that
`invoke`s a service, whose `onDone` targets a state whose **entry action
raises**, under `actionErrorPolicy: "rollback"`.

- **B11**: `starting --invoke subscribe_streams--onDone--> recording`,
  `recording.entry = [cancel_linger, emit_recording_metric]`.
- **B13**: `subscribing --invoke subscribe_in_batches--onDone--> live`,
  `live.entry = [reset_backoff, drain_deferred, emit_feed_healthy, arm_pong_deadline]`.

**Observed (`g3_r6.py`, scenarios `R6-B11-01`, `R6-B13-01`).** The entry
action raises → rollback restores the *source* state → the source state
re-enters → its `invoke` re-arms → the service completes again → `onDone`
fires again → entry raises again. Forever, at full CPU, with no backoff:

| Machine | service | 20 s of wall clock | rate | resting state |
|---|---|---:|---:|---|
| B11 | `subscribe_streams` | **131,313 invocations** | ~6,570/s | `recording.starting` |
| B13 | `subscribe_in_batches` | **72,305 invocations** | ~3,615/s | `ws_conn.subscribing` |

The loop is **not** bounded by the round‑6 per-macrostep settle budget, does
**not** trip `RunawayChainError` (`last_error` is the plain `RuntimeError`
from the action, rewritten on every lap), and is **not** ended by external
events — `send("GAP_DETECTED")` between samples returned a normal receipt and
the loop carried on at the same rate (836 / 819 / 842 extra invocations across
three intervening external sends). `status` stays `"running"`; nothing in the
public surface says the machine is sick.

**Why this is a blocker for us, not a curiosity.** `subscribe_streams` and
`subscribe_in_batches` are *real network calls to an exchange*. A single
buggy metric emitter in `recording.entry` — the most trivially fallible code
in the machine — turns the connection manager into a 6,500 req/s subscribe
storm against a venue that will rate-limit, then ban, the API key. The
failure mode is "one bad log line bans the account."

**Sync engine is correct.** With a plain-`def` service (the sync engine
refuses async services with `NotSupportedError`, so the naive parity run is
vacuous — re-run with `def`), `SyncInterpreter` executes **2** service calls,
**3** actions, rests in `recording.starting` with
`last_error = RuntimeError`, and returns to the caller in ~0 ms. The bug is
async-engine-only, exactly as filed in round 6.

**Classification: LIBRARY. Severity: 🔴 Blocker. Status: not fixed by #177/#178.**

**Required mitigation (NEEDS-WRAPPER until fixed upstream).** Our wrapper must
not rely on the engine to bound this. Either (a) forbid the shape at build
time — reject any machine where a state reachable by `invoke.onDone` has an
entry action, unless that action is registered as infallible; or (b) wrap
every entry action reachable from an `onDone` in a swallow-and-report
decorator so it can never raise into rollback; plus (c) an out-of-band
invocation-rate watchdog per service name that hard-stops the interpreter.
(a)+(c) is the cheap, verifiable pair.

## 4. ✅ R6-03 class is bounded — and that exposes a *contract* problem

**Shape:** a state whose entry raises, with an `always` leaving it.
Present in B14 (`desynced.entry = [emit_book_desynced, bump_resync_count,
emit_resync_metric]`, `always -> snapshot_pending`) and B15
(`liquidating.entry = [apply_liquidation_haircut, write_liquidation_journal]`,
`always -> liquidated`).

Both **terminate immediately and cleanly** (`R6-B14-03`, `R6-B15-03`, and the
sync twins): ≤9 action calls, <0.3 s, no runaway. The round‑6 budget work
holds here. Good.

But look at *where they rest* — and this is the part that matters for an OMS:

| Scenario | raising action | resting state | `Receipt` |
|---|---|---|---|
| B14 `SEQUENCE_GAP` | `emit_resync_metric` | **`book.live`** (tag `consumable`) | `changed=False, error=RuntimeError, denied=False` |
| B14 `SEQUENCE_GAP` | `emit_book_desynced` | **`book.live`** | `denied=False, error=RuntimeError` |
| B14 `SEQUENCE_GAP` | `stamp_desync` | **`book.live`** | `denied=False, error=RuntimeError` |
| B15 `MARK_UPDATE` | `write_liquidation_journal` | **`paper_account.active`** | `changed=False, error=RuntimeError, denied=True` |
| B15 `MARK_UPDATE` | `apply_liquidation_haircut` | **`paper_account.active`** | `denied=True` |

Rollback is behaving exactly as documented — and the result is that **a
failing telemetry call cancels the desync and cancels the liquidation.**
After the B14 rollback: `resync_count == 0`, `desynced_since_us == null`,
state `book.live` still carrying the `consumable` tag — i.e. the order book
advertises itself as safe to trade off *while it is known to have a sequence
gap*. After the B15 rollback the account is back in `active` and, critically,
**retrying `MARK_UPDATE` reproduces the same denial** — the account can never
be liquidated while the journal writer is broken.

This is not a library bug: `rollback` is doing what `rollback` means. It is
an **our-contract** defect — we put non-essential, fallible side effects
(`emit_resync_metric`, `emit_book_desynced`, and arguably
`write_liquidation_journal`) in the same atomic entry set as the safety
transition, under a policy that makes the whole set all-or-nothing.

**Classification: OUR-CONTRACT (B14, B15). Severity: 🟠 High.**
**Fix in the catalogue, not the library:** move telemetry out of `entry` into
a post-settle observer, and keep only infallible state mutation in the entry
sets of `desynced` and `liquidating`. Note the asymmetry worth encoding in
the wrapper: B15's receipt sets `denied=True` while B14's sets
`denied=False` for the same class of outcome, so `denied` alone is not a
usable "did my safety transition land?" test — `error is not None` is.

## 5. Invariants, snapshot and parity — the parts that are healthy

**Catalogue invariants (`g3_b11.py`, `g3_b12.py`, `g3_b13.py`,
`g3_b14_b15.py`).** 31 scenarios; every declared invariant that is actually
*expressed in the JSON* passes on `221ce7c`:

- **B11** 7/7 — linger-on-open-position, `reasons_remain` branch ordering,
  reason re-added during `lingering` returns to `recording` **without**
  restarting the stream, gap counting, degraded entry/exit on stream health.
- **B12** 7/7 — cursor monotonicity (SEEK is the only rewind),
  `CONSUMER_SLOW` degrades the clock and drops nothing, coverage gaps
  surfaced from `seek_and_prime`, loop re-buffer, `destroyed` truly final,
  and `CANCEL` during `buffering` — the late invoke result correctly does
  **not** land afterwards.
- **B13** 10/12 — public and private connect paths, connection-budget block
  (no socket opened), backoff doubling to max and resetting only on `live`,
  `subscribed_topics == pending_topics`, partial-batch subscribe never
  reaching `live`, full reconnect/resync with topic restoration, PONG
  re-arm and `PONG_DEADLINE` demotion, clean `SHUTDOWN`. The 2 failures are
  `LIB-01` and the `strict` wildcard issue — see §6.
- **B14/B15** 7/9 — snapshot/delta ordering with buffered replay after
  `snapshot_seq`, `SEQUENCE_GAP` re-snapshot with no delta applied across
  the gap, `SNAPSHOT_TIMEOUT` re-entry counting a resync, margin-call round
  trip, `liquidated` terminal against a favourable mark, journal-before-
  terminal ordering, and liquidation preempting a busy inbox via
  `send_priority`. The 2 failures are `OUR-B14-01` and `LIB-01` — see §6.

**Snapshot/restore at quiescence (`g3_snapshot.py`) — 5/5.** For each machine
the scripted run is executed twice: once uninterrupted, once with
`get_persisted_snapshot()` + restore into a fresh interpreter **between every
macrostep**. States, context, action trace and transition trace compare equal
in all five. The #169 entry/exit-action refusal produced no false refusal at
quiescence, which is the property we actually need.

One follow-on worth recording: a snapshot taken right after a
rollback-swallowed transition faithfully persists the *rolled-back* state
(`book.live`, `resync_count: 0`). That is correct-by-construction, and it
means the §4 contract defect is **durable** — it survives a restart, so an
operator restarting the ingester does not clear a swallowed desync.

**Async to sync parity (`g3_parity.py`) — 5/5.** Identical scripts produce
identical states, context and action traces on both engines for all five
machines. Parity holds everywhere we can express the script on both engines;
the one place it does **not** hold is §3, and that gap is invisible to a
naive parity harness because `SyncInterpreter` rejects the async service with
`NotSupportedError` before the shape is ever exercised. **Any parity suite
over these contracts must use plain-`def` services or it will silently pass.**

## 7. Verdict for adoption

The round-6 work is real and it holds: every cycle we can build out of
`always` is now bounded on both engines, snapshot/restore is trustworthy at
quiescence across all five contract machines, and async/sync parity is clean
on every script we can express on both engines. B12 in particular is
unblemished.

But **`LIB-R6-01` is still open on `221ce7c`, on two of our five machines,
on the two services that talk to the exchange.** Until it is fixed upstream,
adoption is conditional on the wrapper owning the bound:

1. **Build-time shape rejection** — refuse any machine where a state targeted
   by `invoke.onDone` has an `entry` containing an action not on an
   `INFALLIBLE` allowlist. This is a static check over the JSON; it catches
   B11 `recording` and B13 `live` today.
2. **Entry-action isolation** — all telemetry actions (`emit_*`, metric
   `record_*`) wrapped so they cannot raise into `rollback`. This removes
   §3's trigger *and* §4's swallowed-safety-transition problem in one move.
3. **Per-service invocation-rate watchdog** — hard-stop the interpreter above
   N invocations/second of any single service name. Defence in depth for
   shapes (1) misses; also the only thing that would have caught §3 in
   production, since `status` stays `"running"` throughout.
4. **Send wrapper** — treat `error is not None` (never `denied`) as "my
   transition did not land", and subscribe `on_unhandled_event` and
   `on_event_dropped`, since `LIB-01` makes the receipt mute on a fatal kill.
5. **Catalogue edits** — B11 `degraded` gains `STREAM_UNHEALTHY`; B14 gains a
   real buffer bound; B14 `desynced` and B15 `liquidating` entry sets drop
   their telemetry.

Items 1–4 are wrapper work we control; item 5 is JSON we control. None of it
blocks on upstream. The upstream blocker is a single issue: §3.
