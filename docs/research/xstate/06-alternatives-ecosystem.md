# Study 6 — Ecosystem & Alternatives (Python statecharts/state machines)

Raw research findings for CandleViewer's evaluation of `basiltt/xstate-statemachine` (aka
`xstate-statemachine` on PyPI) against the wider Python state-machine/statechart ecosystem.
No git operations were run against GitHub; `gh issue list` (read-only) was used only to
pull issue metadata for the library itself.

## 1. Libraries surveyed

| Library | PyPI | Latest / activity | Paradigm |
|---|---|---|---|
| `xstate-statemachine` (basiltt) | yes | v0.7.0 docs site; 11 releases on PyPI (0.2.1→0.7.x range seen); repo created 2025-07-06, 164 commits, 14 stars, 1 fork | XState-JSON-compatible statechart interpreter, zero deps |
| `python-statemachine` (fgmacedo) | yes, active | Actively maintained, docs at readthedocs, "3.2.x" series; well-known, widely used | Statecharts: compound (hierarchical) states, parallel regions, history; sync+async unified engine (auto-switches to AsyncEngine if any callback is async) |
| `transitions` (pytransitions) | yes, active | v0.9.3 (Jul 2025); long-running project, big extension ecosystem (`transitions-anyio`, GUI, diagrams) | HSM extension (`HierarchicalMachine`) supports nested + parallel states; separate `AsyncMachine`/`HierarchicalAsyncMachine` classes for asyncio; not statechart-spec-complete (no SCXML/history-state formalism baked in, though nesting/parallel exist as extensions) |
| `sismic` (Alexandre Decan) | yes | Mature academic project (Univ. of Mons); requires Python ≥3.9; full UML2 statechart concept coverage | Full statechart interpreter: composite/orthogonal(parallel) states, shallow/deep history, guarded/eventless/internal transitions, Design-by-Contract, BDD testing, YAML-based definitions, sync+async simulation |
| `pysm` | yes but effectively dormant | Small, minimal HSM library; last significant activity years ago | Basic hierarchical FSM, no async, no XState interop |
| `Miros` (or `miros`) | yes, niche | Small community (HSM/Harel formalism implementation, informed by Samek's "Practical UML Statecharts") | Hierarchical, reflection-based; not async-native; steep conceptual learning curve; low adoption |
| `automat` (glyph) | yes, active (used inside Twisted-adjacent projects) | Maintained by Twisted's Glyph Lupton; stable, low-churn | Flat FSM only (no hierarchy/parallel/history) — deliberately hides the state machine behind a plain method-call API; sync only, no built-in async story |
| `statesman` | yes, niche | "modern state machine library," async-native from the start, Pydantic-based data modeling, decorator API | Flat FSM with guard/before/on/after hooks; no hierarchy or parallel regions; async-first design (asyncio callbacks) |
| `temporalio` (Temporal Python SDK) | yes, very active, backed by a company | v1.24.0 latest observed; large ecosystem, Pydantic data-converter support | Different paradigm entirely — durable workflow orchestration (event-sourced execution history + deterministic replay), not a statechart library; workflows are Python functions/classes with `@workflow.defn`, not XState-style state graphs |
| `eventsourcing` (pyeventsourcing) | yes, maintained | Established generic event-sourcing framework for Python | Not a state machine library — an aggregate/event-store framework; state is derived by replaying a stream of events onto an aggregate. Complements (does not replace) a statechart: an OMS aggregate could store its state-transition history as events while a statechart library decides the *legal* transitions. |
| `hsm-py` (artcom) | GitHub only, no notable PyPI presence found | Very new (created 2025-02), 0 stars, 48 commits | Minimal own-brand HSM: nested (Sub), orthogonal regions (Parallel), external/internal/local transitions, guards, LCA algorithm — essentially a fresh from-scratch HSM implementation, not XState compatible, negligible community |

Note: "PyXState"/"xstate-python" as a direct XState JSON runtime distinct from basiltt's library was
not found as a currently maintained, separately-branded PyPI package in this search; basiltt's project
appears to be the only actively promoted "run XState JSON unmodified in Python" library at present.
(basiltt also has an older/parallel repo `basiltt/XStateMachine`, description-similar, likely a
predecessor/rename — worth the owner double-checking which repo is canonical before deeper adoption.)

## 3. xstate-statemachine (basiltt) — PyPI/GitHub facts found

- PyPI project: `xstate-statemachine`, "A robust Python library for parsing and running XState JSON state machines." Author `basiltt` (PyPI profile shows exactly 1 project, joined Jul 2025).
- Docs site (`basiltt.github.io/xstate-statemachine`) advertises v0.7.0, "2,800+ Tests Passing," "6 Python Versions," "0 Dependencies," "5 CLI Templates," Python 3.9→3.14 support.
- GitHub repo `basiltt/xstate-statemachine`: 14 stars, 1 fork, MIT license, created 2025-07-06, 164 commits on `main`.
- Release history seen via Libraries.io: 0.2.1 (Jul 7, 2025) → 0.2.2 → 0.2.3 → 0.3.0 → 0.3.1 → 0.4.0 → 0.4.1 → 0.4.2 (Aug 14, 2025) → ... → 0.4.3 (Feb 3, 2026); docs site claims a current v0.7.0. That's roughly 11+ releases in under a year — a fast cadence, consistent with active single-maintainer iteration, but also meaning the API/behavior has been actively moving (relevant for "battle-testing": pinning behavior in CandleViewer will require careful version pinning + regression tests since minor versions have shipped frequently).
- `gh issue list -R basiltt/xstate-statemachine --state all` returned exactly **1 issue total** (closed): *"Bug Report: logic_providers Auto-Discovery Fails to Map camelCase JSON Actions to snake_case Python Methods"* (closed 2026-02-03). This is a real, substantive interop bug class — XState JSON typically uses camelCase action/guard/service names (JS convention) while idiomatic Python uses snake_case; the auto-discovery/mapping layer had a gap here. It was reportedly fixed, but the fact that this bug reached a filed issue at all is a concrete "gotcha" for the exact use case CandleViewer wants (importing/hand-authoring XState-style JSON against Python `logic_providers`). Only 1 issue also means the issue tracker has essentially no long tail of edge cases reported by outside users — the "battle-testing" the owner wants done has largely not yet happened via community usage; CandleViewer would be one of the first non-trivial production consumers.

## 4. Honest "is this the right pick" assessment

**Why it might be the right pick for CandleViewer:**
- It is the only Python library in the survey offering genuine XState-JSON interop (nested + parallel + history + invoke/actors), which the owner explicitly wants for cross-tooling (visual editor in Stately.ai, JSON as source of truth) and because he authored it and wants to dogfood/battle-test it.
- Feature checklist (hierarchy, parallel, history, actors, snapshots, dual sync/async interpreters, zero runtime deps) is the most complete on paper of any Python option surveyed — `sismic` is the closest formal competitor on spec completeness but has no XState-JSON compatibility and a heavier YAML/SCXML-flavored workflow, and `python-statemachine` (the most broadly adopted statechart-flavored library) lacks actor/invoke semantics and XState interop entirely.
- Zero dependencies is a genuine operational advantage for a self-hosted trading system where supply-chain/dependency surface matters (OMS, risk-critical paths).

**Why caution is warranted (the honest challenges to report, not smooth over):**
1. **Maturity/community risk is real and material.** 14 stars, 1 fork, a single maintainer, and exactly one filed GitHub issue (ever) is a very thin evidence base for "production-grade." Every other statechart-capable competitor (`sismic`, `python-statemachine`, `transitions`) has years of real-world usage surfaced in their issue trackers; this library does not yet have that trail. Adopting it for OMS/order-state-machine logic (a risk-critical path per CandleViewer's own architecture) means CandleViewer itself becomes the primary source of battle-testing, not a beneficiary of prior battle-testing by others.
2. **API churn.** ~11 releases in under a year (0.2.x→0.7.x) suggests the public API and semantics have been actively evolving. That's good for a young project fixing bugs, but risky for a monolith backend that wants stability in its state-machine core; version pinning + a strong internal regression-test harness around the exact statechart behaviors CandleViewer depends on (guards, actors, history, timers) is mandatory, not optional.
3. **The one known bug is exactly in the seam CandleViewer would stress.** camelCase(JSON)↔snake_case(Python) auto-mapping for actions/guards/services is precisely the mechanism CandleViewer would rely on if it authors/imports XState JSON and wires it to Python `logic_providers` for OMS/rule-engine callbacks. That this already broke once is a concrete signal to add explicit naming-convention tests, not to assume the mapping "just works" going forward.
4. **No independent third-party production adoption found.** Web search turned up no blog posts, case studies, or Stack Overflow discussion of `basiltt/xstate-statemachine` in production use outside the author's own docs/marketing site. This is a strict inverse of `transitions`/`python-statemachine`, which have abundant independent usage evidence.
5. **Comparison claims on the library's own docs site should be treated as marketing, not fact-checked-by-us data** — e.g., the site's own "How It Compares" table (Hierarchical/Parallel: ✅ vs. transitions ⚠️/❌, python-statemachine ❌) should be independently verified against the actual current feature set of `python-statemachine` (which as of the version surveyed here *does* support parallel regions and compound/hierarchical states — the library's comparison table may be stale or inaccurate on this specific point and should not be taken at face value when making the adoption decision).
6. **Different paradigm options exist and shouldn't be dismissed.** For the OMS/reconciliation/failover pieces specifically, `temporalio`'s durable-workflow model (event-sourced execution history, automatic replay/retry, native crash recovery) solves a different but overlapping problem (surviving process restarts mid-order-lifecycle) that an in-process statechart library — including xstate-statemachine — does not natively address; CandleViewer's own recorder/persistence design will need to supply that durability itself if it goes with an in-process statechart library instead of a workflow engine.

**Net assessment:** Feature-for-feature, `xstate-statemachine` is the most XState-aligned and functionally complete option for CandleViewer's stated goal (JSON-portable statecharts with hierarchy/parallel/actors, zero deps). But it is unambiguously the least battle-tested option in this comparison by every external community metric (stars, issues, third-party adoption, release-history stability). Adopting it should come with: (a) pinning an exact version and vetting the changelog before each bump, (b) a CandleViewer-side regression suite covering guards/history/actors/naming-convention mapping, (c) explicit internal issue-filing back to `basiltt/xstate-statemachine` for every limitation found (per the owner's mandate to report, not smooth over), and (d) accepting that CandleViewer will effectively be doing first-line production battle-testing that no other user has done yet.
