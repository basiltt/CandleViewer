# R6-08 adversarial refutation — "onUnhandled=error kill is invisible to the sender"

Claimed severity: High. **Verdict: DOWNGRADE to Low.**

Repro re-run at cec108b (`/tmp/r608.py`, `/tmp/r608b.py`; B13, strict=true,
onUnhandled="error"; async `Interpreter` + `SimulatedClock`, plus the
documented sync example from `docs/_guide/core-concepts.md`).

## What reproduces

`await it.send("CONNECT", wait=True)` in `ws_conn.live` returns
`Receipt(state_ids={'ws_conn.live'}, changed=False, error=None, deferred=False,
denied=False)` — byte-identical to a benign no-op — while `status='error'`.
`last_error` is `None`. Same on `SyncInterpreter` (`send()` returns `None`).

## What does NOT hold (the High rests on these)

1. **"Invisible to the sender."** False. The moment the receipt resolves —
   no sleep needed — `status='error'`, `.error` is the `UnhandledEventError`,
   `.is_running` is `False`, and the `on_error` plugin hook has already fired
   (plus `on_unhandled_event(..., 'errored')`). This is exactly the surfacing
   channel the docs prescribe: `docs/_guide/core-concepts.md` L134-136 shows
   `print(interp.status) # "error"` / `type(interp.error).__name__ #
   UnhandledEventError` as *the* way to observe this policy. Documented.
2. **"`last_error is None`" is a defect.** No. `last_error` is documented
   (`docs/api/index.md` L738) as the exception behind the most recent
   `last_transition_ok=False`. Here `last_transition_ok` is `True` — no
   transition was attempted. `None` is its contract, not a hole.
3. **Compounding: "every later send is dropped with only a WARNING log."**
   Refuted by measurement. `_refuse_if_not_running` fires
   `on_event_dropped(event, "not_running")` **and** fails the receipt:
   later sends return `error=InterpreterStoppedError("Interpreter 'ws_conn'
   is error; event 'PING' was dropped.")`. The post-kill state is loudly
   observable on the per-send channel, including for an undeclared name.

## Residual, genuine, small

`Receipt.error` is documented as "the exception raised while processing this
event". The `UnhandledEventError` *is* that exception, and `_handle_unhandled_
event` routes to `_fail()` without touching the caller's receipt — so a caller
that inspects only the receipt (the natural async pattern; #153 added `denied`
for precisely this "otherwise identical receipts" ergonomics class) cannot tell
kill from no-op for the one killing event. Also a doc nit: the
`docs/_guide/interpreters.md` L996 table says `"error"` | *Raises*
`UnhandledEventError` — neither engine raises at the call site.

Fix is one line of plumbing (populate the pending receipt in the `policy ==
"error"` branch before `_fail`) + the table wording. Workaround is free and
already in the docs (`if interp.status == "error"` / `on_error` hook), the
window is one event, and every subsequent send is explicitly errored.
Not a High; **Low**.
