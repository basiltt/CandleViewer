## 0. Bottom line

**43 reproduced source ids merge to 40 canonical findings: 5 Blocker · 17 High ·
11 Medium · 7 Low.**

The Blocker set is not a list of unrelated bugs. Four of the five are the same
sentence written four ways: *the library has state-corrupting windows and
restore paths that report `status="running"`, `error=None`,
`last_transition_ok=True`, and are therefore indistinguishable from health.*
On an order-management path that is the single worst failure profile available —
worse than a crash, because a crash is observable.

- **R4-01** is the exit→actions→enter window: a snapshot taken inside it
  restores as a permanently inert machine that reports healthy. Two independent
  tracks (`persistence`, `concurrency`) found it from opposite ends, and a
  property run this pass puts **45.5 % of mid-macrostep snapshots torn**
  (300 cases, 77 snapshots).
- **R4-02** is the other end of the same pipe: `from_snapshot()` performs no
  legality check at all, so an empty configuration, `status="banana"` and
  `context=42` all load clean, while 7 other malformed shapes leak raw
  `KeyError`/`TypeError`/`AttributeError` straight past `XStateMachineError`.
- **R4-03** and **R4-05** are silent-loss defects under the library's *own*
  recommended configuration (`OverflowPolicy.BLOCK`) and its own documented
  error policy (`guardErrorPolicy`).
- **R4-04** is a non-terminating `start()`.

**The diff itself is good work that opened four new High findings.** `28-`'s
reading holds up under re-run: three `3c527b0` Highs are genuinely closed, and
`H-1` is a **fresh regression at default `maxIterations`** — I reproduced the
external-event loss at `burst=1500 → LOST=1` on stock settings. `H-2`/`H-3`/`L-3`
(here **R4-08**/**R4-09**) are a *third* instance in two releases of "the new
provenance rule was not audited across a boundary that reconstructs an `Event`",
which is the finding to put in the upstream issue: the fix is one systematic
audit of `_detach`, `restore_event` and every `deepcopy` site, not three more
point patches.

**Gate impact.** Nothing here moves `27-r4-gate.md` off **DEFER**. R4-01, R4-02,
R4-03, R4-06 and R4-09 all touch the order path directly and none has an
in-library mitigation.

## 4. Disposition

- **R4-01 through R4-05 block adoption on their own.** Each is silent order-state
  corruption or an unbounded hang with no signal, and none has an in-library
  mitigation.
- **R4-06 should block the 0.8.1 tag independently of everything else**: it is a
  *regression introduced by this diff*, at default settings, on the recommended
  engine.
- **R4-08, R4-09 and R4-40 should be filed as one issue**, not three. Three
  instances in two releases of the same root cause ("provenance was not audited
  across a boundary that reconstructs an `Event`") is evidence the point-fix
  approach is not converging; the ask is a systematic audit of `_detach`,
  `restore_event`, and every `deepcopy`/`pickle` site.
- **R4-24 is a CHANGELOG correction**, cheap and worth doing before the tag.
- **CV-C06** (the `onUnhandled: "defer"` discriminator) now has a real mechanism
  in `Receipt.deferred`, but **subject to R4-07**: treat `deferred=True` as
  advisory, never as the sole gate on a retry decision, until the `id()` keying
  is fixed. Our in-house shim (ADR-0016 Part 2) remains the execution path and
  is unaffected by every finding above.
- **Gate verdict is unchanged: DEFER** (`27-r4-gate.md` §8).
