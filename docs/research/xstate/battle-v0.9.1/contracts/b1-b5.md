## What every machine ran through (both passes)

The mandatory config was on for every run:
- `strictConfig`, `rollback`, `defer`, guard `raise`, `strictTargets`, `strict`;
- a bounded RAISE inbox (64, or 4 for the overflow lane);
- `SimulatedClock`.

**Happy path, B1–B5.** Every machine reaches its terminal leaf:

| Machine | Terminal leaf reached |
|---|---|
| B1 | `lifecycle.filled` + `protection.sl_present` |
| B2 | `trade_group.closed` |
| B3 | `leg.closed` |
| B4 | `oco.completed` |
| B5 | `iceberg.completed` |

After **every** step the driver snapshots, restores with `from_snapshot(minimum_version=3, plugins=[p])` and starts the restored interpreter. Then it checks:
- the plugin sees `on_interpreter_start` exactly once, with `restored_from_snapshot == True` (**#240 closed**);
- the booted interpreter's plugin saw `[False]`;
- state ids and context are identical after the restore;
- `chain_trips == 0` live and restored;
- `dropped_receipts == 0` and `on_receipt_dropped` never fired (**#244**);
- no action, guard or service errors and no stranded invocations.

**Shutdown recipe (#239).** The driver reaches a live state, then queues several events without yielding to the loop:
- inbox events via `send(wait=False)`;
- one `send_priority(wait=False)`;
- one extra `send(wait=True)` whose receipt is still pending.

It then runs `drain_pending()` → `get_persisted_snapshot()` → `stop()` → `from_snapshot(plugins=)` → `start()`, and replays the drained list into the restored interpreter. Results for all 5 machines, both passes:
- `drain_pending()` returns exactly what `pending_events` showed, **priority lane first**. For example, B1 returns `['FIRST_FILL'(priority), 'SEND', 'VALIDATE']`.
- The `wait=True` receipt resolves promptly with `InterpreterStoppedError('drained: removed by drain_pending()')`. It does not hang.
- The persisted blob has `pending_events == []`, and `stop()` did not process any drained event: the state is unchanged.
- The restored start hook reads `[True]`. Every replayed event is delivered **exactly once**, counted as a multiset over the transition log. Each machine then reaches its terminal leaf, with `chain_trips 0` and `dropped_receipts 0` on both interpreters.

**Other lanes.**

*Order path (B1):*
- **Rollback:** a raising `stamp_validated` puts the configuration back to `draft`, the machine stays `running`, and `on_action_error` fires.
- **Invoke onError:** when `place_order` raises, the machine goes to `lifecycle.unknown` with no stranded invocation.
- **Guard raise:** the error is on the receipt and in `on_guard_error`, and the machine stays `running`.

## Findings

- **NEEDS-WRAPPER (documented behaviour, not a defect):** after `drain_pending()` the snapshot has **no** pending events, as designed. The drained list is therefore the only copy of that accepted work, so our shutdown wrapper must journal it durably **before** `stop()` and replay it after restore. Drained `wait=True` callers get `InterpreterStoppedError`, so they must re-submit or rely on the journal, not both. Exactly-once delivery then depends on the journal de-duplicating. The driver models this by skipping the failed-receipt duplicate.
- **Noise, not a defect:** deliberately raised action and service errors are logged with tracebacks by the library logger. No warnings were raised to the caller.
