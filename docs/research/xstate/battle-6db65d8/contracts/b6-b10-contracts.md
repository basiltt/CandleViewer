### 2.1 `guardErrorPolicy: "raise"` — corrected reading

Our first probe recorded this as a failure; that was a **probe defect**, retracted here. `k9_wait.py` establishes the real surface, identically in both lanes:

* the exception is **not** raised at the call site;
* it is carried on the **`wait=True` receipt** as `Receipt.error` (`RuntimeError('guard:price_limit_breached')`), with `Receipt.denied=False` — correctly distinguishing "the guard crashed" from "the guard returned False";
* `on_guard_error` fires under every policy;
* the **unguarded fallback in the same transition array is still taken** (#152 / SCXML §5.9) — here `SLICE_DUE` still reached `submitting_slice`.

A coherent contract, but with a sharp edge for us: a fire-and-forget `send()` (the default, `wait=False`) **returns `None` and surfaces nothing**. A crashed risk guard is then visible only to the plugin. See **W-02**.

## 3. Snapshot / restore at every quiescence point (step 3)

Not a separate pass: `cv6db.drive()` performs a full round-trip — `get_persisted_snapshot()` → `Interpreter.from_snapshot()` into a **freshly built machine with fresh stub logic** → `start()` → compare `current_state_ids` **and** the whole context — at `t0` and after **every** script step of every scenario in §2. Both lanes.

* **Every crashpoint matched**, states and context, on all five contracts and both service styles.
* **Zero spurious `SnapshotMidStepError`** at a quiescent point.
* The restored machine is a genuinely different object graph (new `MachineNode`, new stub closures), so this exercises the hash/versioning path, not just object identity. The #185 fix (null `machine_hash` on a versioned blob is drift) and #186 (`configuration` must agree with `state_ids`) are therefore both in the path of every one of these round-trips and neither fired a false positive.
* Snapshot **during** an in-flight coroutine service is correctly *refused*, not torn — that is the #182/#183/#184 surface, and it is why `drive()` snapshots only at quiescence. We did not re-litigate the mid-step refusal here; it is covered in the concurrency track.

One consequence worth recording for our persistence layer: a restored B6 sits in `armed` with `slice_deadlines_us` intact in context but **no live timers** — the contract's `reconciling.entry = rearm_deadlines_from_context` is the only thing that brings deadlines back. That is by design (INV-B6-b) and the restore path honours it, but it means **a restore that skips `reconciling` produces a silently dead algo**. See W-03.

## 4. Findings

### LD-01 (LIBRARY, high) — a plain `def` service is invoked even when its step was rolled back or transiently abandoned

**Repro:** `kc_inline_svc.py` (async engine, both styles) and `ke_syncinline.py` (sync engine). Standalone, no catalogue dependency — a 3-state chart with `actionErrorPolicy: "rollback"`, an entry action and an invoke.

Two cases, both of which must never call the service:

* **case A — transient roll-forward.** The invoking state carries `always: [{target: armed, guard: roll_forward}]` with the guard true. The `always` fires and the machine leaves before the invoke should ever start.
* **case B — rollback.** The invoking state's entry action raises under `actionErrorPolicy: "rollback"`. The step is undone: configuration returns to `armed`, context is restored (`n` stays 0).

| | final state | context | `submit_child` called? |
|---|---|---|---|
| `async def` service, async engine | `m.armed` | correct | **no** ✅ |
| **plain `def` service, async engine** | `m.armed` | correct | **YES** ❌ |
| **plain `def` service, `SyncInterpreter`** | `m.armed` | correct | **YES** ❌ |

The configuration and the context are both correct in every row — **only the side effect leaks**. That is what makes it dangerous: every state-based assertion passes, and the evidence exists only in the service-call trace. Our round-6 and round-7 pins asserted configuration, which is exactly why this survived.

**Root cause (by inspection, `interpreter.py` ~2590–2620 and the `_invoke_plain_service_inline` path).** #116 made a plain, non-coroutine callable run **inline**, inside the macrostep that enters the invoking state, so that its `done.invoke` orders identically to the sync engine's. But "inline" here means *during entry*, before the `always` chain has been evaluated and before the rollback epilogue can undo the step. A coroutine service is armed as a task and the arming is unwound with the rest of the step; a plain one has already been **called** by then, and a call cannot be unwound. `SyncInterpreter` shares the behaviour, which tells us this is the inline path's semantics rather than an async-engine-only slip — so it is not a parity bug, it is a *shared* correctness bug that the coroutine lane happens to avoid.

**Blast radius in our catalogue:** 4 of the 5 contracts here carry `actionErrorPolicy: "rollback"` **and** invoke a service from a state with an entry action (B6 `submitting_slice`, B7 `repricing`, B9 `acting`, B10 `firing`); B6 additionally has the case-A shape (`slice_qty_below_min_roll_forward`). B8 escapes only because it is catalogued `actionErrorPolicy: "fail"`. By inspection the same shape recurs across the wider catalogue. In OMS terms the concrete failures are: an unwanted child order on a sub-minimum slice, and an amendment sent to the exchange from a reprice computation that we already decided had failed.

**Mitigation until fixed:** spell **every** service `async def`. That is already the documented recommendation and the lane round 7 repaired; this finding turns it from a style preference into a **hard requirement** for us. See W-01.

### CD-01 (OUR CONTRACT, high) — the kill switch is deferrable as catalogued

**Repro:** `kb_killdefer.py`, both styles, `ka_killswitch.py` for the priority-lane baseline.

B6's `submitting_slice` and B9's `evaluating` declare **no** `USER_CANCEL` / `KILL_SWITCH` handler. Under the mandated `onUnhandled: "defer"` the kill switch is therefore **held for the full duration of the in-flight service** rather than applied ahead of it — and `priority=True` does **not** change that, because priority orders the **inbox** while defer is decided by the **configuration**. The receipt comes back immediately with `deferred=True`, which reads like success.

Measured against a 1.5 s service, async lane:

| contract | receipt returns | kill actually **applied** | `Receipt.deferred` |
|---|---|---|---|
| B6 as catalogued | 0.001 s | **1.461 s** | `True` |
| B9 as catalogued | 0.001 s | **1.467 s** | `True` |
| B6 + handler on the invoking state | 0.001 s | **0.001 s** | `False` |
| B9 + handler on the invoking state | 0.000 s | **0.000 s** | `False` |

Nothing is ever **lost** — the kill always lands, `dropped` is empty in every row — so this is a **latency and observability** defect, not a correctness one. But a kill switch whose applied-latency is "however long the slowest in-flight exchange call takes" is not a kill switch, and a receipt saying `deferred=True` at t+1 ms while the algo keeps working for another 1.5 s is actively misleading to an operator.

This is **ours, not the library's**: the engine did exactly what the policy block we wrote asks for. The fix is in the contract JSON — **declare the kill/cancel handler on every invoking state**, so the transition exists and defer never applies. Applied experimentally above; it collapses the latency to ~1 ms. It should be applied to the catalogue for B6 `submitting_slice`/`final_sweep`, B7 `repricing`/`market_converting`, B9 `evaluating`/`acting`, and reviewed everywhere else an invoke sits on a path a human can abort.

Note the `def` lane shows ~1 ms in **all four** rows — not because it is better, but because an inline plain service never leaves the machine observably parked in the invoking state at all. That apparent win is the same inline behaviour as LD-01; it is not a reason to prefer `def`.

## 5. Needs-wrapper items

### W-01 — the wrapper must forbid plain `def` services

Direct consequence of LD-01. Our `MachineLogic` factory should **reject** (not warn about) any service implementation that is not a coroutine function, with an error naming LD-01. Two reasons beyond the side-effect leak:

* a plain service also runs on the interpreter's executor and changes the defer/latency shape (§4, CD-01 table), so the two styles are not interchangeable for reasoning about operator latency;
* the `async def` lane is now the tested-clean one (52/52 here, and the round-7 pins are parametrised over both), so it is where the library's own guarantees are strongest.

An `async def` that internally offloads blocking I/O to `asyncio.to_thread` gives us the same concurrency with none of the semantics.

### W-02 — no fire-and-forget `send()` on any control path

`send()` defaults to `wait=False` and then resolves to `None`. Everything the engine wants to tell us about that event — a crashed guard under `guardErrorPolicy: "raise"` (§2.1), an `onUnhandled: "error"` kill (#189), `deferred=True` (CD-01), `denied=True` — lives on the `Receipt`, which `wait=False` throws away. The wrapper should expose only a `wait=True` send for order-path and control-path events, and route every `Receipt` with a non-`None` `error`, or an unexpected `deferred`/`denied`, into `CvErrorHooks`. Fire-and-forget stays available for market-data-shaped traffic only.

### W-03 — obligations the engine structurally cannot enforce

Recorded so they are tested at the action layer rather than assumed:

* **counter bounds.** The engine guarantees `bump_slices_done` runs exactly once per `SLICE_DUE` (INV-B6-a, asserted here) but cannot enforce `slices_done <= slices_total`; same for `repricings <= max_repricings` and `delivery_attempts <= max_delivery_attempts`. These are action-level assertions.
* **restore must go through `reconciling`.** A restored B6 has its deadlines in context but no live timers; only `rearm_deadlines_from_context` brings them back (§3). A restore path that lands straight in `armed` yields a silently dead algo. The wrapper's restore must force the `reconciling` entry, and should assert that a restored algo either has live timers or is in a state that is about to arm them.
* **idempotency across restore.** `record_child` / `persist_fired_row` can re-run after a restore from a snapshot taken before the corresponding completion landed. The snapshot round-trip is exact on states and context, so the engine will faithfully re-drive the completion; de-duplication is ours.
