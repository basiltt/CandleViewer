# Contract machines B11–B15 end-to-end on `6db65d8`

**Library:** `xstate-statemachine` @ `6db65d8` (merge of #191, round-7 fixes
#179–#190 + reopened #167/#168/#175; unreleased 0.8.1 — `__version__` still
reports `0.8.0`, so key on the commit).

**Scope.** The five OMS-shaped contract machines — B11 `RecordingSession`,
B12 `ReplaySession`, B13 `ExchangeConnection`, B14 `IngestionPipeline`,
B15 `PaperMatcher` — driven end to end under the mandatory config
(`actionErrorPolicy: rollback`, `onUnhandled: defer` on the order path /
`error` on the control path, `guardErrorPolicy: raise`, `strictTargets`,
`strict`, bounded inbox `OverflowPolicy.RAISE`, `SimulatedClock`, trace
plugin standing in for `CvErrorHooks`).

**Corpus.** Corrected catalogue JSON copied verbatim from
`battle-3ed3099/contracts/B1{1..5}.machine.json` (`diff` clean against the
`battle-221ce7c` copies). Scripts in `battle-6db65d8/contracts/`, raw
results in `contracts/results/*.json`.

**Both lanes.** Every service-touching scenario was run twice: `async def`
stubs (primary — the recommended style and the lane round 7 unblinded) and
plain `def` stubs (`CV_SVC_STYLE=def`, plus dedicated probes). The harness
`Stub` gained an `svc_style` knob for exactly this.

the lane round 7 was explicitly about: a plain `def` service is not
cancelled when its invoking state is exited, so its `onDone` lands in a
state that already left — *and the exiting transition itself is discarded*.

## 3. 🔴 CV-6DB-01 — NEW. A plain `def` service is never cancelled. Blocker.

**Repro:** `repro/cv_6db_01_def_invoke_not_cancelled.py` — 60 lines, no
contract JSON, exits 1. Also `h5_cancel.py` (`CANCEL-def`), `h6_block.py`
(`BLOCK-def`), `h7_conc.py` (`CONC-def-task`, `CONC-def-seq`) on real B12.

**Shape.** A state `invoke`s a service and also has an `on` transition out
of it (`CANCEL`). This is INV-B12-a — B12 `buffering` invokes
`seek_and_prime` and carries `CANCEL -> paused`.

```
busy: invoke work onDone-> done (actions: land)
      on CANCEL -> cancelled
```

| service | mid-service state | after `CANCEL` | final | `cursor` |
|---|---|---|---|---|
| `async def` | `m.busy` | `m.cancelled` | `m.cancelled` | 0 ✅ |
| **`def`** | `m.busy` | **`m.done`** | **`m.done`** | **4242** 🔴 |

Two distinct defects, both `def`-lane only:

1. **The abandoned service's `onDone` lands.** The exit of `busy` does not
   cancel the in-flight `def` service, so `work` completes and its `onDone`
   runs `land`, writing `cursor = 4242` into a configuration that had
   already left `busy`. On B12 this is a *cancelled* `seek_and_prime`
   mutating the replay cursor after the user cancelled the seek.
2. **The `CANCEL` transition is silently discarded.** The machine does not
   even pass through `cancelled` — `after_cancel` is already `m.done`. The
   `CANCEL` receipt is `changed=False, error=None, denied=False`: a
   *success-shaped* receipt for an event whose transition never happened.
   The caller has no channel that says "your cancel was lost."

**Why it is a `def`-lane bug and not a `def`-lane property.** The service is
*not* run inline — `h6_block.py` measures it: the service runs off the loop
thread (`service_thread_is_loop_thread: false`) and the event loop keeps
ticking (21 heartbeats during a 0.6 s service). So the engine *can* observe
an exit mid-service; it simply does not cancel the worker or gate its
completion on the invoking state still being active. Confirmation: a
*concurrent* canceller sees `mid_service == ['replay.buffering']` — the
window is genuinely open and observable — and its `CANCEL` is still lost
(`CONC-def-task`).

A second, subtler consequence: `send("GO", wait=True)` on the `def` lane
does not return until `onDone` has been applied
(`send_wait_returned_after_s: 0.607` for a 0.6 s service, returning already
in `replay.paused`). A sequential caller therefore has *no* cancel window at
all; only a concurrently scheduled canceller can even try, and it loses too.

**Financial impact.** B12 is the replay path, so the blast radius is a wrong
cursor. But the shape is generic: any `invoke` + `on CANCEL` pair. In B13
`subscribing` that is a cancelled subscribe landing `live` after we decided
to tear the socket down; in B15 it would be a cancelled liquidation step
completing into a terminal state after the operator aborted it.

**Classification: LIBRARY. Severity: 🔴 Blocker (async engine, `def`
services). Async lane correct. Not covered by the #179 completion-lane work
— that unified *charging*, not *cancellation*.**

**NEEDS-WRAPPER until fixed:** either (a) forbid plain `def` services
entirely in the wrapper — register every service as `async def`, offloading
blocking work with `run_in_executor` ourselves, which restores correct
cancellation; or (b) if a `def` service is unavoidable, forbid an `on`
transition out of the invoking state and model cancellation as a context
flag the service polls. (a) is the one-line rule and it is already the
documented recommended style.

## 4. 🟠 LIB-R6-01 downgraded — bounded now, but the shed is silent

**Shape:** `invoke.onDone` → a state whose **entry action raises**, under
`actionErrorPolicy: rollback`. Present in B11 (`starting --subscribe_streams
onDone--> recording`, `recording.entry` includes `emit_recording_metric`)
and B13 (`subscribing --subscribe_in_batches onDone--> live`, `live.entry`
includes `emit_feed_healthy`).

**`221ce7c`:** 131,313 `subscribe_streams` invocations in 20 s at ~6,570/s,
for ever, with `send(wait=True)` never returning.
**`6db65d8`:** terminates in **0.186 s**.

| machine | lane | service invocations | actions | elapsed | resting state |
|---|---|---:|---:|---:|---|
| B11 | `async def` | 150–154 | ~300 | 0.19 s | `recording.starting` |
| B11 | `def` | 119–123 | ~245 | 0.19 s | `recording.starting` |
| B13 | `async def` | 160–167 | ~665 | 0.19 s | `ws_conn.subscribing` |
| B13 | `def` | 120–130 | ~500 | 0.19 s | `ws_conn.subscribing` |

`send(wait=True)` returns normally, `stop()` does not hang, and the bound
**tracks `maxIterations`**: at `maxIterations: 5` the loop makes ≤7 service
calls, at 25 it makes ≤27, identically on both lanes (`h1_r601.py`,
`R601-mi*`). The `LAP-B11` scenario confirms the lap count is *stable across
repeats and identical between `def` and `async def`* — the #179 parity
property holds on real contract machines.

**The residual — the trip is silent on every programmatic channel**
(`h2_obs.py`, both lanes):

| channel | value |
|---|---|
| `receipt.error` | `None` |
| `receipt.changed` | **`True`** |
| `receipt.denied` | `False` |
| `interp.status` | `"running"` |
| `interp.last_error` | `RuntimeError` (the action's, rewritten each lap — **not** `RunawayChainError`) |
| `on_event_dropped` | **never fires** (0 drops) |
| WARNING/ERROR log | 304 records (async) / 238 (def) — the only channel |

So the caller of `REASON_ADDED` is told the transition *succeeded and
changed state*, while the machine actually made ~150 real exchange
subscribe calls, threw ~150 times, and came to rest in the state it started
in. Unlike the #166 `always` bound — which sets
`last_error = RunawayChainError` and fires `on_event_dropped` — this bound
is reached by a path that reports nothing structured.

**Classification: LIBRARY. Severity: 🟠 High (was 🔴 Blocker).** The
unbounded-storm half is fixed; the observability half is not. Note the
asymmetry worth filing: the round-6 settle bound is observable, this one
is not, and they are reached by the same user-visible symptom.

**NEEDS-WRAPPER (reduced from round 6):** the per-service invocation-rate
watchdog is still required, because ~150 subscribes per triggering event is
still a rate-limit event at an exchange if the trigger repeats. The
build-time shape rejection and entry-action isolation remain the cheap fix.

## 5. ✅ LIB-01 is FIXED — the `onUnhandled: "error"` kill now reaches the sender

This was High and open on `221ce7c`: a stray event killed the interpreter
while the sender got `Receipt(changed=False, error=None, denied=False)`.

On `6db65d8` (#189), for B13 `CONNECT` in `live` and B14 `UNSUBSCRIBE` in
`snapshot_pending` alike:

```
Receipt(state_ids=frozenset({'ws_conn.live'}), changed=False,
        error=UnhandledEventError("Event 'CONNECT' is not handled in any
        active state ['ws_conn.live'] and the machine's onUnhandled policy
        is 'error'."), deferred=False, denied=False)
last_error = UnhandledEventError(...)      status = "error"
```

`last_error` is now populated too (it was `None`), the `on_unhandled_event`
hook still fires with disposition `"errored"`, and a follow-up event after
the kill returns `InterpreterStoppedError` on its receipt rather than
vanishing. Every channel agrees. **The two scenarios that still report FAIL
(`B13-unh-2`, `B14-unh`) are stale assertions written against the broken
behaviour — they asserted the interpreter survives; the interpreter dying is
the documented `onUnhandled: "error"` contract, and the point of the finding
was always that the death was *invisible*.**

The wrapper guidance changes accordingly: `error is not None` on the receipt
is now a complete "did my transition land?" test for the unhandled case.
It is **not** complete for §4 — that path reports `changed=True` — so the
wrapper still cannot rely on the receipt alone.

## 6. Invariants, snapshot and parity — healthy on both lanes

**Catalogue invariants.** 31 scenarios, run under `async def` and again
under `def`:

- **B11 7/7** both lanes — linger-on-open-position, `reasons_remain` branch
  ordering, reason re-added during `lingering` returns to `recording`
  *without* restarting the stream, gap counting, degraded entry/exit.
- **B12 7/7 async / 6/7 def** — cursor monotonicity, `CONSUMER_SLOW`
  degrading the clock without dropping, coverage gaps from
  `seek_and_prime`, loop re-buffer, `destroyed` truly final. The def-lane
  failure is `B12-cancel` — that is §3, and it is the finding, not a flake.
- **B13 12/12** both lanes — public and private connect paths,
  connection-budget block (no socket opened), backoff doubling to max and
  resetting only on `live`, `subscribed_topics == pending_topics`,
  partial-batch subscribe never reaching `live`, full reconnect/resync with
  topic restoration, PONG re-arm and `PONG_DEADLINE` demotion, clean
  `SHUTDOWN`. **Both prior failures (`LIB-01`, strict wildcard) are gone.**
- **B14/B15 7/9** both lanes — snapshot/delta ordering with buffered replay
  after `snapshot_seq`, `SEQUENCE_GAP` re-snapshot with no delta applied
  across the gap, `SNAPSHOT_TIMEOUT` re-entry counting a resync, margin-call
  round trip, `liquidated` terminal against a favourable mark,
  journal-before-terminal ordering, liquidation preempting a busy inbox via
  `send_priority`. The 2 failures are `OUR-B14-01` and the stale `B14-unh`
  assertion (§5).

**Snapshot/restore at quiescence — 5/5, both lanes.** Each machine's
scripted run is executed twice: once uninterrupted, once with
`get_persisted_snapshot()` + restore into a fresh interpreter **between
every macrostep**. States, context, action trace and transition trace
compare equal in all five, on `async def` and on `def`. The #182/#183
in-flight-flag work produced **no false refusals at quiescence**, which is
the property we actually need.

**Async ↔ sync parity — 5/5.** Identical scripts, identical states, context
and action traces on both engines for all five machines. The R6-01 shape
(§4) is now bounded on *both* engines and `R601-B11-sync` / `R601-B13-sync`
pass, so the round-6 caveat — that a naive parity harness silently passes
because `SyncInterpreter` rejects async services — no longer hides a
divergence there. It still holds as harness advice, and §3 is precisely a
divergence a parity suite cannot see (it is async-engine, `def`-service).

**`always` → invoked-child / rollback shapes (R6-03 class) — 4/4.** B14
(`desynced.entry` raises, `always -> snapshot_pending`) and B15
(`liquidating.entry` raises, `always -> liquidated`) terminate immediately
and cleanly on both engines: ≤9 action calls, <0.3 s, no runaway.

**#180 external priority sends — 240/240, 0 dropped.** `h3_prio.py` /
`h4_prio2.py`: 60 external `send_priority` calls per machine on B11, B13,
B14, B15, on both service lanes, issued so they land mid-macrostep. Zero
`chain_budget` drops, zero receipt errors, `status` stays `"running"`,
`last_error` never `RunawayChainError`. The B18 kill-switch lane is safe:
**a priority send is never charged.**

## 8. Verdict

Round 7 is a real improvement on this corpus. Two of the three library
findings we carried in are **closed** (`LIB-01`, `LIB-R6-strict`) and the
blocker is **downgraded** — the subscribe storm that would have banned an
API key now costs ~150 calls and 190 ms instead of 6,500/s for ever, and it
costs the same on both service lanes, which is exactly the #179 parity
claim holding on real machines. Snapshot/restore is trustworthy at
quiescence across all five machines on both lanes, priority sends are never
charged across 240 trials, and B13 is now unblemished.

**But adoption is still conditional, on a new blocker.** CV-6DB-01 is in
the `def` service lane on the async engine — a lane that the round-7
parametrisation was specifically built to stop being blind to, and which
this corpus reaches through INV-B12-a. The defect is not merely "the result
lands": *the cancelling transition is dropped and the receipt says nothing*.

**Required wrapper posture:**

1. **Register every service as `async def`.** One rule, closes CV-6DB-01
   entirely, and is already the documented recommended style. Blocking work
   goes through `run_in_executor` inside the coroutine so cancellation stays
   the engine's to manage. Enforce at registration time — reject a
   non-coroutine service function.
2. **Build-time shape rejection** — refuse any machine where a state
   targeted by `invoke.onDone` has an `entry` action outside an
   `INFALLIBLE` allowlist. Catches B11 `recording` and B13 `live` today and
   removes §4's trigger.
3. **Per-service invocation-rate watchdog** — hard-stop above N
   invocations/second of a single service name. Still required: §4 is
   bounded but silent, so nothing else would tell us.
4. **Receipt interpretation** — `error is not None` is now a complete test
   for the unhandled-event kill (§5) but is **still not** a complete
   "did my transition land?" test, because §4 reports `changed=True` on a
   transition that rolled back. Subscribe `on_unhandled_event` and
   `on_event_dropped`, and treat the WARNING/ERROR log as a monitored
   channel until §4's observability lands.
5. **Catalogue edits** — B11 `degraded` gains `STREAM_UNHEALTHY`; B14 gains
   a real buffer bound; B14 `desynced` and B15 `liquidating` entry sets drop
   their telemetry.

Items 1–4 are wrapper work we control; item 5 is JSON we control. The
single upstream blocker is §3.
