## 5. Findings

### LD-01 (LIBRARY, high) — *residual*: a plain `def` service is still invoked when an `always` rolls the step forward

**Status:** open, **narrowed** by #193. The rollback half is fixed on the async engine; the roll-forward half is not fixed on either engine, and `SyncInterpreter` still leaks both halves.

**Repro:** `repro/ld01_always_rollforward.py` — STANDALONE (stdlib + `xstate_statemachine` only, no catalogue dependency), exits 1 while the defect is present. Six lanes: {case A, case B} × {`async def`/async, `def`/async, `def`/sync}.

```
ok   case A | async service | async engine | calls=[]
LEAK case A | def   service | async engine | calls=['submit_child']
LEAK case A | def   service | sync  engine | calls=['submit_child']
ok   case B | async service | async engine | calls=[]
ok   case B | def   service | async engine | calls=[]     <-- #193 fix
LEAK case B | def   service | sync  engine | calls=['submit_child']

3/6 lanes leaked the service call
```

Also reproduced on the real contract, twice over: `k7_invariants.py def` row **B6 INV-c**, and `kf_drives.py` **D2** (both engines).

**The chart** is the shape our catalogue actually has — `armed --GO--> submitting`, where `submitting` has an entry action, an `invoke`, and (case A) `always: [{target: armed, guard: roll_forward}]` with the guard true.

**Root cause (by inspection).** #193 moved the `def`-service executor handoff out of arm time and into the task the engine holds, so a cancellation issued during the step's epilogue lands before the callable is submitted. That epilogue is reached on the **rollback** path. The **eventless settle pass** — which is where `always` is now selected, per #196/SCXML §3.13 — leaves the invoking state on a different path that does not cancel the armed handoff first, so the callable is submitted anyway. On `SyncInterpreter` neither path cancels: the entering step awaits the service inline, which is the documented plain-`def` contract, so the call has already happened before either the `always` or the rollback can be considered.

**In every leaking row the configuration and the context are correct.** Only the side effect escapes — every state-based assertion passes and the evidence exists solely in the service-call trace. This is why it survived round-6/round-7 pinning and why it partially survived round 8: the new pin covers rollback, not roll-forward.

**Blast radius in our catalogue:** B6 `submitting_slice` carries exactly this shape (`slice_qty_below_min_roll_forward`), and in OMS terms the failure is concrete — *a child order placed on the exchange for a slice we just decided was below minimum size*. The rollback shape (B7 `repricing`, B9 `acting`, B10 `firing`) is now safe on the async engine. B8 is `actionErrorPolicy: "fail"` and never had the rollback exposure.

**Mitigation:** unchanged and still mandatory — spell **every** service `async def` (W-01). The `async def` lane is clean on all six repro rows, all 52 invariants and all 14 drives.

### CD-01 (OUR CONTRACT, high) — the kill switch is deferrable as catalogued

**Unchanged from `6db65d8`; re-measured, still true.** Repro `kb_killdefer.py`, both styles.

B6's `submitting_slice` and B9's `evaluating` declare no `USER_CANCEL` / `KILL_SWITCH` handler, so under the mandated `onUnhandled: "defer"` the kill is held for the full duration of the in-flight service. Against a 1.5 s service, async lane:

| contract | receipt returns | kill **applied** | `Receipt.deferred` |
|---|---|---|---|
| B6 as catalogued | 0.000 s | **1.493 s** | `True` |
| B9 as catalogued | 0.001 s | **1.461 s** | `True` |
| B6 + handler on the invoking state | 0.001 s | **0.001 s** | `False` |
| B9 + handler on the invoking state | 0.001 s | **0.001 s** | `False` |

Nothing is ever lost (`dropped` empty in every row) — this is a latency and observability defect, not a correctness one. It is **ours**: the engine did exactly what our policy block asks. Fix in the contract JSON — declare the kill/cancel handler on every invoking state (B6 `submitting_slice`/`final_sweep`, B7 `repricing`/`market_converting`, B9 `evaluating`/`acting`).

### CD-02 (OUR CONTRACT, medium) — B18 `RELEASE` is undeclared on the chain's intermediate states — *new*

Surfaced by D3. B18 is catalogued `onUnhandled: "error"` and declares `RELEASE` only on `engaged`. A `RELEASE` arriving while the kill-switch chain is still in `cancelling` or `flattening` is therefore genuinely unhandled, and the machine **halts into the error state mid-kill** — 39 of 40 sends dropped `not_running` once it had. Under `onUnhandled: "defer"` the same script drops nothing and the chain completes.

Same class as CD-01: a control-plane contract that does not declare a handler on an invoking state. The library behaved exactly as instructed. Fix: declare `RELEASE` (guarded, or as an explicit refusal that records an audit) on `cancelling`, `flattening` and `engaging` — an operator hitting release during a kill sequence must get a decision, not a halted machine.

## 6. Needs-wrapper items

### W-01 — the wrapper must forbid plain `def` services *(still required; scope narrowed)*

Round 8 repaired the rollback half of LD-01, so the case for W-01 is narrower than at `6db65d8` — but it is not weaker, because the surviving half is the one B6 actually exercises. Our `MachineLogic` factory should **reject** (not warn about) any service implementation that is not a coroutine function, with an error naming LD-01:

* the roll-forward leak is live on both engines in the `def` lane;
* a plain service also changes the defer/latency shape (§5 CD-01's `def` column shows ~1 ms in all four rows, not because it is better but because an inline service never parks the machine in the invoking state at all), so the two styles are not interchangeable for reasoning about operator latency;
* the `async def` lane is the tested-clean one — 52/52 invariants, 14/14 drives, 6/6 repro rows.

An `async def` that offloads blocking I/O via `asyncio.to_thread` gives the same concurrency with none of the exposure.

### W-02 — declare a control handler on every invoking state

The contract-side fix for **CD-01 and CD-02** should be enforced by the wrapper's loader, not left to review: refuse to build any catalogue machine that has an `invoke` on a state reachable from a human-abortable path without a `USER_CANCEL` / `KILL_SWITCH` / `RELEASE` handler on that state. Both findings this round are instances of it, in two different contract families (execution algo and control plane).

### W-03 — counter bounds stay an action-level obligation

Unchanged. `slices_done <= slices_total` (B6), `repricings <= max_repricings` (B7) and the B10 attempt bound are enforced by *actions and guards we write*, not by the chart. The wrapper should assert them centrally rather than trusting each action, and the 1:1 count equalities asserted in §2 are the pattern to generalise.

Five contract machines build unmodified, hold every catalogued invariant on the recommended service style, round-trip snapshot/restore at every quiescence point, and keep sync parity on configuration, actions and services. The three mandated drives pass on the async engine in both service styles, with the single exception of the LD-01 roll-forward leak.

**Go, conditional on W-01** — `async def` services only, enforced in code rather than by convention. With that condition met, `f28719c` is clean on this track: 52/52 invariants, 14/14 drives, 15/15 parity, all snapshots matching. Without it, B6 can place a live child order for a slice it has just rejected.
