## 3. ⚪ CV-6DB-01 withdrawn — the `def` cancellation gap is a documented contract

Round 7 filed "a plain `def` service is never cancelled on state exit" as a
blocker, on INV-B12-a (B12 `buffering` invokes `seek_and_prime` and carries
`CANCEL -> paused`). Round 8 documents the behaviour deliberately (#193), and
`docs/_guide/production-characteristics.md` §2 now states it:

> a non-coroutine service is *part of the macrostep that entered its state* …
> an event that arrives during that step — `CANCEL`, say — is not processed
> until the step is over … That is the documented plain-`def` contract —
> identical on both engines — not a defect of one of them.

Re-driven on `f28719c`, B12 behaves exactly as documented on the `def` lane:
`CANCEL` does not pre-empt, `onDone` is taken first, `CANCEL` is then
processed in the **new** state, and the result is never applied to an exited
state (SCXML §6.4.2 holds). `cursor` ends at the service's value because the
service genuinely completed first — not because a cancelled service wrote
through.

**Classification: LIBRARY → withdrawn; now OUR-CONTRACT.** The behaviour is
correct and specified. What it costs us is a *design constraint*:

> **INV-B12-a requires `seek_and_prime` to be `async def`.** Any contract state
> that both `invoke`s and carries an escape transition out of it must use a
> coroutine service, or the escape is not an escape. In B11–B15 that is
> B12 `buffering` (`CANCEL`), B12 `stepping`, and B13 `subscribing`.

`g3_b12.py` `B12-cancel` is now lane-aware and asserts the documented
behaviour per lane; it passes 7/7 on both. This constraint belongs in the
adoption gate as a catalogue rule, not as a library defect.

## 4. 🟠 CV-F28-02 — rollback + `invoke.onDone` storm is still silent at the default limit

**Repro:** `repro/rollback_ondone_silent_wedge.py` — standalone, no contract
JSON, exits 1 on **both** lanes. Also `repro/r6_rollback_ondone_silent.py`.
Suite: `g3_r6.py` `R6-B11-01` / `R6-B13-01` FAIL on both lanes.

**Shape.** A state `invoke`s; its `onDone` targets a state whose `entry`
raises; `actionErrorPolicy: rollback`. The rollback returns to the invoking
state, which re-arms the invoke, whose `onDone` re-enters the raising state…
This is B11 `starting`→`recording` and B13 `subscribing`→`live` verbatim.

**What #201 promises:** both async lanes trip `RunawayChainError`.

**What actually happens at the default `maxIterations` (1000):**

| `maxIterations` | limit on machine | svc invocations (async / def) | `last_error` |
|---|---|---|---|
| **DEFAULT** | 1000 | 252 / 190 | **`RuntimeError`** — the action's own |
| 10 | 10 | 12 / 12 | `RunawayChainError` ✅ |
| 50 | 50 | 52 / 52 | `RunawayChainError` ✅ |
| 200 | 200 | 202 / 179 | `RunawayChainError` / `RuntimeError` |

The storm **self-terminates below the default limit** after a
non-deterministic number of laps (190–252 across runs), so the runaway
detector never fires. `last_error` is the entry action's own `RuntimeError`,
the caller's receipt is clean (`error=None, denied=False`), and:

> the machine is left parked in the **transient invoking state**
> (`r6.starting`) with `status="running"`, no service in flight, and no
> `onDone` that will ever arrive.

It stays there indefinitely (re-checked after further settle ticks). The
session is wedged in a state it is only ever supposed to pass through, and
nothing in the API says so — the operator sees a successful send.

The diagnostic exists and works; it is simply unreachable at the shipped
default for this shape. **Classification: LIBRARY (severity: medium — bounded,
no corruption, but silent) + NEEDS-WRAPPER.**

**Wrapper:** set `maxIterations` explicitly and low (≤ 50) on every contract
machine, and treat "quiescent in a state that carries an `invoke` with no
service in flight" as a health-check failure. Do not rely on the default.

## 5. 🟠 CV-F28-01 — a rolled-FORWARD `def` invoke IS submitted (both engines)

**Repro:** `repro/always_rollforward_def_invoke.py` — standalone, 90 lines,
exits 0 on `async`, **exits 1 on `def`**. Also `repro/mandated_drives.py` D1.

**The claim under test** — CHANGELOG [Unreleased] #193:

> a `def` service armed by a transition that is then rolled back
> (`actionErrorPolicy: "rollback"`) or rolled forward (an `always` out of the
> state before it stabilises) is **never submitted to the pool**.

**Result — the two halves do not behave the same:**

| half | `async def` | `def` |
|---|---|---|
| **rolled back** (entry raises, `actionErrorPolicy: rollback`) | 0 submissions ✅ | **0 submissions ✅** |
| **rolled forward** (`always` leaves in the same macrostep) | 0 submissions ✅ | **1 submission 🔴** |

Sync engine, `def`, roll-forward: **also 1 submission** — so this is not an
engine-parity gap, it is the `def` lane on both engines.

**Contract relevance.** B14 `desynced` is exactly this shape — a transient
state with `always -> snapshot_pending`. B15 `liquidating` likewise
(`always -> liquidated`). Neither currently carries an `invoke`, so B11–B15
are **not** hit today. But a transient state that also invokes is legal SCXML
and is the natural way to express "fire the resync request, then move on".
If we ever write one with a `def` service, the call fires from a state the
machine never settled in, and its `onDone` can never be taken (SCXML §6.4.2
correctly discards it) — an order, socket, or IO call issued and then orphaned.

**Classification: LIBRARY (documentation-vs-behaviour mismatch; severity:
low today, medium if the shape is adopted).** The rollback half of the
sentence is true; the roll-forward half is true only for `async def`.

**Wrapper:** never put an `invoke` on a state that carries `always`, or make
that service `async def`. Add this as a catalogue lint.

## 6. Mandated hazard drives — results

`repro/mandated_drives.py`, both lanes.

**D1 `always` → invoked child.** `async def`: rolled-forward invoke never
submitted, target's own invoke runs once, machine lands in `live`. `def`:
target correct, but the doomed invoke fires once — **CV-F28-01**, §5.

**D2 B18-shaped `send_priority` under a self-generated chain.** An action
raises a 40-deep self-chain while 60 external `send_priority("WORK")` land
mid-macrostep. Result on **both** lanes:

- **60/60 external priority events applied**, `0` dropped, `0` shed as
  `chain_budget`.
- The kill switch (`send_priority("KILL")`) **preempts the busy inbox** and
  the machine reaches `dead`.

This is #192/#180 working as specified — provenance-based shedding. On the
round-6 engine roughly half of an external producer's priority traffic was
destroyed by an unrelated runaway. ✅ **No finding.**

**D3 forged `DoneEvent` (#195).** A hand-built
`DoneEvent("done.invoke.fill", …)` sent while the genuine service is still
running is **refused on both lanes**:

> `UnknownEventError: Event 'done.invoke.fill' is an engine-generated name and
> cannot be sent as user traffic to machine 'd3'.`

The machine stays in `busy`, and when the real service finishes the real
`onDone` runs **exactly once**. On `6db65d8` the forgery drove a real
`onDone` past `strict` and `onUnhandled`. ✅ **FIXED, no finding.**

## 7. Snapshot / restore and engine parity

`g3_snapshot` — for each of B11–B15: snapshot at quiescence **between every
macrostep**, restore into a fresh interpreter, continue the identical script,
and compare the full trace (states, context, action sequence, transitions)
against an uninterrupted run. **5/5 on both lanes.** No torn or relocating
payloads; #198's both-fields rule and #199's in-flight window hold for every
contract shape we drive.

`g3_parity` — the same script against `Interpreter` and `SyncInterpreter`.
**5/5 on both lanes.** The one place the engines are documented to differ
(rollback + `onDone`: sync stops at the first rollback, async storms) is §4's
shape and is stated in the #201 pin.

## 8. Carry-forward our-contract gaps (unchanged, both known)

- **INV-B14-d "buffer is BOUNDED" is prose-only.** 1000 `DELTA`s while awaiting
  a snapshot produce a 1000-element `buffered_deltas`; nothing in the B14 JSON
  expresses a bound (`g3_b14_b15` `B14-d`, `g3_confirm` `CONF-3`).
  **OUR-CONTRACT — add an explicit cap to `buffer_delta`.**
- **INV-B11-d defer-flap.** With `onUnhandled: defer`, a second
  `STREAM_UNHEALTHY` arriving in `degraded` (which has no handler for it) is
  parked; the next `STREAM_HEALTHY` then flaps `degraded → recording →
  degraded`, re-emitting `emit_recording_metric` while a stream is still down,
  and if no further event arrives the second failure is never recorded at all
  (`g3_b11_hazard` `B11-d-hz1`/`hz2`, `g3_confirm` `CONF-2`).
  **OUR-CONTRACT — `degraded` needs its own `STREAM_UNHEALTHY` handler.**

Also carried: `onUnhandled: error` kills the interpreter and the caller's
receipt carries the error but the machine is already dead
(`g3_b13_unh` `B13-unh-2`). Known LIBRARY shape, surfaced since #189 —
**NEEDS-WRAPPER** (never run the control path on `onUnhandled: error` without
a supervisor that restarts on `status == "error"`).

## 9. Verdict

**B11–B15 are adoptable on `f28719c`** under three wrapper rules:

1. Set `maxIterations` explicitly (≤ 50) on every contract machine; health-check
   for quiescence in an `invoke`-bearing state (**CV-F28-02**).
2. Any state that both `invoke`s and can be left by an event or by `always`
   uses an `async def` service (**CV-6DB-01** constraint, **CV-F28-01**).
3. Validate contract JSON against a known-key allowlist before
   `create_machine` (unknown keys are still silent).

Plus the two our-contract JSON fixes in §8. No blocker remains: round 7's
blocker is withdrawn as a documented contract, and both findings here are
bounded, non-corrupting, and wrapper-addressable.
