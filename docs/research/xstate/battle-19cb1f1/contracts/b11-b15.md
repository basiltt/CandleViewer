## 3. ✅ CV-F28-01 closed — a rolled-forward `def` invoke is no longer submitted

**Drive D1** (`g9_d1_always.py`), the mandated *`always` → invoked-child*
check. Two shapes × two service kinds × two engines = 8 cells:

| shape | `async def` | `def` |
|---|---|---|
| **roll forward** — `always` leaves the invoking state in the same macrostep | async 0 ✅ / sync 0 ✅ | async **0 ✅** / sync **0 ✅** |

## 6. 🟠 NEEDS-WRAPPER (carry-forward, unchanged) — unknown config keys are silent

A misspelled top-level key is accepted with no diagnostic and the declared
value is silently dropped to the default:

```python
create_machine({..., "spawnBlockingTimeoutMs": 1234})   # note the Ms
# -> builds clean; machine.spawn_blocking_timeout_ms is None
```

Bad *values* for *known* keys are refused properly; it is only unknown *keys*
that pass. Every one of our five machines carries six policy keys whose
misspelling would downgrade a safety policy to its default in silence —
`actionErrorPolicy` and `guardErrorPolicy` above all.

**Classification: NEEDS-WRAPPER** (arguably LIBRARY-nice-to-have). The wrapper
must validate the config key set against a whitelist *before* `create_machine`
and refuse unknown keys. Unchanged from `6db65d8` and `f28719c`.

## 7. 🔴 The two catalogue Blockers are OURS and are STILL PRESENT

The brief asked whether C-04 and C-07b had been fixed in a later contracts
pass. **They have not.** Both reproduce against the corrected JSON in
`battle-f28719c/contracts/`, on `19cb1f1`, on both lanes. Neither is a library

### 7.1 C-04 — a privilege elevation survives `LOGOUT` (B16 `session`)

**Repro:** `repro/c04_elevation_survives_logout.py` — standalone, stdlib +
`xstate_statemachine` only, run from `C:/Users/basil`, **exits 1**.

B16 is a **parallel** machine: an `auth` region and an `elevation` region.
`elevation.elevated` handles `ELEVATION_DEADLINE`, `STEP_UP_OK` and `REVOKE`
— **but not `LOGOUT`**. `LOGOUT` is handled only in the `auth` region.

```
MFA_OK, STEP_UP_OK, REVOKE -> ['session.auth.revoked','session.elevation.normal']
                              clear_elevated ran      ✅
MFA_OK, STEP_UP_OK, LOGOUT -> ['session.auth.revoked','session.elevation.elevated']
                              clear_elevated did NOT run, elevated_until_us=1  🔴
```

After a clean logout the session sits in `auth.revoked` — a **final,
`terminal`-tagged** state — while the elevation region is **still
`elevated`** and `elevated_until_us` is still stamped. Any authorisation
check that reads the `elevated` tag or `elevated_until_us` rather than auth
liveness grants admin-level rights on a logged-out session. On an OMS control
plane that is a privilege-escalation hazard, not a cosmetic leak.

**Classification: OUR-CONTRACT, Blocker, on any runtime.**
**Fix (ours):** add `LOGOUT` (and every other `auth`-terminal escape —
`IDLE_DEADLINE`, `ABSOLUTE_DEADLINE`, `MFA_TIMEOUT`) to
`elevation.elevated`'s `on` with `target: elevation.normal, actions:
[clear_elevated]`; or better, make the elevation region's clearing
`onDone`-driven off the `auth` region reaching `revoked`, so no future
`auth` escape can be forgotten. A catalogue lint rule (*every terminal
transition in one region must have a matching clearing transition in every
privilege-bearing region*) is the durable form.

### 7.2 C-07b — a guard-denied `RELEASE` bricks the kill switch (B18)

**Repro:** `repro/c07b_killswitch_bricked.py` — standalone, run from
`C:/Users/basil`, **exits 1**.

`28-statechart-catalogue.md` records that `onUnhandled: "error"` was *removed
from B18* under round-6 Amendment 6. **It is still there** in the corrected
JSON: `B18.machine.json` declares `"onUnhandled": "error"`, and
`kill_switch.engaged`'s only handler is a **guarded** `RELEASE`
(`owner_and_elevated`).

Under `onUnhandled: "error"` a guard-denied transition is not an inert
refusal — the event is unhandled, and unhandled is fatal:

```
ENGAGE                        -> engaged   status=running  last_error=None
RELEASE (wrong operator)      -> engaged   status=ERROR    last_error=UnhandledEventError
RELEASE (elevated operator)   -> engaged   status=ERROR    last_error=UnhandledEventError
                                 released=0
```

The second, legitimate RELEASE by a properly elevated operator **cannot be
processed**. The kill switch — the one control that must always be releasable
— is bricked by a wrong button press, and `send()` returns "accepted" both
times, so the operator gets no signal at the call site.

**Classification: OUR-CONTRACT, Blocker, on any runtime.**
**Fix (ours):** the round-6 decision was correct and simply never landed in
the JSON — drop `onUnhandled: "error"` from B18 (use `defer`, or `ignore` on
the release path), **and** give `engaged` an explicit guard-denied fallback
branch (`RELEASE` with no guard → self, `actions: [audit_release_denied]`) so
a denial is an audited no-op rather than an absence of transition. The
catalogue lint should forbid `onUnhandled: "error"` on any state whose sole
handler for a safety-critical event is guarded.

## 9. `after` timers under `SimulatedClock`, and the #203 provenance fix

`g9_d5_timers.py`. B11–B15 declare **no `after`** — their deadlines are
context stamps driven by `LINGER_DUE` / `PONG_DEADLINE` / `ELEVATION_DEADLINE`
events — so the timer contract is exercised on a minimal chart shaped like the
deadlines the catalogue *would* use if it moved them into the engine.

| check | result |
|---|---|
| armed, not yet fired | `waiting` ✅ |
| `+59 s` — must not fire | `waiting`, 0 marks ✅ |
| `+61 s` — fires exactly once | `fired`, 1 mark ✅ |
| `CANCEL` then `+120 s` — disarmed for good | `idle`, 0 marks ✅ |
| sync engine parity (`clock.increment` + `tick()`) | identical ✅ |

**#203 — a forged `AfterEvent` is refused**, with a genuinely good message:

```
UnknownEventError: Event 'after.60000.tmr.waiting' is an engine-generated name
and cannot be sent as user traffic … timers (`after.*`) and engine sentinels are
minted by the interpreter when the work they describe actually happens; a
hand-built one is refused under strict mode.
```

The machine stays in `waiting` and the 60-second timer does **not** fire
instantly, which is the whole of #203. This matters to us directly: it is the
same class as CV-C45 (never accept completion events off a wire), and it means
a snapshot's `pending_events` cannot be used to fast-forward a deadline.

**Harness note (not a defect).** `SimulatedClock.increment()` takes
**milliseconds**, and calling it *inside a running event loop* without
`await` is a no-op that emits a `RuntimeWarning` rather than firing timers —
so the `SyncInterpreter` + `SimulatedClock` combination must be driven from
outside `asyncio.run`. Worth a line in our test-harness guidance.
