## 4. #207 — the rollback + onDone storm (`q3_sharp.py`, part A)

The mandate says this drive "trips `maxIterations` + 3". Measured across four shapes and both lanes, the rule is sharper than that and worth stating exactly.

**Shape availability.** Only **B7** carries the storm shape natively: `chase.arming` invokes, and rollback re-enters `arming`, so the cycle closes on the initial descent with no external event. B6, B9 and B10 do **not** — each one's `onDone` *leaves* the invoking state, so their cycles need an external kick. Those three are therefore driven on a **clearly-labelled overlay** (`onDone` re-enters the invoking state), spelled by `overlay_rearm()` in the script. The overlay is named in every result row; nothing here is presented as shipped-contract behaviour.

| shape | `maxIterations` | plateau (service calls) | over | parked in | stranded hook | dormant |
|---|---|---|---|---|---|---|
| **B7** (native, seed-standing) | 7 | 10 | **+3** | `chase.arming` | ✅ `("chase.arming","arm")` | ✅ |
| B6 (overlay, external kick) | 5 | 7 | **+2** | `twap.submitting_slice` | ✅ | ✅ |
| B9 (overlay, external kick) | 6 | 8 | **+2** | `rule_instance.acting` | ✅ | ✅ |
| B10 (overlay, external kick) | 4 | 6 | **+2** | `alert.firing` | ✅ | ✅ |

**Identical in the `def` lane, cell for cell.** Polled to convergence in every case (the last two laps are equal before anything is called a plateau); a sweep over `maxIterations` ∈ {3,5,7,9} on B7 gives plateau = limit + 3 at every point, so this is a law and not a sample.

**The correction to the mandate.** `maxIterations + 3` is the plateau for a cycle entered with **seed standing** — the initial descent, per #209/#215. A cycle kicked by an **external** event costs exactly one lap less: **`maxIterations + 2`**. Both numbers are deterministic, engine-independent and lane-independent. The `+3` figure in the task statement is the seed case, which is the one B7 exhibits; it is not universal, and an OMS runbook that asserts `+3` for an externally-triggered cycle will assert a number that is reliably wrong by one.

**#207 is delivering what it promised.** In every tripped cell the cut is *observable* rather than inferable: `RunawayChainError.stranded` names the invoke, `on_invocation_stranded(interpreter, state_id, invoke_id, error)` fires with the right state and invoke id, `has_dormant_invocations` answers `True` on demand, and an ERROR log names the state. At `f28719c` this configuration was distinguishable from "waiting on a slow venue" only by polling the configuration against the chart — which in an OMS means a stuck TWAP looks exactly like a busy one.

## 6. #212 / #213 — timers (`q4_timers.py`, 10 checks × 2 lanes, 0 FAIL)

### The fact that has to come first

**Our catalogued B6, B7, B8, B9 and B10 contain no `after` block and no `raise(delay=)` action.** Grepped in all five `.machine.json`: `"after"` → 0 hits, `"delay"` → 0 hits. So #212 and #213, the two round-10 semantic reversals, **touch nothing in the shipped order-path charts**. Their entire relevance to this group is prospective.

That is a real answer, not an evasion, but discharging the obligation as "n/a" would be worthless — the OMS *will* add both timers. So the obligations are run on **contract-shaped overlays** that spell the two timers we know are coming, each labelled as an overlay in the script and in every result row.

### T1 — `after` on `B6.armed` (slice pacing)

"If no `SLICE_DUE` arrives within N ms, fire the next slice ourselves." Six clock ticks at 45 ms against a 40 ms `after`: **6 `submit_child` calls, `last_error is None`**, machine back in `twap.armed` each time. A periodic `after` in a state the chart re-enters is not charged against `maxIterations` — which is the pre-existing `after` rule, and the rule #212 aligns `raise(delay=)` to.

### T2 — #212: a 1 ms `raise(delay=)` ping-pong is a periodic process, not a runaway

Overlay on B10: `poll_up` ⇄ `poll_down`, each entry arming `raise(BEAT, delay=1)`, with **`maxIterations: 8`**. Under the superseded #206 rule this died at 8 beats regardless of period. At `c78ce99`:

```
beats = 77   maxIterations = 8   last_error = None   state = alert.poll_up
```

**77 beats — nearly ten times the budget — with no `RunawayChainError`**, in both lanes. Arming the delay ends the step's chain; the firing is a clock event. This is the behaviour a retry/keepalive pacer needs and #206 made impossible.

*Harness note worth recording as a CV constraint:* the stub originally registered an implementation for **every** action name it scanned, including the built-in `raise` — which silently **disarmed the overlay's timer** (0 beats, no error, no warning). Shadowing a built-in action name is a quiet, total failure. `cvc78.Stub` filters through `actions.is_builtin`; **CV-constraint: never register a user action whose name collides with a built-in**, and lint for it.

### T3 — #213: an armed, unfired delayed self-send survives a snapshot

Overlay on `B6.armed`: entry arms `raise(PACE, delay=5000, id="pacer")`, and `PACE` is the only route onward. Advance the simulated clock 1 s, then snapshot:

```json
{"version": 3,
 "scheduled_sends": [{"kind":"event","type":"PACE","payload":{},
                      "remaining_ms": 4000.0, "send_id": "pacer"}]}
```

- the payload declares **`version: 3`** and the record carries the **remaining** delay (4000 ms of the original 5000), not the original;
- restore with `from_snapshot(..., minimum_version=3)` lands in the same configuration;
- advancing the restored clock 1 s fires **nothing** (`svc_calls == []`), and advancing past the remainder fires the pacer — `submit_child` runs, exactly once, only after the remaining 4 s elapsed;
- **identical on `SyncInterpreter`** (4/4 of the T3 checks pass on both engines).

Before #213 this record existed nowhere the snapshot could see: a state whose only exit is a delayed self-raise restored **permanently parked**. For a TWAP pacer that is an algo that silently stops slicing after a process restart while still holding a position — the single most valuable of the round-10 fixes for this group.

**CV constraints (new):** pin `minimum_version=3` on every restore; assert `scheduled_sends` is present in journal payloads; and treat a restored `remaining_ms` of 0 as "fires on the next pump", not "cancelled".

### OUR-CONTRACT — 2

#### CD-B8 (NEW, high) — `B8.sl.attaching` retries without a bound, and the failure is silent on the risk channel

`repro/cd_b8_unbounded_attach_retry.py` — standalone, neutral cwd, exits 1.

```
attaching --entry[bump_attach_attempts] --invoke attach_native_sl
          --onError[guard attach_attempts_left] --> attaching (reenter)
          --onError (fallback)                  --> naked
```

`attach_attempts_left` is the only thing between a rejecting venue and an infinite attach loop — and **nothing in the chart ever makes it false**. `context` carries `attach_attempts` but no cap, and the catalogue never states one. Held true (venue keeps rejecting), the cycle is pure self-generated work, so the **engine** stops it at `maxIterations`, correctly and observably. Measured on the real B8 (`maxIterations: 25`, async lane):

```json
{"state": ["position_protection.sl.attaching", "position_protection.watchdog.scanning"],
 "svc_calls": 27, "raise_critical_alert": 0,
 "stranded": [["position_protection.sl.attaching", "att"]], "dormant": true}
```

The OMS consequence is the finding:

- the machine parks in `sl.attaching` — **a live position with no stop-loss and nothing in flight**;
- `sl.naked`, the state that carries `raise_critical_alert` and `emit_naked_metric`, is **never reached**, so **zero risk alerts fire**;
- the only signal is `RunawayChainError` / `on_invocation_stranded`, which routes to *engine health*, not to *position risk*. The position is naked and the risk channel is silent.

B6 bounds its equivalent retry (`failures_exhausted`), B10 bounds its (`delivery_attempts_left` against `max_delivery_attempts` in context). **B8's `sl` region does not.** Fix is ours and is config-only: give `attach_attempts_left` a real cap (`attach_attempts < max_attach_attempts`, with `max_attach_attempts` in `context`) so the **chart** decides when to fall through to `naked` and alert, instead of `maxIterations` deciding to stop.

A second-order note from the same probe, worth carrying into the runbook: with `exchange_reports_sl` false the `naked → attach_fallback_sl → verifying → naked` pair is a second unbounded cycle driven by **service completions** — clock/IO events, which `maxIterations` correctly does *not* bound. That one would spin indefinitely rather than park. Both cycles want the same fix, a chart-level attempt cap.
