## 4. Findings

Two new, both **OUR-CONTRACT** (one with a **NEEDS-WRAPPER** remedy). No new

### G13-01 — B11 is a one-way trip into `degraded` (Blocker, OUR-CONTRACT / NEEDS-WRAPPER)

**Reproduced** — `g1_b11_b12.py`, both spellings, both engines, standalone,
neutral cwd, polled to convergence.

`B11.degraded.on.STREAM_HEALTHY` is an ordered pair whose **first** arm
carries `guard: all_streams_healthy` *and* `actions: [mark_stream_healthy]`:

```jsonc
"STREAM_HEALTHY": [
  { "target": "#recording.recording",
    "guard":  "all_streams_healthy",      // <-- reads PRE-action context
    "actions": ["mark_stream_healthy"] }, // <-- the write it depends on
  { "actions": ["mark_stream_healthy"] }
]
```

The guard is evaluated **before** the transition's own actions run, so it
reads a `streams_healthy` map in which the very stream the event is
announcing healthy is still `False`. The recovery arm can therefore *never*
be selected. Instrumented proof (`G2.B11.rootcause.guard_sees_pre_action_ctx`):
the guard observes `streams_healthy = {'trades': False}` on the event that
says `trades` is healthy, and the machine stays in `recording.degraded`.

Consequences on the recording path, all observed:

- `lands_stopped`: ends in `recording.degraded`, never `recording.stopped`;
- `both_services_ran`: `unsubscribe_and_flush` **never runs** — the stream
  subscription and its buffers are never released;
- `gap_counted`: `gap_count_24h` stays `0` (see G13-02).

**Not a library defect.** XState v5 and SCXML both specify that a
transition's guard is evaluated against the configuration/context *before*
that transition's actions execute; the engine is spec-correct. The chart
asks the guard a question only the action can answer. Same class as the
documented-trust-boundary pattern (R10-01): the engine does what it says.

**A second instance of the identical class in the same chart.** Once the
`STREAM_HEALTHY` guard is fixed, `REASON_REMOVED` fails the same way: it
ranks `guard: reasons_remain` ahead of its own `remove_reason` action, so the
guard counts the reason that is *about to be dropped* and the session never
reaches `lingering`. Both arms of `recording` and `degraded` share this shape.

**Remedy (NEEDS-WRAPPER — no config change).** The guards are *our* code and
must be written **event-aware** — "the predicate as it will hold once THIS
event is applied":

```python
def all_streams_healthy(ctx, e):          # OMS must ship this shape
    h = dict(ctx.get("streams_healthy") or {})
    s = getattr(e, "payload", {}).get("stream")
    if s is not None:
        h[s] = True                       # fold in the pending write
    return bool(h) and all(h.values())

def reasons_remain(ctx, e):               # 'remaining AFTER this removal'
    return len(ctx.get("reasons") or []) - 1 > 0
```

Proven in `g2_b11_fix.py`: **11/11 both spellings**, `recording.stopped`,
both services run in order `['subscribe_streams','unsubscribe_and_flush']`,
`recording` re-entered exactly twice, `chain_trips == 0`, every snapshot
round-trip clean, and **sync-engine parity** identical.

> **Catalogue action.** This is a trap that any guard-plus-its-own-action arm
> in the catalogue can fall into. Recommend a lint over all 20 charts for
> "guard on an arm whose `actions` write the state the guard reads".

### G13-02 — B11 stops counting gaps exactly while degraded (High, OUR-CONTRACT)

**Reproduced** — same driver and lanes.

`recording.on.GAP_DETECTED` bumps `gap_count_24h` and emits the metric, but
`degraded` has **no `GAP_DETECTED` handler**, and root `onUnhandled: "defer"`
swallows it silently — no drop, no unhandled hook, no counter movement. Gap
telemetry therefore goes dark precisely during the degraded window, which is
when gaps actually happen; the 24 h gap budget under-reports and the operator
sees a *healthier* number the worse the feed gets.

**Config-only remedy**, proven (`G2.B11.fixed.gap_counted`, both spellings):

```jsonc
"degraded": { "on": { "GAP_DETECTED": {
    "actions": ["bump_gap_count", "emit_gap_metric"] } } }
```

## 6. C-04 (B16) and C-07b (B18) re-check — `g4_c04_c07b.py`, 11/11 both spellings

**Both still reproduce on 0.9.0/`main`. Both remain OUR-CONTRACT, config-only,

**C-04 / R12-13 — CONFIRMED, 4/4 kill events.** Two distinct shapes, and the
distinction matters for the acceptance test:

| Kill event | Observed |
|---|---|
| `LOGOUT`, `IDLE_DEADLINE`, `ABSOLUTE_DEADLINE` | leave `['auth.revoked', 'elevation.elevated']` — dead session, still elevated |
| `REVOKE` | lands `elevation.normal`, but a later `STEP_UP_OK` **re-elevates the revoked session** |

**The round-12 correction is re-proved on 0.9.0.** With the root hoist alone
(`G4.C04.root_hoist_alone_leaves_REVOKE_broken`), `REVOKE` + `STEP_UP_OK`
still ends `['auth.revoked', 'elevation.elevated']`, because the deeper
`elevated.on.REVOKE` handler outranks the root arm. **The region-level
`REVOKE` handler must also be deleted.** With both edits,
`G4.C04.corrected_fix_closes_all_4` passes: all four kill events drop
elevation *and* resist re-elevation. E50-T43's amended acceptance criteria
stand and are re-verified here.

**C-07b / R12-14 — CONFIRMED, `bricked: true`.** A guard-denied `RELEASE`
under root `onUnhandled: "error"` makes the kill switch **fatal**
(`status='error'`, `UnhandledEventError`), and the subsequent *authorised*
`RELEASE` is accepted by `send()` but dropped — final state is still
`['kill_switch.engaged']`. One mistaken press permanently wedges the kill
switch on the order path. The config-only fix (`onUnhandled: "defer"` plus an
ordered **unguarded auditing `RELEASE` fall-through**, the B17/B20/B13 shape)
is re-proven: denial is non-fatal, `audit_release_denied` fires, the
authorised release reaches `kill_switch.clear`, `chain_trips == 0`.
