## 1. #225 — self-send provenance by task identity

This is the round-12 fix with the most direct commercial bearing on our charts, because the broken predicate silently **stalled a machine**: a helper task spawned from an action inherited the action's `ContextVar`, so its later plain `send()` was routed to the internal queue and — with the loop idle — sat there forever.

Our B10 `firing.entry` action `persist_fired_row` is exactly the shape at risk: an OMS alert action that hands work to a delivery worker. Three probes, both lanes:

| probe | what it asserts | result |
|---|---|---|
| `/225/worker-send-advances` | an action spawns a worker that outlives it; the worker `await`s `send("ACK", wait=True)` **with the loop otherwise idle** | `alert.acknowledged` — the machine advances |
| `/225/worker-receipt-resolved` | the worker's receipt actually resolves | `Receipt(changed=True, denied=False)` |
| `/225/handout-not-refused` | the documented `ensure_future(i.send(..., wait=True))` hand-out **with the action awaiting again afterwards** — the shape that flipped to a refusal before #225 | not refused; receipt awaits clean |
| `/225/in-step-refused` | the genuine in-step await is **still** refused | `ReentrantWaitError` — #219 is not undone |

**CV consequence.** The "spawn a worker from an action, let it talk back" pattern is now safe, and it is the pattern our alert-delivery and fill-reconciliation actions want. Before #225 this was a **silent stall**, not an error — the worst failure mode for an OMS. W-02 (the wrapper that forbade spawning from actions) can be **narrowed**: it no longer needs to ban the shape, only to keep the in-step await out.

**Harness note that is itself a finding.** Our `Stub` wraps every action impl in a plain `def`, which is right for the contract passes but **hides an `async def` action from the engine** — the returned coroutine is never awaited and, under `-W error::RuntimeWarning`, CPython says so. The #225 probes are *about* the action's own task, so `e7_round12.py::_direct()` registers the real callable in `MachineLogic.actions` instead. **CV constraint:** any house action registry must register coroutine functions directly, never behind a sync wrapper, or the action silently never runs.

## 2. #232 — a dropped `wait=True` receipt is now audible

A `def` action cannot await, so `r = i.send("B", wait=True)` used to hand it the #219 guard object with nothing ever saying so. The object now emits a `RuntimeWarning` when finalised unused.

| probe | result |
|---|---|
| `/232/dropped-receipt-warns` — the mistake planted deliberately in a `def` action | **1 warning**, `"send('ACK', wait=True) on 'alert' was called from inside an action and its receipt was never…"` |
| `/232/handout-silent` — `ensure_future(...)` counts as use | **0 warnings** |

The detector is live and the supported shape is silent. **The whole of this round ran under `-W error::RuntimeWarning` and every contract pass stayed green**, so none of our B6–B10 stubs drops a receipt — which is the assertion the mandate asked for, and it is now machine-checked rather than argued.

## 3. #226 — the chain-trip latch crosses a restart

`chain_trips` / `last_chain_error` are v3 envelope fields now. Our harness (`cv09.py::snap_roundtrip`) was upgraded to assert this at **every quiescence point of every drive**, not just in a dedicated probe: the round-trip now fails on chain-trip drift, on a spurious chain error after a clean snapshot, and on a restored latch that is not a `RestoredError`.

| probe | result |
|---|---|
| `/226/persisted-fields` | `chain_trips: 3`, `last_chain_error: "cv-synthetic-budget-trip"` in the raw v3 blob |
| `/226/count-restored` | `3` after restore — monotonic across the restart |
| `/226/restored-error-type` | `RestoredError('cv-synthetic-budget-trip')` — the `error` precedent, so a restored latch is distinguishable from a live one |
| `/226/restored-error-message` | message carried verbatim |
| `/226/clear-keeps-count` | `clear_chain_error()` clears the error, **keeps the count at 3** |
| `/226/happy-path-zero-all5` | all five contracts persist `0` / `None` and restore `0` / `None` — **the mandated `chain_trips == 0 and preserved` assertion, on B6–B10, both lanes** |

**CV consequence.** This closes a real supervisor gap for us: a restart is precisely the event our supervisor reacts to, and before #226 a restart reset the evidence that work had been discarded to `0`/`None` with nobody having acknowledged it. Our journal can now carry "this instance has tripped the chain budget N times, and here is the last reason" across a process bounce. Monitoring should alert on `chain_trips > 0` **after** restore, not only in-process.

## 4. #227 / #230 — the two restore lanes now agree, and the plugin sees it

`_rearm_restored_self_sends` used to re-arm every record unchecked, so an undeclared type in `scheduled_sends` was admitted silently on a `strict: True` machine while the same record in `pending_events` was refused (#214). All five of our contracts are `strict: true`, so this was live for us.

The probe plants the **same undeclared event in both lanes** of a B10 snapshot:

| probe | result |
|---|---|
| `/227/both-lanes-refused` | `on_invalid_event` fired **twice** — both lanes refuse, identically |
| `/230/plugin-saw-restore-refusal` | the stub passed via `from_snapshot(plugins=[...])` **saw both**, so it was registered before admission — `.use()` after the fact would have missed them |
| `/227/machine-not-derailed` | `['alert.armed']` — a schema refusal no longer aborts the whole restore |
| `/227/no-chain-trip` | `0` |
| `/227/declared-rearms-and-fires` | a **declared** `DISABLE` in `scheduled_sends` still re-arms and still fires (`alert.disabled`), `invalid=0` — the fix did not break the legitimate lane |

The refusal is loud at WARNING level and names the machine and the known-event set.

**CV consequence.** `plugins=` is not optional for us — it is the only way our `CvErrorHooks` sees a restore-time refusal, which is exactly when a deadline gets silently dropped. **This is now mandatory in our restore wrapper**, and it is the one API change in 0.9.0 that our code must actively adopt rather than merely benefit from.

## 6. C-04 (B16) and C-07b (B18) — re-checked, unchanged

Both re-reproduced on `v0.9.0`, both still closed by a **config-only** edit, both lanes, `6 / 6`:

- **C-04 (B16).** The four revocation events (`LOGOUT`, `IDLE_DEADLINE`, `ABSOLUTE_DEADLINE`, `REVOKE`) are not visible to the parallel `elevation` region, so a revoked session stayed `elevation.elevated`. Hoisting them to the root with a terminal `elevation.dead` closes it: "all 4 revocation events drop elevation". Plus C-04b, the re-enter arm must audit.
- **C-07b (B18).** A denied `RELEASE` on the kill switch bricked the chart. `onUnhandled: defer` plus an unguarded fall-through arm that audits the denial and stays engaged: `denied RELEASE → status='running', states=['kill_switch.engaged']`, and a legitimate release still reaches `kill_switch.clear`. `chain_trips=0`.

**Eighth consecutive round with the same verdict: OUR-CONTRACT, config-only, no library involvement.** These are catalogue edits we owe ourselves, not blockers on the library. Recommend they land in `28-statechart-catalogue.md` rather than being re-verified a ninth time.

## 7. BENCH-6 — materially better, now inside our bar

Per the round-12 correction, this is **their** `benchmarks/production_characteristics.py --quick` (≈6 s), §2 = `after: 10` lateness at 500 busy machines. Our bar: **≤100 ms**. Five runs on `e3a1f22`:

| busy machines | r1 | r2 | r3 | r4 | r5 | median |
|---|---|---|---|---|---|---|
| 0 | +0.2 | +0.2 | +0.1 | +0.2 | +0.2 | **+0.2** |
| 10 | +2.5 | +1.5 | +1.3 | +1.3 | +1.6 | **+1.5** |
| 100 | +13.0 | +13.3 | +10.6 | +11.2 | +10.7 | **+11.2** |
| **500** | **+82.7** | **+66.4** | **+71.0** | **+75.9** | **+69.8** | **+71.0** |

**Distribution at 500: min +66.4, median +71.0, max +82.7, spread 16.3 ms. All five runs are under our 100 ms bar.**

Round-12 readings on the same tool were **+89.6 / +94 / +113 / +110 / +111** (median ≈ +110, two of five *over* the bar). The v0.9.0 distribution is **≈35 % lower and, unlike round 12, entirely inside the bar with ~17 ms of headroom on the worst run.** I did not isolate which fix accounts for it; #218 (the delayed-self-send clock-handle leak, fixed in round 11) and the #225 removal of the `ContextVar` from the send hot path are the plausible candidates, and the benchmark is unchanged between the rounds.

**Caveat, unchanged and important:** these are single-host figures with wide run-to-run spread on a Windows dev box, and the library's own note says "order-of-magnitude figures for THIS host; your macrostep cost sets your budget." **BENCH-6 should be re-measured on target hardware before it is treated as closed** — but on this evidence it is no longer the open risk it was in round 12.

## 8. Findings

**LIBRARY: 0.** No new library defect on B6–B10 at `v0.9.0`. Every round-12 fix behaves as the changelog claims when driven through our five contracts, on both service spellings, on both engines where parity is the point, under `-W error::RuntimeWarning`.

**OUR-CONTRACT: 2 (unchanged).** C-04 (B16 revocation not visible to the parallel elevation region) and C-07b (B18 denied `RELEASE` bricks the kill switch). Both config-only, both re-verified, both ours to land in the catalogue.

**NEEDS-WRAPPER: 3 (W-01, W-02, W-03), one of them now smaller.**
- **W-01** (unchanged) — restore wrapper. **Now carries a hard requirement:** `from_snapshot(..., minimum_version=3, plugins=[CvErrorHooks()])`. `plugins=` is the only way a restore-time strict/schema refusal reaches our alerting (#230). A restore path that calls `.use()` afterwards is silently blind to exactly the failure it exists to catch.
- **W-02 (narrowed by #225)** — previously "do not spawn workers from actions." A worker that outlives its action is now ordinary external traffic and the hand-out idiom is safe whether or not the action yields again. The wrapper only needs to keep the **in-step await** out, which the library itself now refuses with `ReentrantWaitError`. Downgrade from a prohibition to a lint.
- **W-03** (unchanged) — the sync engine still takes no `max_queue_size` / `overflow_policy`; the bounded RAISE inbox is async-only. Any sync-engine use in the OMS needs its own admission bound.

**Two briefing corrections, both in our favour:** 0.9.0 **is** on PyPI and the wheel is byte-identical to the tag (vendoring caveat dropped); BENCH-6 is **inside** our bar on this host, ~35 % better than round 12.
