# #231 verify — v0.9.0/main

**Classification: FIXED**

An inline-dict `invoke.src` is now rejected in `InvokeDefinition.__init__`
(`models.py:668-681`) with a named `InvalidConfigError`, before
`logic_loader` ever sees it — so the previous `TypeError: unhashable type:
'dict'` from deep inside `logic_loader` no longer surfaces.

Result (`231_invoke_src_named_error.py`):
- Well-formed inline-dict `src`, `strict_config=False` → `InvalidConfigError`
  naming state `'m.a'`, invoke id `'kid'`, and the supported `src` shapes.
- Same, `strict_config=True` → same named error (fix applies unconditionally
  per source comment, a stricter guarantee than "matches #220's strict/warn
  split" — it's a hard error regardless of `strict_config`, which is
  reasonable since the shape is structurally invalid, not a warn-worthy
  typo).
- Typo'd inline-dict `src` under `strict_config=True` → same named error
  (never reaches the typo at all, since `src`'s value is rejected first).
- Message includes state path and invoke id in all three cases.

One deviation from the issue's literal ask: the proposed fix suggested
warn-vs-raise following `strict_config`; the shipped fix always raises
`InvalidConfigError` regardless of `strict_config`. This is stricter than
requested, not weaker, and matches the acceptance criteria's core ask (a
named `InvalidConfigError` instead of `TypeError`, mentioning `src` and the
path) — classified FIXED, not PARTIAL, since nothing in the acceptance
criteria requires the warn-only path to survive; the shape is unsupported
either way and giving it a hard error is a valid interpretation of "reject
the shape by name at validation time."
