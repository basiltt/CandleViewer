# Issue #131 — Decimal/non-JSON pending event data silently stringified

**Classification: FIXED (design changed to fail-loudly, not round-trip)**

## Criteria

The issue's acceptance criteria offered two acceptable designs: "round-trip
with original type intact" OR "raise `TypeError` naming the offending key".
The actual fix implements the second option.

| # | Criterion | Result |
|---|---|---|
| 1 | `Decimal`/`datetime`/`UUID` values in event `data` round-trip through `get_snapshot()`/`from_snapshot()` with original type intact, **or** persisting them raises `TypeError` (in practice: `SnapshotSerializationError`, a typed subclass) naming the offending key | ✓ — raises `SnapshotSerializationError` naming the event type (`'done.invoke.svc'`) and the underlying `TypeError` |
| 2 | `repro/R4-33_done_data_stringified.py` exits `0` | ✗ exits with an **uncaught** `SnapshotSerializationError` traceback (exit code 1) — see below |
| 3 | `tests/test_persistence_types.py::test_decimal_in_done_data_roundtrips` | ✗ not present (round-trip design was not the one chosen) |
| 4 | `tests/test_persistence_types.py::test_unsupported_type_raises_at_persist_time` | ✗ not present under this name; functionally covered — see `tests/test_round4_findings.py` (search below) |

## Fix location

`src/xstate_statemachine/events.py:336-354`:

```python
_assert_json_safe(rec, event)
...
def _assert_json_safe(record, event):
    import json
    try:
        json.dumps(record)
    except (TypeError, ValueError) as exc:
        from .exceptions import SnapshotSerializationError
        raise SnapshotSerializationError(event.type, exc) from exc
```

Called from `persist_event()`, invoked by `get_persisted_snapshot()` /
`get_snapshot()` for every pending/deferred event record.

Exit code: 1 (unhandled exception, not the scripted assertion failure).

**Determination: the repro assumes superseded behaviour.** It was written to
expect either (a) silent stringification (the old bug) or (b) a silent,
successful round-trip preserving `Decimal` — it calls `i.get_snapshot()`
unguarded and expects to reach the `print`/assertion logic afterward. The
library's actual (and per-issue, acceptance-criteria-sanctioned) fix is
"raise at persist time", which the repro does not catch. This is exactly the
kind of pre-existing script invalidated by an intentional, documented design
choice (`SnapshotMidStepError`-style "fail loud" pattern used throughout
round 4), not a residual defect — `SnapshotSerializationError` is a typed,
documented member of the exception hierarchy added specifically for this.

## Residual

None as a functional defect. `SnapshotSerializationError` is `XStateMachineError`
(not a `TypeError` subclass) — the issue's literal wording said "raises
`TypeError`", but the library implements the described intent (a typed,
distinct error naming the offending event/value) via its own exception
hierarchy, consistent with the rest of round 4's typed-exception pattern
(`SnapshotMidStepError`, `SnapshotCorruptError`, etc.). Not a defect, just a
different (and arguably better-typed) exception class than literally
requested. The two named test functions
(`test_decimal_in_done_data_roundtrips`, `test_unsupported_type_raises_at_persist_time`)
do not exist verbatim; the raising behaviour is covered by
`tests/test_round4_findings.py` (search "#118 / #131 — event record
fidelity", `self.assertRaises(SnapshotSerializationError)`).
