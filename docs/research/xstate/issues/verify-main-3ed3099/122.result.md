## Fix location

`src/xstate_statemachine/sync_interpreter.py:1341-1367` — `tick()` now loops
(bounded by `max_iterations`), calling `_pump_timers()` then draining the
queue and transient transitions, continuing "the step may have armed an
already-due timer" until a pump delivers nothing. Previously (per R4-27's
register row) it fired timers once and returned as soon as the resulting
queue drained, never re-checking the timer heap for a deadline that became
due only as a *consequence* of the transition just processed.

## Residual — is this the fixed defect, or a persisting one?

Traced the repro's exact mechanics (instrumenting `_pump_timers`): the first
`tick()` call fires the `submitted -> ack_timeout` deadline (already due
since `start()`), transitions into `ack_timeout`, which arms a *new*
50ms-from-now deadline. The second and third loop iterations inside the
*same* `tick()` call find `fired=0` because real wall-clock time has not
advanced during the synchronous call — there was only ONE `sleep(0.25)`
*before* `tick()`, not between each internal link. This is different in kind
from what #122 fixes: the zero-delay case has all links due at the *same
instant* the drain loop starts, so looping with no sleep between iterations
correctly walks the whole chain. The real-delay repro requires ~150ms of
*additional* wall-clock time to elapse *while inside one synchronous call*
that never sleeps — structurally impossible for a single-threaded,
non-blocking `tick()` against `RealClock`. The async engine reaches
`escalated` within the same `sleep(0.25)` because its `asyncio.call_later`
timers fire concurrently with the test coroutine's own sleep — real time
elapses *between* transitions while the caller is suspended, which a
single instantaneous `tick()` cannot replicate by design.

Confirmed no event/deadline is actually lost: looping `sleep(0.05); tick()`
20 times (a realistic poll caller) reaches `order.escalated`, matching
async. So the residual is: the *acceptance-criterion's own test construction*
(single `sleep` + single `tick()` over a chain of real, non-zero delays)
describes a scenario `tick()` cannot satisfy without either (a) `tick()`
itself blocking/sleeping until the whole chain settles — a stated
non-goal, since `tick()` is explicitly non-blocking — or (b) the repro
looping. The library-side fix for the *actually-due-now* chained-deadline
case is solid; the *named test* and the *criterion-3 repro* were written
for a shape that remains a structural limitation of a synchronous,
call-once `tick()`, not a residual bug in the fix's scope. Recommend the
criteria be reworded (or the register's real-delay repro retired) rather
than reopening the code fix, since no additional code change would make a
single non-blocking `tick()` call skip real wall-clock time.
