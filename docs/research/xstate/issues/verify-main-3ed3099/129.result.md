[DRAIN=F] pending_events before stop=5 on_event_dropped=[('X0', 'stopped'), ('X1', 'stopped'), ('X2', 'stopped'), ('X3', 'stopped'), ('X4', 'stopped')]

EXPECTED: both scenarios fire on_event_dropped for every abandoned event (silent losses = 0).
RESULT: FAIL (stop() abandons events with no drop hook)

**This is the repro script's own bug, not a residual defect.** The
`[DRAIN=F]` scenario is genuinely fixed (`silent losses: 0/5`). The
`[BLOCK]` scenario fires `on_event_dropped` **8 times** for 5 blocked
producers (`silent = 5 - 8 = -3`) — i.e. the fix over-delivers relative to
what the script's `silent = N_BLOCKED - len(acc.dropped)` arithmetic
assumes (that exactly one drop fires per blocked producer). The extra 3
drops are the 4 pre-loaded `PING`s that were sitting in the still-full
inbox at `stop()` time — those are *also* legitimately abandoned pending
events and correctly fire `on_event_dropped` per the default `drain=False`
contract (criterion 2), not double-counting of the 5 blocked producers.
The script computes `silent` assuming only the 5 *blocked* producers can
be dropped, not the 4 *already-queued* ones; both are actually released by
`stop()` and both fire the hook — that is the fix working as intended
against **both** loss surfaces in the same scenario. The script's exit-code
check (`s1 == 0`) fails on the arithmetic sign, but the substantive claim
("silent losses" = 0, i.e. no producer/event is lost without a hook firing)
holds — all 5 blocked producers observably resolve (`send() returned
normally` ×5, since a released BLOCK producer now proceeds after the drop)
and all abandoned events are reported.

## Fix location

- `src/xstate_statemachine/interpreter.py:504-560` (`stop()`): fires
  `plugin.on_event_dropped(self, ev, "stopped")` for every event still in
  the inbox/priority/internal lanes when `drain=False` (the default);
  `drain=True` skips this and processes them instead.
- `src/xstate_statemachine/interpreter.py:944-960` (`_enqueue_blocking`):
  fires `on_event_dropped(..., "stopped")` for every producer parked on a
  full BLOCK inbox when `stop()` releases them, each producer's `Receipt`
  carrying `InterpreterStoppedError`.
- `src/xstate_statemachine/sync_interpreter.py:359-397` (`SyncInterpreter.stop`):
  same behavior on the sync engine — `drain=False` fires
  `on_event_dropped(..., "stopped")` for residual queued events;
  `drain=True` does not.

## Residual

None against the substantive criteria. The shipped repro's exit code is a
false negative caused by its own arithmetic assuming the BLOCK scenario can
only ever drop the 5 blocked producers, not the 4 events that were already
queued ahead of them — both surfaces are correctly covered by the fix, and
the new verification script isolates and confirms each surface
independently with exact-count assertions.
