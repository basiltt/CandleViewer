## The `+2` / `+3` contradiction — settled, and worth a changelog fix

The changelog says `maxIterations+2` under #207 and `maxIterations+3` under #210. We swept it to settle which is right, and **both are, for different shapes**:

| shape | plateau |
|---|---|
| descent-seeded (the raise has seed standing) | **`maxIterations + 3`** |
| externally kicked cycle | **exactly `maxIterations + 2`** |

Confirmed across limits {3, 5, 7, 9} at every point, and identical cell-for-cell in the `def` lane. Your own pin (`test_round9_findings.py`) asserts `1000+2`, i.e. the external case.

So the behaviour is correct and deterministic; it is the **documentation** that conflates two shapes into one number. A reader sizing a budget against the external number under-provisions the descent case by roughly 2.7× — we hit exactly that. One sentence distinguishing the two would fix it.

We have recorded the descent/external asymmetry itself as an intended design consequence, not a defect: the sync drain gives the initial descent's raises seed standing, and this issue brought the async engine to the *sync* number, which is the right direction.

## One new shape, filed separately

The gate this issue added at the top of `_run_event_loop` —

```python
await self._descent_done.wait()
```

— is set only at the **end** of `start()`'s try-body. So an `async def` entry action that awaits a receipt on its own interpreter (`await i.send("GO", wait=True)`) creates an unsatisfiable cycle: the receipt resolves only when the run loop processes `GO`, and the run loop is parked on `_descent_done`, which only that same entry action can open. **`start()` never returns.**

It is completely silent — `last_error is None`, status `running`, configuration legal, indistinguishable from a slow entry action. `on_invocation_stranded` does not cover it because no `invoke` is involved.

Two things we checked before filing:

- **The settle budget *does* cover the descent.** An `always` self-cycle inside the initial descent is correctly bounded and `start()` returns with `RunawayChainError` after `maxIterations+1` entries. Only the receipt cycle hangs — so this is a narrow shape, not a general descent problem.
- **It is new at this commit.** The identical chart on a subclass that opens the gate before spawning the loop (pre-#215 behaviour, **library source untouched**) returns from `start()` in 0.00 s.

Awaiting one's own receipt from an entry action is admittedly unusual. What is not unusual is calling a helper that happens to wrap `send(..., wait=True)` — and the caller of that helper has no local signal that it is unsafe in entry position. The failure mode is an unbounded hang inside `start()` with every health surface reporting normal, which is why we filed it rather than treating it as misuse.

Suggested fix, from your own comment in that code: set `_descent_done` **before** running entry actions and use a re-entrancy flag to preserve the ordering guarantee — which is what the comment describes as the sync engine's approach. Bounding the gate with `wait_for` and raising a named error would also be a reasonable safety net regardless.

It would additionally be worth documenting that `send(..., wait=True)` is not reentrant from within entry/exit actions on the same interpreter. That constraint is not stated anywhere today and is not evident from the receipt API.
