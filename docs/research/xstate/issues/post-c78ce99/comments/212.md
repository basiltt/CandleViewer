# Comment for issue #212 — a `raise(delay=)` self-send is a timer (supersedes #206)

**Action:** comment + **close**
**Disposition:** **FIXED as specified — verified, closing. The semantic reversal is exact, not approximate. One resource consequence filed separately as a new issue.**

---

Verified on `main` @ `c78ce99` (merge of PR #217, `fix/0.8.1-round10`; unreleased 0.8.1). Build identified **by commit** — `__version__` still reports `0.8.0`. Reproduced from a neutral working directory, both `def` and `async def` actions, both engines.

The reversal landed cleanly and completely. Arming ends the step's chain, firing is a clock event, and a self-paced ping-pong of any period is legal periodic work.

What we measured:

- **200 machines × a 1 ms ping-pong for 10 s: 0 `RunawayChainError`, 0 `chain_budget` drops, 200/200 still beating** — on both action kinds.
- **Zero-delay cycles still trip**, including in a chart that *also* arms a delayed send, so the exemption is correctly scoped to delayed work rather than to `raise` as such.
- **A 500-config × 2-kind × 2-engine livelock fuzz with a two-sided oracle: 2000/2000 clean.**
- **540 fuzz cells, 0 violations, `cpu/wall = 0.26`** — the cycle is genuinely paced by the clock rather than spinning.
- **The parity claim is exact, not approximate.** The measured `raise(delay=)` beat rate is indistinguishable from the `after:` spelling at every rung we tested.
- Confirmed on a real invoke-bearing chart: 40 beats / 21 laps with live services.

We also re-ran our own round-10 finding against the new rule. #206's chain charge was time-blind, and that is exactly what #212 removes; the finding is superseded and we have retired the test that encoded the old rule rather than reporting it as a regression.

## One collateral consequence, filed separately

#212 did not open any semantic hole — we went looking specifically for a previously-bounded cycle class that became unbounded, with watchdogs on both lanes, and found none.

It did, however, make a pre-existing **resource** defect unbounded. `_timer_handles` retains one handle per `raise(delay=)` beat and nothing prunes it before `stop()`. Before #212 that was invisible because #206's trip killed such a cycle at roughly `maxIterations` beats, capping retention at ~12 entries. Now the cycle is legal, so the growth has no ceiling: **+455 MB / 24 s at 200 machines, strictly linear, no plateau.** The `after:` path is keyed by state id and is pruned correctly — it is flat under the same load.

That is filed as its own issue with a standalone repro, since the fix is in `_schedule_send`/`_cancel` rather than anything #212 changed. We mention it here only because the two are causally linked: **#212 is correct, and it made a latent leak observable.**

## A note on sub-millisecond delays

We briefly held a finding that #212's exemption keys on delay *truthiness*, so `raise(delay=0.0001)` escapes `maxIterations`. **We refuted it ourselves and are not filing it.** Plain `after:` at the same delays behaves identically on the same charts — it has been exempt from `maxIterations` since long before #212 — so nothing regressed; #212 achieved parity with a path the budget never bounded by design. It is also not a liveness failure: an external `send` during the spin is served in ~16 ms, the same Windows timer floor as a quiescent chart.

The only real observation there is that `delay` is milliseconds, so `0.0001` is 100 ns and is API misuse. If it is cheap, warning on a delay below the platform clock granularity would be a kindness; it is not a defect.

## Suggested changelog sentence

It would be worth stating explicitly that **`maxIterations` has never bounded delayed work, in either spelling** — that `after` and now `raise(delay=)` are scheduler-driven and outside the microstep budget, in line with SCXML §6.2 and XState v5. `production-characteristics.md` §2 now says this for the new rule; readers coming from #206 will be looking for it next to `maxIterations` itself.
