Verified on `main` @ `c78ce99` (merge of PR #217; unreleased 0.8.1). Build identified **by commit** — `__version__` still reports `0.8.0`. Reproduced from a neutral working directory.

This is the cleanest fix in the round and we could not break it:

- **47/47** policy-key mutations warned, **47/47** raised under `strict_config=True`, and the did-you-mean hint named the right key **47/47**.
- Independently at scale: **120/120** top-level mutations caught in one harness, **200/200** warned and **200/200** raised in another, **17/17** in a third.
- Both switch spellings work and **either one alone is sufficient**: `"strictConfig": true` in the config with no kwarg raises, and `strict_config=True` with `"strictConfig": false` in the config also raises.
- Every key our parser reads is present in `KNOWN_MACHINE_KEYS` — we checked for the inverse gap (a real key missing from the list, which would produce false positives) and found none.
- Across a 20-machine production catalogue: **0 unknown top-level keys**, with a positive control confirming the check was live rather than vacuous.

We have made `strictConfig: true` mandatory in our own build path on the strength of this.

## The scope gap — filed separately

`validate_top_level_keys` iterates `for k in config` — the **root dict only** — and is invoked once from the factory. But `KNOWN_MACHINE_KEYS` is overwhelmingly a list of **state-level** names: `entry`, `exit`, `on`, `after`, `always`, `invoke`, `onDone`, `initial`, `type`, `states`. Those keys do their work *inside each state node*, where nothing checks them — `StateNode.__init__` reads the keys it knows via plain `.get()` and silently ignores the rest.

So most of the known-key list names keys that are never validated where they are actually used:

```
typo                  built   exc       warnings
entry -> entyr        True    None      0
exit -> exti          True    None      0
on -> onn             True    None      0
after -> afer         True    None      0
always -> alwyas      True    None      0
invoke -> invoek      True    None      0
onDone -> onDoen      True    None      0
```

7/7 accepted silently under `strict_config=True`. `{"states": {"a": {"entryy": [...], "onn": {...}}}}` builds a **clean machine** with no entry actions and no transitions — we confirmed behaviourally: entry actions run 0 times (expected 1), and the machine stays in `a` after the event that should move it to `b`. At scale: **0/120** nested mutations caught, and 30/30 silently accepted in a separate fuzzer.

The nested case is in one respect **worse than the pre-#216 top-level behaviour**: it emits **no WARNING either**, so the did-you-mean safety net is absent exactly where a typo is most likely. A realistic machine has one root dict and dozens or hundreds of state nodes, so the typo surface is almost entirely below the line this check draws.

**One nuance that narrows the report honestly:** nested *policy* misspellings (e.g. `actionErrorPolicyy` under a state) are inert either way, since policies are read from the root only. The **structural** keys above are the real exposure.

**Suggested fix: recurse.** `KNOWN_MACHINE_KEYS` already contains every state-level name, so the recursion is the only missing part — walk `states` (and nested `states`, and parallel regions) and apply the same check and the same hint to each node. If the root and state-node key sets should differ, splitting into `KNOWN_ROOT_KEYS` / `KNOWN_STATE_KEYS` and checking each at its own level would be stricter still and would make the intent explicit.

Filed separately with a standalone repro. We mention it here rather than only there because the value of this issue's mechanism roughly multiplies with the recursion: the machinery, the hint and the strict switch all already exist and already work.

## Minor note

The root-level WARNING is emitted through `logging` rather than the `warnings` module. That is a defensible choice, but it means `pytest.warns` / `warnings.catch_warnings` do not see it, and a caller writing a test for "did my typo get flagged?" will most likely reach for the latter. Worth a sentence in the docs, or a `caplog` example.
