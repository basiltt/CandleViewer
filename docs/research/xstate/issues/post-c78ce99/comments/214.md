# Comment for issue #214 — restore applies `strict`; v2 upcast; records carry `lane`

**Action:** comment + **close**
**Disposition:** **FIXED as specified for `pending_events` — verified, closing. Three scope residuals filed separately, and one Blocker-class finding we raised internally and then REFUTED ourselves.**

---

Verified on `main` @ `c78ce99` (merge of PR #217; unreleased 0.8.1). Build identified **by commit** — `__version__` still reports `0.8.0`. Reproduced from a neutral working directory, both `def` and `async def` actions, both engines.

The strict-on-restore mechanism works as specified for `pending_events`: an unknown restored user event is refused, recorded in `last_error`, and dropped, on both engines and both kinds. A fired timer restores ahead of the inbox. The v2 upcast closes the migration cliff we reported last round — a 0.8.0-era `after` record used to be *refused* rather than demoted, dropping the deadline silently, and that is now handled.

## A correction we owe you

We filed a **Blocker** internally against the v2 upcast: `upcast()`'s `if version < 3` block applies `rec.setdefault("engine", True)` to `done`/`error`/`after` records, so an attacker who edits one integer (`"version": 3` → `2`) gets forged completion records minted as engine-authentic. The mechanism reproduces exactly — a 60,000 ms `after` firing in ~1 ms, a forged `onDone` landing attacker context, `last_error=None` throughout, with the v3 controls correctly refusing.

**We refuted it ourselves and are not filing it as a vulnerability.**

The control probe is what killed it: an attacker who can edit `version` can equally edit `state_ids`, and doing so **lands in the target state directly with no event forgery at all**. `from_snapshot` is a documented trusted-input boundary — #205 applies `state_ids`/`configuration`/`context` verbatim, and `machine_hash` is explicitly a fingerprint rather than a MAC. The upcast therefore confers no privilege the payload did not already have. `from_snapshot(minimum_version=3)` raises `SnapshotVersionError` on the forged blob, which we confirmed works.

This is the third round running in which we have filed a Blocker against engine-event provenance and then refuted it on a control. We are adopting the check as a triage precondition rather than a refutation step: **any finding whose threat model requires blob-write must first be tested against "what does the same writer achieve with `state_ids`/`context` alone?"** If the answer is "the same thing", there is no defect. We would suggest the same test for any future report of this shape you receive.

**One doc nit falls out of it:** the snapshot guide still recommends `minimum_version=1` as the anti-downgrade floor. Now that v3 is the layout carrying provenance, **it should recommend `3`** — that one line is the difference between the documented mitigation working and not.

## Three residuals, filed separately

**1. `scheduled_sends` does not get the strict check that `pending_events` does.** `base_interpreter.py` stores those records verbatim into `_restored_self_sends` and `_rearm_restored_self_sends` arms them through `_deliver` with self-generated standing; `_admit_restored` — the `strict` mirror this issue added — is called only from the `pending_events` loop two lines below. So #214's stated invariant is true for one half of the restore path and false for the field added in the same release.

We looked hard at whether this is a security issue and concluded it is not, for the same reason as above: forging the snapshot's `configuration` alone reaches the same target state with no event at all, and `events.py:421` states that boundary explicitly. A *live* `raise(delay=)` is strict-checked at arm time, so an undeclared event enters `scheduled_sends` only via forgery or a chart change.

**What does survive is a genuine contract inconsistency.** A chart upgrade that undeclares an event yields **silent delivery** through this path instead of the `on_invalid_event` / `last_error` refusal this issue promises. Fix looks like one line: route `_rearm_restored_self_sends` through `_admit_restored`. We would also suggest refusing `kind in (done, error, after)` in `scheduled_sends` outright — a delayed *self-send* is never a completion.

**2. `on_invalid_event` is structurally unreachable on the restore path.** `_admit_restored` does call `_report_invalid_event`, which iterates `self._plugins` — but it runs inside the `from_snapshot` classmethod, which is still *constructing* the interpreter. `from_snapshot` takes no `plugins=` parameter, and the only registration path is `interpreter.use(p)` on the object `from_snapshot` has not yet returned. **No ordering exists** in which a plugin observes a restore refusal: `on_invalid_event` was empty in all 10 cells we tried (5 record shapes × both engines), while `last_error` was set and the WARNING logged.

This contradicts the changelog's claim that the refusal "is reported (`on_invalid_event`, `last_error`)". The `last_error` half works, but only *before* `start()` — it reverts to `None` afterwards once one legitimate neighbouring record is present, and it holds only the **last** refusal, so with *n* refusals *n−1* are invisible on that channel too.

Worth noting that the pin in `tests/test_round10_findings.py` constructs the plugin, calls `r.use(plug)` *after* the restore, and asserts only on `last_error` — never on `plug.seen` — so the suite does not currently notice. Suggested fix: add `plugins=` to `from_snapshot`, or defer the refusal report to `start()`.

**3. `lane` is persisted but cannot be honoured on the sync engine.** `SyncInterpreter` has a single queue by construction, so a restored deadline loses its precedence there: the same blob yields `['after.1000.l.w', 'EXT']` on async and `['EXT', 'after.1000.l.w']` on sync. Not a lost *live* guarantee — the sync engine never had lanes — but the field is written by one engine and unenforceable on the other, so cross-engine restore is not order-equivalent. Documenting `lane` as async-only would be enough.
