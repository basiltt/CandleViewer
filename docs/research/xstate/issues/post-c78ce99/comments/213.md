# Comment for issue #213 — snapshot layout v3 with `scheduled_sends`

**Action:** comment + **close**
**Disposition:** **FIXED as specified — verified, closing. The round-trip is exact. One second-hop gap filed separately.**

---

Verified on `main` @ `c78ce99` (merge of PR #217; unreleased 0.8.1). Build identified **by commit** — `__version__` still reports `0.8.0`. Reproduced from a neutral working directory, both `def` and `async def` actions.

This closes the gap we reported last round, and it closes it precisely rather than approximately:

- **600/600 trials exact.** 300 random machines × 2 action kinds, each snapshotted at a random point *inside* the delay window: every one carried the right `remaining_ms` (±0.5 ms) and the right `send_id`, and fired **not early, not late, exactly once** after the remainder.
- **200 concurrent restores behave identically** — no interference, no lost records.
- A separate 300-machine property run over the normal snapshot→restore→start hop: **0 failures, 0 missing records**.
- Confirmed on a real contract machine: a 4000.0 ms armed send round-trips with its `send_id` intact.

The `remaining_ms` design (rather than an absolute deadline) is the right call for a blob that may sit in storage for an arbitrary time, and it behaved correctly across every restore delay we tried.

## One gap, one hop out — filed separately

`from_snapshot` parks the restored records in `_restored_self_sends`, and only `start()` converts them into live armed sends via `_rearm_restored_self_sends`, which also **consumes** the list. But `get_persisted_snapshot` builds `scheduled_sends` from `_armed_self_sends` only — the live dict, empty before `start()`.

So the parked list is written by neither path:

```
snapshot (1 record) -> from_snapshot -> get_persisted_snapshot -> 0 records
```

Both action lanes, `snapshot_version: 3`. The **normal** hop (restore → `start()` → re-persist) is sound and is the control in our repro — it preserves the record and its `send_id`.

This matters because loading a snapshot and writing it back without starting an interpreter is what a journal-compaction or storage-migration job does, and such a job has every reason *not* to `start()` the machine. The result is that a maintenance pass silently destroys every deadline it touches — the exact failure mode #213 was filed to fix, re-appearing one hop later.

Filed as its own issue with a standalone repro. The suggested fix is small: have `_persist_scheduled_sends` union `_armed_self_sends` with any unconsumed `_restored_self_sends`, so the round-trip invariant holds regardless of whether `start()` has run.

## Two smaller notes

**`structure_hash` does not cover `raise(delay=)` delays**, although it does cover `after` delays (`_node_shape` includes `"after"` but excludes action params by design). Changing `delay: 60000` to `delay: 100` leaves the hash byte-identical, so a v3 snapshot carrying a 60,000 ms armed send restores against a chart that now means 100 ms with the drift check silent. Now that delays are *persisted*, they are arguably part of the shape the fingerprint is meant to pin. Filed as a Low.

**`SimulatedClock` does not fire restored `scheduled_sends`** (nor `after`). A 1000 ms `raise(delay=)` persists correctly as `remaining_ms: 1000.0`, but `clock.increment(2.0)` plus a pump leaves the machine parked. We verified the real-clock property 300/300, so this is a test-ergonomics gap rather than a correctness one — but it means callers cannot unit-test restored deadlines under virtual time, which is precisely what they will reach for after adopting v3.

## Interaction worth flagging

#213 makes `raise(delay=)` the only restart-safe in-chart deadline primitive, since `after` deadlines are deliberately not persisted (#128). Combined with the `_timer_handles` retention we filed separately, that means the recommended path to snapshot-safe deadlines is currently also the one that leaks a timer handle per beat. The two fixes are independent and both small, but together they decide whether in-chart deadlines are usable in a long-lived process.
