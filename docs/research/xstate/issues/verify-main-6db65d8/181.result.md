# #181 — VERIFY on main @ 6db65d8

## Classification: FIXED-OPT-IN

`children_timeout` is a keyword argument on `start()` with a default
(`DEFAULT_CHILDREN_TIMEOUT = 2.0s`), so the bound applies by default — but it
is only effective when the slow bring-up work is genuinely awaited
(`async def` entry action). A blocking `def` entry action (`time.sleep`)
still holds the event-loop thread for its full duration and cannot be
preempted by any asyncio-level timeout — this is the same, separately
documented, blocking-`def` limitation as #149, not a residual of #181.
Classifying FIXED-OPT-IN because the default value already bounds the
realistic (async) case; `None` opts out for an unbounded wait if desired.

## Root cause of fix (file:line)

`src/xstate_statemachine/interpreter.py`:
- `DEFAULT_CHILDREN_TIMEOUT: float = 2.0` (~L219).
- `start(self, *, children_timeout: Optional[float] = DEFAULT_CHILDREN_TIMEOUT)`
  (~L466), documented at L476-484: bounds the wait for the initial
  configuration's invoked-child bring-up; `None` waits unbounded; on timeout a
  WARNING is logged and `start()` returns with the interpreter running, child
  addressable once its bring-up completes.
- `await self._await_actor_bringups(timeout=children_timeout)` (~L601) — the
  call site that plumbs the bound into the previously-unbounded
  `asyncio.gather`.
- `docs/api/index.md:701` documents the same contract.

## Residual

None within scope of #181. The blocking-`def`-entry-action case is a known,
separately-tracked and documented limitation (services/actions written as
plain blocking `def` hold the event-loop thread — see #149's rationale for
running plain services off-thread via an executor; the same treatment is not
applied to entry *actions*, which the CHANGELOG and docs do not claim). This
does not defeat #181's own acceptance criteria, which are stated in terms of
`async def` entry actions (the documented recommended style) and are met.
