# #174 verification — main @ 6db65d8

## Classification: DOCUMENTED-ONLY (code unchanged; behaviour re-characterised as by-design)

## Whether code changed
**No functional code change for the plain-`def` service lateness case.**
Confirmed by direct measurement against `main` @ `6db65d8`:

```
after:100 fired at 528 ms (budget 100ms, plain-def service 500ms in flight)
```
A `def` service occupying the executor still delays a same-machine `after`
timer to roughly the service's own duration — the exact behaviour #174
reported as a regression. `git diff 221ce7c..HEAD -- src/` shows no change
to the timer/settle-budget/executor code that would alter this.

What DID change is the `async def` case, as a side effect of the round-7
`_publish_completion`/priority-lane rework (#179 et al.), not a #174-targeted
fix:
```
after:100 fired at 127 ms (async def service in flight)
```
An `async def` service no longer starves the event loop the way a `def`
service occupying a thread-pool slot does, so its `after` timer fires close
to on time. This matches the CHANGELOG's own framing under "#174 re-measured
on the fixed tree" — 0–1 ms late for busy-loop/busy-machine scenarios, and
"the plain-`def`-service case is unchanged and documented; `async def` — now
budget-safe — is the documented remedy".

## Documentation change
`CHANGELOG.md` "Changed" section (~line 165): "Production Characteristics
documents that a plain-`def` service blocks its own machine's `after` timers
for its whole duration (#174) ... make the service a coroutine if a timer
must interrupt it — and that the `maxIterations` settle budget bounds
microsteps, not wall-clock lateness." This is a documentation-of-limitation
change, not a fix to the plain-`def` lateness itself.

## Verdict rationale
- The busy-loop / `maxIterations`-microstep lateness scenario the original
  #174 report emphasised (`AfterEvent` timestamps + iteration-budget
  interaction) is genuinely improved per the CHANGELOG's re-measurement
  (0–1 ms), consistent with the round-7 completion-accounting rework.
- The plain-`def`-service-blocks-`after` scenario (the "second, independent
  probe" in the original issue body) is **unchanged in code** — reproduced
  above at ~528 ms, essentially identical to the ~500-600ms class reported
  originally — and is now explicitly documented as expected/by-design
  rather than fixed.
- Net: no source-level fix for the plain-`def` case; the issue is resolved
  by re-scoping expectations in documentation, hence DOCUMENTED-ONLY rather
  than FIXED or NOT-FIXED.

## Residual
Anyone relying on `after` as a hard latency bound alongside a plain-`def`
service still needs the documented mitigation (use `async def`, or drive
timing from an external monotonic scheduler, as the reporter had already
done in their own system).
