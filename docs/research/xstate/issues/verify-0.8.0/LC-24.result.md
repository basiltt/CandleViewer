# LC-24 — pending queue lost on crash — Verification on 0.8.0

## Classification: **FIXED-DEFAULT** (new observability/durability API), with
the pre-existing `stop()` discard-by-default behaviour intentionally kept
and now logged (documented as `stop(drain=True)` opt-in for the discard
itself; the *visibility/inspection* half of the issue is unconditional).

## Fix location

- CHANGELOG: "**[wave 2] Inbox durability** (#47), both engines:
  `interpreter.pending_events` (accepted-but-unprocessed, FIFO),
  `drain_pending()` (remove without processing), `stop(drain=True)`
  (process to empty; async engine also takes `timeout=`). Snapshots carry
  `pending_events` and restore re-enqueues them, recursively for child
  actors."
- `src/xstate_statemachine/base_interpreter.py`: `pending_events` property
  (`:1368`), `_snapshot_pending_events` (`:1374`), snapshot dict now
  includes `"pending_events"` (`:970`), `from_snapshot` re-enqueues them
  (`:1196`).
- `src/xstate_statemachine/interpreter.py`: `drain_pending()` (`:973`),
  `stop(*, drain=False, timeout=None)` (`:416`), warning log when `stop()`
  discards a non-empty queue (`:456-462`).
- `src/xstate_statemachine/sync_interpreter.py`: analogous
  `_snapshot_pending_events` (`:533`) and warning (`:367`).

## Residual gap

- Recursive child-actor `pending_events` capture was not independently
  exercised in this verification pass.
- The original repro script is now stale (it predates the fix and asserts
  against 0.7.0 shape); it should be updated to check for the
  `pending_events` snapshot key and to call `stop(drain=True)` /
  `drain_pending()`, at which point it would pass. Not modifying the
  original per instructions — flagging via the follow-up comment below
  instead.
- `stop()` (no `drain=True`) by design still discards a non-empty queue; it
  now warns loudly, which closes the "silent" half of the original
  complaint but not the "lost" half — that is a deliberate default (matches
  0.7.x semantics) requiring `drain=True` to change.

## Recommended CandleViewer constraint

- **MUST** call `interpreter.stop(drain=True, timeout=<bounded>)` (or
  explicitly `drain_pending()` + persist) on every graceful shutdown path
  in the OMS order machine and any machine handling exchange fills, so a
  planned shutdown never silently drops an accepted-but-unprocessed fill
  event. `timeout=` should be set to a bounded value appropriate to the
  machine's SLA rather than left `None` (unbounded) on a shutdown path with
  a deadline.
- **MUST** persist `pending_events` as part of every `get_snapshot()` call
  used for crash recovery (this is automatic in 0.8.0 — no action needed
  beyond upgrading), and rely on `from_snapshot`'s automatic re-enqueue on
  restart.
- **SHOULD** treat a "non-empty queue on stop()" warning log line as an
  alerting signal in production, since it now indicates a shutdown path
  that should have used `drain=True`.

## Draft follow-up comment for GitHub issue #47

> Verified against 0.8.0. `pending_events`, `drain_pending()`,
> `stop(drain=True, timeout=)`, and the `pending_events` snapshot field all
> exist and behave as specified in this issue's acceptance criteria — FIFO
> order, snapshot round-trip, drain-to-empty. This closes the
> **observability/durability capability** gap completely: an embedder can
> now always see and persist what is pending. The **default** `stop()`
> behaviour (no `drain=True`) intentionally still discards a non-empty
> queue, now with a warning log instead of silence — please confirm this
> is the intended permanent default rather than a transitional one, since
> teams that don't audit every shutdown path for `drain=True` will keep
> losing events, just loudly instead of silently. Consider whether
> `stop()`'s default should eventually flip in a future major version, the
> same way `actionErrorPolicy` is slated to flip to `"rollback"` in 1.0.
