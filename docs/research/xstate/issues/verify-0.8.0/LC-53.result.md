**Classification: FIXED-DEFAULT** — no option needed; the docs page ships and is linked by default in every 0.8.0 install.

## Summary

CHANGELOG `[0.8.0]` wave 2 entry: *"Docs: Production Characteristics (#53, #56) — a new guide page with measured numbers for the per-process throughput budget, `after` timer lateness under load, and the `SyncInterpreter` threading contract, plus `benchmarks/production_characteristics.py` to reproduce them."* This is a pure documentation fix — no flag, no policy, active for every user who reads the shipped docs.

As a bonus, 0.8.0 also changed the underlying behaviour the docs describe: wave 3's injectable `Clock` removed the background-thread timer implementation from `SyncInterpreter` entirely (`after` timers now fire on the calling thread inside `send()`/`tick()`), so criterion (2) of the original issue — "SyncInterpreter timers mutate context from an unlocked background thread" — is now also **moot as a live bug**, though the docs still correctly describe the residual concurrency model (only non-blocking `spawn_<key>` children still use a background thread).

## Residual gap

None against the issue's acceptance criteria. One item is worth flagging for CandleViewer's own risk register even though it's not a criterion of this issue: the docs now correctly state that throughput improved from ~20k to ~30k trivial ev/s per process (wave 3 fast-path work) and `after` lateness at 500 busy machines improved from ~2,250 ms (0.7.0) to ~63 ms → ~46 ms (0.8.0, per the wave-3 CHANGELOG entry) — a large improvement, but the budget is still a *fixed per-process* number, not per-machine, and CandleViewer sizing must still treat it that way.

## Recommended CandleViewer constraint

- No code change required to consume this fix — it is documentation + an already-applied perf/behaviour improvement.
- Continue to treat per-process event throughput (~30k trivial ev/s at 0.8.0, verify on target hardware) and `after` timer lateness under load as *shared, fixed budgets across all interpreters in one process* when sizing CandleViewer's machine count per process; do not assume horizontal scaling by adding more interpreters to the same process.
- If CandleViewer relied on `SyncInterpreter` "after" timers running on a background thread (e.g. assumed isolation from the calling thread), re-audit: 0.8.0 changed this so timers now fire on the thread that calls `send()`/`tick()` — this is a *behavioural* change from 0.7.0 that happens to remove the LC-53 concern but could itself affect code that depended on the old (buggy) background-thread behavior. Recommend testing any `SyncInterpreter` + `after` code paths against 0.8.0 directly.
