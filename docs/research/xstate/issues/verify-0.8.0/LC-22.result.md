# LC-22 — `from_snapshot` context wholesale — Verification on 0.8.0

## Classification: **FIXED-DEFAULT**

The aliasing and schema-drift merge behaviour described in LC-22 is fixed
unconditionally in `from_snapshot` — no opt-in flag controls the merge/copy
itself. (0.8.0 does add a *separate*, related default-on guard —
`verify_machine_hash=True`, from #45 — that refuses to restore into a
structurally different machine at all unless the caller passes
`verify_machine_hash=False`. That guard is a good thing for accidental
drift, and CandleViewer must call the escape hatch deliberately for known
schema migrations; see "Recommended CandleViewer constraint" below.)

## Fix location

- `src/xstate_statemachine/base_interpreter.py::from_snapshot` — CHANGELOG
  line: "`from_snapshot` deep-copies the persisted context and merges it
  over the machine's defaults instead of aliasing the caller's dict (#46)."
- Also new in 0.8.0: `persistence.py::check_identity` raises
  `SnapshotDriftError` when `machine_hash` differs, unless
  `verify_machine_hash=False` is passed. This runs *before* the context
  merge and is why our verification script (and the original repro) must
  pass that flag to reach the code path LC-22 is about.

## Residual gap

- `SyncInterpreter` and recursive child-actor restore were not independently
  re-verified in this pass (async engine only). Given both interpreters
  share `base_interpreter.py::from_snapshot`, and the recursive child-actor
  path (`:937` in the original 0.7.0 line numbering) calls the same method,
  this is very likely also fixed, but "very likely" is not "verified" —
  flagged as a small residual gap, not a defect.
- New tests under `tests/test_persistence_context_merge.py` were not
  independently confirmed to exist/pass in this session.

## Recommended CandleViewer constraint

- **MUST** treat `from_snapshot`'s default `verify_machine_hash=True` as a
  deliberate schema-migration gate, not an obstacle to route around
  reflexively. When restoring a snapshot written by an older release across
  a **known-compatible** context-schema change, pass
  `verify_machine_hash=False` explicitly at the call site (never blanket-
  disable it), and log that the escape hatch was used so drift is still
  observable in ops.
- No further mitigation is needed for the aliasing/merge defect itself —
  it is fixed unconditionally.
