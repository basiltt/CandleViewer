# LC-12 — `spawn_blocking_<key>` silently ignored by async Interpreter

**Classification: FIXED-DEFAULT**

CHANGELOG [0.8.0][wave 2] (#41): "`spawn_blocking_<key>` on the async
`Interpreter` honoured only the `spawn_` half and ran non-blocking. Both
engines now wait for the child to reach a terminal status before the
parent's next action; the sync engine also waits out a child driven by
`after` timers, which it previously did not." Also adds the
`spawnBlockingTimeout` machine key (default 30 s) bounding the wait so a
never-terminating child cannot wedge the parent forever.

No opt-in flag needed — this is default behaviour on both engines as of
0.8.0.

## Why the *original* repro still exits 1 (and why that's not a regression)

The original repro's child action is a **synchronous `time.sleep(0.25)`
inside an `entry` action**, not an invoked/awaited service. On the async
engine a synchronous sleep blocks the single event-loop thread for its
whole duration *regardless* of spawn mode, because `await
child_interpreter.start()` runs the child's `entry` actions synchronously
in-line before yielding control back. That is why the original repro shows
`spawn_worker` also taking ~251 ms on the async engine — the repro's own
test design cannot distinguish blocking from non-blocking on the async
engine at all (both look "slow"), which is exactly the ambiguity called out
in the original issue text itself: *"the async engine only looks blocking
here because the child's entry action is a synchronous time.sleep occupying
the event-loop thread ... The defect is the loss of the distinction, not
the measured duration."*

The new verification script (`verify-0.8.0/LC-12_spawn-blocking-async-engine.py`)
fixes this by using a genuinely asynchronous invoked service
(`await asyncio.sleep(...)`), which lets the async engine's non-blocking
path actually return control to the parent immediately. With that change:

```
OBSERVED async spawn_worker           start_blocked_ms=     1 actors_after_spawn=1
OBSERVED async spawn_blocking_worker  start_blocked_ms=   263 actors_after_spawn=0
OBSERVED sync  spawn_worker           start_blocked_ms=     1 actors_after_spawn=1
OBSERVED sync  spawn_blocking_worker  start_blocked_ms=   251 actors_after_spawn=0
OBSERVED async distinguishes spawn_ vs spawn_blocking_: True (1 ms vs 263 ms)
OBSERVED sync  distinguishes spawn_ vs spawn_blocking_: True (1 ms vs 251 ms)
exit=0
```

Both engines now correctly distinguish blocking from non-blocking spawn.

## Recommended CandleViewer constraint

None required — default behaviour is now correct. If CandleViewer relies on
`spawn_blocking_<leg>` semantics, no `spawnBlockingTimeout` override is
needed unless a leg machine can legitimately take longer than 30 s to reach
a final state, in which case set `spawnBlockingTimeout` explicitly on that
machine.
