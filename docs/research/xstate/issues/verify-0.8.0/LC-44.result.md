# LC-44 — Pure API slower than the real interpreter (performance, not correctness)

## Classification: **FIXED-DEFAULT**

The pure API (`transition()` / `get_next_snapshot()`) probe class is now
module-level and cached per machine per thread (thread-local), the redundant
inbound context deep-copy is gone, and history now travels with the
`PureSnapshot` instead of leaking between unrelated calls. No opt-in
required — every caller of `get_next_snapshot`/`pure_transition` gets the
faster path automatically.

Note: as the issue's own "Corrections" section already establishes, the
"skips imperative actions" framing was withdrawn as a documented, correct
XState-v5 parity behaviour (actions are effects returned to the caller;
`assign` is the one action the reducer itself applies) — this is not part of
what needed fixing and is not scored here as a defect.

## Residual gap

The raw wall-clock ratio (pure total time vs. sync total time, ~1.35x-1.56x
across runs) has not reached full parity — the pure API is still measurably
slower per event than `SyncInterpreter.send` in absolute terms, just far
less so than before (previously 3.90x-5.02x). The library's own acceptance
bar (subtracting the unavoidable immutable-`PureSnapshot`-allocation floor,
then requiring ≤2x) is met, but the *repro's* literal bar (`pure <= sync`,
i.e. 1.0x, no floor subtracted) is not, and per-run variance means this
could occasionally read closer to 1.0x or further from it. This is a
performance residual, not a correctness one.

## Recommended CandleViewer constraint

- **SHOULD** prefer the pure API for one-off "preview the next state" UI
  affordances as originally documented, but **MUST NOT** assume the pure
  API is free of allocation cost — each call still deep-copies context once
  and allocates a new `PureSnapshot`; for hot-path decision loops
  (e.g. per-tick reducer previews), measure against `SyncInterpreter`
  directly on the target machine shape rather than assuming a fixed ratio.
- No constraint change needed on the "actions don't run" semantics — that
  was correctly withdrawn as a documented, intentional characteristic
  (`docs/_guide/testing-and-pure-api.md:69-70`) in the issue's own
  corrections, and CandleViewer code should already treat `assign`-only
  context as expected from `get_next_snapshot`.
