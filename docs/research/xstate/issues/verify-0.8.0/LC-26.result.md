# LC-26 — `after` timer starvation under event-loop load — Verification on 0.8.0

## Classification: **FIXED-DEFAULT**

`RealClock` (the unconditional default clock for both engines as of 0.8.0)
delivers a fired `after` timer through a priority lane the async run loop
checks ahead of the inbox. No flag is required — this is simply how timers
now work.

## Fix location

- CHANGELOG: "**[wave 3] Injectable `Clock`** (#48, #49, #50) ... `RealClock`
  now delivers a fired `after` timer through a priority lane the async run
  loop checks ahead of the inbox, so a due timer can no longer be starved
  behind a burst of external events; `AfterEvent` gains `scheduled_for`,
  `fired_at`, and `lateness_ms`."
- `src/xstate_statemachine/clock.py::RealClock` — wall-clock via
  `loop.call_later` (async) / deadline heap + `pump()` (sync, no thread).
- `src/xstate_statemachine/interpreter.py:1622-1641` — fired timer goes into
  the priority lane; `AfterEvent._replace(fired_at=self.clock.now())`.
- `src/xstate_statemachine/events.py:155-200` — `AfterEvent.scheduled_for`,
  `.fired_at`, `.lateness_ms` property.

## Residual gap

- `SyncInterpreter`'s side of the priority-lane fix (it uses `pump()` /
  `tick()` rather than an async priority lane) was not independently
  load-tested in this pass — only the async `Interpreter` was benchmarked.
- New test files under `tests/test_timer_scheduling.py` and the promised
  docs page were not independently confirmed to exist in this session.
- Lateness figures are machine/run dependent (as the original issue notes);
  the ~+22-25ms measured here is well within tolerance but is not a formal
  SLA — no code path currently asserts a documented bound outside this
  repro-derived test.

## Recommended CandleViewer constraint

- No mandatory workaround remains for the core starvation problem — this
  is now fixed by default with no opt-in needed. CandleViewer's execution
  algorithms (TWAP/VWAP slicing, peg re-price timers) can rely on `after`
  under load again, subject to a **SHOULD**: re-run this issue's own
  load-lateness benchmark against CandleViewer's actual busy-interpreter
  count in a soak/perf test before depending on any deadline tighter than
  ~50ms, since the bound is empirical rather than formally guaranteed by
  the library.
