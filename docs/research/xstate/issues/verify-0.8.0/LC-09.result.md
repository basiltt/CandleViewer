# LC-09 — guard exception swallowed — 0.8.0 re-verification

**Classification: FIXED-OPT-IN** (option: `guardErrorPolicy`, default `"false"`
which preserves 0.7.0 semantics for the *transition outcome*, but the
`on_guard_error` observability hook is additive and fires under **every**
policy including the default — so the core "invisible to every observer"
complaint is actually FIXED-DEFAULT, while only the *transition-outcome*
behaviour change requires opting in via `guardErrorPolicy: "true" | "raise"`)

- GitHub: https://github.com/basiltt/xstate-statemachine/issues/35
- Fix landed as `guard_error_policy: "false" | "true" | "raise"` machine
  config (`models.py:1450-1451`, config key `guardErrorPolicy`, default
  `"false"`), applied in `base_interpreter.py:3945-3960`, plus
  `PluginBase.on_guard_error(interpreter, guard_type, event, error)`
  (`plugins.py:247,598`) which fires **unconditionally** whenever a guard
  raises, regardless of policy.

## Note on the original repro's continued failure

The original repro asserts `a != b` where `a`/`b` are dicts containing only
`state`, `raised`, and `plugin` (built from `on_guard_evaluated`, NOT the new
`on_guard_error`). Under the **default** `guardErrorPolicy: "false"`, the
`state`/`raised`/`on_guard_evaluated`-reported-`result` are all still
byte-identical between the `False`-returning guard and the raising guard —
this is intentional per the issue itself (default preserves 0.7.0). The
distinguishing signal (`on_guard_error`) is a **different, new** hook the
0.7.0-era repro script does not listen to. So the original repro correctly
still reports `FAIL`/exits 1 under default settings — it is testing exactly
the axis the fix declines to change by default. It is not evidence of a
regression; it's evidence the repro needs updating to observe
`on_guard_error` to see the fix, which our verify script does.

## Residual gap

  re-verified this pass (criterion 4, sync half).
- Invalid-`guardErrorPolicy`-value rejection at `create_machine()` not

- Interpreter-level override of machine-config policy not tested (criterion 6).
- The original repro script (as filed) will always exit 1 against a

  library defect.

## Recommended CandleViewer constraint

**MUST** attach a plugin (e.g. our `GuardErrorMetrics`-style hook) that
implements `on_guard_error` and increments an alertable counter on EVERY
machine — this closes the "invisible to every observer" half of LC-09 for
free, with no default-behaviour change needed.

**MUST** additionally set `guardErrorPolicy: "true"` on every *allow-polarity*
guard machine (kill-switch, risk-lockout: B18/B20) where `False` means "safe
to proceed" — a crashing `breach_detected` must fail closed (lock out
trading), which requires the guarded (`locked_out`) branch to win, i.e.
`guardErrorPolicy: "true"`. Leave `guardErrorPolicy` at its default `"false"`
for *deny-polarity* guards (`risk_ok`) where `False` is already the safe
direction — matches the issue's own worked kill-switch example verbatim.
