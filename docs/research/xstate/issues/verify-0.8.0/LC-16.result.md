# LC-16 — `sendTo` cannot address an invoked actor by `id`/`systemId`

**Classification: FIXED-DEFAULT**

CHANGELOG [0.8.0] (#40): "`sendTo` can address an invoke by its explicit
`id` and by `systemId`; a duplicate live `systemId` raises
`ActorSpawningError`." No flag required — this is unconditional default
behaviour.

## Residual gap

The "unresolved/ambiguous target raises" criterion (acceptance criterion 5
in the issue, and `test_unresolved_target_raises_in_strict_mode`) was not
independently re-verified in this pass — worth a follow-up check of whether
`strict_actor_targets` (or 0.8.0's general `strict=` machine flag) covers
this specifically for `sendTo`, since 0.8.0's `strict` mode as documented in
the changelog is about *inbound* event validation (`send()` of an unknown
event type), not resolution of a `sendTo` destination. If `sendTo` to an
unresolved id still just logs a warning and drops the event under all
settings, that would be a PARTIAL gap worth flagging upstream.

## Recommended CandleViewer constraint

Use explicit `id` (and `systemId` where cross-actor lookup via `system.get()`
is needed) on every `invoke` a CandleViewer machine expects to address
individually — e.g. `invoke: {"id": "leg-0", "src": "leg", "systemId": "leg-0"}`
per trade-group leg. This closes the reconciliation-break scenario described
in the original issue (an unaddressable leg believed cancelled while still
live on the exchange). CandleViewer should separately confirm whether an
unresolved/ambiguous `sendTo` target now raises under any available flag; if
not, treat "no such actor" as still silently swallowed and add an
application-level assertion after every `sendTo` to a leg id (e.g. check
`interp.pending_invocations()`/actor registry membership before sending) as
a defensive measure.
