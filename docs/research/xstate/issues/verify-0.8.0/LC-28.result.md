# LC-28: actor poll two tasks — 0.8.0 verification

**Classification: FIXED-DEFAULT**

## Summary

CHANGELOG `[0.8.0]` "[wave 2] Invoked child actors no longer poll" (#43):
`_spawn_and_manage_actor` replaced `while status == "running": await
asyncio.sleep(0.005)` with `await child_interpreter.wait_done()`, a future
resolved the instant the child reaches `done`/`error`. `_ACTOR_POLL_INTERVAL`
is removed. This is unconditional — not a policy or opt-in.

## Residual gap

The **mechanism** changed exactly as promised (poll → future, `wait_done()`
exists, latency dropped from a 5ms floor to sub-millisecond) but the **task
count per idle child is still 2**, not the targeted ≤1. Source
(`interpreter.py:_spawn_and_manage_actor`) still does:

```python
child_interpreter = Interpreter(actor_machine, ...)
...
await child_interpreter.start()      # child's own event-loop task (task #1)
...
await child_interpreter.wait_done()  # this coroutine runs inside the task
                                      # asyncio.create_task()'d by _invoke_service
                                      # (task #2) — it no longer POLLS, but the
                                      # task itself is not collapsed away
```

So the "collapse the second task" half of the proposed fix (item 3 in the
issue) was not done — only the "await instead of poll" half (item 2) was.
The result is 2 tasks/child exactly as before, but the second task now
blocks on a future instead of spinning, which eliminates CPU/latency cost
while leaving the memory/task-count cost unchanged.

## Recommended CandleViewer constraint

- Task-count-per-actor sizing plans should still budget **2 asyncio tasks
  per invoked/spawned child actor**, not 1 — the 0.8.0 release notes'
  framing ("parent awaited child.status every 5ms in a second task; it now
  awaits a completion future") describes the *second* task's behaviour
  changing, not its removal.
- The **latency** win is real and can be relied upon: `onDone` propagation
  no longer carries a 5ms-per-nesting-level floor. CandleViewer's
  fill-propagation risk-check concern (issue Impact section) is resolved.
- The **idle CPU / wakeup** concern is resolved: the second task now blocks
  on `await fut` rather than a `sleep()` loop, so it contributes zero
  periodic timer callbacks while idle.
