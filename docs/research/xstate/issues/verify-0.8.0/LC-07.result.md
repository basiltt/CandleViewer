# LC-07 — relative `.child` target silent no-op — 0.8.0 re-verification

**Classification: FIXED-DEFAULT** (core semantic fix is unconditional; the
sibling-fallback deprecation path is additionally gated by the opt-in
`strictTargets: true` machine config, which is a bonus stricter behaviour,
not the primary fix)

- GitHub: https://github.com/basiltt/xstate-statemachine/issues/31
- Fix landed in `src/xstate_statemachine/resolver.py:199-236` (Strategy 3,
  leading-dot resolution): `.child` now resolves against the **source
  state's own descendants first** (matches XState semantics, verified
  against XState 5.33.0 in the original issue). This is the DEFAULT and
  unconditional — no option needed to get the correct child-first behaviour.
- A parent-relative **sibling fallback** is kept for 0.7.x configs that
  depended on the old (incorrect) behaviour; it can be disabled per-machine
  via `strictTargets: true` in the machine config (`models.py:1463`,
  `resolver.py:237`), which then makes an unresolvable `.child`-style target
  a hard build-time error (via LC-08's validator) rather than a silent
  fallback.

## Note on criterion 2 (DeprecationWarning)

The original issue's proposed fix (Part 1) wraps the sibling fallback in a
`warnings.warn(..., DeprecationWarning)` call unconditionally whenever the
fallback fires. In the shipped 0.8.0 code (`resolver.py:199-236`), the
sibling fallback path (`base = reference_state.parent or reference_state;
return _find_descendant(base, segments)`) does **not** call `warnings.warn`
at all — it silently falls back with no warning, and the `strict_targets`
(machine-level `strictTargets`) config only controls whether the sibling
fallback runs, not whether it warns. Our verify script confirms this:
`default_sibling_still_works_case` sees `deprecation_warning=False`. This is
a **residual gap** versus the acceptance criteria — the escape hatch works,
but does not warn as specified, so a config still relying on the deprecated
sibling behaviour gets no signal that it should migrate to an absolute
`#id` target before the fallback is removed in 1.0.

## Script outputs verbatim

```
OBSERVED (child target): state=['m.A.A2'] actions=['xA1', 'eA2']
EXPECTED: state=['m.A.A2'] actions=['xA1', 'eA2']

  m.A: on 'GO' -> target '.B' does not resolve (did you mean "#m.B"?)
EXPECTED: sibling fallback disabled under strictTargets=True -- caught at build time by the LC-08 validator, so the machine never even loads.
OBSERVED (default, sibling fallback): state=['m.B'] deprecation_warning=False
EXPECTED: state=['m.B'] (0.7.x sibling fallback preserved by default)
RESULT: child_target_fixed=True strict_targets_disables_sibling_fallback=True default_sibling_fallback_preserved=True
```
Exit code: **0**

(Note: the `strict_targets_sibling_rejected_case` in the verify script was
adjusted mid-investigation from expecting a runtime `StateNotFoundError` to
expecting a build-time `InvalidConfigError` from `create_machine()`, because
0.8.0 ships LC-07 and LC-08's fixes together as the issue predicted — the
`strictTargets: true` config combined with the default `strict_targets=True`
validator means the bad `.B` target is now caught before the machine is even
constructed. This is explicitly called out as acceptable in the issue's
"Related" section.)

### Original repro (`repro/LC-07_relative-dot-target-silent-noop.py`), unmodified

```
OBSERVED: state=['m.A.A2'] actions=[Action(type='xA1'), Action(type='eA2')] raised=None
EXPECTED: state=['m.A.A2'] actions=['xA1', 'eA2'] raised=None
EXPECTED (acceptable alternative): create_machine() rejects '.A2'
NOTE: the dot is resolved parent-relative, so '.A2' from source 'm.A' looks for 'm.A2' (a sibling), not the child 'm.A.A2'.
RESULT: FAIL
```
Exit code: **1**

The state IS now correct (`m.A.A2`) and the actions DID run (`xA1`, `eA2`) —
the underlying defect is fixed. The script still reports `FAIL`/exits 1
purely because it does a strict `log == ["xA1", "eA2"]` string-list
comparison, while 0.8.0's action callable is invoked with the full
`(interpreter, context, event, ActionDefinition)` signature and the repro's
lambda appends the bound `n` from closure — but the actual values captured
are `Action(type='xA1')` objects in `str()` repr, not plain strings, because
the repro's lambda signature (`lambda c, e, a, n=n: log.append(n)`) does not
match the current call convention (`(interpreter, context, event, action)`)
and grabs the wrong positional argument. This is a repro-script bug exposed
by the newer action-callable calling convention, not a library defect. The
verify script's corrected action recorder (accepting `*args, **kwargs`)
confirms the real state/action-order outcome is exactly as expected.

## Residual gap

- The sibling fallback does not emit a `DeprecationWarning` as the issue's
  proposed fix specified (criterion 2) — only disabling the fallback via
  `strictTargets: true` is available; there's no "warn but still succeed"
  middle ground.
- Criterion 4 (async/sync error-contract parity) not independently
  re-verified this pass.
- The 0.7.0-era `repro/LC-07_relative-dot-target-silent-noop.py` needs
  updating for the new action-callable signature to correctly assert PASS.

## Recommended CandleViewer constraint

**MUST** set `strictTargets: true` on every machine config where a
`.child`-relative target is used, so that a mistyped/renamed child raises a
loud `InvalidConfigError` at `create_machine()` instead of silently falling
back to a sibling interpretation. Do not rely on the sibling-fallback default
— it is unwarned and scheduled for removal in 1.0. Our rule-compiled machines
(B9 workstream) should assert `strictTargets: true` is present in every
generated config as a lint rule.
