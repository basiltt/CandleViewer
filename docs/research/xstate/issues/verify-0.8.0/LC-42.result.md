# LC-42 — `send()` is fire-and-forget, no answer channel

## Classification: **FIXED-DEFAULT** (additive API, default `send()` unchanged)

`send(..., wait=True)` returns a `Receipt` after the macrostep completes;
`send(..., priority=True)` / `send_priority()` jump the backlog. Default
`await interp.send("E")` (no `wait`/`priority`) is byte-for-byte unchanged
from 0.7.0 — returns `None` immediately once queued.

Interesting: the priority API check inside the original repro (`prio = [...]`)
now finds `send_priority`/`_priority_queue` and would not itself have flagged
`ok = False` for that check — the repro's overall `REPRODUCED` verdict is
driven entirely by asserting default (no-`wait`) `send()` transitions
synchronously, which is intentionally still false. This is expected, not a
regression; a maintainer note in the original issue's "corrections" section
already anticipated this (the fix is additive, `wait=True`/`priority=True`
opt-in, not a change to bare `send()`).

## Residual gap

- Reserved-payload-key `DeprecationWarning` and docs page not independently
  re-verified in this pass.
- FIFO-among-priority-events not isolated from the aggregate latency
  measurement.

## Recommended CandleViewer constraint

- **MUST** use `await interp.send(event, wait=True)` (or `send_priority`)
  anywhere the caller needs to know the outcome of an event synchronously
  (kill switches, risk lockouts, "did this fill land" checks) — never poll
  `current_state_ids` in a spin loop as the pre-0.8.0 workaround did.
- **SHOULD** check `receipt.error` explicitly after every `wait=True` send
  in risk-critical code paths; a `None` receipt.error does not mean nothing
  happened elsewhere in the transition (only that the awaited event's own
  action chain did not raise unhandled).
