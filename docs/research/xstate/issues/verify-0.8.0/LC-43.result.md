# LC-43 — Cross-thread `send()` silently lost

## Classification: **PARTIAL** (core fix is FIXED-DEFAULT; one documented workaround pattern regresses)

`send()` from a foreign thread now raises `WrongThreadError` **eagerly, at
the call site** — this is a default, always-on behaviour change (one of the
CHANGELOG's "two deliberate exceptions" to the "defaults preserve 0.7.x
semantics" rule, the other being `send()`/`send_threadsafe()` on a
closed-loop interpreter raising `RuntimeError`). `send_threadsafe()` is the
new, additive, correct cross-thread API and works as specified. However,
the pattern the *original issue itself* documented as "the only correct
form" today — `asyncio.run_coroutine_threadsafe(interp.send(...), loop)` —
is now **broken**: because `send()` does its thread-check eagerly rather
than inside the coroutine body, and `run_coroutine_threadsafe`'s wrapped
callable still evaluates `interp.send(...)` (the call expression, not just
`await`) on the **calling** thread to produce the coroutine/awaitable
object, the eager check fires on the foreign thread and raises
`WrongThreadError` before scheduling ever happens.

## Residual gap

**`asyncio.run_coroutine_threadsafe(interp.send(...), loop)` — a pattern the
original LC-43 issue text explicitly named as "the only correct form" for
0.7.0 — now raises `WrongThreadError` instead of working, because `send()`'s
thread-check runs eagerly on the calling thread before
`run_coroutine_threadsafe` gets a chance to hand the coroutine to the owning
loop.** Any CandleViewer code (or third-party code) that adopted this
documented 0.7.0 workaround will break on upgrade to 0.8.0, with no
deprecation warning — it simply starts raising. This is a real regression
for existing correct callers, distinct from the bug LC-43 originally
described (silent loss). The CHANGELOG does flag "two deliberate
[breaking] exceptions" but does not explicitly enumerate
`run_coroutine_threadsafe(interp.send(...))` as one of them in the text we
read; it is a direct, mechanical consequence of making `send()`'s guard
eager, described only in the `send()` docstring/architecture comment, not
in the user-facing CHANGELOG bullet.

Secondary, smaller residual gap: `send_threadsafe()` on an interpreter that
has been `stop()`ped (but whose asyncio loop is still open, i.e. the common
case) does not raise — it silently returns `None` from
`run_coroutine_threadsafe` scheduling a no-op-ish `_deliver` onto a torn-down
run loop. This does not violate the letter of criterion 5 ("not
AttributeError/None deref") but doesn't affirmatively signal the drop either.

## Recommended CandleViewer constraint

- **MUST NOT** use `asyncio.run_coroutine_threadsafe(interp.send(...), loop)`
  from any CandleViewer code going forward — migrate every such call site to
  `interp.send_threadsafe(...)` before upgrading to 0.8.0. Grep the codebase
  for `run_coroutine_threadsafe` combined with `.send(` before merging the
  upgrade.
- **MUST** wrap any direct cross-thread `send()` call (if any survives in
  legacy code) in a `try/except WrongThreadError` during the transition
  period, or better, remove it entirely in favor of `send_threadsafe()`.
- **SHOULD** add a lint rule or CI grep step that fails a build containing
  `run_coroutine_threadsafe(*.send(` to catch regressions of this pattern.
