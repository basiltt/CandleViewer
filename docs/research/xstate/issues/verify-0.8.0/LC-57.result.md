# LC-57 re-verification on xstate-statemachine 0.8.0

**GitHub:** https://github.com/basiltt/xstate-statemachine/issues/60
**Classification: FIXED-DEFAULT** for the issue's core, user-visible claim (one shared algorithm, no per-engine duplication of the six steps, no renamed forks, LC-58 misclassification fixed) — **PARTIAL** against the issue's literal grouped sub-checklist (a few named tests/APIs from the issue's own implementation *sketch* were not delivered verbatim; the underlying bugs they targeted are fixed by other means, see below).

## Summary

CHANGELOG `[0.8.0]` wave 3: *"One core algorithm, two execution strategies (#60). The step, transition-execution, state-entry/exit, lifecycle-action, and built-in-action logic is now implemented once on `BaseInterpreter`; `SyncInterpreter` inherits it unchanged and drives each coroutine to completion synchronously instead of re-implementing it as a parallel set of plain-`def` methods... an action trace is now pinned byte-identical across both engines by test... functools.partial-wrapped async actions on the sync engine now raise `NotSupportedError` instead of having their coroutine silently discarded."*

This is the fix, and it is a **different implementation of the same acceptance criterion** than the issue's own proposed design. The issue's "Suggested fix" section (lines 181-189) sketched a `core/algorithm.py` sans-io module + `ExecutionStrategy` Protocol. 0.8.0 instead kept the six algorithm steps as `async def` methods directly on `BaseInterpreter` and added `SyncInterpreter._drive()`, which runs each base coroutine to completion with a single `coro.send(None)` (documented at `sync_interpreter.py:90-99`: since none of the base coroutines ever actually suspend, the first `send(None)` always raises `StopIteration` carrying the return value — a drive-to-completion trick, not a thread pool or `asyncio.run`). This is architecturally narrower than "extract a pure core + strategy protocol," but it satisfies the issue's actual, checkable acceptance criterion: **no core step is implemented by both engines, no base async def is shadowed by a same-named sync override, no renamed fork remains, and the sync engine rejects `functools.partial(async_fn)`.** All four of those are the repro's literal assertions and all four now pass.

## Residual gap

1. **LC-52 (`ErrorEvent` rename) did not ship.** `error.platform.*` events are still delivered as `DoneEvent` — a "Done" event that actually signals failure, exactly the naming confusion the issue described. The CHANGELOG's `#52` reference is unrelated (arity auto-registration), so this specific grouped sub-fix appears to have been dropped or deferred past 0.8.0, not merged into a different-named mechanism the way LC-47/58 were.
2. **No dedicated regression test pins the LC-47 target_str non-mutation fix** by the name the issue asked for, though the code fix itself is present and commented.
3. **The architectural ask (separate `core/algorithm.py` + `ExecutionStrategy` Protocol) was not delivered** — 0.8.0 solved "one algorithm, not two" differently (shared async coroutines + a synchronous coroutine-driving trick in `SyncInterpreter._drive()`). Functionally equivalent for the issue's stated purpose (stop silent divergence between engines), but if CandleViewer specifically wanted the pure/testable-without-an-interpreter core the issue proposed, that does not exist as a public surface.
4. CI mypy job presence confirmed; coverage-floor and branch-coverage specifics (LC-61) not independently measured in this pass.

## Recommended CandleViewer constraint

- Safe to drop any workaround CandleViewer had for the two engines silently diverging on the six core steps — this is now structurally enforced (both engines call the same `BaseInterpreter` coroutines; `SyncInterpreter` has no independent implementation of `_process_event`/`_execute_transition`/`_enter_states`/`_exit_states`/`_execute_actions`/`_execute_builtin_action`).
- If CandleViewer ever passed a `functools.partial`-wrapped async action, an object with an async `__call__`, or an async generator as an action implementation to a `SyncInterpreter`, that now raises `NotSupportedError` instead of silently no-op'ing — audit for any such usage before upgrading, since previously-"working" (but silently broken) code paths will now raise.
- **Do not rely on `error.platform.*` events being anything other than a `DoneEvent`** — the type-naming confusion (a failure delivered as "Done") is still present in 0.8.0; keep branching on `event.type.startswith("error.")` / inspecting `.data` for an exception, not on an `ErrorEvent` type that does not exist.
- If CandleViewer needs the pure/sans-io core the issue envisioned (e.g. to unit-test transition selection without spinning up an interpreter), that is not available in 0.8.0 as a public API — file or track separately if it becomes a real need; `tests/test_core_algorithm.py` in the library itself is the closest analogue but it is a private test module, not public API.
