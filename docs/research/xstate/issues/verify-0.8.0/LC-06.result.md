# LC-06 — over-forgiving target resolution — 0.8.0 re-verification

**Classification: FIXED-DEFAULT**

- GitHub: https://github.com/basiltt/xstate-statemachine/issues/34
- Fix landed under: `create_machine(..., strict_targets: bool = True)` (default `True`) +
  build-time `validate_machine()` walk, in `src/xstate_statemachine/validation.py`.
  Runtime resolution (`base_interpreter.py`) still contains the last-segment
  tree-walk fallback, but it is now dead code on the default path because the
  validator rejects the config before an interpreter is ever built.
- Escape hatch: `create_machine(cfg, ..., strict_targets=False)` restores the
  0.7.x fallback-search behaviour, with a `DeprecationWarning` naming every
  finding and the suggested `#id` fix. Per CHANGELOG this hatch is slated for
  removal in 1.0.

## Note on criterion 1 wording

The issue asked for `StateNotFoundError`; 0.8.0 actually raises
`InvalidConfigError` from the build-time validator (`validation.py:211`). This
is a stronger guarantee (rejects at `create_machine()`, not lazily at `send()`)
and is fully in the spirit of the acceptance criterion, but the exact
exception type named in the issue is not what's raised. Not a residual gap —
just a naming mismatch worth flagging to the filer.

## Note on the opt-in fallback (criterion 2 / 4)

Somewhat surprisingly, even with `strict_targets=False` the interpreter does
**not** bind the foreign `m.audit.archive.filled` node at runtime in the 0.8.0
build — `order.submitting` stays `submitting` and `audit` stays at
`archive.open` (see verify script output: `bound_foreign_state=False`). This
is because `validate_machine()` runs `resolve_strict()` unconditionally to
memoize `TransitionDefinition.resolved_target` even when `strict_targets=False`
only emits a warning rather than raising — and `resolve_strict` does not
include the last-segment tree-walk fallback. So the last-segment
fallback (`base_interpreter.py`'s Fallback 2/3) appears to now be entirely
bypassed by the runtime once a transition has been build-time-validated
(whether it resolved or not), which is a bonus improvement beyond what the
issue asked for. This should be treated as an *undocumented* behavioural
detail, not something CandleViewer should rely on without a matching
regression test in the library, since the docstring for `strict_targets=False`
still describes it as "restoring 0.7.x behaviour."

## Residual gap

- Criterion 5 (ambiguous last-segment match raises) not independently
  re-verified.
- Exception type is `InvalidConfigError`, not `StateNotFoundError` as the
  issue specified.
- The original repro script needs a one-line update (catch `InvalidConfigError`
  from `create_machine()` and treat that as PASS) to reflect the new contract;
  it currently still "fails" by crashing, which is arguably the correct
  terminal state but is not machine-checkable as written.

## Recommended CandleViewer constraint

**MUST** rely on the default `strict_targets=True` on every `create_machine()`
call (do not pass `strict_targets=False`). This closes LC-06 for our OMS
machines: an unrelated leaf name (`filled`, `cancelled`, `failed`) reused
across parallel regions can no longer be silently bound by a typo'd/refactored
`target`. No CandleViewer-side workaround (our former house-rule build-time
target validator) is required for this issue any more, though we should still
add a CI assertion that no machine construction anywhere in the codebase
passes `strict_targets=False`.
