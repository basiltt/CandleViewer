# LC-38 — Re-evaluation on xstate-statemachine 0.8.0

**Classification: FIXED-DEFAULT**

Fix location: CHANGELOG `[0.8.0] Added — Injectable Clock (#48, #49, #50)` plus
the `[wave 3]` "One core algorithm, two execution strategies" refactor.
`src/xstate_statemachine/sync_interpreter.py` no longer starts
`threading.Thread` for `after` timers; comment at `:193`: `"Timers no longer
own threads; see _after_timer."` A `Clock` protocol (`clock.py`) with
`RealClock`/`SimulatedClock` is now injectable, and `tick()` (`:1095`) is the
explicit seam for delivering elapsed timers on the caller's thread. This is
unconditional default behaviour (default `clock=RealClock()`), not an opt-in
policy — the thread-per-timer architecture was removed outright, matching
option 1 from the issue's three proposed remedies ("scheduled but only
delivered when the caller pumps the machine").

## Option needed

None for the core fix (no more background threads by default). The only
constructor knob is `clock=` (defaults to `RealClock`); passing
`SimulatedClock()` is for deterministic tests, not required for the
thread-safety fix itself.

The original repro's part 1 (state must not advance from a bare sleep, no
mutating background thread) now holds. Part 2 (lost-update race under
concurrent `send()` + timers) did not trigger even in the 0.7.0 baseline per
the issue's own verification notes ("Part 2 (lost update) did not trigger, as
the issue text already states"), so its passing here is not new evidence
either way for that specific race, but the primary defect (background thread
mutating state with no pump) is resolved.

## Residual gap

Re-entrancy-under-load (`test_timer_event_not_dropped_when_queue_is_busy`) and
the 1000-iteration stress test were not independently re-run in this pass —
recommend a follow-up pass specifically targeting concurrent `send()` +
`tick()` calls if CandleViewer's OMS drives `SyncInterpreter` from more than
one thread (which the fixed architecture no longer expects to be safe/needed,
since everything is meant to run on the caller's thread now).

## Recommended CandleViewer constraint

- MUST call `SyncInterpreter` methods (`send`, `tick`, `start`, `stop`) only
  from a single owning thread — the library's contract is now "no internal
  threads, no internal locks," so thread-safety is entirely the caller's
  responsibility if multiple threads must reach the same interpreter (use
  `Interpreter.send_threadsafe()` on the async engine instead, or your own
  lock around `SyncInterpreter` calls).
- SHOULD call `tick()` on a schedule (e.g. driven by a single timer/loop) if
  `after` timers must fire promptly without waiting for the next external
  event.
