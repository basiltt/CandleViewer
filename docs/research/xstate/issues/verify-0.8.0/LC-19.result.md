# LC-19 — restore does not restart invokes; parked machines report `running`

**Classification: FIXED-OPT-IN** — option `Interpreter.from_snapshot(..., restart_services=True)`, default `False` (preserves 0.7.x static-restore behaviour). The unconditional `pending_invocations()` inspection API is a **FIXED-DEFAULT** addition (always available, no flag).

CHANGELOG [0.8.0][wave 3] (#44): "`from_snapshot(restart_services=True)` and
`pending_invocations()` — restoring a snapshot is still a static rebuild
that starts nothing by default, but `pending_invocations()` now lists every
`PendingInvocation(state_id, invoke_id, src)` in the active configuration
with no live service or child actor, and `restart_services=True` re-invokes
each of them from scratch (not resumed) through the same path
`_enter_states` uses on both engines."

## Residual gap

- `status` still reports `"running"` for a parked default-restored machine
  with no qualification distinguishing "genuinely live" from "statically
  restored, services dormant" — the issue's proposed fix suggested this as
  a nice-to-have ("Consider also making `status` reflect it...") but it was
  not a hard acceptance criterion. `pending_invocations()` is the correct
  way to detect this today; CandleViewer's health checks MUST call it
  rather than trust `status` alone.
- Task-cancellation-on-exit for restarted invokes not independently
  verified in this pass.
- Sync-engine parity not independently verified in this pass.

## Recommended CandleViewer constraint

- MUST call `Interpreter.from_snapshot(blob, machine, restart_services=True)`
  when restoring any CandleViewer machine that has a live `invoke` in its
  restored configuration — order, reconciliation, and TWAP machines all
  qualify per the issue's own impact analysis.
- MUST design every re-invoked service (order placement, exchange sweep,
  slicing) to be idempotent (e.g. client-supplied idempotency key), since
  `restart_services=True` re-invokes from scratch, not resumed.
- MUST NOT rely on `interpreter.status == "running"` alone as a liveness
  signal after restore; check `pending_invocations()` is empty as well.
- Recommended: call `pending_invocations()` immediately after every restore
  (even with `restart_services=True`) as a boot-time assertion that nothing
  was missed, and drop the current hand-rolled "walk every machine, hard-code
  which states have invokes" boot procedure described in the issue — it can
  now be replaced entirely by `restart_services=True` + `pending_invocations()`.
