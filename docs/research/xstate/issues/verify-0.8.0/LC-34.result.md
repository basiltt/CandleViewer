# LC-34: no strict mode — 0.8.0 verification

**Classification: FIXED-OPT-IN** (option: `strict=True` on `create_machine`/
machine config, or `Interpreter(..., strict=True)` / `SyncInterpreter(...,
strict=True)`; **default is `strict` unset → `False`**, preserving 0.7.x
silent no-op semantics for undeclared event types)

## Summary

CHANGELOG `[0.8.0]` "[wave 3] Strict mode" (#51): `strict` machine config
key or `Interpreter`/`SyncInterpreter(strict=)` constructor flag (ctor
wins). Under strict, `send()` of an event type the machine never declared
raises `UnknownEventError` synchronously at the call site, before queueing,
with a difflib suggestion. `MachineNode.is_known_event()` honours partial
(`'mouse.*'`) and bare `'*'` descriptors. `create_machine(event_schemas=
{'FILL': Fill})` adds opt-in payload validation via `InvalidEventPayloadError`,
**regardless of the strict setting**. Default (strict unset, no schemas) is
explicitly unchanged.

## Residual gap

None for the acceptance criteria actually re-tested. This is a genuine
`FIXED-OPT-IN`: default behaviour is unchanged (typo'd events remain silent
no-ops unless the caller opts into `strict=True`), and the opt-in itself
delivers on every re-tested criterion (raises `UnknownEventError` with a
"Did you mean" suggestion, `event_schemas` validates payloads independent
of `strict`). Criteria this pass did not re-verify (wildcard/partial
descriptors, internal `raise`, `after`/`invoke` event allowlisting, sync
engine) are plausible-but-unverified based on source presence
(`base_interpreter.py:1466` `_check_strict`, called from both the public
`send()` path and the internal-raise path at `base_interpreter.py:2555`).

This exits 0 ("NOT REPRODUCED") because the repro itself checked for the
*absence* of a `strict` capability and its default-mode behavioural probes
(without opting in) — it never actually tries `strict=True`, so it correctly
reports the feature now exists but doesn't validate the opt-in path itself.
The new verify script fills that gap by exercising `strict=True` directly.

## Recommended CandleViewer constraint

- **MUST set `Interpreter(machine, strict=True)` (or the `strict: true`
  machine-config key) on every order/leg machine.** Given events here are
  commands with money attached (`FILL`, `CANCEL`, `REJECT`, `AMEND`), the
  default `strict=False` (silent no-op on a typo) is exactly the worst
  failure mode the issue describes and remains the out-of-the-box
  behaviour.
- **SHOULD register `event_schemas` for every command event** with a
  numeric/typed payload (e.g. `{"FILL": FillSchema}`) — this validation is
  independent of `strict` and closes the "a type error introduced at the
  boundary surfaces much later inside an action" gap regardless of the
  strict setting.
- Retire the hand-rolled `MachineGateway` closed-enumeration wrapper
  described in the issue's "current workaround" section once `strict=True`
  + `event_schemas` are adopted — the library's `known_events` set is now
  authoritative and derived from the same config the gateway had to
  hand-mirror.
- Because `strict` covers internal sends (`raise`, `sendTo`, `sendParent`,
  `forwardTo`) per the CHANGELOG description, verify this explicitly in a
  follow-up test before relying on it for machine-of-machines designs (not
  re-tested in this verification pass).
