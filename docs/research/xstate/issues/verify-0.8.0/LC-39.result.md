## Original repro (`repro/LC-39_throughput-global-budget.py`)

Exit code: **1** — this is the **expected, correct** result per the issue's
own acceptance criteria ("note that it exits 1 *by design* while the
behaviour stands"). Verbatim run against 0.8.0:

```
OBSERVED: N=1    aggregate=  347,029 ev/s   per-machine=347,029.4 ev/s
OBSERVED: N=10   aggregate=  341,924 ev/s   per-machine= 34,192.4 ev/s
OBSERVED: N=100  aggregate=  323,608 ev/s   per-machine=  3,236.1 ev/s
OBSERVED: N=500  aggregate=  292,146 ev/s   per-machine=    584.3 ev/s
OBSERVED: aggregate scaling factor from N=1 to N=500 = 0.84x (per-machine share fell 594x)
EXPECTED (naive reading of the docs): aggregate throughput grows with N, or the docs state plainly that it does not.
```

Aggregate throughput remains flat (~0.84x from N=1 to N=500, essentially the
same shape as the 0.7.0 baseline, ~300k ev/s vs ~33k ev/s previously — this
machine happens to be faster, but the *flatness* is unchanged), confirming
the single-event-loop architecture is unchanged, as intended. The library
README now also directly quotes this budget concept and links to the
production-characteristics page.

  OS processes, exactly as the issue's original "CandleViewer trading OMS"
