## Summary

A `SyncInterpreter` invoking a child **machine** whose own inner service raises never delivers `onError` to the parent. The parent stays in the invoking state with `status='running'` and `error=None`, and never learns the child failed.

The async engine handles this correctly (`interpreter.py:2028`, `_deliver_invoked_completion` with `status == "error"`).

**This is pre-existing, not introduced by PR #83** — the sync `_invoke_service` changes in that commit are pure `DoneEvent` → `ErrorEvent` renames, and baseline comparison confirms identical behaviour before and after. It is raised now because #80's stated scope is *"service and child-actor failures"*, the new `test_actor_perf.py::TestErrorEvent::test_child_machine_failure_delivers_error_event` covers only the async engine, and engine parity is claimed elsewhere in the release notes.

## Environment

- `xstate-statemachine`, `main` @ `3c527b0` (merge of PR #83). `__version__` reports `0.8.0`.
- CPython 3.13.7, Windows 11 x64 (10.0.26200)

## Minimal reproduction

A `SyncInterpreter` on a parent that invokes a child machine; the child's own service raises. Full script: `g16_sync_child_failure.py`. Async control: `g8_unhandled_child_failure.py` case C (reaches `p.bad`).

## Observed

```
parent state : {'p.w'}
parent status: running   error: None
onError event seen: []
```

The parent is stuck, silently, forever.

## Related, also pre-existing

An invoked **child machine** that fails with **no** `onError` handler leaves the parent at `status='running', error=None`, whereas a failing **callable** service correctly calls `_fail()` and the parent reaches `status='error'`. The `_has_error_handler` / `_fail` escalation applied to callable services at `interpreter.py:1824` has no counterpart in `_deliver_invoked_completion`. See `g8_unhandled_child_failure.py` cases A vs B. Confirmed identical on both commits.

## Expected

1. `SyncInterpreter` delivers `ErrorEvent` to the parent's `onError` for a failed invoked child machine, with the same shape as the async engine.
2. With no `onError` handler declared, a failed invoked child machine escalates to the parent's failure path the same way a failed callable service does — on both engines.

## Acceptance criteria

1. `g16_sync_child_failure.py` shows the parent reaching the `onError` target with an `ErrorEvent`.
2. A parity test exercising both engines on the same parent/child pair produces the same state, status and event class.
3. `test_child_machine_failure_delivers_error_event` is parameterised over both engines.
4. The unhandled case (no `onError`) is decided and documented: either both engines escalate, or both park, but not one of each.
