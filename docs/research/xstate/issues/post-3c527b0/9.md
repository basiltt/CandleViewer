## Summary

`create_machine()` writes resolved aliases **back into the registry dict the
caller owns**. `MachineLogic.__init__` copies the caller's input mapping, but
the `MachineLogic` *instance* is shared whenever it is reused across machines —
a documented pattern (module-level logic, `logic_modules`).

Aliases therefore accumulate on that shared registry from every machine built
against it, with three silent consequences.

## Environment

- Library: `xstate-statemachine`, local clone, `main` @ commit `3c527b0`, `pip install -e .`
- Python: 3.13.7 (CPython) · Windows 11 x64 (10.0.26200)

## Location

`src/xstate_statemachine/factory.py:212`, `:241-258` (`_alias_logic_names`);
`src/xstate_statemachine/machine_logic.py:158-186` (`resolve_aliases` —
`registry[name] = registry[candidates[0]]`).

## Minimal reproduction

`g1b_alias_ambiguity_and_leak.py` (part 2), `f_shared_logic.py`,
`f_pollute.py`.

## Observed

**1 — the registry grows keys nobody registered.**

```
registry before build 1 : ['fetch_data']
registry after  build 1 : ['fetchData', 'fetch_data']   <- injected by create_machine
```

```
after m1, keys: ['storeUser', 'store_user']
after m2, keys: ['STOREUSER', 'storeUser', 'store_user']
```

Code inspecting `logic.actions` (introspection, diagnostics, `len()` in the
init log) sees keys nobody wrote. Each `create_machine()` against a new
spelling grows the dict permanently.

**2 — the ambiguity guard becomes self-suppressing.**

Machine 1 creates the alias key; the caller later registers a *real, different*
`fetchData`; machine 2 sees two distinct callables and does **not** raise,
because one of them is now an "exact" key:

```
build 2 requiring 'fetch_data' with BOTH now present -> BUILT   (guard suppressed)
```

**3 — action at a distance into a hard, unactionable error.**

```
m1 ok, registry now: ['storeUser', 'store_user']
m2 ERR: InvalidConfigError Logic name 'Store_User' is ambiguous:
  ['STOREUSER', 'storeUser', 'store_user'] are all registered and differ only by case...
```

The user registered exactly **two** callables. The error names **three**
candidates, one of which the library injected itself during an earlier,
unrelated `create_machine()`. The remedy the message suggests ("Keep one") is
not actionable — the third key is not in the user's code.

**4 — retroactive rebinding.** Because the alias is an ordinary dict entry, a
later overwrite of that key changes what an **already-built** machine calls. In
a direct check, a machine built against `fetch_data` executed `CAMEL-REAL` — an
implementation registered *after* it was built.

## Expected

`create_machine()` does not modify the object it was handed. Alias resolution
populates a **machine-owned** resolution map (or a copy of the registry owned by
the `MachineNode`), giving identical hot-path performance without mutating
caller state.

Re-running `create_machine` on the same logic is at least idempotent today
(`f_repeat.py`), so the fix does not need to preserve any accumulation
semantics.

## Acceptance criteria

1. `f_shared_logic.py` exits 0 — `logic.actions.keys()` is byte-identical
   before and after `create_machine()`.
2. `f_pollute.py` exits 0 — building `m1` cannot cause `m2` to raise
   `InvalidConfigError`, and any ambiguity error names only keys the caller
   registered.
3. A machine built against one spelling keeps calling the implementation that
   was registered at build time, even if that registry key is later overwritten.
4. One `MachineLogic` shared across N machines behaves identically to N fresh
   `MachineLogic` instances.
5. Tests: `test_create_machine_does_not_mutate_logic_registry`,
   `test_shared_machine_logic_across_machines_is_isolated`,
   `test_ambiguity_error_names_only_user_registered_keys`.
