# Comment for issue #77 (N-3) — the sync macrostep budget clears the queue

**Action:** comment+reopen
**Disposition:** REOPEN (fix still required: overflow must raise, not drop silently)

---

Verified on main @ 3c527b0 (pre-0.8.1). Re-verification after PR #83, as part of our adoption audit (#26). Build identified by commit — `__version__` still reports `0.8.0` on this tree. CPython 3.13.7, Windows 11.

**The data-loss defect is genuinely fixed**, and we want to say so clearly before the rest:

| # | Acceptance criterion | |
|---|---|---|
| 1 | A 1 501-event batch is fully processed, `queue_depth == 0` afterwards | ✓ |
| 2 | A 5 000-event batch likewise | ✓ |
| 3 | 3 000 independent one-deep `raise`s all delivered | ✓ |
| 4 | Sync and async traces byte-identical for the same machine | ✓ for the shapes tested |
| 5 | Named parity tests present | ✓ |
| 6 | **Overflow raises** rather than silently discarding | ✗ |

Criterion 6 is unmet by code. On overflow the engine still drops the remainder and logs: `send()` returns normally, `status` stays `"running"`, `last_transition_ok` stays `True`, and no hook fires. For a caller, a cut chain is indistinguishable from a completed one. The criteria asked for a raise, and we would ask for one — or, if a raise is too disruptive by default, an `on_budget_exceeded` hook plus a status flag, so the condition is at least *detectable*.

**Disposition: reopen** (or keep open), re-scoped to raise-on-overflow.

**Three further defects live in this fix's own code path.** We have filed each separately with a runnable repro, but listing them here since they belong to this change:

1. **(High) The `tripped` flag is scoped to the drain, not to the offending chain.** One self-feeding `SPIN` event starves five subsequent, *unrelated* `WORK` events in the same `send_events()` batch — `INNER handled: 0 of 5 (expected 5)`. The async engine does not behave this way, so the engine-parity claim in the CHANGELOG is not accurate for this shape. This is a data-starvation bug reachable from a single `send_events()` call, on the engine the fix was written for; we would want it fixed before 0.8.1 tags.
2. **(Medium) A `done.invoke` from a sync service is classed as self-generated.** After a trip, a legitimate invoke completion is dropped and the machine parks in the invoking state (`state: {'m.work'}`, expected `m.done`).
3. **(Medium) `max_iterations` does not bound an action-side `send()` on the async engine.** It bounds the `raise` built-in only. Sync stops at 1 001 steps; async spins to 112 486 steps in 3 s and is still climbing, `status='running'`, `queue_depth=0`.

## Ride-along — the per-chain budget cuts a legitimate chain, silently, and the engines disagree by one (Low)

A legitimate 1 001-deep chain **is** cut — which is the budget working as designed — but the two engines land one state apart for the same machine: `SYNC landed: {'m.s1000'}` vs `ASYNC landed: {'m.s1001'}`. An off-by-one in a parity claim is small, but it is a parity claim.

The cut being silent is the part that matters to us: nothing in the public surface distinguishes "your chain completed" from "your chain was truncated at 1 000". We have had to add a design-review rule banning any machine that could rely on a chain deeper than 1 000, precisely because the failure is undetectable.
