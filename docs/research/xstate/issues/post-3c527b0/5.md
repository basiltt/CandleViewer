## Summary

The #77 fix replaced "count every dequeued event" with a per-chain
self-generated budget — correctly. But the overflow flag it introduced,
`tripped`, is **deliberately never cleared for the remainder of the drain**, and
it is scoped to the **drain**, not to the offending chain.

The chain-reset that gives the budget its per-chain semantics is gated on
`not tripped`. So after any single event self-feeds past the budget, `generated`
stays above `limit` forever and **every subsequent self-generated event in that
drain is dropped on arrival** — including events generated by entirely
unrelated user events that arrive later in the same `send_events()` batch.

`send_events()` makes a drain arbitrarily long, so the blast radius is the
whole batch.

## Environment

- Library: `xstate-statemachine`, local clone, `main` @ commit `3c527b0`, `pip install -e .`
- Python: 3.13.7 (CPython) · Windows 11 x64 (10.0.26200)

## Location

`src/xstate_statemachine/sync_interpreter.py:636-655` (drop on arrival) and
`:672-684` (chain reset gated on `not tripped`; the comment at `:679-683`
states the stickiness is intentional).

## Minimal reproduction

One `SPIN` event that self-feeds, followed by five ordinary `WORK` events whose
handlers each raise exactly **one** `INNER` — one deep, no loop whatsoever:

```python
i.send_events(["SPIN"] + ["WORK"] * 5)
```

Full script: `f_tripped_sticky.py`. Async control on the identical
machine: `f_sticky_async.py`.

## Observed

```
SYNC  INNER handled: 0 of 5   (expected 5)
ASYNC INNER handled: 5 of 5
```

All five `WORK` events are accepted and processed; all five `INNER` events they
raise are silently discarded. The async engine resets `_raise_depth`
unconditionally when a macrostep raised nothing (`interpreter.py:1222-1226`),
so it delivers all five.

The loss is also hard to see: `:646` downgrades the log to `DEBUG` after the
first trip, so the repeated discard is invisible at default log levels.

## Expected

The budget resets per chain, as the CHANGELOG describes and as the async engine
implements. A chain that overflows is cut; a *different* event's one-deep raise,
arriving later in the same drain, is not affected by it.

The CHANGELOG states the drop "never [loses] events the caller was told were
accepted". That holds for the *inbox*, but the `INNER` events here are the
observable effect of five events the caller **was** told were accepted, and
they are lost.

## Proposed fix

Scope `tripped` to the chain, not the drain: clear it in the same place the
chain counter resets (when a macrostep generates nothing), exactly as the async
engine does. If the intent is genuinely to punish a machine that keeps
regenerating, that needs a separate, explicitly-documented counter — and it
should still not silently consume unrelated events.

## Acceptance criteria

1. `f_tripped_sticky.py` exits 0 — `SYNC INNER handled: 5 of 5`.
2. Sync and async engines produce identical action traces for the
   `["SPIN"] + ["WORK"] * 5` batch.
3. A genuine self-feeding loop is still bounded (existing #77 behaviour
   preserved) — `f_chain.py` and `f_parity.py` still agree.
4. The existing `test_sync_runaway_does_not_discard_external_events` is joined
   by `test_sync_runaway_does_not_starve_later_independent_raises`, which
   exercises a second independent raise **after** a trip (the current test pins
   only that the inbox survives).
5. The repeated-discard log is not downgraded to `DEBUG` in a way that hides
   ongoing loss — or the discard count is exposed on the interpreter.
