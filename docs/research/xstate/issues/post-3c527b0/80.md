# Comment for issue #80 (LC-52) — `error.platform.*` is delivered as a `DoneEvent`

**Action:** comment
**Disposition:** confirm closed

---

Verified on main @ 3c527b0 (pre-0.8.1). Re-verification after PR #83, as part of our adoption audit (#26). Build identified by commit — `__version__` still reports `0.8.0` on this tree. CPython 3.13.7, Windows 11.

| # | Acceptance criterion | |
|---|---|---|
| 1 | `error.platform.*` delivered as a dedicated error class exposing `.error` | ✓ — `ErrorEvent(type='error.platform.failing', error=ValueError('boom'), src='failing')` |
| 2 | `.error` is the actual exception raised | ✓ |
| 3 | `.src` is the failing invoke id | ✓ |

**Disposition: confirm closed.** This is a real ergonomics win for consumers — we have replaced our own `event.type.startswith("error.")` string-matching with `isinstance(event, ErrorEvent)` / `event.error`.

**Four defects sit around the new type rather than in its criteria.** Filed separately with repros; listing them here because they belong to this change:

1. **(High) A pending `ErrorEvent` is silently dropped by `get_persisted_snapshot()`.** `base_interpreter.py:1007-1010` filters the inbox with `isinstance(e, Event)`, and `ErrorEvent`/`DoneEvent` are `NamedTuple`s. #47 added `pending_events` to the snapshot precisely so that "a crash between accept and process" could not lose an event — and #80 routed *every* service and child-actor failure through a class that falls through that filter. A machine restores believing the invoke never failed, sits in the invoking state, and no `onError` ever fires. The filter is silent; even a `logger.warning` on a dropped non-`Event` would have surfaced it. Pre-#80 a failure was a `DoneEvent` and was dropped the same way, so the mechanism is not new — but the blast radius went from "invoke completions" to "all invoke completions *and* all failures".
2. **(Medium) The library trips its own deprecation warning.** `plugins.py:435` and `base_interpreter.py:1781` read `ErrorEvent.data`. With only a `LoggingInspector()` attached and no user code touching `.data`, one `DeprecationWarning` is raised from library code. Anyone running `-W error::DeprecationWarning` in CI — the recommended way to be 0.9-ready — now fails on code they cannot change. Both sites should branch on `isinstance(event, ErrorEvent)` or use `getattr(event, "error", None) or getattr(event, "data", None)`.
3. **(Medium) `_resolve_event_spec` builds an `Event` whose `payload` is an exception.** `base_interpreter.py:1779-1782` normalises a non-`Event` by reading `.data`; for an `ErrorEvent` that is the deprecated property returning the exception, so the resulting `Event.payload` is a `ValueError` rather than a mapping. `Event.payload` is typed `Dict[str, Any]` and every other path maintains that invariant, so `event.payload.get(...)` now raises `AttributeError`. Reachable end-to-end via `sendParent` forwarding the triggering error upward — a standard supervision idiom. The shape bug pre-dates #80 (it read `DoneEvent.data`, which held the exception), but #80 was the natural moment to fix it.
4. **(Medium) `escalate` is the one failure path not converted.** `base_interpreter.py:2665-2668` still mints a plain `Event` with the error under `payload["error"]`, so a parent handling both invoke failures and escalated child failures needs two different accessors for the same concept.
