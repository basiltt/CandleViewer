## Summary

Two features that are individually correct are jointly wrong.

When `onUnhandled: "defer"` parks an event, the run loop still resolves that event's `wait=True` receipt at the end of the macrostep, by comparing configuration and context before/after. Nothing changed — because the event was never processed — so the receipt reports `changed=False, error=None`.

That is **indistinguishable from "the machine looked at your event and correctly decided to do nothing"**, for an event that is in fact parked and *will* drive its transition on replay, after the caller has already acted on the receipt.

This is not a hang and not data loss. It is a gate that says *no* about an event that is about to say *yes*.

## Environment

- `xstate-statemachine`, `main` @ commit `3c527b0d04c0d2d0ebb565af7e9e905f7178f620` (merge of PR #83), editable install. `__version__` reports `0.8.0`; CHANGELOG `[Unreleased] — targeting 0.8.1`.
- CPython 3.13.7, Windows 11 x64 (10.0.26200)

## Minimal reproduction

```python
import asyncio
from xstate_statemachine import Interpreter, MachineLogic, create_machine

CFG = {
    "id": "gate",
    "initial": "closed",
    "onUnhandled": "defer",
    "context": {"filled": 0},
    "states": {
        "closed": {"on": {"OPEN": "open"}},
        "open":   {"on": {"FILL": {"target": "filled", "actions": ["mark"]}}},
        "filled": {},
    },
}

def mark(interp, ctx, event, action):
    ctx["filled"] += 1

async def main():
    i = Interpreter(create_machine(CFG, logic=MachineLogic(actions={"mark": mark})))
    await i.start()
    receipt = await i.send("FILL", wait=True)      # no FILL handler in `closed`
    print("changed =", receipt.changed)            # False
    print("error   =", receipt.error)              # None
    await i.send("OPEN")                           # replay
    await asyncio.sleep(0.05)
    print("states  =", i.current_state_ids)        # {'gate.filled'}
    print("receipt still says changed =", receipt.changed)   # False
    await i.stop()

asyncio.run(main())
```

## Observed (on `3c527b0`)

```
receipt at defer time:
  changed = False      <- the caller's gate says "nothing happened"
  error   = None       <- and "nothing went wrong"
  states  = ['gate.closed']

after OPEN (replay):
  states  = ['gate.filled']   <- the transition the receipt denied
  context = {'filled': 1}
```

Side by side with a genuinely handled, action-less event:

```
deferred event  -> changed=False  error=None
true no-op      -> changed=False  error=None
```

Byte-identical. `Receipt` on this commit is still `('state_ids', 'changed', 'error')` — no field carries the disposition.

**`deferred_count` is not a usable discriminator from the call site.** At the caller's `await` point it reads `0` in **both** cases. (It reads `1` only if observed from inside the macrostep, which a caller cannot do.) We had proposed exactly that as our own mitigation and it does not work.

## Expected

A receipt must be able to distinguish three outcomes, not two:

1. **processed, changed something** — `changed=True`
2. **processed, correctly no-op** — `changed=False`, not deferred
3. **deferred, not yet processed** — the caller must not read this as (2)

Any one of these would resolve it:

- a `Receipt.deferred: bool` (or a tri-state `disposition`) set from the `defer` decision `_handle_unhandled_event` has already made; or
- resolving the receipt on **replay** instead of at defer time, so `wait=True` means "wait until this event is actually processed"; or
- at minimum, a plugin hook (`on_event_deferred`) carrying enough identity to correlate with the send, plus a loud note in the `onUnhandled` guide.

The first is the cheapest and preserves the existing timing contract.

## Cause

`interpreter.py` resolves the pending receipt at the end of the macrostep by comparing configuration and context, with no knowledge of the `defer` disposition that `base_interpreter._handle_unhandled_event` recorded microseconds earlier. The two code paths never exchange that fact.

PR #83 rewrote `_handle_unhandled_event` (for #79) and reworked `interpreter.py` (for #43) without either change reaching the receipt, so this is unchanged from the previous commit.

## Why this matters

For any caller that uses the two features together — which is the combination `defer` exists to make safe — a legitimate event arriving one microstep early returns a confident "no". A caller that retries, or reports failure and unwinds, does so against a machine that is about to succeed. Carefulness does not detect a confidently wrong answer.

In the adopting project both settings are *mandated* on the order path (`onUnhandled: "defer"` plus `send(wait=True)` for every gated decision), so this is the normal path rather than an edge case. It is currently the single defect blocking that path.

## Acceptance criteria

1. A deferred event's receipt is distinguishable, **from the receipt object alone**, from a genuinely-processed no-op — without the caller reading interpreter-level counters in the same instant.
2. On replay, the caller can learn the eventual outcome (either the original receipt resolves then, or the deferral is explicit enough that the caller knows to wait).
3. `onUnhandled: "error"` and `"ignore"` receipts are unchanged.
4. Tests: `test_receipt_reports_deferred_disposition`, `test_receipt_not_changed_is_distinguishable_from_deferred`.
5. The `onUnhandled` guide and the "Getting an answer from a machine" page both state the composed contract.
