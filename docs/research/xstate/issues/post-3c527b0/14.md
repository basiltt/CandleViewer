## Summary

#80 converted every `DoneEvent`-carrying-an-exception site to `ErrorEvent` — verified exhaustively: the five surviving `DoneEvent(` constructions in the tree (`base_interpreter.py:3150`, `interpreter.py:1784`, `:2039`, `sync_interpreter.py:1062`, `:1257`) are all success paths. Good.

`escalate` is not among them. `base_interpreter.py:2665-2668`:

```python
escalate_event = system_event(f"xstate.error.actor.{self.id}", error=error_payload)
```

So an escalated child failure is still a plain `Event` with the error under `payload["error"]`. A parent that handles both invoke failures and escalated failures needs two different accessors for the same concept, and a handler written to the documented pattern fails.

## Environment

- `xstate-statemachine`, `main` @ `3c527b0` (merge of PR #83). `__version__` reports `0.8.0`.
- CPython 3.13.7, Windows 11 x64 (10.0.26200)

## Minimal reproduction

```python
import asyncio
from xstate_statemachine import MachineLogic, create_machine
from xstate_statemachine.interpreter import Interpreter

seen = {}
def look(i, c, e, a=None):
    seen.update(cls=type(e).__name__, type=e.type,
                has_error_attr=hasattr(e, "error"),
                payload=repr(getattr(e, "payload", None)))

CHILD = {"id": "c", "initial": "w", "states": {"w": {"entry": [
    {"type": "escalate", "params": {"error": "child exploded"}}]}}}
PARENT = {"id": "p", "initial": "w", "states": {
    "w": {"invoke": {"src": "kid", "id": "kid"},
          "on": {"xstate.error.actor.p:kid": {"target": "caught", "actions": ["look"]}}},
    "caught": {}}}

async def main():
    child = create_machine(CHILD, logic=MachineLogic())
    m = create_machine(PARENT, logic=MachineLogic(services={"kid": child},
                                                  actions={"look": look}))
    it = await Interpreter(m).start()
    await asyncio.sleep(0.3)
    print(seen)
    await it.stop()

asyncio.run(main())
```

Full script: `g15_escalate_shape.py`.

## Observed

```
{'cls': 'Event', 'type': 'xstate.error.actor.p:kid',
 'has_error_attr': False, 'payload': "{'error': 'child exploded'}"}
isinstance(ErrorEvent)? False
```

The contract the CHANGELOG and `docs/api/index.md` advertise — *"branch on `isinstance(event, ErrorEvent)` or read `event.error`"* — does not hold for escalated failures. These are the actor-supervision failure path, and the one closest to XState v5's `xstate.error.actor.*` naming the docs explicitly invoke. A handler written to the documented pattern gets `AttributeError: 'Event' object has no attribute 'error'`.

## Expected

Either convert `escalate` to mint an `ErrorEvent` (preferred — it is a failure, and the type exists precisely for failures), or scope the documented `event.error` pattern explicitly to *invoke* failures and say what `escalate` delivers instead.

## Aside, noted while probing (not part of this report)

The escalate event is reachable only by an exact `on` key — `xstate.error.actor.p:kid`, including the parent-namespaced actor id. Both `"xstate.error.actor.*"` and `"xstate.*"` fail to match it (correctly, per the new provenance rule), which makes escalate handlers depend on an internal id-minting convention. Worth a documented helper or a stable descriptor.

## Acceptance criteria

1. An escalated child failure delivers `isinstance(event, ErrorEvent)` with `.error` carrying the escalated payload — or the docs state the `escalate` shape separately and explicitly.
2. Whichever is chosen, `invoke`-failure and `escalate` handlers can be written against one documented accessor.
3. Test: `test_escalate_delivers_error_event` (or `test_escalate_shape_is_documented`).
