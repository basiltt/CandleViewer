## Ride-along — the completion-delivery task is untracked (Low)

`interpreter.py:1958-1963` schedules delivery via `_loop_create_task` (`:2069`), which calls `loop.create_task(coro)` and returns; the result is assigned to nothing. Unlike every other task in the file it is **not** `task_manager.add(owner_id, task)`'d, so it is not owned by the invoking state, not cancelled on exit, and not awaited by `stop()`. CPython's `asyncio` holds only a *weak* reference to a running task, and the stdlib docs explicitly say to keep a strong reference.

**We could not make it bite.** 300 invoke/complete cycles calling `gc.collect()` on every loop iteration while the delivery task was in flight lost 0/300 completions; a `stop()` racing a completion leaves `tasks left = 0` and simply drops the `onDone`, which is defensible for a stopping machine.

So: latent rather than reproducible. Worth a one-line fix (hold the reference, or register it with the `TaskManager`) rather than a behaviour change.
