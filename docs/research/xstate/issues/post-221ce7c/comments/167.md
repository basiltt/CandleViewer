The fix is real and we verified it end-to-end. It lands on **one service kind
only**, and the other one is the kind your own documentation recommends.

| Service spelled as | Result at `maxIterations=20` |
|---|---|
| `def svc(...)` | **23 calls**, `last_error = RunawayChainError` — bounded, observable, correct |
| `async def svc(...)` | **28 108 calls in 2.0 s**, `last_error = None`, `status = "running"` — unbounded, silent |

Identical chart, identical config, one word changed. Runnable repro below.

## Why

There are two publication paths for a service completion:

| Kind | Path | Charged? |
|---|---|---|
| plain `def` | `_finish_plain_service` → `self._deliver_priority(done_event)` (`interpreter.py:2690`) | **yes** — `_deliver_priority` (`:2287-2288`) does `if self._processing: self._raise_depth += 1` |
| `async def` | `_invoke_service_task` → `await self.send(done_event)` (`interpreter.py:2414`); child-actor `onDone` likewise at `:2882` | **no** — never reaches `_deliver_priority` at all |

So it is not that `self._processing` happens to be `False` when the coroutine
resolves — we checked that hypothesis and it is wrong. The coroutine completion
**never passes the charging site under any value of `_processing`**, because it
goes out on the public inbox lane. A lane probe counting `done.invoke*` per lane
over a ping-pong `a↔b` chart at `maxIterations: 20`:

```
{"kind": "plain", "lanes": {"priority": 23, "inbox": 0},    "last_error": "RunawayChainError"}
{"kind": "async", "lanes": {"priority": 0,  "inbox": 27948}, "last_error": null}
```

There is a compounding second effect. Arriving from the inbox, the completion
also satisfies the `from_inbox` disjunct at `interpreter.py:1647`
(`if not is_system_event(event) or from_inbox:`) and **resets**
`_settle_iterations` / `_settle_tripped` on every lap. The coroutine path is
therefore both uncharged *and* actively budget-clearing — which is why raising
`maxIterations` changes nothing: we measured 2, 5, 25, 100 and 1000 as identical.

## Two consequences worth seeing

**A variant settles into an empty configuration and reports success.** With an
`async def` service, 10/10 runs: a resolved `await send("GO", wait=True)` returns
`ok=True, err=None, status="running"` with `current_state_ids == []`, still empty
500 ms later. With a plain `def` service, 0/10 — it trips correctly. The sync
engine keeps a legal configuration on the identical chart. And a
`get_persisted_snapshot()` at that instant is refused `SnapshotMidStepError` —
**the interpreter knows it is mid-step while `send(wait=True)` has already told
the caller the step finished successfully.**

**The rollback family is the same defect, not a separate one.** One word changed
in the `rollback` + `invoke.onDone` ablation: `{"kind": "plain", "svc_calls": 23}`
versus `{"kind": "async", "svc_calls": 2783}`. On a realistic machine — a kill
switch — one operator press produced **3 547 side-effecting service invocations
in 3.0 s**, still accelerating linearly, `status="running"`, receipt
`changed=True, error=None`.

## Why the suite does not see it

All three pinned regression tests for this family
(`tests/test_round6_findings.py:124/184/486`) declare `def svc(...)`. The suite is
structurally blind to the other lane.

**This is the highest-value change available in this release, and it is one
line:** parametrise every service-invoking test over service kind.

```python
@pytest.mark.parametrize("kind", ["def", "async def"])
```

Six independently-filed findings on our side collapse into this one defect. All
six would have been caught before the fix shipped by that parametrisation.

## Suggested fix

Publish coroutine-service and child-actor completions on the **same charged lane**
the plain-`def` path already uses — route `:2414` and `:2882` through
`_deliver_priority` rather than `await self.send` — and stop treating an engine
completion that arrives `from_inbox` as external at `:1647`.
