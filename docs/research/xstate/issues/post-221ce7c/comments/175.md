# Comment for issue #175 — `stop()` leaves duplicate-`Event`-instance receipts unresolved

**Action:** comment + **reopen**
**Disposition:** **NOT FIXED (Case D)** — and the shipped regression test passes while it is broken

---

Verified on `main` @ `221ce7c` (unreleased 0.8.1; `__version__` still reports
`0.8.0` — key on the commit) as part of our adoption audit (#26). CPython 3.13.7,
Windows 11. Reproduced in a fresh process against a clean venv.

Cases A, B and C are fixed and we confirm them. **Case D is not fixed**, and we
want to flag something about *how* it was closed that matters more than the defect
itself.

`stop()` still never resolves duplicate-`Event`-instance receipts with
`InterpreterStoppedError`. Across **20 trials, 160 of 160 receipts** resolved as
ordinary successes. Not "usually" — every one, deterministically.

The part worth your attention: the regression test added for this pins only a
weaker `ok == applied` invariant, **which holds while Case D is broken**. The test
passes on a build that exhibits the defect it is named after. A test that cannot
fail on its own defect is worse than no test, because it closes the issue.

The same pattern appears once more in this release — `tests/test_persistence.py`
has no null/absent-`machine_hash` case, and we have filed a defect that lives
exactly there. Both are cheap to strengthen and both would have held the line.

Reopening on Case D only.
