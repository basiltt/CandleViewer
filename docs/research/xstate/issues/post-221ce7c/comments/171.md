Verified on `main` @ `221ce7c` (merge of PR #178, on top of #177 and the hot-path
PRs #165/#176; unreleased 0.8.1) as part of our adoption audit (#26). Build
identified **by commit** — `__version__` still reports `0.8.0` on this tree, so
nothing here should be keyed on the version string. CPython 3.13.7, Windows 11.
Every claim below was reproduced in a fresh process against a clean venv before
it was written down.

Confirmed fixed. An invoked `MachineNode` child is present in `_actors` **the
instant `start()` returns**, so an immediate `sendTo` no longer drops with
`unresolved_target`. 20 consecutive runs give an identical trace on both engines.

We specifically checked that #149 is preserved: `start()` does **not** block on a
plain service's result. It does not.

**One regression this introduced, filed separately:** `_await_actor_bringups`
gathers the bring-up tasks with no timeout, and a bring-up awaits `child.start()`
— i.e. user entry actions. A child whose async entry action sleeps 30 s makes
`await start()` hang for 30 s with `status` reading `"running"` throughout. The
interpreter is live and unharmed during the hang (a `POKE` sent concurrently is
accepted and processed), so it is a misleading unbounded await rather than a
deadlock — but there is no timeout knob anywhere in `src/`.

Thank you — this one verified cleanly.
