# Comment for issue #174 — blocking-service / timer interaction

**Action:** comment only — **leave open**
**Disposition:** **DOCUMENTED, NOT FIXED** — the behaviour is now stated; the behaviour is unchanged

Verified on `main` @ `221ce7c` (unreleased 0.8.1; `__version__` still reports
`0.8.0` — key on the commit) as part of our adoption audit (#26). CPython 3.13.7,
Windows 11. Reproduced in a fresh process against a clean venv.

`production-characteristics.md` now states the blocking-timer behaviour, which is
a genuine improvement — it turns a surprise into a documented constraint, and we
have rewritten our own house rules against it rather than against guesswork.

Recording plainly that **no code changed**, so anyone reading the CHANGELOG should
not infer the timing behaviour improved:

- busy-loop `after` lateness is unchanged at ~15–30 ms over a 50 ms budget;
- the `after: 100` behind a 500 ms plain-`def` service class reproduces unchanged;
- under 100 concurrent busy interpreters we measure ~130–160 ms mean timer error
  (no hang, no livelock — it degrades, it does not break).

We are not asking for a fix here; coarse timers are a legitimate design point and
we route all critical timing through an external monotonic scheduler with absolute
deadlines. Leaving the issue open only so the documented limitation stays visible.

**One interaction worth flagging, because it removes the escape hatch.** The
documented remedy for a blocking service is "prefer `async def`". Separately, we
have filed a defect where an `async def` invoked service's completion is never
charged to the chain budget, making self-generated invoke cycles unbounded — and
its only available mitigation is "use plain `def` services", which is exactly what
this issue documents as blocking the machine's own `after` timers. **There is
currently no service kind that is safe on both axes.** That interaction, not
either issue alone, is what holds our adoption gate down.
