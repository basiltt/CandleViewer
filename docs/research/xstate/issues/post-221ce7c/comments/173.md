# Comment for issue #173 — service thread-pool size is hard-coded at 4

Verified on `main` @ `221ce7c` (merge of PR #178, on top of #177 and the hot-path
PRs #165/#176; unreleased 0.8.1) as part of our adoption audit (#26). Build
identified **by commit** — `__version__` still reports `0.8.0` on this tree, so
nothing here should be keyed on the version string. CPython 3.13.7, Windows 11.
Every claim below was reproduced in a fresh process against a clean venv before
it was written down.

Confirmed fixed. The public `service_pool_size=` kwarg feeds
`ThreadPoolExecutor(max_workers=...)`; the default is unchanged at 4;
`service_pool_size=0` raises `ValueError`. A widened pool genuinely helps —
`pool_size=8` completes 50 queued plain services in 0.154 s against 1.208 s at
`pool_size=1`, a **7.8×** difference, and `service_pool_size=1` correctly
serialises them. `stop()` mid-service returns cleanly at every pool size.

**One trivial follow-up filed separately:** `DEFAULT_SERVICE_POOL_SIZE` is
documented but absent from `__all__`.

Note for anyone reading this hoping it removes the need for `async def` services:
it does not, and that is not this issue's fault. `send(PING, wait=True)` latency
is 0.001 s with an `async def` service against **0.441 s** with a plain `def` one
— and 0.437 s with a custom executor, i.e. the pool is not where the block is.
The entering macrostep still awaits the plain service's result, so the block is
**in the macrostep, not the pool**.

Thank you — this one verified cleanly.
