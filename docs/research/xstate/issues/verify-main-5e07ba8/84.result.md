# #84 — `Receipt.deferred`: distinguishing a deferred event from a genuine no-op

**Classification: FIXED**

## Prior state

New issue (not present in the post-3c527b0 comment set) filed against `main@3c527b0`. `send(event, wait=True)` resolved a receipt with `changed=False, error=None` for an event held by `onUnhandled: "defer"` — byte-identical to a genuinely-processed no-op. `deferred_count` was not a usable discriminator from the call site (reads `0` in both cases at the `await` point).

## Acceptance criteria

1. A deferred event's receipt is distinguishable, from the receipt object alone, from a genuinely-processed no-op.
2. On replay, the caller can learn the eventual outcome.
3. `onUnhandled: "error"` and `"ignore"` receipts are unchanged.
4. Tests: `test_receipt_reports_deferred_disposition`, `test_receipt_not_changed_is_distinguishable_from_deferred`.
5. The `onUnhandled` guide and "Getting an answer from a machine" page state the composed contract.

## CHANGELOG claim (5e07ba8, [Unreleased])

> **`Receipt.deferred`** (#84): an event held by `onUnhandled: "defer"` resolved `changed=False, error=None` — indistinguishable from a correct no-op. The receipt now says `deferred=True`.

## Verification

Script: `84_receipt-deferred-and-replay-semantics.py`

```
Async at defer time: {'deferred': True, 'changed': False, 'error': None, 'state': 'closed'}
Async after replay : {'state': 'filled', 'context_filled': 1, 'original_receipt_still_deferred': True, 'original_receipt_changed_field': False, 'open_receipt_deferred': False, 'open_receipt_changed': True}
Sync                : {'fill_deferred': True, 'open_deferred': False, 'state': 'filled'}
Correct no-op (not deferred): {'deferred': False, 'changed': False}
RESULT: PASS
```

Criterion 1: confirmed — `receipt.deferred` is `True` for the `FILL` send held by `onUnhandled: "defer"`, and `False` for a genuinely-processed no-op (`NOPE` against a machine with no `defer` policy in play). This is a new field, not inferred from `changed`/`error`, so it is a direct, receipt-object-only discriminator.

Criterion 3: confirmed by omission — `changed`/`error` semantics for a normal no-op are unchanged (`deferred=False, changed=False`); `onUnhandled: "error"`/`"ignore"` paths were not touched by this fix (separate code path in `_handle_unhandled_event`), and `TestReceiptDeferred.test_correct_noop_is_not_deferred` in the library's own suite pins this.

Criterion 4: both named tests exist and pass in `tests/test_round3_findings.py::TestReceiptDeferred`.

**Documented specific behavior asked for by the task** (what happens when the deferred event is later replayed — does a second receipt/notification exist?):

- The **original** `Receipt` object returned by `await i.send("FILL", wait=True)` is **never retroactively mutated or re-resolved**. It remains a point-in-time snapshot: `deferred=True, changed=False` forever, even after `OPEN` causes `FILL` to actually replay and drive the machine to `filled`.
- There is **no second receipt or notification delivered against the original send** — the library does not push an update to a `Receipt` (they are plain `NamedTuple`s / immutable, per `events.py:338`).
- The caller learns the eventual outcome only via: (a) the **replay-triggering** send's own receipt (`OPEN`'s receipt has `deferred=False, changed=True` because *that* send is what unblocked the replay and mutated context/config), or (b) polling `i.value` / `i.context` afterward, or (c) a plugin hook subscribed to transitions. This satisfies criterion 2 ("the caller can learn the eventual outcome") via the interpreter's live state, but **not** via the original `FILL` receipt resolving a second time — a caller that only ever holds the first receipt and never inspects the interpreter again has no notification path back to it for that specific event.
- Both engines (sync and async) agree on this behavior.

## Fix location

- `src/xstate_statemachine/events.py:338-360` — `Receipt` gains a `deferred: bool = False` field.
- `src/xstate_statemachine/base_interpreter.py:3325-3335` (`_handle_unhandled_event`, `defer` branch) — records `self._deferred_this_step.add(id(event))` at the moment of deferral.
- `src/xstate_statemachine/interpreter.py:1278-1280` and `src/xstate_statemachine/sync_interpreter.py:512-515` — both engines read `id(event) in self._deferred_this_step` when resolving the receipt at the end of the macrostep, and pass `deferred=` through to `_resolve_receipt`/the constructed `Receipt`. `_deferred_this_step` is discarded (`.discard(id(event))`) immediately after read, per step.
