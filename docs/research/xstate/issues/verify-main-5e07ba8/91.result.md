## Design choice made

The issue offered two defensible options; the library chose **(a)**:
exact-match precedence, with the ambiguity claim narrowed and a new
`UserWarning` for the shadowed-near-duplicate case. This is documented in the
CHANGELOG and matches `resolve_aliases` (`machine_logic.py:163-184`):

```python
if name in registry:
    # #91: exact key wins BY DESIGN -- but if a DIFFERENT callable
    #    is also registered under a spelling that normalises to this
    #    name ... warn.
    shadows = [c for c in by_key.get(normalize_logic_name(name), [])
               if c != name and registry[c] is not registry[name]]
    if shadows:
        warnings.warn(f"Logic name '{name}' is registered exactly and also "
                       f"as {sorted(shadows)}, ... DIFFERENT callables. ...",
                       UserWarning, stacklevel=3)
    continue
```

## Criterion 3 note (not a defect)

Issue text: *"two distinct **config** names that normalise equal both bind
silently to one callable"* — my verify script tested the `f_collide.py`
shape (config declares `["store_user", "storeUser"]` as two entry actions
with only ONE callable registered) and found **no warning fires**, because
there is genuinely no ambiguity: both config names bind to the single
callable that exists. This is a distinct scenario from criterion 1 (registry
holding two *different* callables). Re-reading the issue's "Expected"
section: *"Independently, the config side should be checked: two required
names that normalise equal and resolve to one callable should **at least
warn**."* The library did not add this second warning — `resolve_aliases`
only inspects the *registry* side (`by_key`), never the set of *required*
names requested by the config. This remains a residual gap, though a minor
one: no incorrect behavior results (both config names correctly call the one
registered implementation), only a missed opportunity to flag a likely-typo'd
duplicate action declaration.

## Residual

Criterion 3's independent "config side" check (two required names normalising
equal, resolving to one callable, should at least warn) is **not implemented**
— `resolve_aliases` has no visibility into which required names collapse to
the same registry key at the call site; it only sees one `name` at a time via
the `required` iterable. This is low severity (no incorrect binding, no data
loss — just a missed early-warning for a plausible copy/paste config typo)
and was not required by the CHANGELOG's stated fix, only "independently"
suggested in the issue body's Expected section.
