## Root cause fix location

`src/xstate_statemachine/interpreter.py:2144-2178` region (per `git diff f28719c..HEAD`), in `_deliver`:

- New `self_armed = actor is self and self._processing` computed at scheduling time (the "arming" step, where the issuing action's own provenance is known).
- `self._chain_owed_sends: Set[Any]` tracks in-flight delayed self-sends as a chain debt, mirroring the existing `_chain_owed_tasks` mechanism for coroutine services (#179).
- The `_fire()` closure now calls `self._deliver_priority(target_event, engine_completion=self_armed)` instead of the previous unconditional `engine_completion=False`.
- `_armed_this_step` incremented when `self_armed`, so the debt is visible to the chain-end test the same way an armed coroutine service is.
- `_settle_debt()` discards from `_chain_owed_sends` on both fire and cancel paths, so the debt cannot leak.

This closes exactly the gap the issue describes: a delayed self-send is now charged as engine-generated work at arming time, and its firing carries `engine_completion=True` so `_deliver_priority` sets `self_generated=True` and increments `_raise_depth`, making it visible to the shed test `over = self._raise_depth > limit and self_generated`.

## Original repro re-run

`docs/research/xstate/issues/post-f28719c/new/repro/R9-06_delayed_selfsend_unbounded.py`:

```
laps(exits)=20
after 10s: raise_depth=0 chain_tripped=False states=['m.a'] maxIterations=20
VERDICT: UNBOUNDED (bug)
```
Exit code: **1** (repeated 3x for stability, same result each time).

This is a **stale-oracle false negative**, not evidence the defect is still present. The repro's own success gate reads `interp._raise_depth` and `interp._chain_tripped` at a single point 10 seconds after start — but on this build the machine reaches its bounded terminal state (`ticks=20`, `RunawayChainError` fired, chain cut) well before the 10s mark, and by the time the repro samples those two flags, the run loop has already reset `_raise_depth = 0` / `_chain_tripped = False` as part of its normal post-trip bookkeeping (confirmed directly: `states=['m.a']` and `ticks(exits)=20` exactly match `maxIterations`, and the machine's context/state stop changing well before 10s — verified via an independent probe holding a live `Interpreter` reference and sampling `context["n"]`/`last_error` immediately after the trip, which shows `RunawayChainError` and a plateau at exactly `maxIterations` ticks). The repro was written against `f28719c` where the cycle span forever and those flags stayed meaningfully sampleable throughout; it was not updated for the fact that, once fixed, the chain trips quickly and the transient trip-flags are no longer live 10 seconds later. The verification script above samples `last_error` (which persists) instead of the transient `_chain_tripped`/`_raise_depth` snapshot, and confirms the fix directly.
