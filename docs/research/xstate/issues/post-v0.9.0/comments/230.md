## The other half: `on_interpreter_start` has no route at all on a restored actor

Not a regression from this fix, but the same structural gap on the neighbouring hook, and it is the natural companion to what #230 just closed - so it seems most useful reported here as well as separately.

`Interpreter.start()` has two paths. The resume branch (`interpreter.py:588-624`) detects the restored shape (`status in ("running","done","error")` and `_event_loop_task is None`), logs `"Resuming restored interpreter"`, binds the loop, re-arms scheduled sends (#213), optionally re-drives invokes (#44) and `after` timers (#128), resumes child actors, and **`return self` at line 624**. The plugin notification loop -

```python
for plugin in self._plugins:
    plugin.on_interpreter_start(self)
```

- sits at `interpreter.py:663-665`, **below that return**, and is never reached. `SyncInterpreter.start()` has the identical shape (`sync_interpreter.py:311-347` returning above its own hook loop at `:388`), which is why the sync engine fails the same way rather than via a separate bug.

Measured 6/6 cells, `{async, sync} x {def, async def} x {plugins=, .use()}`:

```
CONTROL fresh  .use()           : ['start', 'transition', 'stop']
RESTORED from_snapshot(plugins=): ['recv:GO', 'transition', 'stop']
RESTORED .use() after restore   : ['recv:GO', 'transition', 'stop']
```

Three things make this worth fixing rather than documenting:

1. **`on_interpreter_stop` does fire** (`stop()` has one path), so a lifecycle plugin observes a `stop` with **no matching `start`**. An unbalanced pair is a stronger failure signal than a merely absent one: anything holding a span, a correlation id, a latency clock or an audit "actor came up" record either leaks or under-reports.
2. **There is no working route.** It is not `plugins=`-specific - `.use()` after `from_snapshot` is equally blind. The 0.9.0 changelog says `plugins=` has "the same effect as `.use()` on the result", which holds for `on_invalid_event` but is vacuously true here because neither route works.
3. **The docs do not carve out resume.** `docs/_guide/plugins.md:175` says `on_interpreter_start` fires "**when `start()` is called**"; `docs/api/index.md:1919` says "`start()` begins". And `start()` is the library's own documented way to resume a restored actor - the architecture comment at `interpreter.py:582-587` says so explicitly.

The actor itself is fine: `restored_machine_is_live=true` in all six cells, with `on_transition`, `on_action_execute` and `on_interpreter_stop` all normal. It works; it just never announces itself. Confirmed independently at fleet scale - 40/40 chaos restores in a soak, `plugin_start_counts=[0]`.

**Suggested fix:** run the plugin loop on the resume branch too (or hoist it above the early return), ideally passing a `restored=True` discriminator so a plugin can distinguish bring-up from resume - the two want different telemetry.

**Our mitigation meanwhile:** no per-process bring-up work hangs off `on_interpreter_start`; we do it at construction/restore time in our own wrapper.
