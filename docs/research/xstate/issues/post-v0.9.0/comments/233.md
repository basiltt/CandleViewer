# Comment draft - issue #233 (sync `_enqueue_restored` honours the priority lane)

**NOT POSTED. Draft.**

**Verified at tag `v0.9.0` = `91bd979`** (tested tree `main` @ `e3a1f22`; `git diff v0.9.0..HEAD --stat` is `.github/workflows/publish.yml` only, so this applies to the tag). Re-verified with standalone repros (stdlib + `xstate_statemachine` only, every helper inlined) from a neutral working directory, on **both engines** and with **both `def` and `async def`** service spellings, polled to convergence.

## Result: CONFIRMED FIXED

`SyncInterpreter._enqueue_restored` places priority-lane restores ahead of the inbox. Verified live, not by reading: restore order comes out `['GO', 'PING']`, priority first.

## A divergence this fix exposes on the async side

Reported here only because this issue is the reason it is now visible; we have written it up separately with a standalone repro.

`SyncInterpreter` has one queue and `drain_pending()` reads it, so the sync engine now drains everything - priority lane included. The async engine has **two** queues, and `Interpreter.drain_pending()` (`interpreter.py:1715`) reads only `self._event_queue`; `_priority_queue` (`interpreter.py:374`) is never touched. On a live async interpreter, public API only, no snapshot:

```
pending_events        : ['P1', 'P2', 'I1', 'I2']
await drain_pending() : ['I1', 'I2']
LOST                  : ['P1', 'P2']       # both send_priority() events
sync  drain_pending() : ['P1', 'P2', 'I1', 'I2']
```

Before this fix, both engines were wrong in the same direction, which at least made the behaviour uniform. Fixing one engine's *restore* ordering turned a symmetric bug into an **engine-dependent** one - which is precisely the parity class this issue exists to close, so it seems in scope to flag it here.

It is not merely cosmetic: `_teardown()` calls `_priority_queue.clear()` (`interpreter.py:1635`), so the documented `drain_pending()` -> persist -> `stop()` shutdown recipe **permanently destroys** whatever was in the lane - fired `after` timers, invoke completions, and `send_priority()` traffic. The sibling view `_snapshot_pending_events()` (`interpreter.py:1675`) deliberately includes the lane (#107), so the two durability views of the same interpreter disagree, and the one whose docstring promises "every accepted-but-unprocessed event" is the lossy one.

**Suggested fix:** drain `_priority_queue` first, then the inbox - the order `_snapshot_pending_events` already uses.
