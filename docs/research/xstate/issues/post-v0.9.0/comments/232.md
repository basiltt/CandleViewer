The negative cells matter as much as the positive one: a warning that also fires on the four legitimate shapes would be worse than no warning, and it does not.

## One limitation worth documenting (we are not filing it separately)

The warning is emitted from `__del__`, so CPython routes any exception escaping it to `sys.unraisablehook` and prints `Exception ignored in:` rather than raising. Verified: machine unaffected (`m.a -> m.b -> m.c`, `status == running`, exit 0), `raised_to_caller: []`, `loop_exception_handler: []`.

The consequence is that a project running `-W error` or `filterwarnings = error` in CI - which is the standard way to make a `RuntimeWarning` actionable - **cannot turn this one into a build failure**. It is visible to a human reading logs and invisible to the tooling most likely to be watching for it.

We are not asking for this to be reworked; `__del__` is the natural place to detect an unretrieved result, and the alternatives all have worse trade-offs. But it would be worth a line in the docs next to the warning's description, because "add `-W error` and you will catch this" is the reasonable inference from the current text and it is not true. If a cheap alternative exists, a queryable counter of dropped receipts on the interpreter would be strictly testable in a way the warning is not.
