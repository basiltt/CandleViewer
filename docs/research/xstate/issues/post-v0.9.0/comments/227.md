## Result

Restored `scheduled_sends` now go through `_admit_restored`, so `strict` and `event_schemas` apply to them - and, importantly, **a refusal is reported without aborting the restore**.

| Check | Result |
|---|---|
| Undeclared event in restored `scheduled_sends`, `strict=True` | refused |
| Refusal visible | reaches `on_invalid_event` **and** `last_error` |
| Machine after the refusal | starts normally, stays in its restored state, `status == "running"` |
| Re-persist after restore | contains **only the surviving records** - the refused one does not come back |
| Schema-invalid payload | same path, same reporting |

The "report but do not abort" choice is the right one for our use, and we want to say so explicitly since it was the open question on the issue. A restore that hard-failed on one bad deadline record would take down a process holding a large population of otherwise-healthy machines; a restore that silently dropped it would lose a deadline with no trace. Reporting-and-continuing is the only option that lets a supervisor decide.

Note for others adopting this: the refusal is only observable if the plugin is registered **before** admission, i.e. via `from_snapshot(..., plugins=[...])` (#230). A `.use()` after `from_snapshot` returns is blind to exactly the refusal it was added to catch.
