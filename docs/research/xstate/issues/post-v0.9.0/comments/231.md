## Result

**Fixed, and deliberately stricter than the issue proposed.** The error is raised in `InvokeDefinition.__init__`, carries both the **state name and the invoke id**, fires **regardless of `strict_config`**, and lands **before** `logic_loader` runs.

The issue text floated a warn/raise split keyed on `strict_config`. Upstream chose always-raise. **We prefer the stricter shape and want that on the record**, because the failure it replaces was the expensive kind: an inline dict in `src` produced a downstream error with no reference to the offending state, so the cost of the mistake scaled with chart size rather than staying local to the typo. A named error at construction is O(1) to diagnose.

Two verification notes:

- The identification is genuinely useful - state name plus invoke id is enough to go straight to the line, which is the whole point.
- Raising before `logic_loader` matters more than it looks: it means the failure cannot be confused with a missing-implementation error, which is the wrong diagnosis a reader would otherwise reach for.

## Compatibility note for other adopters

This is a real behaviour change inside a minor release: a chart that previously loaded (with `strict_config=False`) now fails at construction. We checked our own 20-chart corpus explicitly rather than assuming - **zero charts use the shape** - so it cost us nothing. Anyone with a large chart inventory should grep for a dict literal in `src` before bumping, rather than discovering it at process start. We mention it not as an objection but because it is the kind of change worth a line in the release notes' upgrade section.
