# Comment draft - issue #225 (self-send provenance keyed on task identity)

**NOT POSTED. Draft.**

**Verified FIXED at tag `v0.9.0` = `91bd979`** (tested tree `main` @ `e3a1f22`; `git diff v0.9.0..HEAD --stat` is `.github/workflows/publish.yml` only, so this applies to the tag). Re-verified with standalone repros (stdlib + `xstate_statemachine` only, every helper inlined) from a neutral working directory, on **both engines** and with **both `def` and `async def`** service spellings, polled to convergence.

## Result

`_ACTIVE_ACTION_OWNER` is gone; provenance now keys on task identity via `_action_tasks`. We tested the two halves separately, because they pull in opposite directions:

| Shape | Before | At 0.9.0 |
|---|---|---|
| Worker task spawned inside an action, sends **after** the machine is idle | refused as a self-send (the ContextVar was inheritable, so the task carried the owner for its whole life) | `worker_send='ok'`, machine advances, `chain_trips == 0` |
| `asyncio.ensure_future(i.send(..., wait=True))` hand-out from an action | refused | accepted - the documented escape hatch works again |
| Genuine in-step `await i.send(..., wait=True)` on the machine's own interpreter | `ReentrantWaitError` | `ReentrantWaitError` - **unchanged, correctly** |

Nesting, spawning and the executor lane all behave.

## Consequence on our side

We had a constraint forbidding any action from awaiting **or handing out an `ensure_future` for** a self `send(wait=True)`. It was written against the ContextVar's inheritance, and **that ground is now closed, so the prohibition retires** - it drops to a lint. That is the strongest thing we can say about a fix: it removed a rule from our architecture rather than merely making one unnecessary to tighten.

One note for anyone reading later, not a complaint: because the `ensure_future` hand-out is legal again, the old blanket ban no longer incidentally catches a *hand-written* reentrant await. The library still refuses the real thing at runtime, which is the right place for it; we keep a lint for the shape so it is caught at review time rather than in production.

## One thing we found while verifying this

Our own harness was masking these probes. We wrapped every action implementation in a plain `def` for uniformity, which silently **drops the coroutine** an `async def` action returns - it is never awaited and never runs, so our probes read `exc=None` instead of `ReentrantWaitError`. Running under `-W error::RuntimeWarning` surfaced it (`coroutine ... was never awaited`). Entirely our bug, recorded here only because it is an easy trap for anyone building a generic action registry against this library.
