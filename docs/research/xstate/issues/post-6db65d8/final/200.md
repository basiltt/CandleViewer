## Summary

`_chain_owed` — the debt counter #179 introduced to keep a step's chain open
until a coroutine service's completion lands — **leaks permanently** when the
service's task exits via a `BaseException` that is not `asyncio.CancelledError`
(e.g. `KeyboardInterrupt`, `SystemExit`), and it is settled by a **bare counter
decrement** rather than a debt matched to the invocation that opened it, so a
completion belonging to one invocation can settle a debt opened by another.

## Environment

- Commit: `6db65d8` (merge of #191, "0.8.1 round-7"; `__version__` still
  reports `0.8.0`)
- Python: 3.13.7
- OS: Windows 11 Pro 10.0.26200
- Install: editable (`.venv-main`), `PYTHONIOENCODING=utf-8 PYTHONUTF8=1`

## Minimal reproduction

```python
# -*- coding: utf-8 -*-
"""Standalone repro for R8-10: `_chain_owed` leaks permanently when an
`async def` invoke's task exits via a `BaseException` OTHER than
`asyncio.CancelledError` (e.g. `KeyboardInterrupt`/`SystemExit`), and the
settle path (`_deliver_priority`, interpreter.py:2384-2385) is a bare
counter decrement, not matched to the debt that opened it.

Root cause (interpreter.py @ 6db65d8): `_owe_completion` (:2660-2679)
increments `self._chain_owed` when a coroutine service task is armed and
registers ONE release path, via `add_done_callback`, that fires only if
`t.cancelled()`. `_invoke_service_task` (:2455-2557) catches
`asyncio.CancelledError` (-> task cancelled, handled above) and
`Exception` (routed through `_publish_completion`, decrementing the SAME
counter at :2384-2385). A `BaseException` that is neither -- e.g.
`KeyboardInterrupt`, `SystemExit` -- is caught by NEITHER handler: it
propagates out of the task coroutine, the task ends NOT cancelled, and
both release paths are skipped, so the debt is never settled. Because the
chain-end test ("raised nothing, armed nothing, owes nothing") requires
`_chain_owed == 0`, the leaked debt then blocks a later, wholly unrelated
`always` cycle governed by `maxIterations` from ever reaching chain end --
proof it is a *bare counter*, not a debt matched to its invocation.

Machine: one state `hold` invokes an `async def` service that raises a
`BaseException` subclass; `_chain_owed` must return to 0 once that task ends.

OBSERVED (6db65d8): `chain_owed` stays at 1 forever after the task ends --
the leak (`chain_owed != 0`) is the defect.
EXPECTED: `chain_owed` returns to 0 after the service's task ends.

Exits 1 while the defect is present, 0 once fixed. 20s watchdog.
"""
from __future__ import annotations

import asyncio

from xstate_statemachine import Interpreter, MachineLogic, create_machine


class _SimulatedBaseExceptionExit(BaseException):
    """`BaseException` subclass standing in for `KeyboardInterrupt`/`SystemExit`."""


async def raises_base_exception(i, ctx, e):  # noqa: ANN001
    await asyncio.sleep(0)
    raise _SimulatedBaseExceptionExit("simulated BaseException service exit")


CFG = {
    "id": "r8_10", "initial": "hold", "context": {}, "maxIterations": 20,
    "states": {
        "hold": {"invoke": {"src": "boom", "onDone": {"target": "idle"}}},
        "idle": {},
    },
}


def owed(i) -> int:  # noqa: ANN001
    return getattr(i, "_chain_owed", -1)


async def run() -> int:
    m = create_machine(CFG, logic=MachineLogic(services={"boom": raises_base_exception}))
    interp = Interpreter(m)
    await asyncio.wait_for(interp.start(), 20)
    # Let the task run, raise, and finish; give the loop turns to run any
    # done-callback machinery.
    for _ in range(20):
        await asyncio.sleep(0.05)
    owed_after_raise = owed(interp)

    try:
        await asyncio.wait_for(interp.stop(), 20)
    except asyncio.TimeoutError:
        pass

    print("OBSERVED: chain_owed_after_baseexception=%s" % owed_after_raise)
    print("EXPECTED: chain_owed_after_baseexception=0 (debt released on any BaseException exit)")
    if owed_after_raise != 0:
        print(f"FAIL: chain_owed leaked after BaseException exit: {owed_after_raise}")
        return 1
    print("PASS")
    return 0


async def main() -> int:
    try:
        return await asyncio.wait_for(run(), 20)
    except asyncio.TimeoutError:
        print("FAIL: watchdog timeout (20s) -- interpreter hung")
        return 1


if __name__ == "__main__":
    raise SystemExit(asyncio.run(main()))
```

Exit code: `1`. `interp._chain_owed` remains `1` forever after the invoked

itself is otherwise healthy (`start()`/`stop()` both completed normally).

## Expected behaviour

Per #179's own design contract (interpreter.py:2660-2679 docstring,
`_owe_completion`):

> "Every coroutine service task ends in exactly one of: a `done.invoke` /
> `error.platform` published through `_publish_completion` (which settles
> the debt as it charges), or cancellation because the owning state was
> exited (settled here without a completion). So the count can never leak."

This is a closed disjunction over `{normal completion, Exception, cancellation}`
— it does not account for a `BaseException` that is neither `Exception` nor
`asyncio.CancelledError`. Per Python's own exception hierarchy
(`KeyboardInterrupt`, `SystemExit` derive from `BaseException`, not
`Exception`; a `Task` that ends with such an exception set reports
`t.cancelled() == False`), such an exit is a real, reachable fourth case the
contract does not cover. `_chain_owed` should return to `0` after every
coroutine service task ends, regardless of which of the four ways it ended.

## Root cause analysis

`interpreter.py:2660-2679` (`_owe_completion`):

```python
self._chain_owed += 1

def _settle_if_cancelled(t: "asyncio.Task[Any]") -> None:
    if t.cancelled() and self._chain_owed:
        self._chain_owed -= 1

task.add_done_callback(_settle_if_cancelled)
```

This is the ONLY release path registered against the task directly. It fires
only when the task's final state is "cancelled" (i.e. `CancelledError`
propagated and was not swallowed).

`interpreter.py:2455-2557` (`_invoke_service_task`, the coroutine that
`asyncio.create_task` wraps) has exactly two `except` clauses:

```python
except asyncio.CancelledError:
    ...
    raise  # Re-raise to ensure the task is marked as cancelled.
except Exception as e:
    ...
    self._publish_completion(error_event)  # #179: charged lane
```

`_publish_completion` routes to `_deliver_priority` with
`engine_completion=True`, and `interpreter.py:2384-2385` is the second (and
only other) release site:

```python
if self._chain_owed:
    self._chain_owed -= 1
```

A `BaseException` that is neither `asyncio.CancelledError` nor `Exception` —
`KeyboardInterrupt`, `SystemExit`, or any other direct `BaseException`
subclass — is caught by neither `except` clause in `_invoke_service_task`. It
propagates out of the wrapped coroutine uncaught. The task then finishes with
that exception set and `task.cancelled() is False` (Python's asyncio only
reports `cancelled()` when `CancelledError` was the terminal exception AND the
task's own `cancel()` was requested, or, as here, never at all since nothing
called `cancel()`). Neither release path fires. `self._chain_owed`, which was
incremented to `1` when the task was armed, is never decremented again for
the lifetime of the interpreter.

The settle path itself (`interpreter.py:2384-2385`) is also, independently, a
**bare counter** — `if self._chain_owed: self._chain_owed -= 1` — with no key
identifying which invocation's debt is being paid. Even in the cases that DO
release correctly, a duplicate or unrelated completion arriving while a debt
is outstanding would silently settle someone else's debt rather than its own.
This is confirmed by inspection: there is no per-invocation identifier (id,
token, or set membership check) anywhere near either decrement site.

## Impact

**General.** Any deployment that installs a `SIGINT`/`SIGTERM` handler which
raises inside a running coroutine service (the standard pattern for
`KeyboardInterrupt` delivery into asyncio tasks on some platforms), or any
service code that legitimately allows `SystemExit`/`BaseException` to
propagate (e.g. a service that calls `sys.exit()` internally, or is wrapped by
third-party instrumentation that re-raises `BaseException` subclasses for
control flow), leaks the debt counter permanently. Because the chain-end test
requires `_chain_owed == 0`, this can silently disable `maxIterations`
enforcement for chains that pass back through the state that owned the
leaking invocation — reopening exactly the unbounded-loop hazard #179 was
written to close, for reasons that have nothing to do with the chain that
eventually gets stuck.

**Order-management scenario.** An OMS commonly wires a service invocation to
an external venue/broker call and treats an operator-triggered
`KeyboardInterrupt` (Ctrl-C during a maintenance window, or a supervisor
process delivering `SIGINT` to gracefully quiesce a worker) as an
abnormal-exit signal that should NOT be swallowed by application code — it is
meant to propagate. If that call is in-flight as an invoked service when the
signal lands, this defect leaves `_chain_owed` permanently elevated on the
surviving interpreter (if the process does not immediately exit, e.g. under a
sidecar or web) or corrupts any pre-crash diagnostics that inspect the debt.
Any order-state machine that later transitions through a chain that should
have been governed by `maxIterations` on that same interpreter instance rides
with the safety net silently disabled.

## Proposed fix

Two independent changes:

1. Release the debt for ANY terminal outcome of the coroutine service task,
   not just `t.cancelled()`. Register the release in a `finally`/broad
   `except BaseException` inside `_invoke_service_task` itself (which already
   distinguishes `CancelledError` and `Exception` — add a final
   `except BaseException` that also settles the debt before re-raising), or
   change the `add_done_callback` to release unconditionally on ANY
   task-done state that did not already go through `_publish_completion`
   (e.g. `if task.done() and not <already settled via completion>`).
2. Key the debt to the invocation that opened it (a `set` of invocation ids,
   or a per-invocation token) instead of an aggregate `int`, so a completion
   settles its own debt and cannot cancel out an unrelated invocation's debt.
