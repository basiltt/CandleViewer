# Comment for issue #181 — `start()` hangs on a slow invoked child

**Action:** **reopen, narrowed**
**Disposition:** **FIXED for coroutine entry actions; NO-OP for plain `def` entry actions**

---

Verified on `main` @ `6db65d8` (merge of PR #191, `fix/0.8.1-round7`; unreleased
0.8.1) as part of our adoption audit (#26). Build identified **by commit** —
`__version__` still reports `0.8.0` on this tree. CPython 3.13.7, Windows 11,
fresh venv. Every claim below was reproduced in a clean process before it was
written down, and **every service-bearing check was run with both `def` and
`async def` services**.

**Fixed for the case it was filed against.** With a coroutine child entry action,
`start(children_timeout=0.2)` returns in ~2.01 s instead of hanging 30 s, the WARNING
fires, and the child is still addressable afterwards. All three pinned tests pass.

**Reopening narrowly: the bound is a no-op against a plain-`def` child entry action,
and it suppresses its own WARNING.** The unmet criterion, quoted from `docs/api/index.md:701`,
is "a child's bring-up runs its entry actions — user code (#181)", with **no
restriction to coroutine actions** — yet the measurements below show the bound holding
only for the coroutine case. Filed separately as **R8-03**. Measured at this commit:

| children_timeout | shape | elapsed | WARNING |
|---|---|---|---|
| 0.2 | 1 child, `def` entry action sleeping 3 s | **3.00 s** | none |
| 0.2 | 5 children | **15.0 s** | none |
| 0.2 | 50 children × 1 s | **50.04 s** | none |
| 0.05 / 0.2 / 1.0 / `None` | 20 children × 100 ms | **2.02 s** in all four | none |

`interpreter.py:601` → `_await_actor_bringups:2753` uses `asyncio.wait(timeout=)`,
which cannot pre-empt a non-yielding `def` entry action running on the loop thread
inside `child.start()` (`:2973`); bring-ups are serial, which is the exact N × D
scaling above; and the WARNING sits on the same timeout path, so it is suppressed with
the bound. `docs/api/index.md:701` justifies the parameter precisely by "a child's
bring-up runs its entry actions — user code (#181)", with no restriction to coroutine
actions. The `service_executor` / `service_pool_size` off-loading (#149/#173) covers
plain **services** only — there is no executor path for actions.

**The guarding test cannot fail.** `tests/test_round7_findings.py:557` parametrises
over `KINDS`, but gives the `def` arm `time.sleep(0.05)` against the `async` arm's
`asyncio.sleep(3.0)` — the `def` branch never exceeds the bound;
`test_bringup_timeout_is_observable` is async-only. Giving the `def` arm work that can
actually exceed the timeout makes it fail immediately.

Secondary, same code path: the bound is **aggregate**, not per child — 50 children at
1 s each take 50 s under a 0.2 s bound. A per-child bound is what the docs read like
they promise.

Thank you — round-8 scorecard and the full write-up are in #26.
