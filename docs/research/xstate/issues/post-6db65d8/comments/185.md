Confirmed fixed. Both mutations — `machine_hash: null` and the key removed entirely —
are independently refused as drift on a `version >= 1` payload, and the `version: 0`
and `verify_machine_hash=False` opt-out paths are unaffected. A 300-mutation corrupt
fuzz shows exactly the 10 null-hash cases moving from "accepted" to "refused" with
#185's message verbatim.

Closing. One note, low severity, filed separately rather than held against this issue:
a `version: 0` (or absent-`version`) blob still skips the check entirely, because
`persistence.py:320-329` computes `versioned = bool(version)`. We originally rated that
as a security bypass and then **refuted our own finding**: `structure_hash` is a public,
unkeyed, deterministic SHA-256 prefix of the machine definition — a checksum, not a MAC
— so an attacker who can edit the blob can simply write the *target* machine's hash and
leave `version: 2` intact. The downgrade path confers no additional capability. What is
left is the non-adversarial case #185's own rationale names: lossy transit that drops a
null `machine_hash` may equally drop `version`. That cannot be closed in-band, since
genuine 0.7.x blobs carry neither field and must still restore. Suggested: an API
addition (`expected_machine_hash=` / `minimum_version=1`) plus a docstring line saying
v0 is unchecked **by design** and `structure_hash` is a checksum, not an auth tag.

One knock-on worth flagging for other users: this fix correctly invalidates any
hand-built test fixture that writes `version: N` without a `machine_hash`. Two of ours
were stale in exactly that way, and the failure presented as a regression until we
traced it here.
