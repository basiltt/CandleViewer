# Comment for issue #174 — plain `def` services block the machine's own `after` timers

**Action:** comment (documentation acknowledged; no code change expected)
**Disposition:** **DOCUMENTED-ONLY — behaviour unchanged, documentation correct and now load-bearing**

---

Verified on `main` @ `6db65d8` (merge of PR #191, `fix/0.8.1-round7`; unreleased
0.8.1) as part of our adoption audit (#26). Build identified **by commit** —
`__version__` still reports `0.8.0` on this tree. CPython 3.13.7, Windows 11,
fresh venv. Every claim below was reproduced in a clean process before it was
written down, and **every service-bearing check was run with both `def` and
`async def` services**.

Acknowledged, and the documentation at `docs/_guide/production-characteristics.md:93`
is accurate on re-measurement: a plain-`def` service still blocks its own machine's
`after` timers (~514 ms against a 100 ms budget, unchanged in code). The `async def`
remedy now fires near on-time (125 ms) as a side effect of this release's round-7
rework, which makes the prescribed fix genuinely prescriptive rather than aspirational.

Worth recording that this documentation turned out to be **load-bearing** for us in a
way that may not be obvious. We opened round 8 with a Blocker-rated finding claiming a
plain `def` service runs inline on the loop thread and blocks the whole process. On
refutation that claim was **false** — #149 moved it to `loop.run_in_executor`
(`interpreter.py:2811-2836`), the stall is `:1571-1577` awaiting
`_await_inline_services()`, and it starves only that machine's inbox while other
interpreters keep running — and this page says so explicitly, including the "other
machines unaffected" note and the remedy. That downgraded a Blocker to a High on the
strength of the docs alone. Good documentation did real work here.

What survives after that refutation is narrower and is filed separately: a `def`
service is **uncancellable** (a mid-service `CANCEL` loses to `done.invoke` on the
priority lane), and a `def` invoke is **not unwound** by `actionErrorPolicy:
"rollback"` nor by an `always` roll-forward, because the executor handoff happens at
entry, before the `always` chain and the rollback epilogue — whereas the `async def`
task's arming *is* unwound. Given the documentation above, that asymmetry may be worth
a sentence on the same page even if the behaviour does not change.

Thank you — round-8 scorecard and the full write-up are in #26.
