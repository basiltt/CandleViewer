Verified on main @ 5327ba6 (pre-0.8.1). **Disposition: keep open**, re-scope/re-tag as tracking the "provenance-tagged system events" work explicitly deferred to 0.9.

What shipped (and passes):
- `events.SYSTEM_EVENT_PREFIXES` is now a documented, importable constant (single source of truth, previously duplicated inline).
- `create_machine()` emits a `UserWarning` for an `on` key that names a reserved prefix (`done.`, `error.`, `after.`, `xstate.`, `___xstate`) but isn't shaped like a real engine event (`done.review`, `error.validation`) — confirmed the warning fires with a clear message and does **not** false-positive on engine-shaped keys (`done.invoke.<id>`, `error.platform.<id>`, `after.<ms>`).
- The reserved prefixes are now documented across the guides (events, core-concepts, interpreters, json-config, changelog).

What did **not** ship (the issue's actual acceptance criteria):
- A user-sent `error.myapp.validation` or `done.review` is still invisible to `on: {"*": ...}`.
- `onUnhandled: "error"` still does not trip for an unhandled `done.review` / `error.validation`.
- 2 of the 3 named tests (`test_user_event_in_reserved_namespace_matches_wildcard`, `test_user_event_in_reserved_namespace_trips_onunhandled_error`) are absent, consistent with the runtime behaviour being unchanged; the CHANGELOG explicitly defers this ("Provenance-tagged system events… are planned for 0.9").

This is a reasonable interim step (build-time visibility over silent runtime loss) but does not close the issue as filed — the silent-drop defect itself is still reachable exactly as reported. Recommend keeping open, tagged for 0.9, and adding the deferred-to-0.9 note as a comment for anyone re-triaging.

## Ride-along finding — M-5 (Low): the build-time warning is narrower than the runtime rule

Three gaps in the new guard, all small, all in the same direction (the warning
is narrower than the behaviour it warns about):

1. **Case variants are missed.** `on: {"DONE.review": ...}` and
   `"Error.validation"` do not warn, but the runtime matcher's prefix check
   treats them the same way as the lowercase spellings. Recommend
   case-insensitive prefix matching in the guard.
2. **`send()` is not covered.** The warning fires for reserved-namespace **`on`
   keys** only. A caller doing `interp.send("error.myapp.validation", ...)`
   still gets the silent drop with no build-time or runtime signal — and
   `strict` exempts reserved prefixes, so it is not caught there either.
3. **`SYSTEM_EVENT_PREFIXES` is importable but not extensible.** Making it a
   documented constant is a genuine improvement over the previous inline
   duplication. A consumer who wants to reserve an additional namespace (or,
   more usefully, to assert that none of their own event names collide) has to
   reimplement the matcher's normalisation rules to do it reliably. A small
   public helper — `is_system_event(name) -> bool` — would close that.

## Ride-along finding — F-8 (Low): a typo'd static `raise` into a reserved namespace is not caught at build time

`#51`'s new build-time validation of static `raise` targets on `strict`
machines is a real improvement, but `strict` exempts reserved prefixes, so
`{"type": "raise", "event": "done.reviw"}` (typo intended) is accepted at build
time and silently dropped at runtime. This is the same root cause as the issue
above and will be closed by the same provenance work — noting it so it is not
re-discovered separately.

## One new risk introduced by the warning

Because `create_machine()` now warns for `done.review` / `error.validation`-style
`on` keys, a CI configured with `-W error` will **break machines that
previously worked** (with the silent-drop bug). That is arguably the right
trade, but it is a behaviour change worth a line in the release notes rather
than a surprise.

## ⚠️ SUPERSEDED on `main@3c527b0` (2026-09-18, after PR #83) — DO NOT POST AS WRITTEN

PR #83 (`2459c82`) shipped #79 in full. **Every "What did not ship" bullet above
is now wrong**, and the M-5 ride-along that was to accompany this comment has an
obsolete premise. Re-verified on `3c527b0`:

- System status is decided by **provenance**, not by name:
  `events.is_system_event()` returns `True` only for `DoneEvent` / `ErrorEvent` /
  `AfterEvent` and `Event(system=True)` sentinels. `is_system_event(Event("done.review"))`
  → `False`.
- `"*"` now matches user events in reserved namespaces. Probe F6:
  `matched_by_star: ['ordinary', 'error.validation', 'done.review']`
  (was `['ordinary']`).
- `strict` now rejects them. `probes/main-3c527b0/p1_strict_user_system.py`:
  `done.review`, `DONE.review`, `error.validation` → `UnknownEventError`.
- `onUnhandled` trips for them (same provenance check in
  `_handle_unhandled_event`).
- The build-time reserved-namespace warning praised above is **withdrawn**
  (`validation.py` −50 lines) — its premise no longer holds. Probe F5 now reports
  `no-warning` for every reserved `on` key, by design.

**New disposition: close.** The acceptance criteria are met.

**Residual, if a follow-up is wanted (small, different shape):**
`MachineNode.is_known_event` still treats anything prefix-matching
`ENGINE_EVENT_SHAPES` as known. On a `strict` machine, `after.5` and
`xstate.foo` are still accepted silently while `done.review` is correctly
rejected — those two shapes are matched by prefix rather than by structure, so a
typo in them stays invisible to `strict`.
