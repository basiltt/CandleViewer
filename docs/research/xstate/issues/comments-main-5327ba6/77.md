## Ride-along finding — F-9 (Low): the chain-depth ceiling is silent, and the engines disagree by one

The per-chain budget behaves correctly, but two details are worth pinning:

- A **legitimate** 1001-deep chain is cut. That is the documented contract, but
  the cut is entirely silent: `status` stays `"running"`, `last_transition_ok`
  stays `True`, no hook fires, and only a log line records it. This is the same
  gap as the "should raise rather than drop" acceptance criterion above.
- Sync and async disagree by exactly one step on where the cut lands
  (`s1000` vs `s1001`), despite the CHANGELOG's parity claim
  (`repro/f_chain.py`, `repro/f_parity.py`). Off-by-one, harmless in itself,
  but it means a parity test written against an exact depth will be
  engine-specific.

## Three defects introduced by this fix

Filed separately, all in this fix's own code path — noting them here so the
issue's reviewers see them together:

1. **(High)** The `tripped` flag is scoped to the drain, not the chain, so one
   self-feeding event starves every later unrelated event's one-deep `raise` in
   the same `send_events()` batch. The async engine delivers all of them.
2. **(Medium)** A `done.invoke` from a sync service is classed as
   self-generated; after a trip the completion is dropped and the machine parks
   permanently in the invoking state.
3. **(Medium)** On the async engine, `max_iterations` does not bound an
   action-side `send()` at all, so the entry's parity claim ("they do now
   [agree], and an engine-parity test pins it") holds for the `raise` built-in
   only.
