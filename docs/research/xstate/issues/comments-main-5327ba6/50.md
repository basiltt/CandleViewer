Verified on main @ 5327ba6 (pre-0.8.1). This is **FIXED**.

`RealClock.set_timeout` now takes an explicit `sync: Optional[bool] = None`
kwarg, and `BaseInterpreter._clock_sync_lane` (`False` for the async
engine, `True` for `SyncInterpreter`) decides the lane at construction
time — not by inspecting whether an asyncio loop happens to be running on
the calling thread. Concretely: building a `SyncInterpreter` inside
`asyncio.run(...)` no longer starts any OS thread for `after`, the state
does not advance on a bare `await asyncio.sleep()`, and `tick()` delivers
the elapsed deadline on the caller's thread as expected. A 0.8.0-protocol
`Clock` whose `set_timeout` has no `sync` parameter is detected once via
`_accepts_kwarg` at construction (`BaseInterpreter._clock_accepts_sync`)
and called with the legacy signature exactly once per timer — no retry,
no double-call, its own errors surface unchanged.

Verified with a new standalone script exercising: (1) construction inside
a running loop + no new threads + no advance without a pump + `tick()`
delivery, (2) the sync lane surviving an ambient running loop, (3) a
hand-written legacy (no-`sync`-kwarg) clock still working with exactly one
`set_timeout` call. All 9 assertions pass; original repro also passes
(exit 0).
