The tripped-chain drop path in `sync_interpreter.py` (~617-730) now distinguishes `is_completion` (`DoneEvent` / `ErrorEvent`) from ordinary self-generated events: a completion in the about-to-be-discarded tail is re-queued ahead of it rather than dropped, and a completion that *is* the tripping event is processed directly rather than re-queued (which would re-trip forever). A completion is still *counted* against the budget, so a pathological rollback -> re-arm -> done cycle stays bounded - by design, and exactly criterion 4's guarantee.

One scope note we are filing separately rather than holding against this issue: the "completions are never discarded" sparing is implemented on the **sync** engine's drop path only; we could not find the equivalent guard on the async engine, and the CHANGELOG wording reads as engine-neutral. Worth either mirroring it or narrowing the claim.
