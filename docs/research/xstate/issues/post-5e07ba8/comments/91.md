## The unmet criterion, quoted

From the issue's **Expected** section:

> *"Independently, the config side should be checked: two required names that normalise equal and resolve to one callable should **at least warn**."*

This was not implemented. `resolve_aliases` only ever inspects the **registry** side (`by_key`); it never looks at the set of *required* names the config asked for, and it sees one `name` at a time via the `required` iterable, so it has no vantage point from which to notice that two required names collapsed onto the same key.

## Reproduced fresh on this commit

`91_alias_shadow_warning.py`, run in a fresh process on `5e07ba8`, exit 0. The `f_collide.py` shape — a config declaring `["store_user", "storeUser"]` as two entry actions with exactly **one** callable registered:

```
C3 (informational): distinct config names -> one registered callable
produced UserWarning(s): []
```

No warning fires. For contrast, the criterion-1 shape does warn, correctly:

```
UserWarning: Logic name 'fetchData' is registered exactly and also as ['fetch_data'],
which differ only by case or separators but are DIFFERENT callables. The exact key
'fetchData' is used; remove the others or make them the same object.
```

The companion shape in `issues/new-main/repro/f_loader_twoname.py` (one implementation satisfying two distinct config names via `logic_modules`) still exits 0 with "both bound to one impl" — the same gap reached through the loader rather than the registry, which suggests the check belongs at the point where required names are collected rather than inside `resolve_aliases`.

## Severity and what we would accept

**Low.** Nothing binds incorrectly — both config names call the one implementation that exists, which is very likely what the author meant. What is lost is the chance to flag a near-certain typo: a machine JSON that says `store_user` in one place and `storeUser` in another looks like two distinct actions to a reader and is one action at runtime. A single `UserWarning` naming both config spellings would close it.

**Reopening scoped to criterion 3 only.** We are not asking for the exact-match precedence decision to be revisited; option (a) was the right call and the registry-side warning is correct as shipped.
