## The unmet criterion, quoted

> *"The unhandled case is decided and documented: EITHER both engines escalate, OR both park — not one of each."*

The sync engine now escalates (fails the parent). The async engine still parks. This is the exact asymmetry #99 was filed to close — it has **moved to the other engine** rather than been closed.

We ruled out a timing race with a separate direct check at a 1 s settle: the async task logs `💥 Invoked machine 'kid' ended in error; firing onError.` immediately, but the parent's status never changes — `final running None {'p.w'}`.

## Root cause and the fix we would expect

`Interpreter._deliver_invoked_completion` (`interpreter.py:2039-2073`) — the invoked-**machine** completion path — has no `_has_error_handler` / `_fail()` call in its `status == "error"` branch. The callable-service path a few hundred lines above it in the same file (`_invoke_service_task`, ~line 1858) does. The fix is mechanical: mirror that pairing.

This is pre-existing rather than a regression — the original report noted it for sync, and round 3 patched only the sync side — but it is squarely inside criterion 4.

## Why this is worth reopening rather than shrugging at

A parent whose invoked child machine fails with no `onError` declared sits at `status='running', error=None` forever. That is indistinguishable from a healthy machine waiting on a slow child, on the engine we (and most async users) actually run. There is also no test anywhere in the suite for "async parent invokes a child machine that fails, with no `onError` declared" — which is precisely why this survived round 3. A test of that shape, parameterised over both engines, would have caught it and would keep the two engines honest afterwards.

**Reopening scoped to `_deliver_invoked_completion` only.** If you would rather track it as a fresh follow-up issue than reopen this one, that works equally well for us — the important thing is that the decision be made once and applied to both engines.
