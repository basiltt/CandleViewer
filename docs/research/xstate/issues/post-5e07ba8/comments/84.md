```
Async after replay : {'state': 'filled', 'original_receipt_still_deferred': True, 'open_receipt_deferred': False, 'open_receipt_changed': True}

RESULT: PASS
```

**One behaviour worth a line in the guide**, since the acceptance criteria did not spell it out: the *original* `Receipt` is a point-in-time snapshot and is never retroactively mutated or re-resolved. After `OPEN` causes the parked `FILL` to replay and drive the machine to `filled`, the `FILL` receipt still reads `deferred=True, changed=False` forever, and there is no second notification against it. A caller that holds only that first receipt and never inspects the interpreter again has no path back to the outcome for that specific event. Both engines agree. That matches the "cheapest fix" design the issue itself proposed, so we are not treating it as a defect - but callers will `await` the original receipt a second time expecting an update unless the docs say otherwise.

Separately, and not against this issue: `_deferred_this_step` keys on `id(event)` in a set that only shrinks on a receipt path, which leaks ids and produces false `deferred=True` on fully-handled events in fire-and-forget traffic. Filed on its own with a repro.

No regressions observed against the earlier verification sets, the full suite (3 276 passed / 0 failed, coverage 90%) or our probe baseline.
