# Comment for issue #85 — `Event(system=True)` forgery - provenance not forgeable

**Action:** comment
**Disposition:** CONFIRM CLOSED (all acceptance criteria met)

Verified on main @ `5e07ba8` (pre-0.8.1), as part of our adoption audit (#26). Build identified **by commit** — `__version__` still reports `0.8.0` on this tree. CPython 3.13.7, Windows 11. Verification script: `issues/verify-main-5e07ba8/85_provenance_not_forgeable.py`.

All five acceptance criteria are met, and the forgery surface is closed at the constructor rather than filtered downstream.

| # | Acceptance criterion | Result |
|---|---|---|
| 1 | A user `Event` passed to `send()` / `send_threadsafe()` / `SyncInterpreter.send()` is subject to `strict`, `event_schemas`, `onUnhandled` and `"*"` regardless of any `system` value | OK - the constructor has no `system` parameter at all, so there is no value to set |
| 2 | Engine-minted events remain exempt | OK - a `system_event()`-minted event is exempt from `onUnhandled: "error"` |
| 3 | Both engines identical | OK - async and sync both show `"*"` matching a plain event, `strict` rejecting it, `onUnhandled` tripping on it |
| 4 | Tests cover `"*"`, `strict`, `event_schemas`, `onUnhandled`, both engines, `send_threadsafe` | OK - `tests/test_round3_findings.py::TestProvenanceNotForgeable` (4 tests); our script adds `send_threadsafe` and further forgery vectors |
| 5 | `Event.system` documented or made private | OK - read-only `@property` with docstring (`events.py:126-129`); the criterion's "or" is satisfied by "documented + read-only" |

Forgery vectors we probed beyond the issue text, all closed:

```
[PASS] Event(system=True) raises TypeError
[PASS] Event.system is read-only
[PASS] copy.copy / copy.deepcopy of a user event stays non-system
[PASS] dataclasses.replace cannot forge provenance
[PASS] pickle round-trip of a user event stays non-system
[PASS] object.__setattr__(_provenance, True) does not forge (identity check)
[PASS] object.__setattr__(_provenance, <other object>) does not forge
```

The identity check against the unexported `_ENGINE_MARK` sentinel (`events.py:240`) is what makes this robust: an attacker would have to obtain a reference to the sentinel object itself, which is never exported.

Informational, not a bypass (safe direction): `dataclasses.replace()` on an *engine*-minted event drops provenance rather than preserving it, because `replace()` does not pass `init=False` fields to `__init__`. Worth knowing for anyone who expects `replace()` to clone an engine event and keep it exempt - we have filed the `_detach()` instance of this separately, since that one sits on a live `send(wait=True)` path.

Our old pre-fix repro `post-3c527b0/repro/g1_forge_system.py` now raises `TypeError` at the `Event(..., system=True)` call itself, which is the correct outcome; that probe is retired.

No regressions observed against the earlier verification sets, the full suite (3 276 passed / 0 failed, coverage 90%) or our probe baseline.

**Disposition: confirming closed.**
