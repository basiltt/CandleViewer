# #173 — hard-coded `ThreadPoolExecutor(max_workers=4)` for plain services

**Classification: FIXED**

## Acceptance criteria (from issue body)

1. A public `service_pool_size=` argument on `Interpreter`.
2. Documentation of the default limit and its interaction with macrostep
   blocking (the "(N+1)-th concurrent service waits" behaviour).

## Fix location

`src/xstate_statemachine/interpreter.py`:
- `DEFAULT_SERVICE_POOL_SIZE: int = 4` (module-level constant, line 212).
- `Interpreter.__init__(..., service_pool_size: int = DEFAULT_SERVICE_POOL_SIZE)`
  (line 285), validated (`>= 1`, line 360-361), stored as
  `self._service_pool_size` (line 362).
- `_get_service_executor()` (~line 2556-2560) now builds
  `ThreadPoolExecutor(max_workers=self._service_pool_size, ...)` instead of
  a hard-coded `4`.
- Docstring (line 309-317) documents the default, the (N+1)-th-waits
  behaviour, and explicitly says "size the pool to the number of plain
  services a single configuration can have in flight."

## Verification

Script: `173_service_pool_size.py` (this directory).

```
[1] DEFAULT_SERVICE_POOL_SIZE == 4: True (=4)
default pool: peak=4 elapsed=0.42s max_workers=4
[2] default behaviour unchanged (capped at 4, two waves): True
pool=8   : peak=8 elapsed=0.22s max_workers=8
[3] service_pool_size=8 widens concurrency and is faster: True
[4] docstring documents the knob + macrostep-blocking interaction: True
RESULT: PASS
```
exit code: `0`

- Default behaviour is preserved (still 4 workers, 8 services run in two
  waves of 4, ~0.42s — matching the original repro's finding).
- `service_pool_size=8` genuinely widens the internal executor to 8
  workers, reaches peak concurrency 8, and completes in ~0.22s (one wave),
  ~2x faster than the default-pool case.
- The docstring documents both the default and the macrostep-blocking
  interaction.
