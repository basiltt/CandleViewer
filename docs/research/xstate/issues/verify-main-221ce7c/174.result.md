# #174 — `after` lateness under load (100-iteration busy loop, 50ms budget missed)

**Classification: DOCUMENTED-ONLY**

## What the issue asked for

A regression against `5e07ba8`: under a 100-iteration busy loop, observed
lateness on a 50ms `after` budget was 88-92ms — the round-5 CHANGELOG's
"per-macrostep settle budget" bounds *iterations per macrostep*, not
wall-clock lateness. A second, related probe showed an `after: 100` armed
alongside a 500ms plain-`def` service firing at ~528ms (~428ms late),
"arguably by design" but undocumented.

## What actually changed on 221ce7c

Nothing in the timer-delivery code path. The CHANGELOG "Changed" section
(not "Fixed") states:

> **Production Characteristics** documents that a plain-`def` service
> blocks its own machine's `after` timers for its whole duration (#174) —
> an `after: 100` armed alongside a 500 ms plain service fires at ~500 ms,
> not 100 — make the service a coroutine if a timer must interrupt it —
> and that the `maxIterations` settle budget bounds microsteps, not
> wall-clock lateness.

`docs/_guide/production-characteristics.md` (line 93) now contains:

> "A plain-`def` service blocks its own machine's timers for its whole
> duration (#174). A non-coroutine `invoke` runs on a worker thread, but
> the macrostep that entered the invoking state *awaits its result* before
> it completes... A due `after` on that machine is delivered only when
> that macrostep ends, so an `after: 100` armed alongside a 500 ms plain
> service fires at ~500 ms, not 100."

This is a **documentation change**, not a bound on lateness. No new
"lateness budget", pre-emption, or timer-priority-boost mechanism was
added; the busy-loop class (independent of plain-service blocking) is
also not bounded — only "documented" implicitly via the same
"settle budget bounds microsteps, not wall-clock lateness" sentence.

## Verification

Script: `174_after_lateness_documented_only.py` (this directory).

```

busy-loop lateness: 30.1ms over the 50ms budget
[2] 50ms budget still missed under busy-loop load: True
service-blocks-timer elapsed: 520ms final_states=['s.timeout']
[3] after:100 blocked behind 500ms plain service (documented class): True
RESULT: PASS (confirms DOCUMENTED-ONLY, not fixed)
```
exit code: `0` (this script's convention: `0` == "confirmed
documented-only, not fixed", matching the classification)

- Docs criterion: satisfied — the "blocks its own machine's timers" /
  "~500ms not 100" language is present, referencing #174.
- Behaviour criterion: **the 50ms budget remains missed** under a
  100-iteration busy loop (30.1ms over budget on this run; magnitude
  varies by run/machine load but is consistently well above zero, in the
  same class as the original 88-92ms finding — the exact number is
  environment-sensitive, the miss itself is not).
- The `after: 100` vs 500ms plain-service class reproduces exactly as
  described: the machine takes ~520ms, not ~100ms, because the entering
  macrostep awaits the in-flight plain service before either the `after`
  or `done.invoke` transition can be taken.

## Assessment vs. acceptance criteria

- "State what was documented": the plain-service-blocks-timers behaviour
  and the `maxIterations` vs wall-clock-lateness distinction, both in
  `production-characteristics.md`.
- "Whether the 50ms budget remains missed": **yes, it remains missed** —
  confirmed on 221ce7c by both the original repro and the independent
  verification script above. This is accurately classified as a
  documentation-only change, not a fix, and the CHANGELOG's own section
  header ("Changed", not "Fixed") reflects that.
