## Design rationale assessed

`SyncInterpreter.tick()` fires whatever is due **at the moment it is
called**, then walks any *newly-armed* deadline only if it is *also already
due right then* — it does not re-poll wall-clock time after taking a
transition. Because `after` delays are relative to *when the state was
entered*, a transition taken by `tick()` arms its state's own `after` timer
relative to "now" (the instant `tick()` runs), which by construction is not
yet due. So a `50/50/50` real-delay ladder, after one flat `time.sleep(0.25)`
and a single `tick()` call, only drains the first link — exactly the
behaviour reported. This is not a bug in the drain loop (which does
correctly re-check the timer heap on this call, draining any deadline that
actually is already due) — it is a mismatch between the reporter's implicit
model ("tick() walks all chained deadlines if I slept long enough for the
whole chain") and how relative `after` timers actually re-arm. The async
`Interpreter`'s settle loop reaches the terminal state in one wall-clock
`asyncio.sleep(0.25)` because it is driven by the clock's own callbacks
firing in real time as each link becomes due, not because a single
"settle pass" telepathically walks a chain of not-yet-armed timers.

**Assessment: the rationale holds.** `tick()` is not, and cannot reasonably
be, a substitute for actually letting wall-clock time pass between rungs
when using a `RealClock`; a caller who wants deterministic single-call
draining of a real-delay ladder needs a `SimulatedClock` (whose `increment()`
does advance the clock and re-checks after each fired timer) or must call
`tick()` once per rung after that rung's real delay has elapsed.

**Yes.** `src/xstate_statemachine/sync_interpreter.py:1480-1502`
(`tick()` docstring):

> "fires due timers on the state's [...] does NOT advance [...] a ladder of
> real delays [...] needs one `tick()` per rung, each after that rung's

This matches the CHANGELOG's #122 entry verbatim in spirit ("`tick()`

sync expectation.").
