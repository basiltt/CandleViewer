## Root cause of the residual gap

`_invoke_service` (`interpreter.py`) dispatches on
`_is_plain_sync_callable(service)`:

- **Plain callables** run inline via `_invoke_plain_service_inline`, whose
  completion is delivered through `_deliver_priority`, which — per the #166/
  #167/#168 fix — increments `self._raise_depth` **only while
  `self._processing` is true** (i.e. delivered *during* the macrostep that
  entered the invoking state). That is what makes the plain-service variant
  bounded: the whole rollback→re-arm→done lap for a plain service completes
  synchronously inside one macrostep, so its `done.invoke` delivery lands
  while `_processing` is still `True` and gets charged.

- **Coroutine services** are scheduled as a real `asyncio.Task`
  (`_invoke_wrapper` / `_invoke_service_task`, `interpreter.py:2515-2522`).
  Their `done.invoke.*` event reaches the machine via `await self.send(done_event)`
  (`interpreter.py:2411`), called from the task's own coroutine context —
  **not** from inside `_process_event_and_transient_transitions`, so
  `self._processing` is `False` at delivery time. `send()`'s dispatch
  (`interpreter.py:845-860`) only charges `_raise_depth` when
  `_issued_from_own_action()` is true (i.e. the send happens on the
  interpreter's own run-loop task from inside a user action) — the service
  task is a *different* asyncio Task, so `_issued_from_own_action()` is
  `False` and `_ACTIVE_ACTION_OWNER` isn't set. The event falls through to
  the plain `self._enqueue(event_obj)` branch, exempt from the chain budget
  by construction, exactly as before the fix — because `_deliver_priority`'s
  `self._processing` check and `send()`'s `_issued_from_own_action()` check
  both key off "is this happening synchronously inside a macrostep", which a
  scheduled coroutine service's completion never is, no matter how tight its
  rollback→re-arm loop is.

So the CHANGELOG's claim — "a completion the machine produced *while
processing* … is charged to the chain budget" — is correct only for the
inline (plain-callable) invocation path. The genuinely asynchronous
(`async def`) service path, which is the *documented, recommended* way to
write a slow/real service and is exactly what the original #167 issue
reported, is untouched: the rollback/re-arm/done cycle it drives is still
completely unbounded on `221ce7c`.

## Note on `tests/test_round6_findings.py::TestAsyncRollbackRearmCycleBounded`

The pinned regression test for #167 uses a **plain `def svc`**
(`test_round6_findings.py:124`), not a coroutine, which is why the suite is
green while the coroutine-service path (the shape the original issue and
its repro actually used) remains broken. The pinned test does not cover the
regressed case.
