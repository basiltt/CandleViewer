# #181 — start() bounds the wait for invoked children

**Classification: FIXED**

## Acceptance criteria (from GH issue #181, High)
A timeout knob exists for `start()`'s wait on invoked-child bring-ups; on
timeout a WARNING is logged and the interpreter is left running.

## Cell table

| service kind | children_timeout | start() elapsed | status during wait | WARNING logged |
|---|---|---|---|---|
| `def` | 0.1s | ~1.0s (cannot be pre-empted — documented) | running | yes |
| `async def` | 0.1s | ~0.11s (bounded) | running | yes |

Both cells pass: `async def` entry actions ARE bounded in wall-clock terms
(bring-up yields at the `await`); `def` entry actions cannot be pre-empted on
a single-threaded event loop (Python has no mechanism for this), but the
overrun is now always reported via WARNING — which is the whole of what
#181/#194 promised (see `interpreter.py:2830-2891`, `start()` docstring at
`interpreter.py:492-521`).

## Residual

None against the acceptance criteria. The library is explicit that a
non-yielding `def` entry action cannot be pre-empted on a single OS thread —
this is a Python-level limitation, not a defect in the fix, and is now
documented and observable via the WARNING.
