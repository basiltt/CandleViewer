## Acceptance criteria (from gh issue #201)
The round-7 CHANGELOG claim "both service kinds trip at the same lap count
as the sync engine" was one lap off for a cycle starting from the initial
state (22 vs 23): the first completion the initial descent produces is the
chain's seed, not a link, so `async def` under-counted by one lap relative
to sync/`def`. Criteria verified:
1. `invoke` ping-pong starting from the INITIAL state: sync, async-engine
   `def`, and async-engine `async def` must all trip `maxIterations` at the
   identical lap count (no seed/link off-by-one).
2. `rollback + onDone`: the round-8 fix restates the promise precisely —
   both async lanes (`def`, `async def`) trip `RunawayChainError`/
   chain-budget at the same lap; the sync engine does NOT re-arm a
   rolled-back invoke inside the same drain and instead stops early with
   the raised `RuntimeError` after the first rollback. This asymmetry is
   documented as intentional, not a residual bug — the check verifies it
   reproduces exactly this shape (not something broader).

## Fix location
`src/xstate_statemachine/interpreter.py`:
- `_seed_pending: bool` field (line 446-450): "`True` between `start()`
  returning and the loop's first ... whose completion is still in flight;
  that completion is the seed [not a link]".
- Set at end of `start()` (line 657-659): "The run loop gives the first
  such completion seed standing once (`_seed_pending`)."
- Consumed in the run loop (line 1642-1654): when `_seed_pending` is true
  and the delivered event is a system/engine event, it is treated as the
  chain's seed (not charged as a link), then `_seed_pending` is cleared —
  this is the one-time correction for the off-by-one identified in #201.
