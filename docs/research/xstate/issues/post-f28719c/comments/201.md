Verified on `main` @ `f28719c` (merge of PR #202, `fix/0.8.1-round8`; unreleased
0.8.1) as part of our adoption audit (#26). Build identified **by commit** —
`__version__` still reports `0.8.0` on this tree, so nothing here should be keyed
on the version string. CPython 3.13.7, Windows 11, fresh venv. Every claim below
was reproduced in a clean process before it was written down, and **every
service-bearing check was run with both `def` and `async def` services**.

Confirmed fixed. Seeding initial-descent completions rather than charging them was the right root cause: async lap counts now match the sync engine exactly, and the documented rollback + `onDone` asymmetry is stated explicitly rather than being an unexplained divergence.

One correction to the wording, filed separately as a doc item (`R9-09`) and not a reason to keep this open: the claim *"all three lanes agree at every limit tested"* is still not quite true — the sync engine runs exactly two laps more than async at every **odd** `maxIterations` on the `def` lane. Narrowing the sentence to the lanes actually measured would make it accurate.

Separately, and worth a line here because it caused us to mis-triage this area twice: `tests/test_round6_findings.py::TestAsyncRollbackRearmCycleBounded` reads its call counter 0.6 s after start and asserts it equal to the count at 0.9 s. On a normal host the `def` lane is **still climbing at 0.6 s** and converges around 1.0 s, so the test fails ~80 % of runs while the behaviour it tests is correct. Polled to convergence, both lanes plateau at exactly **1003 = `maxIterations` + 2** and stay there:

```
kind=def   series=[(0.5,781),(1.01,1003),(1.52,1003),(2.03,1003),(2.54,1003),(3.05,1003)]
kind=async series=[(0.51,1003),(1.02,1003),(1.53,1003),(2.03,1003),(2.54,1003)]
```

The bound is solid; only the test's sleep is too short.
