# Comment for issue #195 — `DoneEvent` / `AfterEvent` are forgeable and exempt from `strict`

**Action:** comment — **please keep open for the `after` family**
**Disposition:** **FIXED for `done`/`error`; the `after` family was never wired to the new gate**

---

Verified on `main` @ `f28719c` (merge of PR #202, `fix/0.8.1-round8`; unreleased
0.8.1) as part of our adoption audit (#26). Build identified **by commit** —
`__version__` still reports `0.8.0` on this tree, so nothing here should be keyed
on the version string. CPython 3.13.7, Windows 11, fresh venv. Every claim below
was reproduced in a clean process before it was written down, and **every
service-bearing check was run with both `def` and `async def` services**.

The mechanism is right and it works. Hand-built and unmarked-restored `Done`/`Error` events are refused under `strict` on **both engines and both service kinds**, and marked restores correctly keep their provenance. By-name laundering is closed.

**The `after` family never got switched over to it.** `base_interpreter.py:4523` still selects `after` transitions on a bare `isinstance(event, AfterEvent)` against the **public, package-root-exported** class, never consulting `is_system_event` / `_EngineAfter` — unlike the `DoneEvent`/`ErrorEvent` branch eight lines below it. Same file, same function, same release.

A discriminating control rules out "the `after.*` namespace is simply open". At the **default `strict=False`**:

```
AfterEvent("after.60000.m.work")  ->  ['m.expired']     # fires a 60s timer instantly
Event("after.60000.m.work")       ->  ['m.work']        # same name, plain class: ignored
"after.60000.m.work" (bare str)   ->  ['m.work']        # ignored
```

So it is the **class** that is privileged, and that class is exported from the package root.

**Credit where it is due:** with `strict=True` the send-side vector **is** correctly refused (`UnknownEventError`). Our own findings register overstated this half, and re-running it rather than inheriting it is what caught that. The send-side gate you built does cover hand-built `AfterEvent`s.

**What survives is the vector that never reaches that gate**, and it is the serious one: a `pending_events` record `{"kind":"after","type":"after.60000.m.work"}` with **no `"engine"` flag** restores as user traffic (correct, per this issue's own contract) and is then handed straight to the inbox by `_enqueue_restored` (`base_interpreter.py:1768`) — **bypassing the `send()`-time `strict` check entirely**. With `strict=True` the machine still reaches `m.expired`: a 60-second timer fired instantly from untrusted snapshot data, with no API call at all.

Fix looks like one line: gate `:4523` on the minted subclass, as the completion branch already does. Filed with a standalone repro as `R9-02`.

Two smaller relatives, filed Low: `done.state.*` is likewise an unreserved namespace (`R9-12`), and `strict` does not gate restored `pending_events` at all (`R9-13` — the delivery mechanism above).
