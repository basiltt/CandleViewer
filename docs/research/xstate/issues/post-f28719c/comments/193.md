# Comment for issue #193 — a `def` service is not unwound by `rollback` or by an `always` roll-forward

**Action:** comment — **please keep open**
**Disposition:** **FIXED IN PART — the rollback half landed; the roll-forward half did not**

---

Verified on `main` @ `f28719c` (merge of PR #202, `fix/0.8.1-round8`; unreleased
0.8.1) as part of our adoption audit (#26). Build identified **by commit** —
`__version__` still reports `0.8.0` on this tree, so nothing here should be keyed
on the version string. CPython 3.13.7, Windows 11, fresh venv. Every claim below
was reproduced in a clean process before it was written down, and **every
service-bearing check was run with both `def` and `async def` services**.

Thank you — the rollback half is genuinely fixed on the async engine, and it is the half that matters most in order-management terms (a reprice we had already decided had failed no longer reaches the exchange). Moving the executor handoff into the engine-held task was the right shape.

**But the roll-forward half did not land on either engine, and `SyncInterpreter` still leaks both halves.** Re-run fresh at `f28719c`, 6 lanes:

```
ok   case A (roll-forward) | async service | async engine | calls=[]
LEAK case A (roll-forward) | def   service | async engine | calls=['submit_child']
LEAK case A (roll-forward) | def   service | sync  engine | calls=['submit_child']
ok   case B (rollback)     | async service | async engine | calls=[]
ok   case B (rollback)     | def   service | async engine | calls=[]     <- this is the fix landing
LEAK case B (rollback)     | def   service | sync  engine | calls=['submit_child']
3/6 lanes leaked the service call
```

`docs/_guide/production-characteristics.md:97` states the opposite in so many words — a service "rolled forward (an `always` out of the state before it stabilises) is **never** submitted to the pool" — and the leaking case A row is verbatim that sentence. SCXML 6.4 agrees with the doc: `exitStates` removes the state from `statesToInvoke`, so a state left by an `always` in the same macrostep must never invoke.

One thing worth flagging directly: **`tests/test_round8_findings.py::test_always_rollforward_matches_sync` pins the leaking behaviour as the contract**, so the suite is green against the inverse of the published claim. Whichever way you resolve it, the test and the doc should agree.

Filed with a standalone repro as a new issue. Full detail: `R9-04`.
