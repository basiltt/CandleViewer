# Comment for issue #197 — `send(..., wait=True)` resolves over an empty configuration

**Action:** comment — **please keep open**
**Disposition:** **PARTIAL — the pinned property test passes; the original chart still reproduces**

---

Verified on `main` @ `f28719c` (merge of PR #202, `fix/0.8.1-round8`; unreleased
0.8.1) as part of our adoption audit (#26). Build identified **by commit** —
`__version__` still reports `0.8.0` on this tree, so nothing here should be keyed
on the version string. CPython 3.13.7, Windows 11, fresh venv. Every claim below
was reproduced in a clean process before it was written down, and **every
service-bearing check was run with both `def` and `async def` services**.

The library's own pinned property test passes, and `get_persisted_snapshot()` correctly refuses at the torn instant — so nothing inconsistent can be *persisted*, which is the most important half and it is solid.

**The originally reported chart still reproduces**, though. An `always` + nested-final + `after` chart still returns a success-shaped receipt — `last_transition_ok=True` — at an instant where `current_state_ids == []`.

The inconsistency is internal and it points at its own fix: `get_persisted_snapshot()` already refuses at exactly this instant, so the engine *knows* the configuration is not settled. The receipt path simply does not consult the same condition. Making `send(wait=True)` refuse (or at least not report `last_transition_ok=True`) wherever `get_persisted_snapshot()` would refuse would close it and keep the two paths honest with each other.

Severity from our side is Medium, not High, precisely because the persistence door is shut: a caller can be *told* the wrong thing, but cannot *store* it. Our wrapper contains it by never reading a receipt for configuration.

Filed with a standalone repro as `R9-08`.
