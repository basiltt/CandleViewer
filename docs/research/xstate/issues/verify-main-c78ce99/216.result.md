# #216 verify on main @ c78ce99

**Classification: FIXED-OPT-IN**

## Acceptance criteria (from CHANGELOG #216 entry / issue body)
- Unknown top-level config keys are no longer silently dropped.
- Default behavior: WARNING log naming the unrecognised key, with a
  "did you mean" fuzzy-match hint against the known-key whitelist.
- `create_machine(strict_config=True)` raises `InvalidConfigError` for an
  unrecognised top-level key.
- Config-level `"strictConfig": true` has the same effect as the
  `strict_config=True` kwarg.
- `x-`-prefixed keys, and `meta` / `description` / `tags` / `version`, are
  always accepted without warning, even under `strict_config=True`.
- `KNOWN_MACHINE_KEYS` is a single canonical list backing both the value
  validators and this new key-set check.

## Verification
Standalone script:
`docs/research/xstate/issues/verify-main-c78ce99/215_216_lap_parity_and_unknown_keys.py`

Checked the four representative misspellings from the issue
(`actionErrorPolicyy`, `Strict`, `maxIteration`, `onUnhandledEvent`):
- Default (no `strict_config`): each build succeeds but logs a WARNING that
  names the exact typo'd key AND includes a "did you mean" hint pointing at
  the correct key (all 4/4 confirmed).
- `strict_config=True` kwarg: raises `InvalidConfigError` (confirmed).
- Config-level `"strictConfig": true`: raises `InvalidConfigError` (confirmed).
- `x-custom`, `meta`, `description`, `tags`, `version` together, even with
  `strict_config=True`: build succeeds, zero warnings (confirmed).

Also ran `tests/test_round10_findings.py -k UnknownTopLevel`: passed.

Source inspection (`src/xstate_statemachine/validation.py:274-359`,
`factory.py:80-310`) confirms a single `KNOWN_MACHINE_KEYS` frozenset backs
`validate_top_level_keys`, called from `create_machine`, with `strict_config`
resolved from the kwarg (`None` → falls back to config's own `"strictConfig"`).

Reporter's original repro
(`docs/research/xstate/issues/post-19cb1f1/new/repro/R10-07_unknown_config_keys_accepted_silently.py`)
still exits 1 ("DEFECT PRESENT, 6/6 keys silently dropped") — but this is
expected and does NOT indicate a regression: that repro calls `create_machine`
with **no `strict_config` argument** (the opt-in default), and its own
pass/fail logic requires the DEFAULT behavior to *reject the build outright*
(`built=False`) to count as fixed. The shipped fix intentionally keeps the
default permissive-with-warning (per the issue's own "Suggested direction",
which explicitly asked for an opt-in boolean specifically to avoid breaking
existing callers) and only raises under explicit opt-in
(`strict_config=True` / `"strictConfig": true"`). The repro was written
against the pre-fix behavior and was never updated for the opt-in contract
that shipped; it is not a live acceptance test for the merged design.

## Verdict
FIXED-OPT-IN. The full acceptance criteria from the CHANGELOG and issue body
are met: unrecognised top-level keys are diagnosed (WARNING + hint by default,
`InvalidConfigError` under opt-in `strict_config`), and the reserved namespace
(`x-`, `meta`, `description`, `tags`, `version`) is preserved. The original
repro's exit-1 result reflects that it measures the pre-existing, now
superseded default-silent behavior rather than the shipped opt-in contract,
not an unresolved defect.
