# Comment draft — issue #219 (`ReentrantWaitError` on in-step self-wait)

**NOT POSTED. Draft.**

**Verified FIXED at `main` @ `de2da4e`** — and verified *narrow*, which is the part that matters. Standalone repro from a neutral cwd, both engines, both `def` and `async def`, polled to convergence.

## What we confirmed

| Shape | Result |
|---|---|
| action awaits `send(..., wait=True)` on its own interpreter | **`ReentrantWaitError`**, and **`start()` returns** (previously a permanent silent hang) |
| same, from a post-start action | `ReentrantWaitError` |
| same, from an `after`-fired clock handler | `ReentrantWaitError` |
| same, on the **sync** engine | `ReentrantWaitError` — parity holds |
| receipt handed out, action returns immediately, awaited later | **OK** — the refusal is in-step only, as the changelog claims |
| child actor → parent `wait=True` | **OK**, correctly not refused |
| parent → child `wait=True` | **OK**, correctly not refused |
| 100 concurrent deferred `ensure_future` receipts | **100/100 resolve**, no hang, no spurious refusal |

This also closes a hang we reported against the previous commit — an `async def` entry action awaiting its own receipt deadlocked `start()` forever with `last_error = None`, `status = running` and a legal configuration. **A loud immediate exception is strictly better than a silent permanent deadlock**, and we want to say that plainly before raising the residual below.

## One residual: the documented escape hatch is timing-dependent (filed as <DE-L1>)

Filed separately as <DE-L1>, with a standalone repro in the body. In short: the guard is

```python
if _ACTIVE_ACTION_OWNER.get() is self and not receipt.done():
    raise ReentrantWaitError(self.id, event_type)
```

and `_ACTIVE_ACTION_OWNER` is a `ContextVar`. `asyncio.ensure_future` / `create_task` **copy the current context**, so a task spawned inside an action keeps `_ACTIVE_ACTION_OWNER is self` for its whole life — long after the action returned and the loop went idle. The result is that the documented idiom (`asyncio.ensure_future(i.send(..., wait=True))`, awaited later) is refused whenever the spawning action does **any** further awaiting, and a background worker born in an entry action is refused even 300 ms after the machine has gone quiet. The pinned test passes because its action returns immediately — the idiom's safety is scheduling order, not an API property.

Suggested direction: gate on the interpreter actually being mid-step — a plain instance flag set around the synchronous action call — rather than on an inheritable `ContextVar`. A `ContextVar` is the right tool for the provenance question ("who produced this event") and the wrong one for the liveness question ("can this await make progress").

## One behavioural note for the release notes (filed as <DE-L3>)

A **`def`** action calling `send(..., wait=True)` receives the `_Awaitable` guard unawaited — no exception, no warning, no usable receipt. Nothing hangs, because it cannot await; but the call is silently useless. Worth one line in the docs alongside the `async def` behaviour; filed as <DE-L3> with a repro, since the two engines disagree here (`sync_interpreter.py:584` raises for the analogous shape).

## And a request

**Please put the breaking change at the top of the release notes, not inside the fix list.** An action that awaited `send(..., wait=True)` on its own interpreter previously deadlocked and now raises — it is the only change in this set that can break working code, and the in-step await was a natural way to write "act, then confirm". Suggested wording: *audit every action body for `wait=True`, `ensure_future` and `create_task` before upgrading.*

For what it is worth, our own corpus needed **zero** changes: 0 of 573 scripts and 0 of 20 production-shaped charts contain the shape, because our architecture has banned sending from inside an action for some time. We mention that not as reassurance — it is a property of our constraints, not of the change — but because it means we could verify the refusal's *narrowness* without any confound from our own code needing to move.
