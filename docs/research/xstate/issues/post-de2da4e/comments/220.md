## Why this mattered more to us than its severity suggested

Our twenty production-shaped charts all build clean under the recursive check, with zero warnings, on both service spellings. That is not just "no regression" — **it retroactively establishes that none of those charts was silently dropping an entry action or a transition on any prior release.** That fact could not be established before this fix existed, and it validates a long series of contract results we had taken on trust. It is the most valuable thing this fix bought us, and it is worth knowing that a scope fix can have that effect.

We had a wrapper-level recursive key check of our own, written because the previous version looked at the root dict only. It **stays**, but only for the residual below.

## One residual: inline-dict `invoke.src` (filed as <DE-L2>)

The recursion itself we could not fault — nested `states`, parallel regions, `on` / `always` / `after` / `onDone` transition bodies, `invoke` entries and their `onDone` / `onError` are all covered, at every depth we could reach.

The one shape that never arrives at the validator is an `invoke.src` written as an **inline machine config dict**. We originally reported this to ourselves as a recursion gap; on checking it properly, it is not. That shape is simply **not supported** — and that is a perfectly reasonable design choice. The problem is only how it says so: `TypeError: unhashable type: 'dict'`, raised from `logic_loader.py:229` (`services.add(invoke_def.src)` against a `set`), under every strict setting, naming no machine, no state path and no config key.

A well-formed inline-dict `src` with **no typo anywhere** fails the same way, which is how we established it is a support question rather than a validation one.

Filed separately as <DE-L2> with a standalone repro. The ask is one type-check in the invoke loop so the rejection comes back through your existing path-named `InvalidConfigError` channel instead of a bare `TypeError` — it would inherit this issue's strict/warn split and "did you mean" voice for free. Low severity and latent for us; we raise it because an inline nested machine is the shape XState's JS API accepts, so it is a plausible first-hour experience for a new adopter, and the current error gives them nothing to search for.

## One note for the release notes

A machine that built clean on 0.8.0 may now raise `InvalidConfigError` — **and if it does, the typo was always there and was always silently dropping an action or a transition.** Worth framing explicitly as a discovery rather than a regression, so the first adopter who hits it reads it correctly.
