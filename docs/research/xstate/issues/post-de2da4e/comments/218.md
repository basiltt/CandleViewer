# Comment draft — issue #218 (timer handle released on fire/cancel)

**NOT POSTED. Draft.**

**Verified FIXED at `main` @ `de2da4e`** (merge of PR #223). `__version__` still reports `0.8.0` on this tree — we key on the commit.

Re-verified with a standalone repro (stdlib + `xstate_statemachine` only, every helper inlined) from a neutral working directory, on **both engines** and with **both `def` and `async def`** actions, polled to convergence.

## Result

| Check | Result |
|---|---|
| 200-beat `raise(delay=)` heartbeat | **peak 1 handle** on every engine/kind cell |
| 500× superseding re-arms of one send id | peak 1 handle, exactly 1 fire |
| 500× arm/cancel storm | `fired=0`, `peak_handles=0`, `armed=0`, **no double-release crash** |
| cancel-after-fire | clean no-op |
| `stop()` | releases the handle |
| 200 machines × 10 s = **93,168 beats** | `handles_max_per_machine = 1`, **RSS Δ 0.00 MB** |
| 200 machines × 150 s soak | **1.00 handles per machine**, flat |

Our original repro, **unmodified**, now exits 0 (`retained_per_beat: 0.0` over ~630 beats). On the previous commit the same script measured **+753 MB** on the soak shape and 1.00 retained handles per beat with no plateau.

This is fixed **at the mechanism**, not merely under load: the handle was registered under the interpreter id while the only pruner popped by *state* id on state exit, and both engines now release on fire and on cancel. The fire path, the cancel path, the supersede path and `stop()` are all covered.

## Consequence on our side

We had a lint rule banning `raise(delay=)` self-paced periodic work, originally written against a different finding and then re-grounded on this leak. **Both of its grounds are now closed** (this issue, and #212 before it), so **we are retiring it.** That is the strongest statement we can make about a fix: it removed a constraint from our architecture rather than merely making one unnecessary to tighten.

We are keeping `len(i._timer_handles.get(i.id, []))` exported as a gauge — as telemetry, not as a mitigation. It is the instrument that let us assert `1.00 per machine` rather than "we observed no growth", and it is how we would detect a recurrence.

Thank you — this was the single open High on our board and it cost us a row in our own adoption gate. Closing it moved us back up two rows.
