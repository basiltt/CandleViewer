## On `last_error` staying per-step

We want to be clear that we think this is right. Our original repro asserted `last_error` still named `RunawayChainError` after one benign event, and it still "reproduces" on this build — because the release documents `last_error` as the per-step read it always was and moves stickiness to the new API. **That repro is testing an oracle this release deliberately retired**, and we have rewritten it against the latch rather than reporting it as a failure. Changing `last_error` would have been the worse fix; adding a latch beside it is the better one.

## One residual: the latch is process-local (filed as <P-1>)

`chain_trips` and `last_chain_error` are **not snapshot fields** — after `from_snapshot`, `chain_trips == 0` and the latch is `null` (`snapshot_has_chain_key == []`).

On reflection we have filed it after all, as <P-1> — not because the design is wrong, but because the field's own documentation calls the signal "sticky", and stickiness that stops at the process boundary is worth an explicit decision rather than an omission. But it is a real operational hole for anyone restarting from a snapshot: the evidence that the previous process discarded work is erased by the restart, which is precisely the moment an operator most wants it.

Two options, either fine from our side: persist the counter and latch in the v3 layout, or state in the docs that they are deliberately process-local so integrators know to carry them in their own envelope. We have done the latter on our side (we read both before persisting and carry them ourselves), so either resolution closes it for us — and if you choose the docs route, <DE-A13> asks for exactly that sentence in `snapshots.md`.

Thank you — the hook-ordering and once-per-trip guarantees are the parts we leaned on hardest, and both held under every shape we could build.
