## Result

| Check | Result |
|---|---|
| random chain of **1–4** `from_snapshot` → `get_persisted_snapshot` hops **without `start()`** | **600/600** and **640/640** property cases survive |
| `remaining_ms` and `send_id` at every hop | **byte-identical** |
| `remaining_ms` behaviour | counts **down**, not reset — a compaction hop does not refresh the deadline |
| firing after the remainder elapses | exactly once — **not early, not twice** |

| union of restored + newly armed self-sends across a no-start re-persist | preserved |
| sync engine | identical |
| production-shaped chart, 2 compaction hops | verbatim, **20,000 ms remainder honoured** |

The double-hop idempotence is the part we tried hardest to break, because a journal-compaction job can touch the same blob many times before anything starts it, and "re-emitted verbatim" has to mean verbatim on hop four as much as on hop one. It does.

## One residual, on the sibling lane (filed as <P-2>)

Nothing in #221's own scope — the parked-record round-trip is exact. But working on this lane surfaced that `scheduled_sends` and `pending_events` disagree about `strict`.

#214 routed every restored `pending_events` record through `_admit_restored`, so an undeclared event type is refused on restore. `scheduled_sends` — the list #213 added, and the one this issue hardened — has no equivalent check: `_rearm_restored_self_sends` (`base_interpreter.py:1269`) re-arms each record straight through `_arm_restored_self_send`.

The same record dict, on a machine with `strict: True`, is refused in one lane and armed and delivered to the run loop in the other. We verified both directions in one run, with a positive control confirming `send()` of the same type is refused. Filed as <P-2> with a standalone repro; it looks like a one-line fix.

## Consequence on our side

We wrote a constraint against this — *never re-persist an interpreter that has not been `start()`ed* — when a compaction pass silently dropped every deadline it touched. **Its ground is now closed.** We are keeping it one more release as defence in depth, purely because the fix is one release old and the constraint costs us nothing, and we will re-examine retiring it next round. We mention this so the retention is not misread as a residual doubt about the fix: 640/640 with byte-identical records across four hops is as clean a verification as anything on our board.

Thank you — this was the sharpest of the round-11 findings for us, because it was the one that could corrupt data in a job that never touches a running machine.
