**Two follow-ups, neither blocking this close, both filed separately:**

1. A 0.8.0-era persisted `after` record has `kind:"after"` (so the v1 name-based
   fallback does not catch it) but **no `engine` flag**, so this gate now refuses
   it — and the deadline is **dropped rather than demoted**: no raise, no
   warning, nothing in `last_error`, and `has_dormant_timers` does not cover it
   because the event was already in the persisted inbox. The security direction
   is right; the failure mode should be loud. Filed as a migration issue.
2. Provenance is still a Python *type* rather than a value the engine mints and
   holds, so `_replace`, `pickle`, `deepcopy`, the module-scope `engine_after`
   factory and a hand-edited `"engine": true` record all reconstitute it. We
   audited this hard and concluded it is **hardening-grade, not a trust-boundary
   break** — every vector needs either attacker-controlled Python in-process
   (which already grants strictly more: a plain registered action writes context
   arbitrarily, and a live `Interpreter` exposes `_enter_states`/`_exit_states`)
   or blob-write (a hand-edited snapshot with *no* event forgery at all already
   relocates the machine and rewrites context). Filed as a hardening issue, not
   a vulnerability.

Closing. This one landed cleanly on both engines and both service spellings —
the first round in our audit where that is true of every fix in the release.
