# LC-19 (GH #44) — `has_dormant_invocations` on both engines

## Classification: **FIXED** (unconditional inspection API; `restart_services` remains opt-in, `False` default, unchanged)

CHANGELOG `[Added]` (#44, unchanged wording since 0.8.0): "`has_dormant_
invocations` on both engines. After a static `from_snapshot()` the machine
reports `status == 'running'` ... while every `invoke` in the configuration
is parked. `status` is therefore not a liveness signal after a restore;
this boolean (and `pending_invocations()`) is." `has_dormant_invocations`
is a `@property` on `BaseInterpreter` (`base_interpreter.py`), inherited by
both `Interpreter` and `SyncInterpreter` unchanged — no engine-specific
override, so parity is by construction (both call the same
`_invocation_is_live`-driven property), and this pass exercises both
engines directly to confirm rather than assuming parity from shared code.

## Fix location

- `src/xstate_statemachine/base_interpreter.py`:
  - `pending_invocations()` (~line 1293) — lists every dormant invoke.
  - `has_dormant_invocations` property (~line 1311) — `any(not self.
    _invocation_is_live(state, inv) for state in self._active_state_nodes
    for inv in state.invoke)`.
  - `_invocation_is_live` (~line 1325) — abstract, engine-specific
    liveness check; both `Interpreter` and `SyncInterpreter` implement it
    (not separately audited line-by-line this pass, but exercised
    end-to-end above and behaviour matches for both).
  - `from_snapshot(..., restart_services=False)` (~line 1091) — default
    unchanged: static rebuild, nothing restarted.
- No diff vs the 0.8.0 baseline for this feature — CHANGELOG confirms it
  shipped in `[0.8.0]` wave 3 and has no `[Unreleased]` follow-up entry.

Note: for the sync engine, the "parked mid-invoke" snapshot is hand-crafted
by starting a base `SyncInterpreter` (whose sync `place_sync` service
completes inline during `start()`), taking `get_persisted_snapshot()`, and
overwriting `state_ids`/`configuration`/`value` back to `submitting` —
mirroring exactly what the library's own
`tests/test_restore_services.py::test_restart_services_behaves_identically_on_both_engines`
does, since a sync service cannot be snapshotted "genuinely mid-flight" the
way an `await asyncio.sleep(...)` async service can.

## Residual gaps

- `test_restarted_invoke_is_cancelled_on_state_exit`,
  `test_restart_services_behaves_identically_on_both_engines` (the
  library's own named test), and the `docs/_guide/snapshots.md` doc audit
  were not independently re-exercised in this pass (all noted as
  not-exercised in the 0.8.0 pass too, and nothing in `[Unreleased]`
  suggests they changed).
- `status` still reports `"running"` for a parked default-restored machine
  with no qualification — by design; `has_dormant_invocations` /
  `pending_invocations()` are the correct liveness signal, and both engines
  now expose it identically.

## Recommended CandleViewer constraint (unchanged from 0.8.0 pass, now with engine parity confirmed)

- MUST check `interpreter.has_dormant_invocations` (or
  `pending_invocations()`) immediately after every restore, on **both**
  the async and sync engine — behaviour is now confirmed identical, so a
  single boot-time health check can be written once and reused across
  engines.
- MUST NOT rely on `status == "running"` alone as a liveness signal after
  restore.
- MUST design every re-invoked service to be idempotent when opting into
  `restart_services=True` (re-invoked from scratch, not resumed).
