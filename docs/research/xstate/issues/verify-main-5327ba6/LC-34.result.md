# LC-34 (GH #51) — Verification on main @ 5327ba6 (pre-0.8.1)

**Classification: FIXED** (for the specific "need" under test: `send_threadsafe`
strict/schema guardrail, and static-vs-dynamic `raise` validation — all on
top of the existing `strict` opt-in from the 0.8.0 pass, which remains
`FIXED-OPT-IN`, default `False`)

## Fix location

- `src/xstate_statemachine/interpreter.py:859-902` — `send_threadsafe()` now
  calls `self._check_strict(event_obj)` (`:897`) on the **calling thread**,
  before `asyncio.run_coroutine_threadsafe` schedules the enqueue. Previously
  it skipped `_check_strict` entirely (the CHANGELOG's #78/#51 entry).
- `src/xstate_statemachine/base_interpreter.py:1514-1541` — `_check_strict`
  is the single guardrail used by both `send()` (`interpreter.py:602`,
  `sync_interpreter.py:478`) and `send_threadsafe()`; raises
  `UnknownEventError` for an undeclared type under `strict`, and
  `InvalidEventPayloadError` when a registered `event_schemas` validator
  rejects the payload (independent of `strict`).
- `src/xstate_statemachine/validation.py:236-330` — `_static_raise_event_type`
  extracts a literal `raise` target from `action.params["event"]`;
  `_collect_unknown_raises` walks every state's actions on a `strict`
  machine and raises `InvalidConfigError` at `create_machine()` time for any
  static `raise` naming an undeclared event, with a `difflib`-based "Did you
  mean" suggestion (`:281-286`). A **dynamic** (callable) `params["event"]`
  returns `None` from `_static_raise_event_type` (`:245`, "checked at runtime
  by `_check_strict`") and is therefore only validated when it actually
  fires, via `base_interpreter.py:2622`
  (`self._check_strict(target_event)  # #51: internal typos too`).

surfaced for the test. This mirrors LC-36/`_check_strict`'s documented
behaviour, not a gap.
