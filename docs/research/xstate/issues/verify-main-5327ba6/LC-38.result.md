## Fix location

- `src/xstate_statemachine/clock.py` — `RealClock.set_timeout` accepts an
  explicit `sync: Optional[bool] = None` kwarg (`:187-205`); `Clock` protocol
  updated to match (`:66-81`).
- `src/xstate_statemachine/base_interpreter.py:406-414` — `_clock_sync_lane`
  (set unconditionally `False` in `BaseInterpreter.__init__`, overridden to
  `True` in `SyncInterpreter.__init__`, `sync_interpreter.py:182`) and
  `_clock_accepts_sync` (decided ONCE via `_accepts_kwarg`, `:273-289`).
- `src/xstate_statemachine/base_interpreter.py:3435-3449` — `_set_timeout`
  calls `self.clock.set_timeout(fn, delay_sec, owner=owner, sync=lane)` when
  the clock accepts the kwarg, else the legacy 2-arg form — exactly once,
  never a retry-after-TypeError.
- `src/xstate_statemachine/sync_interpreter.py:858,1130` — both `after` and
  delayed-`send` timer sites route through `self._set_timeout` (previously
  `self.clock.set_timeout` directly).

This closes GH #50 / LC-38 fully: the lane a `SyncInterpreter` uses now
follows the owning engine (`self._clock_sync_lane = True`, unconditional),
not whatever asyncio context happens to be ambient when the timer is
scheduled. The prior 0.8.0 fix already removed the thread-per-timer
architecture; this follow-up specifically closes the "constructed inside a
running loop" gap that GH #50 called out.
