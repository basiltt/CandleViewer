## Summary
`SyncInterpreter._process_event_queue` was reworked (`sync_interpreter.py`)
to budget only *self-generated* work per chain: `external_budget` is seeded
to `len(self._event_queue)` at drain start (plus credited back for any
deferred-events replayed at the head), and only events that are NOT drawn
from that pre-existing external budget (i.e. internal-queue events, or
external events arriving after the budget is exhausted) increment
`generated` against `max_iterations`. The budget resets to 0 whenever a
macrostep produces no new queued work (parity with the async engine's
`_raise_depth` reset), so N independent one-deep raises never trip it. This
directly fixes the reported silent-truncation defect (1501/3000/5000-event
batches now fully processed) and the CHANGELOG's claim that "the two engines
now agree" is a materially better description of the fixed state than the
0.8.0 note it corrects — but the fix does **not** raise an exception on
genuine-runaway overflow; it still drops the self-generated tail and logs at
`ERROR`/`DEBUG`, exactly the "silent-ish" mechanism criticized in the
original issue's "Suggested fix" alternative #2. `send()` returns normally,
`i.status` stays `"running"`, and no exception reaches the caller.

## Fix location
- `src/xstate_statemachine/sync_interpreter.py::_process_event_queue`: the
  entire budgeting rewrite (external vs. generated accounting, per-chain
  reset, drop-on-arrival `tripped` latch). The overflow branch still ends in
  `logger.log(logging.ERROR if not tripped else logging.DEBUG, "🛑 Exceeded
  %d self-generated events...")` followed by `continue` — no exception is
  raised, matching the 0.8.0 predecessor's overall shape (log + drop) rather
  than the issue's preferred "raise on overflow" alternative.

## Residual gaps
1. **Criterion C, taken literally, is unmet.** The runaway guard is fixed
   from a *correctness* standpoint (it no longer discards events the caller
   was told were accepted, and it does bound a genuine self-feeding loop),
   but it still fails silently from the caller's perspective — `send()`/
   `send_events()` return normally, `status` remains `"running"`, and the
   only signal is a log line. The issue's own "Suggested fix" explicitly
   offered raising as an acceptable alternative to the `_raise_depth`-style
   port, and the shipped fix chose neither literally: it ported the
   `_raise_depth` concept (good) but kept the log-and-drop overflow
   behavior (not chosen: raise). This is the one place where the CHANGELOG
   entry's tone ("It now budgets only self-generated work... every event...
   is processed in full... a self-feeding loop is still broken and only the
   generated tail is discarded") is accurate on data-loss but silent on the
   fact that overflow is still not surfaced to the caller as an exception —
   which was an explicit, numbered acceptance criterion.
2. All other criteria and "need" items are solidly fixed and covered by
   named regression tests in `tests/test_core_algorithm.py`.
