# #149 — plain-`def` invoked service runs off-loop (verify main@cec108b)

## Classification: PARTIAL

## Criteria (issue #149 + CHANGELOG [Unreleased])

| # | Criterion | ✓/✗ |
|---|---|---|
| 1 | A 0.3s blocking plain-def service does not block the event loop (concurrent ticker keeps advancing) | ✓ |
| 2 | #116 ordering guarantee preserved: a service invoked from the machine's **initial** state completes (its `onDone` taken) before an event sent immediately after `start()` returns is processed — same landing point as the sync engine | ✗ |
| 3 | A raising plain-def service still reports `error.platform` (`onError` taken) | ✓ |
| 4 | A plain-def service returning an awaitable is still awaited (`onDone` taken) | ✓ |
| 5 | Service executor is released (shut down) on `stop()` | ✓ |
| 6 | Concurrent services (independent machines) run in parallel, not serialized | ✓ |

5 of 6 criteria pass. Criterion 2 (the core #116-preservation promise the
issue itself calls out — "the ordering half of that fix is correct and worth
keeping" / "#116's ordering guarantee") **fails** for the specific case of a
service invoked from the machine's *initial* state.

## Evidence

`issues/verify-main-cec108b/149_plain_def_service_off_loop.py` (exit 1):

```
Criterion 2: #116 ordering preserved for a service on the INITIAL state
    async value after start()+immediate send(X): 'x'
    sync  value after start()+immediate send(X): 'd'
  [FAIL] async matches sync landing after start()+immediate send
```

Repro:
```python
CFG = {
    "id": "s2", "initial": "w",
    "states": {
        "w": {"invoke": {"id": "svc", "src": "slow", "onDone": "d"}, "on": {"X": "x"}},
        "d": {}, "x": {},
    },
}
# async: await Interpreter(m).start(); await interp.send("X", wait=True) -> "x"
# sync:  SyncInterpreter(m).start(); i.send("X")                          -> "d"
```

On the sync engine, `start()` runs the invoked service to completion inline
before returning, so an immediately-following `send("X")` finds the machine
already in `d` and the transition is a no-op. On the async engine, `start()`
returns *before* the off-loop future has completed (the executor call has not
even had a scheduling turn to run yet), so `send("X", wait=True)` races ahead
and lands the machine in `x` instead — the exact divergence #116 was written
to close, now reopened for the initial-state case (a service entered from a
later transition IS awaited correctly, per the passing pinned test
`TestPlainServiceOffLoop::test_ticker_advances_and_start_returns_promptly`,
because `_process_event_and_transient_transitions` calls
`_await_inline_services()` after processing an event/settle — but `start()`'s
own initial-entry path does not).

## Fix location (root cause)

`src/xstate_statemachine/interpreter.py`, `async def start()`:
- Line 486: `await self._enter_states([self.machine], init_event)`
- Line 496: `await self._settle_transient_transitions()`
- **Missing**: no call to `self._await_inline_services()` between or after
  these two lines (contrast with `_process_event_and_transient_transitions`
  at lines 1645/1649, which calls it after both the event-processing step and
  the settle step). Any plain-`def` service invoked directly from the initial
  configuration (or entered via the initial `always`-settle) is fired off to
  the executor but never awaited by `start()`, so `start()` returns before it
  completes — reopening the #116 race for exactly the states `start()` itself
  enters.

## Original repro

`docs/research/xstate/issues/post-3ed3099/new/repro/R5-07_plain_def_service_blocks_loop.py`
still exits 1, but for the *originally reported* reason (loop-blocking) it is
now a **false negative on that specific claim** — the loop is in fact not
blocked (criterion 1 above passes fresh). Re-inspection: the original repro's
`during` counter is measured only up to `await start()` returning (not after
waiting for completion), so it reports 0 ticks regardless of whether the loop
was blocked or the service simply had not been scheduled yet by the time
`start()` returned early. Re-running with a wait-for-completion loop (as the
pinned test does) shows the ticker in fact advances (during ≈ 66 in the
adjacent manual probe with `await asyncio.sleep(1.0)`). So the original
repro's PASS/FAIL signal is **stale/imprecise** for the loop-blocking claim,
but it *does* correctly point at the same underlying gap: `start()` returns
without the invoked service having reached its `onDone`, which is precisely
the residual ordering defect found independently above (criterion 2).

## Residual

`start()` does not await pending inline plain-def services before returning,
so the #116 ordering guarantee (sync/async parity for services invoked from
the *initial* state) is not held. Every other aspect of #149 (off-loop
execution, error handling, awaitable fallback, executor teardown, real
concurrency) is fixed correctly.
