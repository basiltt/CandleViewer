# #157 — send_threadsafe backpressure on the calling thread

**Commit:** cec108b
**Classification: NOT-FIXED**

## Acceptance criteria (from issue #157 + CHANGELOG "#157" bullet)

> Under `OverflowPolicy.RAISE` a full inbox raises `QueueOverflowError` at
> the `send_threadsafe()` call site instead of on a future the
> fire-and-forget pattern never reads.

- [ ] **A.** Single-thread flood of a bounded inbox under `RAISE` raises
  `QueueOverflowError` synchronously at the `send_threadsafe()` call site.
- [ ] **B.** Concurrent producers (many threads) do not end up with
  overflow signalled *only* on unread `Future`s while zero calling-thread
  raises occur.

## Fix location examined

`src/xstate_statemachine/interpreter.py::Interpreter.send_threadsafe`
(~line 1046-1145): a `self._inbox_is_full()` check was added on the
calling thread before scheduling `_deliver()` via
`run_coroutine_threadsafe`, guarded by `not self_issued and
self._overflow_policy is OverflowPolicy.RAISE`.

## Verification script

`157_send_threadsafe_backpressure.py` (this directory).

## Result

```
  [A] single-thread flood raised QueueOverflowError at call site: False
  [B] concurrent: raised_on_calling_thread=0, overflow_landed_on_unread_future=3100
CRITERION A (single-thread sync raise): FAIL
CRITERION B (concurrent, no silent-future-only overflow): FAIL
EXIT: 1
```

Both criteria **fail**. `_inbox_is_full()` reads `self._event_queue.qsize()`
via a plain read from the calling thread, but the queue in these scenarios
never appears "full" from the caller's vantage point at the time each
`send_threadsafe()` call is made — the loop is processing/dequeuing
concurrently and `_max_queue_size` is large enough (100) relative to
per-call check timing that the calling-thread snapshot never sees
`qsize() >= max_queue_size`. Even in the single-thread case (criterion A,
inbox bound 10, 500 rapid calls with no consumer pacing), no
`QueueOverflowError` was raised on the calling thread — the loop keeps
draining the queue between calls fast enough that the TOCTOU-style
snapshot check never trips, so the code path added for #157 exists but
does not reliably fire in the load pattern the issue itself describes
(a "flooding" producer).

## Original repro

`docs/research/xstate/issues/post-3ed3099/new/repro/R5-16_send-threadsafe-no-backpressure.py`
against `cec108b`:

```
  calls_returned_without_raising_on_calling_thread = 3200
  raised_on_calling_thread                         = 0
  QueueOverflowError_landed_on_unread_future        = 3100
RESULT: FAIL - no calling-thread backpressure signal
EXIT: 1
```

Confirms: the exact original defect (overflow observable only via unread
futures, 0 calling-thread raises) is still reproducible verbatim on
`cec108b`.

## Verdict

**NOT-FIXED.** The mechanism (`_inbox_is_full()` pre-check +
`QueueOverflowError` raised inline in `send_threadsafe`) is present in the
source and would work for a caller that pauses long enough between sends
for the queue to actually accumulate past the bound while it is read — but
under the realistic load pattern the issue describes (many producers, or
even one producer sending faster than the consumer drains), the
event-loop side keeps draining concurrently with the calling-thread check,
so `qsize()` rarely if ever reads as full at the exact moment of the call.
The original repro's exact failure signature reproduces unchanged.
