Root cause of the residual (or, arguably, why it's not actually a residual defect): `after: 50` is relative to when the *state was entered*, not to the wall clock at the moment `tick()` is called. The repro sleeps 0.25s while sitting in `submitted` (whose `after:50` fired long ago), calls `tick()` once: the first due deadline fires, transitioning into `ack_timeout`, which arms a NEW `after:50` timer relative to *now* (i.e., not due for another 50ms) — the drain loop correctly finds nothing else due and stops. So the chain only walks one link per `tick()` because only one link's deadline was actually due at call time; the other two links' deadlines get (re-)armed fresh each time and are never "already due" the way the repro's docstring assumed. This matches the *new* documented contract precisely ("a ladder of real delays needs one tick() per rung, each after that rung's delay has actually passed") — i.e. the round-5 fix resolved this by clarifying the contract rather than by making a single call walk a real-delay chain, and the original repro's stronger assumption (that all links are "already due" after one flat sleep) does not hold given how relative `after` delays actually arm.

CHANGELOG claim ("per-macrostep settle budget... tick() contract documented") is accurate as stated — it is a documentation + zero-delay/SimulatedClock fix, not a fix to the `RealClock` real-delay-ladder-already-due case the original repro exercises.

Verdict: **PARTIAL** — doc + zero-delay-chain + SimulatedClock acceptance criteria met, and the residual is arguably not a defect (relative `after` re-arming, not a drain-loop bug) but a stale-repro assumption; however the literal `repro/R4-27_sync_tick_chained_deadlines.py exits 0` acceptance criterion still fails as written, and no dedicated `test_sync_tick_drains_chained_after_deadlines` regression test exists, so this is not a clean FIXED.
