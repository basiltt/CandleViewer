# #162 verification on cec108b

**Issue:** v1 snapshot restore re-derives provenance from event NAME,
laundering user events (e.g. `after.hours`, `xstate.custom`) into
`Event(system=True)` on restore.

## Fix location

`src/xstate_statemachine/events.py:391` (diff `3ed3099..HEAD`):

```python
# before (3ed3099):
kind = "system" if etype.startswith(ENGINE_EVENT_SHAPES) else "event"
# after (cec108b, HEAD):
kind = "system" if etype.startswith("___xstate") else "event"
```

`ENGINE_EVENT_SHAPES` (broad prefixes like `after.`, `xstate.`, `done.`,
`error.`) is replaced by the narrow, genuinely-reserved engine sentinel
prefix `"___xstate"` (used only for `___xstate_statemachine_init___` /
`___xstate_statemachine_exit___`, `base_interpreter.py:3376,3410,3631`,
`interpreter.py:484,504`, `sync_interpreter.py:325`) — a name space a user
cannot plausibly collide with, unlike `after.*`/`xstate.*`.

## Residual

None found. The narrowing to `"___xstate"` correctly:
- stops laundering `after.*`/`xstate.*`/`done.*`-shaped **user** event names
  into `system=True` on v1-record restore (the reported defect), and
- still correctly classifies the genuine engine init sentinel as
  `system=True` (no under-classification of the one legitimate v1 system
  record the engine itself ever wrote).

The proposed-fix section of the issue floated defaulting *all* v1 records
to `kind="event"` unconditionally (deferring to shape signals only). The
shipped fix instead keeps a narrow, unforgeable-by-users sentinel
exception, which satisfies the acceptance criteria (repro passes, no
name-collision laundering for ordinary user event names) while still
correctly classifying the one genuine engine v1 record. This is a
reasonable, arguably better, resolution than the literal proposal and is
explicitly documented in the changelog as a restore-time behavior change,
per the issue's own compatibility note.
