# Follow-up comment draft — #28 (LC-03, `onUnhandled`)

**Status:** verified on 0.8.0 (commit `9bf6065`).
**Suggested disposition:** close. Docs request only.

---

`onUnhandled: "defer"` is the single most valuable thing in this release for us,
and we attacked it hard: **9/9**, no findings. Recording exactly what we
confirmed, so the behaviour is pinned by something other than the changelog:

* replay is at the **head** of the queue, in original order, ahead of live
  traffic (`A,B,C,LIVE`);
* still-unhandled events are **re-deferred**, not dropped;
* `DEFER_MAX` overflow evicts the **oldest** and reports it against the evicted
  event (1005 sent → 1000 held, 5 `dropped` callbacks, 1000 replayed);
* the buffer survives `get_snapshot()` → `from_snapshot` → replay;
* no replay spin on a state change that arms nothing;
* sync/async replay-order parity;
* replay also triggers on an `after`-driven state change;
* system events are never deferred.

And the original blocker, end to end: a `FILL` arriving one microstep before its
handler is armed — while the submit invoke is still running — is held
(`deferred_count=1`) and applied on `onDone`. This removes the single most
invasive workaround in our design (a `"*": defer` handler on every transient
state plus a drain in every `entry`), and its two dependent findings with it.

Two documentation asks:

**1. Publish `DEFER_MAX` and the eviction policy.** "Bounded by `DEFER_MAX`" is
in the changelog, but the value and the *oldest-evicted* semantics are what an
operator needs to size an alert on `deferred_count`. We would also suggest
`on_unhandled_event`'s contract be stated explicitly as "fires under **every**
policy including `ignore`" — that unconditional observability is the best design
decision in the release and is currently easy to miss.

**2. Document the `error.*` / `done.*` namespace exemption.** `_matching_descriptors`
exempts `("done.", "error.", "after.", "xstate.", "___xstate")` from wildcard and
partial matching, and the same list is now load-bearing in three places (the
matcher, the `onUnhandled` policy, and `_check_strict`). The consequence is that
**a user event named `error.myapp.validation` does not match a bare `"*"` handler,
and `done.review` does not trip `onUnhandled: "error"`.** Both verified on 0.8.0.
For a domain that naturally names events `done.review` / `error.validation` that
is a silent-drop class — precisely the class this release set out to eliminate.
Either document it loudly, or reject user-declared event names in those
namespaces at `create_machine()` time. We have filed this separately as it is not
really an `onUnhandled` bug; cross-referencing here because this is where it bites.
