# Follow-up comment draft — #60 (LC-57, one core algorithm)

**Status:** the issue's checkable acceptance criterion is met on 0.8.0
(`9bf6065`). **One grouped sub-item (LC-52) did not ship.**
**Suggested disposition:** close #60; split LC-52 out into its own issue.

---

The core claim holds and we verified it directly rather than by changelog: the
step, transition-execution, state-entry/exit, lifecycle-action and
built-in-action logic are implemented **once** on `BaseInterpreter`; no core step
is implemented by both engines; no base `async def` is shadowed by a same-named
sync override; no renamed fork remains; and the sync engine now raises
`NotSupportedError` for a `functools.partial`-wrapped async action instead of
silently discarding the coroutine. Those four are the repro's literal assertions
and all four pass. A 36-entry action trace is byte-identical across both engines.

Worth noting for the record that this was solved by a **different design** than
the issue sketched. The issue proposed a sans-io `core/algorithm.py` plus an
`ExecutionStrategy` Protocol; 0.8.0 instead keeps the six algorithm steps as
`async def` methods on `BaseInterpreter` and adds `SyncInterpreter._drive()`,
which runs each base coroutine to completion with a single `coro.send(None)` —
since none of them ever actually suspends, the first `send(None)` always raises
`StopIteration` carrying the return value. `src/xstate_statemachine/core/algorithm.py`
does not exist. This is architecturally narrower than the sketch, but it satisfies
the criterion the issue actually asked to be checked, so we consider it delivered.
`tests/test_core_algorithm.py` exists and tests the delivered design rather than
the sketched one — the name matches, the contents do not, which is fine but will
confuse the next reader of this thread.

**What did not ship: LC-52, the `ErrorEvent` rename.** `error.platform.*` events
are still delivered as `DoneEvent` — a "Done" event that signals failure, which is
exactly the naming confusion that sub-item described. The changelog's `#52`
reference is to arity auto-registration, which is unrelated, so this looks dropped
or deferred rather than merged into a differently-named mechanism the way LC-47
and LC-58 were. Since #60 was the umbrella, it would be easy for this to
disappear on close — we would suggest splitting it into its own issue before
closing this one.

One smaller gap: no dedicated regression test pins the LC-47 `target_str`
non-mutation fix by the name the issue asked for, though the code fix is present
and carries an explanatory comment. Given how easy that one is to reintroduce
during a refactor, a named test seems worth the two lines.
