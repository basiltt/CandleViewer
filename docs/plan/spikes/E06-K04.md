## Honest limits (read first)

No GPU, headless Chromium, Electron, Tauri/WebView2, docker or browser exists in this environment (same as E06-K02/K03). Therefore:

- **Real (Node):** ring cursor/wrap/colTime logic, R16F half-float quantisation, max-pool aggregation, Oklab LUT generation from the real
  `packages/ui/tokens`, price-origin shift row accounting, **all upload-byte counters**, process RSS during the soak.
- **Modelled:** GPU upload/draw time (0.004 ms/KB upload, 0.05 ms/quad) and therefore every frame-time number below. Frame times are
  cost-model outputs, not hardware measurements. The soak runs on a **simulated clock** (126,000 frames = 30 min at 60 Hz) in ~2 min wall time.
- **Not done (needs a real browser/runtime):** per-runtime capability probe (the run records only the profile _selection logic_ for synthetic capability
  sets, plus a clearly labelled assumed-full placeholder), Electron vs Tauri comparison (ADR-0011 criteria 2-4 **remain unevaluated**),

  (no renderer; boundary is asserted numerically, `sourceForAge`). All deferred to E06-T02 / E11 M4 with the harness unchanged.
- The "process memory" figure is the RSS of the Node process holding the CPU shadow of both rings (~16 MB), not a browser/GPU process peak.

## Experiments

- **Constant upload vs trail length (5 min / 1 h / 4 h):** 11,264 B/s in all three; modelled p95 1.17 / 1.17 / 1.22 ms. Equality is exact because upload is
  one column by construction; frame-time equality is by construction in the model, so only the byte counter is evidence.
- **5x message rate:** 3,000 -> 15,000 delta messages over the run, upload stays **11,264 B/s** (coalescing at the 10 Hz visual cadence works).
- **Cadence ladder (06 section 4.4 lever #1):** 100 ms -> 250 ms: upload 11,264 -> 4,096 B/s (-64%), heatmapUpload stage 0.63 -> 0.24 us (modelled).
- **Normalisation:** column-max vs global scale (linear mapping, one sample column): median row 1.5% vs 6.0% of range, p90 8.3% vs 33.6%. Column-max makes every
  column reach 1.0 so a quiet book looks as hot as a spoofed one; global scale keeps absolute liquidity comparable but crushes quiet columns.
  **Recommendation: log mapping (E06-D02 default) with global scale + slow-decaying vMax**, column-max only as a per-panel toggle. Product question for owner.
- **Price-origin shift (40 rows):** shift frame uploads 280,064 B (fine ring 163,840 B for 40 rows x 2048 cols x 2 B, 4 coarse rows 115,200 B, one column 1,024 B);
  total 1,315,840 B (= 40 x (2048+14400) x 2) is spread over 9 ticks (4 coarse rows per tick). A naive shift of both rings in one frame is 1.3 MB; with
  amortisation the worst frame is ~8 ms modelled (CPU row clear dominates, see below). Whole texture would be 16.8 MB: only 7.8% is touched. Counter-asserted in tests.
  **Finding:** the coarse ring's 14,400 columns make a vertical scroll 7x costlier than the fine ring; shifts must be amortised or the coarse ring kept in
  price-relative rows. Open for E11.
- **LUT swap:** exactly 1 x 1,024 B upload; 0 heatmap bytes changed; ~0.06-1.4 ms CPU slice-swap (one frame).
- **Capability profiles** (selection logic only): full -> `full`; no `OES_texture_float_linear` -> `reduced` (nearest sampling); no `EXT_color_buffer_float`,
  no R16F sampling, or no WebGL2 -> `degraded-2d`. The degraded-2d renderer itself is **not built**.
- **Context loss:** recovery = re-upload fine + coarse + LUT = 16,843,776 B from the CPU data model (no column lost, 2,048 fine columns intact), asserted in tests.
  One-time ~16 MB spike; the soak injected it at 15 min with no outlier in the model. Real WebGL context-loss events still need a browser run.
- **Per-symbol memory:** fine 2.00 MB + coarse 14.06 MB = **16.06 MB/symbol** (GPU) plus an equal CPU shadow; 10 recorded symbols = ~161 MB GPU. (06 section 10 capacity.)

## O3 - coarse-ring resolution (1 s vs 2 s)

Decision (recorded in `26-chart-engine-design.md` section 16): **provisionally 1 s**, 14,400 columns = exactly 4 h at 14.06 MB, within the 20 MB budget and
11.0 KB/s. A 2 s ring covers 8 h in the same memory (or 4 h in 7 MB), uploading 0.5 KB/s less (10.5 vs 11 KB/s). The soak shows **no frame-time or memory
differentiator** between them in this environment (p95 1.22 vs 1.17 ms modelled), so the choice rests on visual fidelity: 1 s keeps fast regime changes
legible 100 s after they happen; 2 s halves them. Because the only measurable difference is 0.5 KB/s of a tight 12 KB/s budget, **revisit if real-runtime
upload (not the model) leaves < 10% headroom**; final confirmation needs the real-GPU soak at E11 M4 (consistent with the ticket's scope trim).
