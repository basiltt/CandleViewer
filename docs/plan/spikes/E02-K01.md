## What was built

A throwaway prototype under `.spike-tmp/` (gitignored, not committed, left unmerged per the ticket's
"Spike branch marked throwaway and left unmerged" DoD item):

- `.spike-tmp/proto/` — pnpm workspace: `packages/pkg-a`, `packages/pkg-b` (depends on `pkg-a`, the
  required "package consumed by another package" case), `apps/app1` (depends on both — the fan-in case),
  plus `services/svc1`, a Python package under `uv`+Hatch exercising the full pinned dependency stack from
  `docs/plan/20-architecture.md` §2.1 (FastAPI, uvicorn[standard], numpy, SQLAlchemy 2.0, pydantic v2,
  alembic, duckdb). `turbo.json` wires `lint`/`test`/`build` with `build` depending on `^build`.
- `.spike-tmp/proto-nx/` — an `nx create-nx-workspace` scaffold (real Nx toolchain, not stubbed) for
  comparison of scaffold cost, config shape and `node_modules` footprint.
- `.spike-tmp/proto-poetry/svc1/` — the same Python skeleton and dependency stack under Poetry 2.2.0.
- `.spike-tmp/bench.sh` — the scripted timing harness (median-of-N loops); `.spike-tmp/results.json` —
  the recorded numbers referenced below and in the ADR.

## Deviations

- **ADR number**: ticket text names ADR-0018, which was the next free number at merge time; no
  deviation was needed.
- **Reference hardware**: `docs/plan/06-performance-and-load-standard.md` §3.1's reference hardware was
  not available in this session; timings are wall-clock on the implementing agent's dev container instead.
  All figures are far enough inside budget (ms–low-s vs 5–10 min budgets) that this substitution does not
  change the decision; a follow-up can re-run `.spike-tmp/bench.sh` on reference hardware once E03's CI
  runners exist, if a tighter number is ever needed.
- **Gate stubs**: `lint`/`test`/`build` scripts in the JS prototype are `echo` stand-ins rather than real
  ruff/mypy/pytest/eslint/tsc/vitest invocations, because the prototype's purpose (per the ticket's scope)
  is to exercise the *task graph and cache correctness*, not to benchmark tool-specific lint/test speed —
  those tools' own speed is orthogonal to the pnpm/Turbo-vs-Nx and uv-vs-Poetry choice being decided here.
- **Nx steady-state task execution** was not benchmarked (only scaffold cost) — Turborepo already clears
  budget by a wide margin and Nx's own per-task overhead is not expected to differ materially for
  echo-stub scripts; if Nx is revisited later this gap should be closed first.
