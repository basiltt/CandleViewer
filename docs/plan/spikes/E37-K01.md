# E37-K01 - Spike: graph library for 200-node fps and keyboard connect

Status: criterion 1 is only PARTIALLY answered (headless Chromium + CPU-throttle proxy; Electron and reference hardware NOT measured, deferred to E37-Q04); other questions answered; Rete.js measured with a minimal (lower-bound) prototype (Q6). Owner approval pending.
Method: throwaway harness in `E37-K01-harness/`. Machine: 8 logical cores, Windows 11, headless Chromium
(Playwright 1243), software/default GPU path. **Not the `06-performance-and-load-standard.md` section 3.1
reference hardware, and not Electron** - see Limitations.

## Q1 - 60 fps pan/zoom at 200 nodes / ~260 edges
Scripted wheel zoom + pan dispatched every rAF for 10 s, rAF frame deltas, 1280x800, custom node (DOM, two ports).

| Scenario | frames | p50 ms | p95 ms | p99 ms | mean fps | DOM nodes |
|---|---|---|---|---|---|---|
| 60 nodes | 596 | 16.7 | 16.7 | 16.8 | 60 | 60 |
| 200 nodes | 597 | 16.7 | 16.8 | 16.8 | 60 | 200 |
| 200 nodes, `onlyRenderVisibleElements` | 592 | 16.7 | 16.7 | 16.8 | 59.4 | 100 |

Answer: **yes** in this environment, but the table above is vsync-capped and shows no headroom. Round 2 re-ran
with `--disable-frame-rate-limit --disable-gpu-vsync` and a CDP CPU throttle (`E37-K01-results.json`, 8 s runs):

| 200 nodes | CPU | p50 ms | p95 ms | p99 ms | mean fps |
|---|---|---|---|---|---|
| React Flow | 1x | 9.4 | 17.5 | 18.2 | 95.1 |
| React Flow `onlyRenderVisibleElements` | 1x | 10.0 | 17.9 | 25.7 | 89.7 |
| React Flow | 4x throttle | 48.5 | 60.8 | 71.3 | 20.9 |
| React Flow `onlyRenderVisibleElements` | 4x throttle | 45.8 | 69.3 | 85.0 | 22.9 |

Unthrottled there is ~1.6x headroom on mean fps (p50 9.4 ms). **Under a 4x CPU throttle React Flow falls to ~21 fps**,
below the 45 fps criterion, and virtualisation does not help (cost is per-frame viewport/edge work, not DOM count).
This is the failure path for criterion 1 on a slow machine: see ADR-0029 for the cap and re-estimates. Whether 4x
throttle represents the reference hardware is unknown; still not Electron/reference HW.

## Q2 - Keyboard connect
Each node renders real `<button>` ports (focusable, `aria-label`) beside library `Handle`s. Flow:
focus output port, `Enter` (pending source stored in our own state, live region announces
"Connecting from ..."), focus target input port, `Enter` (edge added through controlled `edges` state, announces
"Connected n0 to n30"). Result in harness: edge count 96 -> 97, both announcements emitted. **No fork and no
library internals needed**: the library's `Handle` is pointer-only, so ports are our own elements; the
library merely renders edges from controlled state. Caveats (to be addressed in E37-S02, not proven here):
arrow-key traversal of candidate targets (the PoC used direct focus), roving tabindex across 200 nodes, and
edge focus/delete. `nodesFocusable`/`edgesFocusable` give focusable nodes/edges out of the box.
Round 2 built and ran the missing pieces (`kb.mjs`): while a connection is pending, ArrowDown/ArrowUp moves
focus through candidate input ports (excluding the source node) with a roving tabindex (exactly 1 tab stop), each
move announced; Enter completes, Escape cancels. Observed: n0 out -> Enter ("Connecting from trigger 0 ...") ->
ArrowDown x5 (trigger 2..6 input) -> ArrowUp (trigger 5 input) -> Enter ("Connected n0 to n5"); edges 96 -> 97;
Escape announced "Connect cancelled". Artefact: `E37-K01-results.json` (keyboard block) and the scripted test
`E37-K01-harness/kb.mjs`; no video (headless; deterministic scripted output is the evidence).
Still unproven: edge focus/delete and spatial ordering of targets (candidates are in DOM order).

## Q3 - Controlled state ownership
`nodes`/`edges` are fully controlled (`applyNodeChanges`/`applyEdgeChanges`/`addEdge`). Positions live on the node
objects we own, so `graph_layout` can be kept apart from the IR and excluded from the canonical hash
(ADR-0026) by projecting positions out at the adapter. Answer: **yes**.

## Q4 - Auto-layout cost (median of 7, main thread, Node 20; first runs include JIT warm-up)

| Graph | dagre median | elkjs median |
|---|---|---|
| 60 nodes / 96 edges | 43 ms | 127 ms |
| 200 nodes / 260 edges | 234 ms | 228 ms |

Both exceed the 100 ms main-thread block criterion at 200 nodes (cold first run up to ~390 ms).
**Consequence executed: auto-layout runs in a web worker by default (E37-T02).** dagre is 17 KB gz vs elkjs
~442 KB gz (bundled), and is no slower at 200 nodes, so dagre is the default; elkjs only if port-constrained
routing is later required.

## Q5 - Bundle cost
Vite 5 production build of the harness (React + React Flow + sample): 329.9 KB JS / 106.6 KB gz, 15.9 KB CSS /
2.7 KB gz. React itself is ~45 KB gz of that, so the library delta is about 60 KB gz. dagre adds ~17 KB gz
(inside a worker chunk). Safely lazy-loadable on the editor route; budget #9 unaffected.

## Q6 - Rete.js fallback (measured, minimal prototype)
`rete@2` + `rete-area-plugin@2` prototype (`rete.jsx`), same 200-node graph, plain-DOM node renderer, 260 edges as
static stub SVG paths (no real geometry), same scripted zoom/pan, same throttles. Bundle: 38.9 KB min / 10.3 KB gz
for rete+area (no render framework plugin, connection plugin or real edge routing).

| 200 nodes | CPU | p50 ms | p95 ms | mean fps |
|---|---|---|---|---|
| Rete (minimal) | 1x | 17.3 | 18.4 | 57.1 |
| Rete (minimal) | 4x throttle | 17.4 | 18.2 | 57.3 |

**Not like-for-like and not a ranking.** Rete holds ~57 fps even at 4x while React Flow drops to ~21: Rete's area
applies one CSS transform to a container and our stub edges are static, whereas React Flow recomputes viewport state
through React. A production Rete build adds a render plugin, connection geometry, selection and focus management,
so real numbers will be lower than this lower bound. Conclusion: Rete is a credible performance fallback and the
failure path is concrete, not opinion. Its keyboard connect was not prototyped.

## Security / supply chain
`npm audit --omit=dev` on the harness lockfile: 0 vulnerabilities (97 packages incl. optional). React Flow
pulls `zustand`, `classcat`, `@xyflow/system` (+ d3 zoom/drag/selection/interpolate). MIT-licensed; licence
allowlist check is still required by the dependency ticket (E37-T01).

## Decision criteria outcome
1. fps >= 45 at 200 nodes: met unthrottled (p50 9.4 ms, 95 fps, vsync off); **not met at 4x CPU throttle (21 fps)**.
   Decision stays React Flow with a provisional 120-node soft cap, now written into SCR-082 and E37-S01; E37-Q04 must measure on reference hardware and Electron before
   the cap is chosen; if that fails, switch per ADR-0029 failure path.
2. Keyboard connect without fork: met in PoC including arrow traversal -> React Flow retained.
3. Layout block > 100 ms at 200: **triggered** -> worker layout in E37-T02.

## Limitations
Not run in Electron; not on reference hardware (CPU throttle is only a proxy); no real GPU profile; synthetic
input; no screen recording (scripted output instead); Rete prototype minimal and not like-for-like; edge
focus/delete and spatial target ordering not built. Carried into E37-Q04 / E37-S02.
Re-estimates are recorded in ADR-0029 (Failure path); the node cap is applied in SCR-082/E37-S01; point changes await owner approval; no risk-register change (R8/R2 unchanged).
The Electron/reference-hardware part of Q1 cannot be run by an agent on this machine (no reference rig); it is an explicit E37-Q04 entry condition, not claimed here.
