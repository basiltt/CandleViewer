## Hardware profile actually used

The ticket calls for the reference VPS profile (4 vCPU / 8 GB, `06-performance-and-load-standard.md` §3.1).
**That profile was not available in this environment** (no VPS/container access from the delivery agent;
docker is not installed in this environment either). Measurements below were taken on the delivery
workstation instead (Windows, Python 3.12.3, single-process, no other CPU load during the run). Numbers
are directionally reliable (they compare configurations against each other, not absolute capacity) but
**must be re-measured on the actual 4 vCPU / 8 GB profile before they are used to size the production
capacity plan (§10)** — filed as a follow-up (see below).

## Method

- Harness: `tests/perf/obs_baseline_overhead/harness.py`. A synthetic `parse -> transform -> emit`
  pipeline shaped like the ingestion path in `20-architecture.md` §12.1, using the same metric names
  (`ws_messages_total`, `topic_staleness_seconds`, `ingest_queue_depth` is referenced but not separately
  modelled — queue depth is a gauge with no per-message cost of its own).
- Four configurations per the ticket: `none`, `metrics_only` (prometheus_client counters/histograms),
  `metrics_structlog` (+ structlog JSON at INFO with a minimal redaction processor), `metrics_structlog_otel`
  (+ OpenTelemetry spans; sampling ratio tested at 100%).
- Two label shapes compared for the metrics path: `inline` (label tuple computed inside the loop,
  `counter.labels(...)` called per message) vs `pre_bound` (label-bound counter/histogram objects hoisted
  out of the loop, looked up once per (topic, symbol) pair before the loop starts).
- Rate: 4,000 msg/s (see "Deviation from 20k msg/s" below), 10 s per run, **3 repeats** per
  (configuration, label_shape) pair, in-process CPU-seconds delta (`psutil.Process.cpu_times()`) divided by
  wall-clock elapsed, RSS via `psutil.Process.memory_info().rss`, and per-message latency sampled 1-in-50
  using `time.perf_counter_ns()` (never `time.time()` in the inner loop, per the ticket's technical notes).
- `contextvars` propagation cost measured independently via `measure_contextvars_cost()`: mean ns per
  `ContextVar.set()` call over 200,000 iterations (a proxy for the per-`asyncio.create_task` context-copy
  cost, since the harness itself does not run an event loop on the measured hot path — see "What wasn't
  measured" below).
- Raw sample data: `tests/perf/obs_baseline_overhead/sample_run_dev_workstation_20260928.json`
  (rate=4000, duration=10s, repeats=3).

### Deviation from 20,000 msg/s

The ticket specifies 20,000 msg/s for 120 s. At 20,000 msg/s **every** configuration — including `none` —
saturated the single measured core on this workstation (CPU% pinned near 100% for all four configurations),
because the harness's own scheduling loop (recomputing "how many messages should have fired by now" every
poll) becomes the dominant cost at that rate on this hardware, which masks the very signal being measured.
4,000 msg/s (~1/5th of the ticket's target) was the highest rate at which the `none` baseline configuration
stayed comfortably under 5% CPU on this box, which is the necessary precondition for a CPU%-based overhead
comparison to mean anything. **The reference VPS profile should be re-run at the full 20,000 msg/s / 120 s
matrix** — a 4-vCPU box has more headroom and the harness's own polling cost is expected to be a much
smaller fraction of total CPU, closer to the ticket's intended shape.

## Results (dev workstation, 4,000 msg/s, 10 s, 3 repeats, mean ± stdev)

| Configuration                          | Label shape | CPU % (mean ± stdev) | RSS (MB) | p95 latency (µs) |
| -------------------------------------- | ----------- | -------------------- | -------- | ---------------- |
| none                                   | inline      | 1.15 ± 0.32          | 42.4     | 2.8              |
| metrics_only                           | inline      | 3.70 ± 0.74          | 42.5     | 20.1             |
| metrics_only                           | pre_bound   | 2.50 ± 0.41          | 42.5     | 9.9              |
| metrics_structlog                      | inline      | 13.28 ± 0.71         | 42.6     | 61.3             |
| metrics_structlog                      | pre_bound   | 11.92 ± 0.18         | 42.6     | 52.0             |
| metrics_structlog_otel (100% sampling) | inline      | 98.43 ± 0.12         | 43.2     | 423.6            |
| metrics_structlog_otel (100% sampling) | pre_bound   | 98.17 ± 0.50         | 43.3     | 387.5            |

`contextvars.ContextVar.set()`: **~257 ns/call** (mean over 200,000 iterations, single measurement — this
is cheap and dwarfed by every other measured configuration; not repeated 3x because its variance was
observed to be negligible run-to-run during development).

RSS shows no meaningful growth across configurations at this run duration (10 s) — this is expected: RSS
growth from log/metric buffering, if any, only shows up over much longer soaks (hours), which is out of
scope for a 3-day timeboxed spike. Flagged as a gap below.

## Findings against the Gherkin acceptance criteria

**Scenario: Overhead quantified per configuration** — met, with the hardware-profile caveat above: CPU%,
p95 latency and RSS recorded per configuration, 3 repeats, variance stated. p50/p99 are also recorded in
the raw JSON (not tabulated above for brevity).

**Scenario: Decision criteria applied (configuration (b) vs 1% CPU budget)** — `metrics_only` (config b)
measured at **3.70% CPU inline / 2.50% CPU pre-bound**, both **over** the 1% CPU budget (US-OBS-002 NFR)
relative to the `none` baseline's 1.15%, i.e. a **+2.55pp / +1.35pp** delta respectively. Per the ticket's
decision rule: **the pre-bound-label fast path is adopted as the mandatory pattern for the metrics facade**,
and E04-T03 must enforce it (see follow-up ticket below). Note the _inline_ shape is nearly 1.5x the cost
of _pre-bound_ at this label cardinality (3 topics x 3 symbols = 9 combinations) — the effect is expected
to grow with cardinality (more symbols in production: up to 10 per `06-performance-and-load-standard.md`
§3.2), so the fast path matters more, not less, at production scale.

**Scenario: Tracing decision confirmed or overturned** — `metrics_structlog_otel` at 100% sampling measured
at **~98% CPU**, vastly exceeding the 5% CPU-over-baseline threshold. **ADR-0014's "metrics only on
market-data hot loops" decision stands, and is now measured rather than assumed.** Sampling at 1% was not
separately re-run as a distinct measured configuration in this pass (see gap below) because the 100%
result alone already conclusively confirms the ADR's existing decision; a 1% sampling run is a cheap
follow-up if the eventual decision to trace _any_ hot-loop path is revisited.

## What wasn't measured (gaps, explicitly)

- **Reference VPS hardware** (4 vCPU / 8 GB) — not available to this agent; flagged as a required
  follow-up before the numbers back the capacity plan.
- **1% OTel sampling as its own measured row** — only 100% sampling was run as a distinct configuration;
  the 100% number already answers the ADR-0014 gate decisively (98% CPU vs a 5% threshold), so a 1%
  sampling run was de-prioritized under the 3-day timebox. Left as a fast follow-up, not a blocker.
- **Long-soak RSS growth** (buffering, GC pressure over hours) — 10s runs show no signal; a multi-hour
  soak is out of scope for this spike per its own "Test plan" (not a production-shippable measurement).
- **`asyncio.create_task` fan-out under real concurrency** — `measure_contextvars_cost()` isolates the
  `ContextVar.set()` cost only; it does not run a full `asyncio` event loop with concurrent tasks, so it
  is a lower bound on the true propagation cost, not a full measurement of it. Explicitly out of scope per
  the ticket ("synthetic and offline"), but should be re-validated once E04-T03 lands a real async metrics
  facade with contract tests.

## Harness disposition

**Promoted** to `tests/perf/obs_baseline_overhead/` (kept in the repo, not deleted) per the ticket's DoD
item "Harness branch promoted to `tests/perf/` or explicitly marked throwaway." Rationale: the harness is
self-contained (no app imports), has a smoke test
(`tests/perf/obs_baseline_overhead/test_harness_smoke.py`), passes `ruff check` clean, and is directly
re-runnable on the reference VPS to close the hardware-profile gap above. It is **not** wired into any CI
required check (no `bench` gate references it) — it is a standalone research tool, run manually via
`python -m tests.perf.obs_baseline_overhead.run_measurements`.

## Follow-up tickets (filed on the board, referencing this spike)

1. **#1523 — Enforce the pre-bound-label metrics pattern in the facade design (blocks/updates E04-T03).**
   The metrics facade's public API must make per-label-tuple binding the only supported pattern (e.g. a
   `bound_counter(topic, symbol)` cache built at symbol-subscription time), not `counter.labels(...)`
   called per message. Reference: this doc's "Decision criteria applied" finding.
2. **#1524 — Re-run the full matrix (20,000 msg/s, 120 s, 3 repeats) on the actual reference VPS profile**
   before R1 exit / before the capacity plan (§10) cites these numbers as authoritative. Reference:
   "Deviation from 20,000 msg/s" above.
3. **#1525 — (Optional, low priority) Add a 1% OTel-sampling row** to the harness's default matrix once
   the reference-VPS re-run (follow-up #2) happens, for completeness — not required to close this spike's
   Gherkin criteria since 100% sampling already exceeded the threshold decisively.
