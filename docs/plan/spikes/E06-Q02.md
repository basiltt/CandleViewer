## 3. degraded-2d evaluation protocol

1. Force GL off (`--disable-gpu --disable-software-rasterizer`, or the harness `?profile=degraded-2d` override).
2. Render scenes A and B; confirm candles/axes are correct and footprint is limited to L2/L3 (26-chart-engine-design.md §3.7).
3. Record p50/p95 frame ms over 3 reps x 10 s (same stats code as `bench/stats.mjs`) at DPR 1.0 and the machine's native DPR.
4. Verify the DOM mirror and data cursor remain functional (05-accessibility-standard.md §6).
5. Verify SCR-030 "low-GPU degraded" and SCR-048 "WebGL unavailable" messaging appears.
6. Verdict, one of: `usable` / `usable with limits (state them)` / `not usable`, with rationale. A number alone is not a verdict.

Result (S1, headless Chromium 153, probes in `E06-Q02-probes/`; protocol steps 2, 4, 5 need the engine/UI and are NOT RUN):

- Forcing GL off needs **both** flags (`--disable-gpu --disable-software-rasterizer`); `--disable-gpu` alone still serves WebGL2 via SwiftShader. Detection must key on `getContext('webgl2') === null` and on the renderer string (SwiftShader/llvmpipe), not on flags.
- Synthetic Canvas-2D 2,500 cells (30 reps, DPR 1): SwiftShader-default p50 9.6 / p95 39.1 ms; GL fully off p50 14.4 / p95 56.4 ms; `--disable-gpu` p50 28.9 / p95 121.4 ms. Single-session, noisy, not a bench.
- **Verdict (provisional, S1 only): `not usable` for 2,500-cell footprint at 60 fps** (p95 well above 16 ms); candle/axis-only scenes and footprint L2/L3 are untested. Confirms K03's modelled ~34 ms p95 order of magnitude. Final verdict needs the real degraded-2d renderer and SCR-030/048 check on hardware.

## 4. RunMode.inline vs worker equivalence protocol

- Run the same seeded scenario (scene A 100k bars, scene B 2,500 cells) in worker mode and `RunMode.inline`.
- Compare: (a) LOD decision trace (per-frame LOD level per layer) via text diff; (b) golden-image diff at fixed DPR/seed,
  zero-pixel tolerance on geometry; (c) interaction semantics (pan/zoom/hover hit-test results for a scripted input list).
- Report throughput (p95 frame ms) separately; throughput difference is expected, anything else is a defect filed against §2 of 26-chart-engine-design.md.
- Pass criterion: (a),(b),(c) identical. Result: **BLOCKED BY CONSTRAINT (verified)**. `packages/chart-engine/src/worker/index.ts` is a placeholder (`export {};`) and a repo-wide grep of `packages/chart-engine/src` finds no `RunMode`, no inline facade and no context/render loop. The inline-vs-worker equivalence AC therefore **cannot be met** until E06/E11 deliver the worker entrypoint and `RunMode`. Recorded as **E11 constraint C-Q02-1**: deliver `RunMode.inline|worker` over one core with a shared LOD trace hook so this protocol is runnable. Environment facts that support it: OffscreenCanvas and WebGL2-in-worker are available in Chromium 153 headless (probe `worker` field).

## 5. Exploratory charters (2 h timebox each; notes template per 03-testing-strategy.md §11.2)

Template per session: mission, areas, oracles, environment/browser/build hash, findings table (id, description, triage = expected | defect | needs-decision, evidence), debrief.

### C1 Context loss and recovery

- Mission: prove documented recovery (26 §3.4): stop loop, invalidate GPU resources, rebuild from data model, resume, <= 1 frame flash, no data loss.
- Areas: `WEBGL_lose_context.loseContext()` + `restoreContext()` at (a) mid-pan, (b) mid-upload (during buffer sub-data), (c) during SDF atlas generation/upload, (d) twice in quick succession, (e) while tab backgrounded.
- Oracles: blank/black canvas after restore, stale or missing candles, lost crosshair/selection state, console GL errors, loop still running while context is lost, atlas not rebuilt.
- Outcome (partial, raw-GL level only, no engine exists to recover): in SwiftShader Chromium 153 `loseContext()` fires `webglcontextlost`, `isContextLost()` is true, `restoreContext()` fires `webglcontextrestored` and the context is usable again. GL calls while lost silently no-op (they do not throw), so the loop must check `isContextLost()` itself. Finding F1: lose followed immediately by restore (no await for the lost event) did **not** recover in the same probe (`doubleLossRecovers: false`, after 300 ms), in both SwiftShader configs. Triage: needs-decision; may be a probe artefact (spec requires restore after the lost event is dispatched) but the engine's recovery must serialise lost -> restore and not assume back-to-back calls work. Mid-pan/mid-upload/atlas variants, backgrounding and the <=1 frame flash oracle: NOT RUN (no engine).

### C2 Hostile display conditions

- Mission: crisp, unclipped rendering under unusual display setups.
- Areas: DPR 1.25/1.5/1.75; browser zoom 100-200 % (reflow, not clip; density classes scale; cell sizes checked against E06-D01 legibility thresholds); monitor switch mid-session; HDR on; multi-monitor mixed DPI.
- Oracles: hairlines blurred or doubled (pixel snapping §3.4), text shimmer, clipped axes/legend at 200 %, cells below legibility threshold without LOD step-down, canvas size not following DPR change.
- Outcome: NOT RUN.

### C3 Resource starvation

- Mission: degrade gracefully, recover cleanly.
- Areas: heavy CPU load; competing GPU-hungry tab; backgrounded tab (rAF throttling) then foreground; battery saver.
- Oracles: heatmap (10 Hz cadence) replays a burst on foreground return instead of catching up in one coalesced frame; unbounded queue growth while hidden; stuck loop; no degraded-profile notice.
- Outcome: NOT RUN.
