## Technical notes / design

**Documentation lives in the repo, is built by CI, and is verified mechanically.** Three layers, mirroring the governance approach established in E01:

1. **Authored prose** under `docs/` (`docs/guide/`, `docs/runbooks/`, `docs/onboarding/`) — Markdown, reviewed like code.
2. **Generated reference** — the REST reference rendered from `docs/plan/22-api-openapi.yaml`; the WS topic/frame reference rendered from `docs/plan/23-ws-protocol.md` and the bundled `ws-schemas.json`; the DB reference rendered from `docs/plan/21-database-schema.md`. Regeneration is a `make docs` target; CI runs `make docs && git diff --exit-code`, exactly the staleness pattern already used for `packages/protocol` (`docs/plan/20-architecture.md` §5).
3. **Checkers** (`scripts/check-docs-*.py`) with stable error codes: `DOC-001` missing required artefact, `DOC-002` stale generated reference, `DOC-003` unrehearsed or stale-rehearsal runbook, `DOC-004` broken internal link, `DOC-005` quoted figure with no source artefact, `DOC-006` secret/PII pattern in published output, `DOC-007` orphan document (not linked from any index).

**In-app help is content-driven, not hard-coded.** SCR-119 renders sections from a versioned content bundle shipped with the web app so the app remains fully usable offline (SCR-119 performance note: "No network calls except an explicit update check; the page is fully available offline"). The only live calls are `GET /system/build` (version/commit/environment, RBAC `permissions: []`, scope `self`) and `GET /detectors/methodology` for the SCR-058 drawer. The keyboard cheatsheet is rendered from the **active** hotkey profile (`GET /me/keymap`) so it always matches the user's remapping rather than a stale screenshot.

**Runbook format** (enforced by front-matter schema, checked by `DOC-003`): `id`, `title`, `failure_ids` (F1–F18 from `20-architecture.md` §11.1), `trigger`, `detection` (the metric/alert from `20-architecture.md` §12), `severity`, `steps` (numbered, each with expected observable result), `verification`, `rollback`, `owner`, `rehearsals: [{date, rehearser, outcome, duration_minutes, notes}]`.

**GA evidence pack** is assembled by a script into `artifacts/ga/v1.1.0/` from CI artefacts (coverage reports, perf budget results from E46, a11y conformance report from E47, chaos catalogue results from E45, scan outputs from E43) rather than transcribed; the PRR ceremony reviews the pack, it does not build it.

## Security notes

Data classification: the documentation set is **internal/confidential** — it describes the trust boundaries (`docs/plan/20-architecture.md` §2.2), the key-vault design (`27-adrs/ADR-0009`) and the incident runbooks, so it is an attacker's shortcut if exposed. Primary STRIDE concerns (detailed in E48-X01): **I**nformation disclosure via generated examples containing real identifiers, via the support bundle (US-OBS-007), or via publishing the docs site outside the Tailscale boundary; **T**ampering with a runbook to induce a destructive operation during an incident; **E**levation via a runbook instructing an over-privileged shortcut ("just run as superuser") that becomes normalised. Controls: docs site bound to the private network only (same rule as the metrics endpoint in US-OBS-001), `DOC-006` secret scanning in the docs build, CODEOWNERS protection on `docs/runbooks/**` so an incident procedure cannot be changed without review, and an explicit rule that no runbook step may disable an audit or a safety control without naming the compensating control. `security` review label required on this epic.

## Accessibility notes

SCR-119 is a static content page: headings in order, a version table as a real `<table>`, links with meaningful text, the licence list in a scrollable region with an accessible name, the copy-diagnostics button announcing exactly what it copies. ## Technical notes / design

**Front-matter schema** (`docs/runbooks/schema/runbook.schema.json`):

```yaml
id: RB-07
title: Fan-out partial failure recovery
failure_ids: [F14]
trigger: "Trade group reports state PARTIAL, or the fanout_partial_failure alert fires"
detection: "metric oms_fanout_leg_failures_total > 0; alert: fan-out partial failure"
severity: P0
prerequisites: ["admin re-auth token <=15 min old (SCR-149)", "read access to SCR-135 audit log"]
steps:
  - do: "Open SCR-078 trade-group detail for the group id in the alert"
    expect: "Per-leg status is listed for every account in the group"
  - do: "For each filled leg confirm a native stop-loss exists via GET /positions"
    expect: "Every filled leg has a non-null stop price; any leg without one is an immediate P0"
verification: "Group state is RESOLVED or CANCELLED; no filled leg is without a native SL; audit entries exist for every remediation action"
rollback: "Reduce-only close of filled legs via POST /positions/{positionId}/close; never a market reverse"
owner: "OMS lead"
rehearsals: []
```

**Writing rules** enforced by review, not just taste: every step has an observable expected result (a step you cannot verify is not a step); every destructive action states what it cannot be undone from; every procedure names the screen (`SCR-nnn`) or endpoint used, because at 2 a.m. "check the admin panel" is not an instruction; no step requires reading source code.

**The safety-clause linter** scans for a keyword set (`disable audit`, `skip reconciliation`, `bypass`, `--force`, `sudo`, `withdrawal`, `drop table`) and requires an adjacent `compensating-control:` annotation. Deliberately noisy-by-default; the allow-list is reviewed by the Security engineer (E48-X02).

## Technical notes / design

**Measurement definitions, written down once so drills are comparable.** RTO clock starts at the recorded "decision to recover" timestamp and stops when the system-specific service objective is verified (Postgres: `GET /health/ready` returns ready against the restored instance *and* a canonical query over `orders` returns the expected row count; QuestDB: the most-recently-traded symbol's bars for the last session are queryable and match golden checksums; cold tier: one symbol's full history is listable and checksum-matching). RPO is measured as the delta between the last committed transaction in the restored system and the last committed transaction before the simulated incident, taken from the WAL position and the `audit_log` sequence.

**Scenario (d) — whole-box rebuild** is the one that actually validates the onboarding guide (E48-T05) and the compose stack: the drill is performed from a bare scratch host using only `infra/compose/`, `infra/scripts/bootstrap`, the backup artefacts and the documentation. Anything the operator has to know that is not written down is a documentation defect, recorded as such.

**Safety**: drills run against a scratch environment with **demo** credentials only; the playbook carries a prominent precondition that a DR drill is never performed against `live` (the environment guard in E44 rejects cross-environment operations structurally, and the drill asserts that guard rather than trusting it).

**Order of operations invariant**: restore → verify integrity (audit chain, key vault) → reconcile → *then* re-enable. `docs/plan/20-architecture.md` §11.1 F7 states positions remain protected by the native exchange SL throughout; the playbook's verification step proves this per open position rather than assuming it.

## Security notes

The DR playbook grants, by construction, the most privileged operations in the system: restoring databases, handling backup artefacts and touching the key vault. Threats: **I**nformation disclosure via a restored copy left in a scratch environment with real data (mitigation: drills use demo-environment data; any scratch environment is destroyed at drill end and this is a checklist step with a recorded confirmation); **T**ampering with backup artefacts (mitigation: backups are encrypted and checksummed — `backups` table carries `checksum_sha256`, `encrypted`, `verified_at` — and the playbook verifies before restoring, never after); **E**levation via long-lived restore credentials (mitigation: restore uses a scoped, time-boxed credential, not the application's runtime credentials); **R**epudiation (mitigation: post-restore audit-chain verification via `POST /admin/audit/verify`, and the drill records who performed it). Classification: restricted — the drill record names hostnames and timings, so it lives in the private docs site only. Security engineer review required (E48-X02).

## Technical notes / design

The evidence pack is assembled from machine sources only: GitHub Actions artefacts by workflow run id, `GET /admin/health`, `GET /admin/security/summary`, `GET /admin/capacity`, `GET /admin/incidents`, `GET /admin/backups`, the project board API for defect counts, and `docs/plan/32-risk-register.md` parsed for acceptance expiry. Manual items that genuinely cannot be automated — the key-permission audit performed in the Bybit console (§6 requires manual verification "not just trusted from app config"), the pen-test summary, the Owner's written authorisation — are represented as signed attestation files with a named human, a date and a scope statement, and the gate check verifies their presence, recency and signer role. The distinction between "measured" and "attested" is explicit in the manifest so nobody later mistakes one for the other.

Gate check error codes: `GA-001` missing artefact, `GA-002` artefact failed its own threshold, `GA-003` stale artefact (produced before the release candidate commit), `GA-004` missing or expired attestation, `GA-005` manifest digest mismatch, `GA-006` open P0/P1 defect, `GA-007` expired accepted risk.

`GA-003` matters: an evidence artefact produced against an earlier commit is not evidence about the candidate. Every artefact records the commit SHA it was produced from, and anything older than the release-candidate SHA fails unless explicitly annotated as commit-independent (e.g. the pen-test, which is scoped to a deployed build and carries its own build identifier).

## Technical notes / design

The bundle is generated, not authored: `scripts/gen-release-notes.py` parses `CHANGELOG.md` (Keep-a-Changelog-shaped sections the existing automation already produces) into the `WhatsNewPanel` entry shape and writes it into the web app's content directory; `make docs`/`make gen` includes it and CI runs the `git diff --exit-code` staleness pattern. Shipping it as a bundled asset rather than an API response satisfies the SCR-119 requirement that the page is "fully available offline".

"Last seen version" is stored in user preferences (`GET`/`PATCH /me/preferences`) rather than local storage, so it follows the user across the browser build and the Electron shell — a user who reads the notes in one should not be shown them again in the other.

The redaction linter's pattern set (CVE identifiers with detail, `poc`, `exploit`, stack-trace shapes, absolute source paths, endpoint+payload pairs) is version-controlled and reviewed by the Security engineer under E48-X02, mirroring the runbook safety-clause linter in E48-T03.

Ordering within a version: Breaking Changes, Security, Features, Performance, Fixes — risk-first, not feature-first, because the audience is a trader deciding whether anything in this build changes how their money behaves.

## Technical notes / design

**Guide content is bundled, not fetched** (SCR-119 performance note). Markdown is compiled at build time into the app bundle, lazily loaded per section so the page mount stays within budget. The docs site (E48-T02) renders the same source files, so there is exactly one copy.

**Role-capability generation**: `scripts/gen-role-capabilities.py` reads the §7 permission matrix and the `x-rbac` blocks in `docs/plan/22-api-openapi.yaml`, emits the per-persona capability table, and fails (`DOC-005` class) when the two disagree — which makes a documentation check into an RBAC regression test, cheaply.

**Support-bundle pipeline** (backend, `services/api/candleviewer/observability/`): collect → redact (serialiser allow-list, the same mechanism US-OBS-003 mandates for logs) → scan (secret patterns, fail-closed) → size-cap (newest-first, truncation manifest) → write locally → audit. Fail-closed is the design: any scanner error aborts generation. Errors: `BUNDLE-001` secret detected, `BUNDLE-002` window invalid, `BUNDLE-003` size cap exceeded before the minimum useful window, `BUNDLE-004` collection partial (named subsystem unavailable — the bundle still generates and says which part is missing, because a partial bundle during an incident beats none).

**Audit**: bundle generation writes an `audit_log` entry `{actor, role, action: "support_bundle.generated", target: window, ts}` per `docs/plan/14-screens-catalogue.md` §0.5 item 8.

## Security notes

This story ships the single most dangerous convenience feature in the product: a button that packages the system's state into a file a user can send anywhere. Threats (`docs/plan/04-security-program.md`): **I**nformation disclosure of API keys, session tokens, correlation-identifiable account data or internal hostnames via the bundle; **I** via the licence/version surface fingerprinting the deployment; **T**ampering with the redaction allow-list; **R**epudiation of who generated a bundle. Controls: allow-list redaction (deny-by-default, not pattern-blacklist), a mandatory pre-write scan that fails closed, local-only storage with no automatic upload (US-OBS-007 NFR), audited generation, and a CI test asserting that a seeded secret aborts generation. Data classification: the bundle is **restricted** even after redaction; the UI says so. Requires `security` review (E48-X02) and a manual abuse-case check (attempt to obtain another user's data in a bundle as a manager).

## Technical notes / design

The cheatsheet is a projection of the keymap, not a document: it reads the same store the hotkey system uses at runtime (`GET /me/keymap`, cached locally for offline), so it cannot disagree with the behaviour. A build-time check asserts that every action in the default map (`05-accessibility-standard.md` §3.2) has a cheatsheet label — a newly added hotkey with no label fails CI, which is what keeps the sheet complete over time (`DOC-001` class).

The glossary is a single source consumed three ways: the SCR-119 list, the guide's inline term references, and tooltips on the trading surfaces. It lives as structured data (`term`, `plain`, `why_here`, `screens: [SCR-nnn]`, `estimated: bool`, `methodology_anchor`) so the `(estimated)` obligation can be enforced by a check rather than remembered: any term flagged `estimated` without a `methodology_anchor` fails the build, and any term appearing in the detectors' output vocabulary but absent from the glossary is reported.

Tour restart is implemented as a replay of the onboarding *presentation* layer only; the underlying checklist state (`GET /onboarding/checklist`) is read, never reset, and the restart is audited so an unexpected tour appearance is explicable.

## Security notes

## Technical notes / design

**Rehearsal method**, fixed so results are comparable: the rehearser is given only the alert (or the scenario statement), not the runbook link, and must find it themselves — that is what measures the routing table. The author observes silently and may not intervene; every question the rehearser wants to ask is written down instead of answered, and each becomes a finding. Duration is wall-clock from alert to verified recovery.

**Injection** uses E45's chaos harness so the fault is real rather than simulated in prose. Faults that cannot be injected safely on staging (key compromise RB-14, whole-box loss) are rehearsed as structured tabletop exercises with the same ledger fields and an outcome of `tabletop`, explicitly distinguished from `executed` in the ledger so the gate check can require a minimum number of executed rehearsals rather than accepting an all-tabletop set.

**Environment**: staging (demo) only. `docs/plan/02-definition-of-ready-done.md` §8 — demos and drills never run against prod (live), the sole documented exception being the live-enablement PRR walkthrough, which is E48-T06's business, not this ticket's.

Scheduling: rehearsals are spread across Sprint 26 week 1 so findings have a week to be fixed and re-rehearsed before the 2027-09-24 gate; the GA regression window (`q11` in the roadmap Gantt, 2027-09-06 → 2027-09-24) is the surrounding container.

##### E48-X01
## Context

`docs/plan/02-definition-of-ready-done.md` §2.1 requires a STRIDE threat-model kickoff for any epic touching auth, keys, OMS, fan-out or money movement, and `docs/plan/04-security-program.md` mandates a STRIDE model per epic. E48 does not build trading functionality, which makes it easy to assume it is low-risk — and that assumption is wrong in three specific ways:

1. The **support bundle** (US-OBS-007) packages logs, configuration, metrics and health results into a file a user can move anywhere. It is an exfiltration primitive with a friendly button.
2. The **runbook set** is an instruction channel executed by privileged operators during incidents, when scrutiny is at its lowest. A tampered runbook is a remote-code-execution-by-social-engineering path that no scanner detects.
3. The **GA evidence pack** aggregates the system's complete security posture — scan results, SBOM, accepted risks, pen-test summary, key-audit attestation — into one place.

##### E48-X02
## Context

E48-X01 enumerates the threats; this ticket proves the controls exist and work. `docs/plan/02-definition-of-ready-done.md` §3.2 requires, for anything `security`-labelled, that "SAST/SCA/secrets-scan clean or findings triaged with accepted-risk sign-off; Security engineer review comment present; for anything touching keys/withdrawal/RBAC, a manual abuse-case check performed". E48 ships a support bundle that touches configuration (and therefore, if redaction fails, keys), a docs site that describes the system's internals, and an evidence pack that aggregates its security posture — all of which need verification rather than assertion before the GA gate.

`docs/plan/07-release-and-prr.md` §5.5 also requires that "STRIDE threat models for all Epics in this train's scope reviewed as a set (not just individually at Epic-close) for cross-Epic interaction risks" — E48's model is one of the inputs to that review, and its findings must be closed before the PRR.

## Scope / Deliverables

- **Executed abuse cases** from the E48-X01 list, each with actor, entry point, attempted action and observed result:
  1. *Manager generates a support bundle and finds another user's data* — expected: bundle is scoped to data the actor may see; any cross-tenant leakage is a P0.
  2. *Seeded secret survives redaction* — a configuration value matching a key pattern is planted; expected: pre-write scan aborts generation, no partial file on disk, alert raised.
  3. *Scanner failure* — the secret scanner is made to error; expected: fail-closed, generation aborts (a fail-open here would be the whole vulnerability).
  4. *Viewer enumerates privileged actions via the cheatsheet* — expected: cheatsheet is filtered by scope and does not list actions the role cannot perform.
  5. *Docs site reached from outside the Tailscale boundary* — expected: no listener on a public interface; verified by scanning the host's bound addresses, not by reading config.
  6. *Runbook tampering* — a PR modifying a `docs/runbooks/**` step to disable auditing; expected: safety-clause linter fails the build **and** CODEOWNERS requires two-key review; both controls verified independently.
  7. *Backup artefact tampering* — a corrupted/modified backup offered to the restore path; expected: checksum/encryption verification rejects it before restore, per E48-T04.
  8. *Forged attestation in the GA evidence pack* — an attestation file with an unrecognised signer; expected: `GA-004` rejects it.
  9. *Exploit detail in a changelog Security entry* — expected: redaction linter fails the build.
  10. *Docs publish workflow token abuse* — inspect the workflow's `permissions:` for write scope beyond the publish step; expected: least privilege, no `pull_request_target` with untrusted checkout.
- **SAST/DAST/secret-scanning rule additions**: Semgrep rules for (a) any code path that writes a support bundle without invoking the scanner, (b) any logging/serialisation path bypassing the redaction allow-list, (c) hard-coded credentials in `docs/**`; a ZAP baseline profile for the docs site host confirming no unintended exposure; the `DOC-006` pattern set extended with anything the abuse cases reveal.
- **SCA review** of the documentation toolchain chosen in E48-K01 (dependency count, maintenance status, plugin execution model, known CVEs) per `docs/plan/04-security-program.md` §6.13.
- **Permission/key checks**: confirm `GET /system/build` exposes no infrastructure detail beyond version and commit for every role; confirm the docs/publish workflows' token scopes; confirm the drill's restore credential is scoped and time-boxed.
- **Security review comment** on each E48 security-relevant ticket (T02, T03, T04, T06, S01, S02, T07) and the epic.
- **Findings triage**: each finding fixed, or accepted with an Owner-signed entry in `docs/plan/32-risk-register.md` carrying an owner and an expiry date (R5 exit criterion 4 requires every acceptance to be current).

## Technical notes / design

Verification is preferred over inspection wherever possible: bound addresses are enumerated on the host rather than read from config; CODEOWNERS enforcement is proven by attempting a merge, not by reading the file; the scanner's fail-closed behaviour is proven by fault injection, not by code reading. This mirrors the §6 key-permission audit principle that permissions are "manually verified in the Bybit account settings (not just trusted from app config)".

New Semgrep rules live in `.semgrep/docs-security.yml` and join the existing SAST job; each rule ships with a passing and a failing fixture so the rule itself is tested (a security rule with no failing test is decoration).

The ZAP baseline profile for the docs host is added to the existing DAST cadence (`s06` in the roadmap's security track) rather than run once, so exposure is re-checked after GA.

- ZAP baseline run from outside the Tailscale boundary and from inside, results compared.
- SCA run over the docs toolchain; results attached.

This ticket handles restricted artefacts (threat model, findings, scan outputs). The review's summary — not its detail — is what enters the GA evidence pack.
