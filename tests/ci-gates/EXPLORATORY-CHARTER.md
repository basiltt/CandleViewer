# E03-Q01 — exploratory charter: bypassing the CI gates

Timeboxed 4 hours, 2026-09-30. Mission: "Can I get code onto `main`, or into a deployed image, without
passing the required checks (`CONSTITUTION.md` C-9.1)?" Session structure follows the ticket AC Scenario
3: attempt each named technique, record the outcome, file any successful bypass as `priority/p0-critical`.

## Session log

| Time | Technique attempted | Control that stopped it | Outcome |
|---|---|---|---|
| 0:00–0:40 | **Rename a required job** so its name vanishes from the required-checks list (e.g. rename `coverage-thresholds` to `coverage-check` in a workflow, hoping branch protection still shows "all required checks passed" for the new, unrequired name). | `scripts/check_required_check_reconciliation.py` (GOV-005, weekly `governance-drift.yml`) diffs job names in `.github/workflows/*.yml` against `.github/branch-protection.json`'s `contexts`; a name present in `contexts` with no matching job fails with `CI-PROT-002`-shaped output ("no job named '<x>' exists"). This is proven by fixture `E03-GT-16b` in this ticket. | **No bypass.** Detected within the week; the same PR that renames the job also needs a `branch-protection.json` update, and `.github/**` changes require the `security-review` label + reviewer (`AGENTS.md` §8), so a silent rename is also blocked at review time, not just by the drift job. |
| 0:40–1:20 | **Merge while a required check is still queued/pending** (race the merge-queue admission window). | GitHub's Merge Queue (`required_status_checks.strict: true`, `.github/branch-protection.json`) re-runs required checks on the rebased head before admitting; a pending/queued check blocks admission by construction — there is no "merge now, check later" state exposed to a non-admin actor. `enforce_admins: true` removes the admin-merge escape hatch too. | **No bypass observed.** Could not construct a case where the merge button is even clickable with a required check outstanding; this is a GitHub platform guarantee once branch protection is applied, not something this repo's own tooling could be tricked into skipping. |
| 1:20–2:00 | **Edit a workflow file in the same PR being gated** (e.g. weaken `_job-security.yml`'s severity threshold in the PR that also introduces the vulnerable code, hoping the weakened gate evaluates the PR's own diff). | `.github/**` is a CODEOWNERS-protected path requiring `security-review` label + security reviewer (`AGENTS.md` §8, C-10.2); `sast`/`pr-metadata` still run against the **current** commit's workflow content (the weakened check *would* run, but with 2 required independent reviews on a security-labelled path, the weakening itself is the finding a reviewer catches before merge). | **Partial finding, not a true bypass:** CI mechanically permits a workflow edit to take effect for its own PR (no separate "workflows are frozen at PR-open" pin was found), so the control is procedural (mandatory security review) rather than a hard technical block. Recorded as a residual risk, not filed as a new Bug — this exact risk is already tracked as `04-security-program.md` G4 ("Tampering: modifying `.github/workflows/` to disable a required check", mitigation: CODEOWNERS + security-review label + branch protection), so it is a known, accepted residual, not a new discovery. |
| 2:00–2:40 | **Force-push to `main` or a shared branch** to rewrite history past a red check. | `allow_force_pushes: false`, `allow_deletions: false` in `.github/branch-protection.json`; GitHub rejects the push at the ref-update hook, before any workflow even runs. | **No bypass.** Rejected server-side; not a CI-gate question at all, a repo-setting one, and it is set correctly. |
| 2:40–3:15 | **Use the release bot's documented bypass allowance** for something other than its scoped purpose (e.g. push an arbitrary code change "as" the changelog bot). | `.github/rulesets/bypass-register.md` names the release bot's bypass scope as "push release/changelog commit only"; `scripts/check_bypass_register.py` (CI-PROT-004) only asserts the register's rows are fresh and non-empty — it does **not** itself technically constrain what the named actor's token can push, that constraint lives in the bot's own credential scope/branch restrictions (out of this repo's static-analysis reach from a QA session with no admin access). | **Could not test end-to-end** without the bot's real credential (out of scope / no access). Flagged as a **documentation gap, not a P0**: the bypass register states intent but this session found no artifact proving the bot's actual GitHub App permissions are scoped to match. Recommend a follow-up Bug against `E03-T13` (owning task) to add an automated check that the bot's token/app installation permissions are least-privilege, not just documented as such. |
| 3:15–4:00 | **Two-approval requirement**: attempt a one-approval merge (self-approve + one review) or approve-and-merge one's own PR. | `required_approving_review_count: 2`, `require_code_owner_reviews: true`, `require_last_push_approval: true` (dismisses stale approvals on new pushes) in branch protection; `70-multi-agent.md` and C-10.1 additionally forbid an agent approving/merging its own PR at the process level. | **No bypass.** GitHub's own review-count enforcement blocks a merge button from appearing at all with fewer than 2 approvals; `require_last_push_approval` additionally invalidates approvals if the author pushes again after approval, closing the "approve, then sneak in one more commit" variant. |

## Findings summary

- **No technique in this session landed code on `main`, or into a deployed image, bypassing a required
  check.** Zero new `priority/p0-critical` bugs filed.
- One **already-tracked** residual risk was re-confirmed in practice (workflow files can be edited in
  the same PR they gate; the control is human review, not a technical freeze) — no new ticket needed,
  it maps to existing risk `G4` in `04-security-program.md` §5.12.
- One **follow-up recommendation** (not a P0, no evidence of an actual exploit): verify the release/
  changelog bot's GitHub App installation is scoped to exactly the branches/paths named in the bypass
  register, as an automated check rather than a documentation-only assertion. Left for the owning task
  (`E03-T13`) to triage, per the ticket's Definition of Done item 6 ("gate defects filed against the
  owning task").
